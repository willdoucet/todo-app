# Test artifact

Loaded by plan-eng-review step 6. The artifact is the QA contract for this branch. It is
written at `$TEST_ARTIFACT` (from `ctx`; the path is fixed, never invented) and consumed by:

- `/execute-plan`: what to test (critical paths, key interactions, edge cases), where
  (affected pages and routes), and in what order (critical paths first). It prefers these
  specs over ad-hoc test decisions and records any gap it finds.
- `/plan-adversarial-review`: hardens it in place, marking each addition with a comment line
  naming the skill, harness, and model.
- `/qa`: its primary input for browser verification.

It holds what a tester needs to know: what to test and where. Not implementation detail, not
test code, not a copy of the plan.

## Rules

- Write it from the coverage diagram: every item in the diagram is represented by at least one
  line here, in the tester's vocabulary (a page, a route, an action, an observable result).
- Backend-only plans still get an artifact. "Affected pages/routes" then lists endpoints,
  commands, or jobs, and "Key interactions" lists the calls and their observable effects.
- Critical paths are numbered end-to-end flows. Each is a sequence a tester can follow and a
  result they can observe. Never collapse one into a summary bullet.
- Completion gates are stated as "not done unless ..." and are never removed once written,
  only rewritten when the plan changes. The adversarial review relies on this.
- On a rerun, or when an adversarial pass already extended the file: read it in full, edit
  surgically, keep every still-valid invariant, reconcile duplicates by content rather than by
  heading, and reread the whole file afterward for contradictions with the reviewed plan.
- Epics get no artifact; each milestone's plan gets its own.

## Format

```markdown
# Test Plan
Generated by /plan-eng-review on <utc-date>
Project: {PROJECT}
Branch: {BRANCH}
Plan: {basename of _PLAN_FILE}

## Affected pages/routes
- {URL path, endpoint, command, or job} — {what to test and why}

## Key interactions to verify
- {interaction} on {page or endpoint} — {expected observable result}

## Edge cases
- {edge case} on {page or endpoint} — {expected behavior}

## Critical paths
1. {name}: {step} → {step} → {step} → {observable result}
2. {name}: ...

## Operational invariants
- {something that must stay true in production after this ships: a count, a log line, a job
  that keeps running, a record that is never orphaned}

## Log hygiene
- {what must be logged, at which point, with which fields}
- {what must never appear in logs: secrets, tokens, PII}

## Deployment guards
- {check to run before or immediately after deploy; migration ordering; flag state}

## Completion gates
- Not done unless {gate}.
```

A section with nothing to say gets one line saying why (for example "Log hygiene: no new log
lines; existing request logging covers this path"), never an empty heading.

## After writing

Read the file back and check each critical path against the coverage diagram: every new UX
flow and every new integration appears in at least one numbered path. State the artifact path
in the completion summary.

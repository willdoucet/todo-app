# Plan templates

Loaded by office-hours step 12. The plan file is `$PLAN_DIR/$SAFE_BRANCH-plan-$TIMESTAMP.md`.
Frontmatter is never typed by hand; the skill sets it with `obsidian-workflow plan-metadata-set`
after the body is written. Every template ends with the REVIEW REPORT placeholder copied
verbatim from `_shared/plan-footer.md`.

Rules that apply to both templates:

- `Supersedes:` appears only when a prior plan exists on this branch (`PLAN_FILE` from `ctx`
  before this session wrote anything). Name the prior filename exactly.
- `Status:` starts as `DRAFT` and becomes `APPROVED` in step 15. Reviews do not change it.
- "What I noticed" quotes the user's words. It never characterizes their behavior.
- Sections are filled from the session. A section with nothing to say gets one line saying why,
  never a placeholder left in.

## Note-sourced plans: Source tasks section

Insert directly after the header block, before Problem Statement.

Single task:

```markdown
## Source task
- Note: {vault-relative note path}
- Task: `^{task-id}` under "{heading}"
- Text: {the task line, verbatim}
- Notes: {every `notes::` line under the task, or "none"}
```

Batch:

```markdown
## Source tasks
Batch of {N} tasks from {vault-relative note path}. Completion is all-or-nothing: `/ship`
checks every box together.

| Id | Heading | Task |
|---|---|---|
| `^{task-id}` | {heading} | {task line, verbatim} |
```

## Milestone children: Inherited constraints section

For a plan started from `<epic-file>#M<n>`, the body starts with this section, before Problem
Statement. Copy, do not paraphrase: the locked decisions verbatim from the epic's Locked
architecture and decisions section, then the milestone's done-when. This section is the
contract; a child that must break one of these stops and asks.

```markdown
## Inherited constraints
From epic `{epic slug}`, milestone {M<n>}: {milestone title}
Depends on: {milestone ids, or "none"}

### Locked decisions (from the epic, verbatim)
1. {decision}
2. {decision}

### Done when (from the milestone, verbatim)
- {criterion}
```

## Startup mode template

```markdown
# Design: {title}

Generated by /office-hours on {date}
Branch: {branch}
Status: DRAFT
Mode: Startup
Supersedes: {prior filename; omit this line if first design on this branch}

## Problem Statement
{from the diagnostic, in the user's words where possible}

## Demand Evidence
{from Q1: specific quotes, numbers, behaviors demonstrating real demand}

## Status Quo
{from Q2: the concrete current workflow users live with today, and what it costs}

## Target User & Narrowest Wedge
{from Q3 and Q4: the specific human, and the smallest version worth paying for}

## Constraints
{technical, product, and roadmap constraints; PRD non-goals and LESSONS decisions touched}

## Premises
{from step 7, as agreed statements}

## Approaches Considered
### Approach A: {name}
{summary, effort on both scales, risk, completeness, pros, cons, reuses}
### Approach B: {name}
{same}
### Approach C: {name}
{same; omit if only two approaches were meaningful}

## Recommended Approach
{the chosen approach and the rationale, including why the others lost}

## Open Questions
{unresolved questions from the session; "none" if none}

## Success Criteria
{measurable criteria; what evidence proves the wedge worked}

## Distribution Plan
{how users get the deliverable: package manager, container image, app store, web service}
{build and publish pipeline, or "existing deployment pipeline covers this"}
{omit this section only for a web service with an existing deployment pipeline}

## Dependencies
{blockers, prerequisites, related plans and TODOS}

## Deferred
{what was consciously left out, each with a TODOS.md entry or a reason there is none}

## The Assignment
{one concrete real-world action the founder takes next; never "go build it"}

## What I noticed about how you think
{two to four bullets quoting specific things the user said during the session}

{REVIEW REPORT placeholder, verbatim from _shared/plan-footer.md}
```

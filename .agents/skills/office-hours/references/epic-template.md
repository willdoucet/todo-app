# Epic template and roadmap entry

Loaded by office-hours step 13. The epic file is
`$PLANS_DIR/epics/<slug>/<slug>-epic-$TIMESTAMP.md`. It defines milestones and locks the
decisions they inherit. It never executes: `/execute-plan`, `/quickfix`, and `/ship` refuse it.
Each milestone becomes its own feature plan (`/office-hours <epic-file>#M<n>`) or quickfix
(`/quickfix <epic-file>#M<n>`), whose frontmatter names `parent_epic` and `milestone`.

Rules:

- One level deep. A milestone too big for one plan becomes two milestones.
- Every milestone, however small, is its own plan or quickfix. Size is `plan` or `quickfix`.
- Dependencies are acyclic and name milestone ids, never line numbers.
- Status is derived from the children's registry entries; never write it into the epic by hand.
  A milestone can be marked `subsumed` with a reason through `milestone-set`.
- Epics always get a CEO review before the first milestone starts.

## Milestones JSON

Passed to `epic-register --milestones-json`. Same order as the table in the file.

```json
[
  {"id": "M1", "title": "Schema and migration", "size": "quickfix", "branch": "cal-sync-m1-schema", "depends_on": []},
  {"id": "M2", "title": "Sync service", "size": "plan", "branch": "cal-sync-m2-service", "depends_on": ["M1"]},
  {"id": "M3", "title": "Settings UI", "size": "plan", "branch": "cal-sync-m3-settings", "depends_on": ["M2"]}
]
```

## Epic file template

```markdown
# Epic: {title}

Generated by /office-hours on <utc-date>
Slug: {slug}
Status: DRAFT
Mode: {Startup | Builder}
Source: {note ref, roadmap phase, or "free text"}

> This file never executes. It defines milestones; each milestone is its own plan or quickfix
> started with `/office-hours {this file}#M<n>` or `/quickfix {this file}#M<n>`.

## Problem
{the problem in the user's words, the demand evidence or the delight, the target user}

## Locked architecture and decisions
{numbered. Each one is a constraint every milestone inherits verbatim. A child that must break
one stops and asks. Include the first-principles insights from the landscape step and link the
matching LESSONS.md Decisions entries.}
1. {decision}
2. {decision}

## Milestones

| # | Milestone | Size | Depends on | Branch | Done when |
|---|---|---|---|---|---|
| M1 | {title} | quickfix | — | {branch} | {one or two criteria} |
| M2 | {title} | plan | M1 | {branch} | {one or two criteria} |

### M1: {title}
{scope in two to four sentences; what it delivers and what it explicitly leaves to later
milestones}

### M2: {title}
{same}

## Deferred
{what was consciously left out of every milestone, each with a TODOS.md entry or a reason}

## Out of scope
{what this epic will not do, and why; PRD non-goals touched}

## Open Questions
{unresolved; "none" if none}

## What I noticed about how you think
{two to four bullets quoting specific things the user said}

{REVIEW REPORT placeholder, verbatim from _shared/plan-footer.md}
```

## Roadmap phase entry

Add or refresh this entry in `$DOCS_DIR/IMPLEMENTATION_PLAN.md`, in roadmap order, editing in
place. `N` is the next phase number, or the existing one when the epic came from a roadmap
phase. `/ship` keeps the Status, Branch, Plan, and Shipped columns current; office-hours writes
the milestone rows.

```markdown
## Phase N: {title}
epic: [{slug}]({repo-relative path to the epic file})
status: 0/{total} milestones shipped

| # | Milestone | Size | Status | Branch | Plan | Shipped |
|---|---|---|---|---|---|---|
| M1 | {title} | quickfix | not-started | {branch} | — | — |
| M2 | {title} | plan | not-started | {branch} | — | — |
```

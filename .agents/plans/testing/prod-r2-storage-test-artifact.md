## Affected Pages/Routes
- **Responsibilities page** — ResponsibilityCard + ResponsibilityForm render `icon_url` via `<img>`; upload + stock-icon picker. Test icons still render, upload works, stock icons still resolve.
- **Family members** — MemberAvatar renders `photo_url`; PhotoUpload flow. Test avatar upload + render.
- **Mealboard / Items** — ItemIcon, ItemCard, ItemDetailDrawer (hero image), ItemFormModal, RecipeImageUpload render `icon_url` / `image_url`. Test item icon + recipe image upload/render.
- **Any authenticated page with images** — after login, every `<img>` under `/uploads/*` must load (PR2: now cookie-authenticated).

## Key Interactions to Verify
- Upload a valid PNG/JPEG/WebP on each of the 4 upload types → preview shows → save entity → **image still there after full page reload**.
- Replace an entity's image with a new upload → old image no longer served (PR2: old R2 object deleted).
- Pick a stock icon for a responsibility/item → renders, and still renders after reload (already-adopted stock refs must not break).
- Swap a managed upload → a stock icon → old uploaded object is reclaimed; stock icon renders.
- Log out → navigate back to a page with images → images **fail to load / 401** (PR2). This is the security-critical check.
- Operator password/session-version rotation → existing image cookie can no longer read `/uploads/*` (PR2). This locks the read guard to the same revocation invariant as normal auth.

## Edge Cases
- **GIF upload → rejected** (NEW behavior, all 4 upload types). Confirm a clear error, not a silent failure.
- Faked extension (e.g. a `.txt` renamed to `.png`, or an executable renamed `.png`) → rejected via magic-byte sniff.
- SVG upload → rejected.
- Over-cap file: icon > 1 MB → 413; family photo / recipe image > 5 MB → 413.
- Upload an image but close the tab WITHOUT saving the entity → object is swept ~24h later (abandoned-upload GC). Verify it does NOT get swept if the entity WAS saved within 24h.
- Unauthenticated `GET /uploads/<any-key>` directly (curl, no cookie) → **401** (PR2). No public static surface remains.
- Missing image key (deleted object or unknown key) → 404, page degrades gracefully (broken-image, not a crash).
- Malformed media keys (`../`, `%2e%2e`, empty segment, unknown subdir, non-UUID managed filename, wrong extension) → rejected before LocalDisk/R2 lookup.
- Copy-pasting another entity's managed `/uploads/*` URL into an image field → rejected instead of silently sharing/deleting a key under the 1:1 key→entity invariant.
- Replace/delete failure ordering: if the DB update/delete rolls back, the previous image is still served; storage cleanup only happens after commit.
- R2 unavailable/timeout on read → distinct 5xx/logged storage-unreachable error, not a misleading missing-key 404.

## Critical Paths
- **Authenticated end-to-end:** log in → upload each image type → images render everywhere → reload → still render (PR2: served from R2 via the cookie-authed proxy).
- **No public leak:** a private image URL cannot be loaded without a valid session cookie (PR2). Verify Cloudflare does NOT serve `/uploads/*` from its edge cache to an unauthenticated client (`Cache-Control: private, no-cache` honored end-to-end; browser revalidation with a valid cookie may return `304`).
- **Prod durability (PR2):** an image uploaded to prod survives a backend redeploy/restart (proves R2, not ephemeral disk).
- **Visual-regression suite green:** the Playwright suite shims `/uploads/*` (like `/auth/refresh`); baseline images unchanged.
- **PR2 rollback smoke:** record the cutover timestamp, keep CF Access Application 1 up, avoid real household uploads during smoke verification, and choose forward-fix vs rollback-with-R2-recovery if media reads fail.

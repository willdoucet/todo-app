## Key Interactions to Verify

- **Backend auth gate (per protected router):** call any protected endpoint with no `Authorization` header → 401. Call with valid JWT → 200. Call with expired JWT → 401. Call with stale `session_version` → 401.
- **FastAPI auto-docs/schema disabled:** `/docs`, `/redoc`, and `/openapi.json` return 404. These routes are registered by `FastAPI(...)`, not the protected APIRouter, so they must be disabled explicitly.
- **Frontend redirect-on-401:** observe network tab during cold-boot to a protected route while logged out → `/auth/refresh` returns 401 → browser redirected to `/auth?return_to=<path>` (URL-encoded).
- **Frontend silent-refresh:** with valid `__Host-refresh` cookie, set tokenStore in-memory token to expired/cleared → next API call hits 401 → axios interceptor calls `/auth/refresh` → mints new token → original API call retries → succeeds. (M4-shipped behavior; M5 verifies it still works post-enforcement.)
- **Login + return_to:** navigate to `/lists` while logged out → redirected to `/auth?return_to=%2Flists` → login → redirected to `/lists`, NOT `/`.
- **Logout flow:** click logout → POST /auth/logout returns 204 → cookie cleared → redirected to `/auth`.
- **Visual-test stack auth flow (CI):** globalSetup.js logs in or registers against api-test, writes access_token to `.vrt-token`. Specs run with auth-base.js fixture, which intercepts `/auth/refresh` in the test browser and returns the cached token. M4's `rootAuthLoader → performRefresh → tokenStore.set` chain runs unmodified.
- **PR2 plumbing-test deletion:** `/plumbing-test` → 404 from FastAPI; main bundle no longer references `PlumbingShell`.
- **PR2 CF Access removal:** mealy.dev loads with no CF challenge; api.mealy.dev/tasks (no token, no CF approval) → 401 from FastAPI (was 403 from CF in PR1).

## Edge Cases

- **`/uploads/*` StaticFiles mount stays public** between M5 PR2 and M7. Verify with `curl https://api.mealy.dev/uploads/stock_icons/<known-file>` after PR2 → 200 with image content-type. PRD §5.7 must reflect this.
- **Upload API vs static mount split.** Protected APIs are `/upload/*` and `/uploads/item-icon`; only the `/uploads` `StaticFiles` mount is public. The structural auth test must not allowlist `/upload`, `/uploads`, or `/uploads/` as APIRoute prefixes.
- **CF Access defense in depth during PR1 soak.** PR1 ships auth enforcement BEHIND CF Access. Anyone hitting api.mealy.dev/tasks without CF approval gets 403 from CF, not 401 from FastAPI. The 401 only manifests on requests that already cleared CF. Verify with: with-CF-approval → 401, without-CF-approval → 403.
- **Local dev breakage after PR1.** Without `JWT_SECRET_KEY` and `HOUSEHOLD_ACCESS_KEY` env vars, every protected route 401s. Plan adds startup warning + `.env.example` update; CLAUDE.md / LESSONS.md gets a note.
- **15-min access token expiry vs. CI suite duration.** Visual-tests CI is currently ~3min. Token comfortably below expiry. Document a revisit trigger if suite grows 5x.
- **Idempotency of globalSetup.** First CI run: register-on-401 path (DB fresh from `down -v`). Local run after first: login-first path (DB persistent). No collision.
- **`HOUSEHOLD_ACCESS_KEY` in frontend-visual container.** Plan must propagate this to frontend-visual service in docker-compose.yml — globalSetup.js reads `process.env.HOUSEHOLD_ACCESS_KEY` and throws if unset.
- **Cookie `Secure=True` is dropped on `http://api-test`.** This is why the design uses Playwright `context.route()` instead of cookie-based session reuse. The cookie hardening at `routes.py:43, 59` is correct and stays untouched.
- **Logout token-validity ordering.** `/auth/logout` calls `validate_bearer` BEFORE any mutation (M3 design — adversarial review run 2). A stale token after password rotation must 401 and must NOT revoke a newer valid refresh token. Already covered by M3 unit tests; verify the wiring did not break the special-case `validate_bearer` direct call vs. `Depends(get_current_user)` wrapper.

## Critical Paths

1. **Backend auth gate enforcement on EVERY protected router** — covered by:
   - Programmatic enumeration unit test (Issue 1C + adversarial hardening resolution): walks `app.routes`, asserts `get_current_user` is in the dependency tree of every non-allowlist `APIRoute`, asserts the only public `Mount` is `/uploads`, and asserts `/docs`, `/redoc`, and `/openapi.json` are absent. Fails the build if a contributor adds a router via `app.include_router(X)` instead of `protected.include_router(X)`, accidentally makes upload APIs public, or leaves FastAPI docs/schema exposed.
   - Per-route integration tests with `auth_headers` (Issue 1A resolution): exercise the real JWT path through every protected router on the happy path.

2. **Auth-config initialization in tests** — covered by:
   - Autouse session fixture `install_auth_config` (Issue 1B resolution) in `tests/integration/conftest.py`. Fixture mirrors `tests/unit/auth/test_dependencies.py:29-37` pattern.

   **Test-isolation refactor inside M5 PR1 (Issue 2C reversal — 2026-05-06):** `db_session` fixture switched from per-test `Base.metadata.create_all`/`drop_all` to session-persistent schema + per-test transaction rollback (`AsyncSession(join_transaction_mode='create_savepoint')`). All 18 existing integration tests must stay green under the new isolation as a hard PR1 gate. Risk-coupling acknowledged: a CI failure on PR1 may surface as auth bug, isolation bug, or interaction.

3. **End-to-end frontend auth flow** — verified manually after PR1 deploy via 5-point smoke list (Step 1.10):
   - Cold-boot to / while logged out → redirect to /auth?return_to=/
   - Login → redirect to /, mealboard renders
   - Logout → return to /auth
   - Open / in new tab while access token expired but refresh cookie valid → silent-refresh kicks in
   - Manually clear refresh cookie + reload / → redirect to /auth?return_to=/

4. **Visual-regression CI green on PR1 and PR2** — non-negotiable per Constraints. Failure modes:
   - HOUSEHOLD_ACCESS_KEY missing in frontend-visual env (Issue 1D)
   - Auth secrets missing in CI .env (Step 1.5 covers; verified via fail-fast secret check)
   - Stale `.vrt-token` from a previous run (globalSetup.js always overwrites)

5. **PR1 → PR2 soak before CF Access removal** — at least 24h with green visual-tests CI runs. Justification: defense in depth window during which a hole in PR1's enforcement is still caught by CF Access.

6. **PR2 merge-first ordering, no exposure window** — verify in this order:
   1. Code merge to master + green CI.
   2. Manual production deploy using the current Vercel + Fly procedure (M5 cannot assume merge-to-master CD; automated deploys are deferred to M8).
   3. Smoke-verify deletes propagated (`/plumbing-test` returns 404, frontend bundle no longer references PlumbingShell) and docs/schema stay disabled.
   4. Only then remove CF Access policy.
   5. Smoke-verify post-CF (no challenge, /tasks returns 401 from FastAPI).
   6. Verify /uploads/* still 200s (Premise 5 acknowledgment).

7. **PR1 rollback path** — single-commit `git revert <merge-sha>` + push. CI runs. CF Access stays up so users hitting mealy.dev/ are still gated by CF. Existing access tokens keep working (stateless JWTs against unchanged JWT_SECRET_KEY). No data migrations to revert.

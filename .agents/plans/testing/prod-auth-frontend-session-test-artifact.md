## Affected Pages/Routes

- `/` (CalendarPage) — verify protected-route gate; cold load with valid cookie renders calendar; cold load with no cookie redirects to `/auth?return_to=%2F`.
- `/lists`, `/responsibilities`, `/settings`, `/mealboard/*` — same protected-route behavior; nav between them after one cold boot must NOT trigger additional `POST /auth/refresh`.
- `/auth` — auto-discriminated form. With `account_exists=true` shows login; `false` shows household setup; malformed response shows login (defensive); `/auth/status` 5xx shows inline retry blocking both forms.
- `/auth?return_to=...` — verify same-origin relative paths only; reject full URL, `//evil.com`, `javascript:`, `/auth*`, control chars.
- `/settings` — logout button clears token and navigates to `/auth`; on 5xx/network/timeout it fails closed locally but warns that server logout could not be confirmed.

## Key Interactions to Verify

- Page reload on a protected route with valid `__Host-refresh` cookie: ends on the same route with no flash of `/auth`.
- Page reload on a protected route with no cookie: lands on `/auth` with `?return_to=<original>`. After successful login, lands back on the original.
- Already-logged-in user typing `/auth` directly: redirects to `/` (or `safeReturnTo(?return_to=...)` if present), does NOT show the login form.
- Login with bad password (401): shows "Invalid email or password" inline; no redirect storm; form stays mounted.
- Login while `/auth/status` is still loading: submit button disabled.
- Login while mutation pending: submit button disabled (no double-submit).
- Register with `HOUSEHOLD_ACCESS_KEY` mismatch (401): shows "Invalid household access key".
- Register when account already exists (backend returns byte-identical 401): refetches `/auth/status`, flips form to login.
- Login/register/refresh under 429: shows "Too many attempts. Please wait a moment and try again."
- Login/register under 5xx or network failure: shows "Couldn't reach the server. Retry."
- Logout via `/settings` button: token cleared, redirected to `/auth`, even when `/auth/logout` returns 5xx or times out.
- First-run flow on a fresh deploy: visit `/` → redirect to `/auth` → setup form (NOT login). Submit valid registration → token set → land on `/`.
- After registration, hitting `/auth` again shows the login form (no toggle UI ever rendered).
- Five concurrent requests during a 401 window: exactly ONE `POST /auth/refresh`, exactly ONE `router.navigate('/auth?...')` if refresh ultimately fails.
- A mechanically migrated imperative caller using the central `api` client gets an API 401, then refresh returns 401: token clears and exactly one `/auth?return_to=...` navigation fires.
- A mechanically migrated imperative caller gets an API 401, then refresh returns 5xx/network/timeout: no `/auth` navigation fires; the caller receives the server/network failure so the feature can show its normal error path.
- One imperative caller and one TanStack Query caller fail terminally at the same time: the shared redirect helper dedupes them to exactly one navigation with deterministic `return_to`.
- Logout with backend 5xx/network/timeout: token clears and `/auth` renders, but the UI warns that the server could not confirm logout instead of claiming the HttpOnly refresh cookie was cleared.
- HydrateFallback spinner respects OS dark mode AND persisted `darkMode` localStorage key (without provider access).
- Backend-uploaded media after the API-client migration: uploaded family photos, recipe images, food-item icons, and responsibility icons render from the API origin via the shared URL helper; already-absolute image URLs pass through unchanged.
- Logout while a refresh is already in flight: logout waits for that refresh to settle before posting `/auth/logout`; when both complete, no access token is resurrected and the user remains on `/auth`.
- `VITE_M2_SHELL=true`: PlumbingShell renders and no `/auth/refresh` call fires. With the flag false, the new data-router auth flow is active.

## Edge Cases

- Backend hung mid-refresh: 10-second timeout fires, loader rejects, BootErrorScreen renders with retry. (NOT a redirect to `/auth`.)
- `/auth/refresh` returns 5xx / network error / malformed JSON: BootErrorScreen, NOT `/auth`. Retry button calls `router.revalidate()`.
- `/auth/refresh` returns 401: redirect to `/auth?return_to=...` with the path sanitized.
- Mid-session original API request returns 401 and refresh returns 5xx / network / timeout: no auth redirect; the original feature sees the infrastructure failure.
- Mid-session original API request returns 401 and refresh returns 401: shared auth redirect helper handles both imperative callers and Query callers.
- `/auth/refresh` returns malformed body (`access_token` not a string): rejects before touching tokenStore; tokenStore stays null.
- Server-side `session_version` bump while user is mid-session: brief one-round-trip flash of the protected route, then 401 → refresh fails → redirect. Documented as acceptable.
- StrictMode dev boot: loader runs twice, single-flight ensures exactly one `POST /auth/refresh`.
- `error.config` undefined in axios interceptor (network error before request sent): interceptor throws cleanly, does not raise `TypeError`.
- Migrated API callers use relative paths with the central client (`api.get('/tasks')`), not absolute `${VITE_API_BASE_URL}/...` URLs. `VITE_API_BASE_URL` should appear only in `lib/apiBase.js`.
- `redirecting` guard reset on EVERY mount of AuthPortalPage (top-level useEffect), including the already-logged-in short-circuit path.
- `return_to` malicious inputs (full URL, `//host`, `javascript:`, `/auth`, `/auth/login`, `\r\n` injection): all rejected, post-login navigation falls back to `/`.
- `HOUSEHOLD_ACCESS_KEY` value never appears in console logs, toast messages, or error payloads.
- No `dangerouslySetInnerHTML` anywhere under `frontend/src/pages/AuthPortalPage*` or `frontend/src/lib/auth/*`.
- Multi-tab logout: tab A logs out; tab B discovers on next API call (401 → refresh fails → redirect). No active broadcast expected in v1.
- Logout failure honesty: because JavaScript cannot clear the HttpOnly refresh cookie, tests must distinguish local sign-out from confirmed server revocation when `/auth/logout` fails before a clearing `Set-Cookie`.
- Calling the auth redirect helper before `setRouter()` has bound the router: token is cleared, a DEV warning is logged, and the `redirecting` guard is NOT set (no test pollution between cases, no production deadlock if a 401 ever fires before bootstrap completes).
- After a successful `POST /auth/register`, the cached `/auth/status` query is invalidated. If the new operator logs out within 30s and lands back on `/auth`, the LoginForm renders (NOT the SetupForm).
- `apiUrl()` helper: relative `/uploads/...` paths are prefixed with `VITE_API_BASE_URL`; absolute `http://` and `https://` URLs are returned unchanged; empty/nullish paths do not crash callers.
- Repo-wide env usage after migration: `grep -r "VITE_API_BASE_URL" frontend/src` returns exactly one source hit, `frontend/src/lib/apiBase.js`.
- Logout/refresh race: a refresh response resolving after the logout click does not leave a token in `tokenStore`; logout remains fail-closed locally even when the refresh promise rejects.

## Critical Paths

1. **Cold-boot happy path**: load any protected route with valid cookie → loader runs → refresh succeeds → token in store → page renders. No flash of `/auth`.
2. **Cold-boot unauthenticated**: load any protected route without cookie → loader runs → refresh 401 → redirect to `/auth?return_to=...` → login submit → token set → land on original route.
3. **First-run setup**: fresh deploy → visit `/` → redirect to `/auth` → setup form (because `account_exists: false`) → submit registration → token set → `/`.
4. **Mid-session 401 → silent recovery**: token expires while user is on `/calendar` → user clicks an action → 401 → axios interceptor performs refresh → original request retried → action succeeds, no UI flicker.
5. **Mid-session 401 → terminal auth failure**: refresh returns 401 → tokenStore cleared → exactly one navigate to `/auth?return_to=<current>` even with N concurrent failing requests across imperative and Query callers → after re-login, lands on original route.
6. **Mid-session 401 → infrastructure failure**: original request returns 401 → refresh returns 5xx/network/timeout → no `/auth` navigation; feature-level server/network error path remains visible.
7. **Logout**: click logout on `/settings` → token cleared → navigate `/auth`. Repeat with backend down → same local outcome plus warning that server logout could not be confirmed.
8. **Open-redirect defense**: `/auth?return_to=https://evil.com/` → after login, navigates to `/`, NOT to `evil.com`.
9. **Backend down at boot**: visit `/calendar` with valid cookie + backend down → BootErrorScreen "Can't reach the server. Retry." → bring backend up → click Retry → loader re-runs → calendar renders.
10. **Logout during refresh**: begin a silent refresh, click logout before the refresh resolves, then resolve the refresh → logout proceeds after the refresh settles, clears local auth, lands on `/auth`, and no new in-memory token remains.
11. **M2 shell coexistence**: run app boot with `VITE_M2_SHELL=true` → PlumbingShell only, no auth loader/network refresh. Run with the flag false → data router mounts and protected-route auth loader behavior applies.

## Adversarial Review Additions

- Shared auth redirect helper is part of the test contract: terminal refresh 401s must redirect for both still-imperative callers and TanStack Query callers.
- Non-401 refresh failures must stay server/network errors, not fake logged-out redirects.

- Rollback/mixed-version safety remains code-only for M4: no schema change, Strict cookie backend is compatible with old frontend, and frontend rollback is a Vercel redeploy.

## Eng Review #3 Additions (2026-05-03, run 3)

Three silent-failure test gaps identified after Adversarial Review #2; folded into the plan as SC #40, #41, #42:

- **SC #40 — `/auth/*` URL guard in the response interceptor.** Test that a 401 from `api.post('/auth/login')` (wrong password) does NOT call `performRefresh` and does NOT trigger `redirectToAuthOnce`. Pins the `original.url?.startsWith('/auth/')` short-circuit so a future regression cannot turn the wrong-password path into a refresh storm.
- **SC #41 — `_retried` infinite-loop guard.** Test that a 401 → refresh succeeds → retry returns 401 produces exactly ONE `POST /auth/refresh` and then throws. Without the `_retried` flag, a second 401 would re-enter refresh-and-retry indefinitely. Verifiable by mocking the original endpoint to return 401 twice with a successful refresh in between, and asserting one refresh call total.
- **SC #42 — handle401 type/status guard.** Test that `handle401` does NOT call `redirectToAuthOnce` when given (a) a 500/network/timeout axios error, (b) a non-axios `Error` with status 401, or (c) a `null`/`undefined` argument. Pins both branches of the type-and-status check so a backend hiccup never logs the user out via the global cache callback.

Plus one minor: pin `waitForRefreshToSettle()` returns immediately when no refresh is in flight (the in-flight case is already covered by SC #38). Folded into Step 2's test list as a one-line addition rather than a new SC.

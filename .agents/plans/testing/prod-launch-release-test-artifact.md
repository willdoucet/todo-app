## Key interactions to verify
- Request straight to the Fly IP with the public Host and no origin header → 421
  `{"detail":"host_not_allowed"}` and one WARNING under `app.gate` with `reason=origin_verify_absent`.
- Same request with a wrong origin header → same body, `reason=origin_verify_mismatch`.
- Request with `Host: mealy-app-prod.fly.dev` and a valid header → same body, `reason=host_mismatch`.
- Request with an empty or missing Host (test client only) → same body, `reason=host_absent`.
- Production with `PUBLIC_API_HOST` unset → same body, `reason=public_api_host_unconfigured`.
- Production with an empty `ORIGIN_VERIFY_SECRET` at request time → same body,
  `reason=origin_verify_secret_empty`.
- The emitter patched to raise on the module `app.main` looks it up from → the 421 and its body are
  unchanged and no 500 escapes; a negative control proves the patch took effect.
- `GATE_BREAK_GLASS=1` → a request with the right Host and no origin header is admitted, a WARNING
  `event=host_gate outcome=bypassed` is logged per request, `/healthz` reports
  `gate_break_glass: true`; a wrong Host is still 421.
- `GATE_BREAK_GLASS` set to `true`, `yes`, `" 1 "`, or `0` → flag is off.
- `GET /healthz` with `GIT_COMMIT=abc123` in the environment → `version: "abc123"`; unset →
  `version: "unknown"`; response header `Cache-Control: no-store`.

  with the last-known rows, `jobs.read: "stale"`, and `jobs.read_at` still the time of the last
  good read; stubbed to raise from boot → `jobs.read: "unavailable"`, `jobs.read_at: null`, and
  `jobs.rows: []` (the server never invents null rows it did not read); the handler issues zero
  database queries in all cases. Every response carries `jobs.now`, the serve time with a `Z`.

## Edge cases
- `Host: api.mealy.dev:443` → admitted (port stripped); `Host: :443` → `host_absent`.
- Non-latin-1 origin header → 421 `origin_verify_mismatch`, no 500 (existing test, now with the
  reason assertion).
- Two web machines during a rollout (only relevant if the count ever returns to 2) → check 8 is
  run after the rollout completes; the runbook says so.
- The worker on the previous image after a code rollback → writes no heartbeats; `/healthz` on the
  previous image has no `jobs` key, so the operator's rollback smoke passes `--skip=healthz_jobs`
  and the daily cron, which has no skip list, exits 1 naming the missing key until the roll
  forward. The cron has no grace of its own after a deploy or a restore: a NULL row passes only
  when the server sent `stale: false` for it, and the only grace is the server's (3× the
  interval after the web process starts).

## Operational invariants
- `beat=1` at all times; `infra/fly-scale.json` is `{"web": 1, "worker": 1, "beat": 1}` and
  `fly machines list --json` agrees after every release.
- The 421 body is exactly `{"detail":"host_not_allowed"}` for every rejection reason.
- `/healthz` never issues a database or Redis call on the request path and always answers within
  Fly's 2-second probe timeout, whatever the heartbeat store is doing.
- `GATE_BREAK_GLASS` is off outside a declared incident; `/healthz.gate_break_glass` is false on
  every cron run.
- `job_heartbeats` has one row per **beat-schedule** task name (four: two 10-minute syncs, two
  hourly sweeps) and `last_success_at` for each 10-minute task is under 30 minutes old whenever
  the worker is up. One-shot tasks never add a row. A NULL row is stale only once this web
  process has been up longer than 3× that task's interval; a row with a timestamp is stale once
  that timestamp is older than 3× its interval. Restarting web rearms the NULL grace only
  (Eng review 4, 1A; adversarial review, 2026-09-21: the rearm is a named limit).
- `/healthz.jobs.rows` is `[]` if and only if `jobs.read` is `"unavailable"`; otherwise it holds
  exactly one row per `beat_schedule` task, in `beat_schedule` order (Eng review 4).
- The most recent `ops-check` run is green and under 48 hours old at the start of every release
  **once the workflow has ever run**; before that the gate records `n/a`.
- At least one restore point under 48 hours exists for `mealy-app-prod-db` (volume snapshot or WAL
  recovery point), and the cron says so daily.
- The deployed frontend and backend commits are ancestors of the release commit after every
  release.
- RUNBOOK header names the 50-day public-repo re-arm for GitHub's 60-day scheduled-workflow disable.

## Log hygiene
- One `app.gate` WARNING per rejection with `event=host_gate`, `outcome=rejected`, `reason`
  (one of six), `ip` from `request.client.host`, `request_id`, `path` (truncated), and the
  presence and length of the Host and origin headers.
- One `app.gate` WARNING per admitted request while the break-glass flag is on
  (`outcome=bypassed`).
- One WARNING from the heartbeat writer per failed store write, naming the task and the error
  class; never the payload. When the second, error-recording write also fails, one more WARNING
  says so. That line is the operator's only signal when the database itself is the problem,
  because once a snapshot ages out with no `write_error` the card reads "Stopped" rather than "Can't record job runs". A table the web has never read reads "Can't check".
  Read "ages out" as the rows passing 3× their interval while the web can still read the table
  (only the worker's side is broken). A table the web cannot read now reads "Can't check" 2
  minutes after its last good read, whether or not it was ever read.
  <!-- plan-adversarial-review · harness: grok · model: Grok 4.7 · 20260921-205706 -->
  <!-- plan-eng-review · Eng review 5 · harness: claude-code · model: Fable 5.1 · 2026-09-21 -->
- Never in any log line, script output, workflow log, or transcript: `ORIGIN_VERIFY_SECRET`, the
  presented `X-Origin-Verify` value, the Cloudflare token, the Fly token, a password, a password
  hash, or a refresh-token value. The integration suite's log-hygiene scanner covers the backend
  lines; the drift and smoke script tests cover their stdout and stderr.
- `CF-Connecting-IP` and `X-Forwarded-For` are never used for the gate line's `ip`.

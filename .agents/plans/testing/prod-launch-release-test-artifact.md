## Operational invariants
- `beat=1` at all times; `infra/fly-scale.json` is `{"web": 1, "worker": 1, "beat": 1}` and
  `fly machines list --json` agrees after every release.
- The 421 body is exactly `{"detail":"host_not_allowed"}` for every rejection reason.
- `/healthz` never issues a database or Redis call on the request path and always answers within
  Fly's 2-second probe timeout, whatever the heartbeat store is doing.
- `GATE_BREAK_GLASS` is off outside a declared incident; `/healthz.gate_break_glass` is false on
  every cron run.
- `job_heartbeats` has one row per **beat-schedule** task name (four: two 10-minute syncs, two
  hourly sweeps) and `last_success_at` for each 10-minute task is under 30 minutes old whenever
  the worker is up. One-shot tasks never add a row.
- The most recent `ops-check` run is green and under 48 hours old at the start of every release
  **once the workflow has ever run**; before that the gate records `n/a`.
- At least one restore point under 48 hours exists for `mealy-app-prod-db` (volume snapshot or WAL
  recovery point), and the cron says so daily.
- The deployed frontend and backend commits are ancestors of the release commit after every
  release.
- RUNBOOK header names the 50-day public-repo re-arm for GitHub's 60-day scheduled-workflow disable.

## Log hygiene
- One `app.gate` WARNING per rejection with `event=host_gate`, `outcome=rejected`, `reason`
  (one of six), `ip` from `request.client.host`, `request_id`, `path` (truncated), and the
  presence and length of the Host and origin headers.
- One `app.gate` WARNING per admitted request while the break-glass flag is on
  (`outcome=bypassed`).
- One WARNING from the heartbeat writer per failed store write, naming the task and the error
  class; never the payload.
- Never in any log line, script output, workflow log, or transcript: `ORIGIN_VERIFY_SECRET`, the
  presented `X-Origin-Verify` value, the Cloudflare token, the Fly token, a password, a password
  hash, or a refresh-token value. The integration suite's log-hygiene scanner covers the backend
  lines; the drift and smoke script tests cover their stdout and stderr.
- `CF-Connecting-IP` and `X-Forwarded-For` are never used for the gate line's `ip`.

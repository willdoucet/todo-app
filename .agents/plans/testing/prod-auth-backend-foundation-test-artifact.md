## Affected Routes
- `POST /auth/register` — verify first-account creation, access-key gating, duplicate-account rejection, refresh cookie issuance, and byte-identical unavailable responses.
- `POST /auth/login` — verify email/password authentication, same-client refresh-cookie replacement, multi-device preservation, login timing-oracle defense, and byte-identical invalid-credential responses.
- `POST /auth/refresh` — verify refresh-token rotation, the 60-second grace window, concurrent refresh serialization, corrupted successor-chain rejection, logout/password-rotation revocation, and uniform failure responses.
- `POST /auth/logout` — verify bearer-token requirement, all-refresh-token revocation, cookie clearing, and expired/malformed bearer rejection.
- `GET /auth/status` — verify public account-existence status only, with no config or host leakage.
- `app/auth/dependencies.py::get_current_user` — verify JWT decode failures, malformed claims, deleted user rows, stale `session_version`, and current `session_version`.
- Production host gate — verify direct Fly-hostname access to non-`/healthz` paths is rejected while `api.mealy.dev` traffic still reaches handlers.

## Key Interactions To Verify
- Register the first account, then confirm `/auth/status` flips from `false` to `true`.
- Attempt registration with a wrong access key, an existing account, and a concurrent register race; all losers must receive the same `401 {"detail": "registration_unavailable"}` shape.
- Run the concurrent register race with two different valid emails; exactly one request succeeds and exactly one user row exists.
- Login with correct credentials and confirm a refresh cookie plus bearer access token are returned.
- Login from device/session B while device/session A still has a valid refresh cookie; session A must still refresh successfully.
- Re-login from the same client while sending its prior refresh cookie; only that prior cookie's token row should be revoked.
- Refresh a fresh cookie, then refresh the old cookie within 60 seconds; the second response should return an access token without a new `Set-Cookie` header.
- Logout from one device and confirm another device's refresh cookie is revoked at the database level.
- Logout with a stale bearer token after simulated password rotation; it must return 401 and must not revoke a newly issued valid refresh token.
- Hit `/auth/status` and one mutating `/auth/*` endpoint through the direct Fly hostname in production mode; both must fail at the host gate before auth logic. The same custom-domain request through Cloudflare must still behave per the endpoint contract.
- Simulate operator password rotation by bumping `session_version` and revoking refresh tokens; old access and refresh tokens must fail.
- Confirm every `/auth/*` request emits exactly one structured JSON log line and no password, access token, refresh token, token hash, or password hash appears in logs.

## Edge Cases
- Missing, blank, sub-32-byte, or deny-listed-placeholder `JWT_SECRET_KEY` / `HOUSEHOLD_ACCESS_KEY` fails closed in production config loading. Deny-list (case-insensitive substring): `changeme`, `change-me`, `your-secret`, `your_secret`, `placeholder`, `example`, `replace-me`, `replace_me`, `todo`, `default`, `insecure`, `test-key`, `test_key`.
- Importing `app.main` without auth env vars in test mode does not fail; production startup/lifespan validation with missing/placeholder secrets fails. Config validation must not run at module import time.
- IP sanitization: `CF-Connecting-IP` precedence, `X-Forwarded-For` first-comma-entry parsing, and 128-char truncation are individually unit-tested; raw header blob never appears in logs.
- Request ID sanitization: oversized `X-Request-Id`, control-character values, and values outside the safe character set are replaced with generated UUID4 values before logging; raw attacker-controlled values never appear in auth logs.
- Case-B no-live-terminal: refresh within grace window where every row in the successor chain was revoked mid-traversal by a concurrent logout or password rotation returns the uniform `refresh_failed` 401.
- Case-B terminal-row revocation race: successor traversal locks successor rows. If logout/password rotation commits first, refresh rejects; if refresh commits first, revocation waits and then revokes. Refresh must not succeed after observing a revoked terminal row.
- Login-success block (revoke-old-cookie + insert-new-refresh) is atomic — partial commit is impossible.
- **Concurrent register race:** two simultaneous `POST /auth/register` requests with different valid emails and valid credentials → exactly one succeeds, exactly one user row exists, and the loser receives a `401` with body byte-identical to the wrong-access-key response.
- **Logout authentication:** `POST /auth/logout` without an `Authorization: Bearer …` header returns `401`; with a malformed (non-`Bearer`) scheme returns `401`; with an expired Bearer token returns `401`. Verifies the CSRF defense at the logout boundary.
- **Logout stale-token mutation guard:** after simulated password rotation, logout with the pre-rotation access token returns `401` and does not revoke a new valid refresh token issued after the rotation.
- **Logout cookie clearing:** successful logout's clearing `Set-Cookie` uses `Path=/`, `Secure`, `HttpOnly`, the same `SameSite` policy, no `Domain`, and `Max-Age=0`.
- **Auth dependency header malformation:** `get_current_user` returns `401` for: missing `Authorization` header entirely; non-`Bearer` scheme (e.g. `Authorization: Basic …`); empty `Bearer ` value with no token; deleted user row between token issuance and use.
- **Dummy-hash lazy-cache mechanism:** first `/auth/login` against an unknown email generates the dummy hash using the currently-injected `PasswordHasher` (mock-spy: `hasher.hash` called exactly once); subsequent unknown-email logins reuse the cached dummy hash (`hasher.hash` not called again); after `set_password_hasher(new_hasher)` the cache is invalidated and the next unknown-email login regenerates with the new hasher.
- **Refresh Case A DB-state assertions:** after a successful Case-A refresh, the old row has `superseded_at` set AND `successor_id` pointing to the new row; the new row has `superseded_at IS NULL`, `successor_id IS NULL`, fresh `issued_at`, and `expires_at = NOW() + 30 days`.
- Register password longer than 128 characters returns `422`; login password longer than 128 characters returns the same `401 {"detail": "invalid_credentials"}` shape as a wrong password.
- Unknown email and wrong password both call password verification and both log only `reason=bad_credentials`.
- Argon2 `VerifyMismatchError`, `VerificationError`, and `InvalidHashError` all map to the same invalid-credential response.
- Two simultaneous Case-A refresh requests with the same fresh cookie serialize on the refresh-token row lock.
- Successor-chain cycle or traversal depth greater than 10 rejects with uniform `refresh_failed` and logs `reason=bad_refresh_chain` without token values.
- Refresh cookie not found, expired, revoked, superseded past grace, and revoked by password rotation all return the same `401 {"detail": "refresh_failed"}` body.
- JWT `ExpiredSignatureError`, `InvalidSignatureError`, `DecodeError`, and `InvalidTokenError` all return 401.
- JWT payloads with missing `sub`, non-integer `sub`, missing `session_version`, non-integer `session_version`, deleted user rows, or stale `session_version` all return 401 without leaking a 500.
- Migration downgrade drops auth tables but leaves the `citext` extension installed.
- Production rollback is code-only by default and leaves auth tables/data in place unless intentionally abandoning M3 auth state after backup.
- Previous app image still boots against the migrated database after at least one user and refresh-token row exist.
- Production host gate rejects direct `Host: mealy-app-prod.fly.dev` requests to `/auth/*` and representative existing API routes; `Host: api.mealy.dev` reaches handlers; `/healthz` remains reachable for Fly health checks.
- Refresh timestamp tests set DB timestamps directly for T+30/T+90 cases instead of sleeping or relying on wall-clock drift.

## Critical Paths

The six paths below are the categories. The numbered Definition-of-Done End-to-End Sequence further down is the canonical drill-down for "Normal auth loop" and is what `/qa` should walk through on a deployed instance.

- **First-run account claim:** status false → register → status true → duplicate register rejected; concurrent registration with two different valid emails still leaves exactly one user row.
- **Normal auth loop:** login → protected-dependency check with access token → refresh → dependency check with new access token → logout → refresh rejected. (See DoD sequence below for the full numbered runbook.)
- **Multi-device household path:** login session A → login session B → session A refresh still succeeds → logout revokes both sessions.
- **Rotation-race path:** register/login → two concurrent refreshes using the same cookie → one Case A response with `Set-Cookie`, one Case B response without `Set-Cookie`, both return usable access tokens.
- **Secret safety path:** configure secrets through Fly secret names only → verify with `fly secrets list` names/digests only → no secret values appear in logs, terminal output, or transcripts.
- **Direct-origin bypass path:** direct Fly hostname rejects `/auth/*` and existing API routes before auth/business logic; custom API hostname through Cloudflare still works; `/healthz` remains reachable.

### Definition-of-Done End-to-End Sequence

The single-most-important end-to-end flow. If any step does not behave as specified, M3 is not done.

1. Operator deploys M3 to Fly.
2. Operator manually calls `POST /auth/register` once (through the Cloudflare Access edge gate) with `HOUSEHOLD_ACCESS_KEY` + chosen email/password.
3. Server returns `200` + access token in body + sets `__Host-refresh` cookie with the attribute set listed in the plan's Cookie Attribute Set table.
4. Subsequent `GET /auth/status` returns `{"account_exists": true}`.
5. Subsequent `POST /auth/register` with any syntactically valid body (right key, wrong key, or otherwise valid-shaped credentials) returns `401` with the byte-identical `{"detail": "registration_unavailable"}` body. Malformed JSON/body shape may still return FastAPI/Pydantic `422`.
6. `POST /auth/login` with correct creds returns `200` + a fresh `__Host-refresh` cookie + access token in body.
7. `POST /auth/refresh` with the cookie from step 6 returns `200` + new access token + a new `__Host-refresh` cookie (Case A — fresh-token path).
8. `POST /auth/logout` with the latest Bearer access token returns `204`; the `Set-Cookie: __Host-refresh=; Max-Age=0` header clears the cookie.
9. `POST /auth/refresh` with the now-revoked cookie returns `401` with `{"detail": "refresh_failed"}`.
10. **Multi-device smoke (Adversarial review):** repeat steps 6-7 from a second browser session B while session A still holds its cookie from step 7. Session A's original cookie must still successfully refresh once after session B logs in. Only a same-client re-login on session A (sending A's own cookie to `/auth/login`) revokes A's refresh row.
11. **Direct-origin smoke (Adversarial review run 2):** `https://<app>.fly.dev/auth/status` and one mutating `/auth/*` request fail at the host gate, while the same path through `https://api.<domain>` behaves per contract.

### Operational Invariants

These must hold at all times, verified by tests in addition to the DoD sequence:

- `password_hasher.verify` is called on EVERY `/auth/login` attempt — success path, wrong-password path, AND unknown-email path. Verified by mock-spy assertion in `tests/integration/auth/test_login.py` AND by the existence of the dummy-hash lazy-cache mechanism in `app/auth/passwords.py`.
- No log line, anywhere in the auth stack, contains a secret value, password hash, refresh-token plaintext, refresh-token SHA-256 hash, access JWT, or `HOUSEHOLD_ACCESS_KEY` value. Verified by the regex scan in `tests/integration/auth/test_log_hygiene.py` over every `caplog` record produced during the integration suite.
- Byte-identical 401 responses across all paired enumeration-prone failure cases (wrong-access-key vs. account-already-exists; wrong-password vs. unknown-email; refresh-cookie-unknown vs. refresh-revoked vs. refresh-superseded-past-grace vs. refresh-expired vs. refresh-chain-corrupt). Verified by exact-equality assertions over response status, body, and headers in the byte-identicality tests.
- `hmac.compare_digest` (not `==`) is the access-key comparison primitive. Verified by source-code grep in `app/auth/service.py` (the timing-microbenchmark approach is brittle and explicitly NOT used — Eng review run 1 line 482).
- `app/auth/dependencies.py::get_current_user` exists, is fully unit-tested, and is **NOT** wired into any non-auth route in M3. Verified by grep over `app/routes/*.py` and `app/main.py`.
- The production host gate exists and is not bypassable via `*.fly.dev` for non-`/healthz` paths. Verified by production-mode host-header tests and post-deploy smoke.

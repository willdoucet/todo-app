## Key Interactions to Verify

### Register first account (M3 + M4)
- Correct access key + new credentials → success + cookie set on `api.todo.williamdoucet.dev`, access token in memory only (DevTools → Storage shows no `refresh_token`/JWT in `localStorage` / `sessionStorage`).
- Wrong access key → error; same wording/shape as "account already exists" (no enumeration).
- Double-click submit → exactly one POST (submit disabled during in-flight).
- Attempt to register after account exists → rejected with the same shape as wrong key.

### Login + refresh + logout (M3 + M4)
- Login success → cookie + access token + redirect to `/` (or `return_to`).
- Login wrong password → error, same shape as unknown email.
- Page refresh while logged in → boot sequence `POST /auth/refresh` → stay signed in, no login flash.
- Two tabs open; logout in tab A; tab B's next API call → silent-refresh attempted → 401 → redirect to `/auth` (no infinite loop).
- Close browser, reopen the next day → refresh cookie still valid (30-day TTL), session restored.
- Logout via cookie only (no Authorization header) → 401 (CSRF guard).

### Rotation + grace (M3)
- Two rapid refresh requests hit the backend in the same second → both succeed (60s grace window).
- Refresh 90s after rotation with the superseded cookie → 401 (grace window expired).
- **Login rotation** (Eng review 2, 2026-04-22): user already holds refresh cookie A (from register or prior login); a second `/auth/login` with valid credentials issues fresh cookie B and marks cookie A's hash `superseded_at`. `POST /auth/refresh` presenting cookie A outside the 60s grace window returns 401.
- Operator password rotation (via `fly ssh console`) → all existing refresh tokens revoked and already-issued access JWTs fail immediately via the server-side token/session version check; every open tab loses API access without waiting for the normal 15-minute JWT expiry.

### Upload path (M7)
- Family-member photo upload → file persists across redeploy (R2-backed).
- Mid-upload: simulate slow network + token expiry → `api.js` silent-refresh retries once; upload completes.
- Mid-upload: user navigates away → no dangling DB row, no orphan R2 object.
- Oversized file (> max size) → 413 returned; no R2 put attempted; no DB row.
- Existing icon URLs / keys (family members, responsibility icons, item icons) continue to resolve after M7 ships for authenticated sessions.
- Unauthenticated media read after M7 → fails closed; stock icons are also not publicly readable in v1.
- **Stock icons via new authenticated route** (Eng review 2, 2026-04-22): `GET /uploads/stock-icons/{brush-teeth,get-dressed,take-bath,make-bed,homework}.png` returns the bundled PNG for authenticated users; unauth returns 401; unknown icon name returns 404; path traversal attempt (`../../etc/passwd` etc.) returns 404 with no disk read. `GET /upload/stock-icons` JSON response points at these new paths rather than the removed StaticFiles mount.
- Browser/media check: pages that use raw `<img src>` tags (member avatar, item icons, recipe images) still load private media successfully for an authenticated session even though the browser does not send an `Authorization` header on the image request.
- Authenticated request for a random / unreferenced media key returns 404, not the raw object.
- **Media reads do not rotate the refresh cookie** (Eng review 3, 2026-04-22): load a page that triggers N authenticated media GETs (e.g. 10 `<img>` tags); assert the `refresh_tokens` row's `token_hash` value is unchanged before and after, and no `superseded_at` rows were created by the media GETs. Rotation must happen only via `/auth/refresh` and `/auth/login`, never via media reads.

### Visual-regression (post-M5)
- Mealboard visual tests still pass under `AUTH_BYPASS_FOR_VISUAL_TESTS=1 APP_ENV=test`.
- Same flags with `APP_ENV=production` reject with 401 (bypass is test-env-only).
- `api-test` healthcheck uses `GET /healthz`, not `GET /`, so the visual-test stack still comes up once unauthenticated root access is removed.

### Deploy + release (M8)
- First real `flyctl deploy` against the runbook → `/healthz` green within expected window (< 5s; no cold-start because `auto_stop_machines = false` on `web`).
- Rollback dry-run → `fly releases rollback` reverts code; verify `/healthz` still green against old image.
- Backup restore dry-run → scratch Fly Postgres restored from the most recent snapshot; basic `SELECT` queries succeed.
- Password-rotation CLI exercised end-to-end → rotation takes effect immediately (all refresh tokens revoked).
- Leave one already-open browser tab alive through the forward deploy and rollback dry-run → old bundle + new backend, and rolled-back frontend + still-new backend, both fail gracefully instead of hard-crashing.
- If the release changes any migration whose own header/runbook says writers must pause, verify the deploy runbook includes the explicit quiesce / restore step instead of plain `fly deploy`.
- Confirm only one beat instance is running after deploy; duplicate periodic schedule execution is a release failure. **Concrete check (Eng review 3):** `fly scale show` reports `web=1, worker=1, beat=1` before closing the release; any `beat > 1` blocks the release.
- **Vercel cache-header verification** (Eng review 3, 2026-04-22): after a deploy, `curl -I https://todo.williamdoucet.dev/` → `Cache-Control` contains `max-age=0` (or equivalent no-cache directive). `curl -I https://todo.williamdoucet.dev/assets/<any-hashed-asset>` → `Cache-Control` contains `max-age=31536000, immutable`. Prevents a cached `index.html` from referencing deleted chunks after deploy.
- **Access-JWT version-check DB lookup** (Eng review 3, 2026-04-22): with two browsers both authenticated, run operator password rotation from browser A; browser B's next API call with its pre-rotation access token fails with 401 **without waiting for the 15-minute JWT expiry window**. The server-side `users.session_version` column enforces this on every protected request.
- After deploy, stale HTML / missing-chunk recovery works: a full reload clears any chunk-load error and restores the app.

## Edge Cases

### Auth flow
- Rate limit: 15 `/auth/login` attempts from the same IP in < 60s → at least one 429 from Cloudflare edge.
- Access-key compare: implementation uses `hmac.compare_digest`; do not rely on CI latency microbenchmarks for constant-time verification.
- Password > 128 chars → 422 at validation; no argon2 CPU burn.
- Concurrent register (two submits in the same millisecond) → exactly one account created (unique constraint); other gets "account already exists".
- `/auth/status` remains public in v1 and returns only `{account_exists: bool}`; it is still covered by the Cloudflare `/auth/*` rate limit.
- Failed login uses one consistent HTTP status for wrong password and unknown email; failed register uses one consistent HTTP status for wrong key and deployment-already-claimed.

### Cookie flow
- Chrome, Safari, Firefox (desktop + mobile) all set + read the `__Host-refresh` cookie across the split-origin XHR. Lax-first verification in M2: if any browser drops Lax on the cross-origin XHR, fall back to None.
- User clears cookies in DevTools → next API call 401s → redirect to `/auth`; no infinite loop.
- Cookie present but refresh token revoked in DB (e.g., logout from another tab) → 401 → redirect.

### Return-to
- `return_to=javascript:alert(1)` → fallback to `/`.
- `return_to=https://attacker.example.com/path` → fallback to `/`.
- `return_to=%2Fmealboard%2Fwed` → decoded and navigated to `/mealboard/wed`.
- No `return_to` → lands on `/`.

### API client (M4)
- All 27 existing `VITE_API_BASE_URL` callers migrated (`grep -rE "localhost:8000|VITE_API_BASE_URL" frontend/src` returns ZERO hits outside `lib/api.js`).
- Central axios client uses `withCredentials: true` for all JSON API requests.
- No direct `axios` imports or ad-hoc `API_BASE` constants remain outside the centralized client and explicitly-approved image/media helpers.
- Local dev (Docker): `VITE_API_BASE_URL` unset → `api.js` defaults work against `http://localhost:8000` with cookie-carrying requests; verify the same-origin local setup still works.

### DB + migrations
- CI `migration-upgrade` job: `alembic upgrade head` from base on a clean container → green. Then `alembic downgrade -1 && alembic upgrade +1` → green. Catches broken migrations BEFORE Fly release_command runs.
- Expand-contract rule: any migration adding NOT NULL to an existing table lands in 3 phases (add nullable + backfill → deploy new code → add constraint).

### Rollback
- Fly deploy abort mid-release (Alembic fails) → previous image keeps serving; verify via `/healthz`.
- `fly releases rollback` → remember this rolls back app code, not the DB schema. Verify the runbook treats forward-fix as the default after a landed migration, and only uses `alembic downgrade` for explicitly tested reversible revisions.
- Roll back frontend first, then backend if still necessary; verify the FE's error handling is graceful during the mixed-version window.
- FastAPI docs / schema endpoints are not exposed in production by accident (`/docs`, `/redoc`, `/openapi.json` fail closed).

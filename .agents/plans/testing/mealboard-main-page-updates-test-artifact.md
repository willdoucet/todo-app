## Eng Review #3 additions (rollout-safety scenarios)

These scenarios exercise the rollout-safety fixes from Eng Review #3. QA should run them against staging or a production-snapshot clone before the production cutover.

- **Rev 1 API maintenance window:** confirm the API container is stopped during `alembic upgrade <rev1>`, write attempts during the window receive connection-refused, and no rows leak into `meal_entries` with NULL `item_id`.
- **Rev 3 code-first deploy ordering:** with `DUAL_WRITE_ENABLED=False` deployed but old tables still present, exercise create/update/delete on `/items` and confirm every write succeeds and lands ONLY in the `items` table.
- **Rev 3 stale-client soak:** keep a cached pre-refresh Mealboard tab open through the Rev 3 soak, exercise a legacy item request, and confirm it gets the refresh-required `410` response with no partial write side effect.
- **Rev 3 dry-run script:** run `.claude/scripts/rev3-rollout-check.sh` against staging, verify a green pass, then introduce a deliberate misconfiguration (`DUAL_WRITE_ENABLED=True` left on) and verify the script fails with non-zero exit.
- **Hourly hard-delete cleanup:** soft-delete a recipe-backed item that has 3 planned meals, fast-forward soft-delete clock past 24h, run `hard_delete_expired_soft_deletes` and confirm both the item AND the soft-hidden meal_entries are gone in a single transaction.
- **Hard-delete assertion gate:** stage a state where an active (non-soft-hidden) meal_entry still references an expired item, run the cleanup task, verify it raises `RuntimeError` instead of silently skipping, and confirm Celery error handling surfaces it as an alert.
- **Hard-delete partial failure rollback:** inject a DB error during step 2c of the cleanup transaction, verify both the items and the soft-hidden meal_entries roll back together (no partial cleanup).
- **Undo name collision:** soft-delete "Chicken Soup" recipe, create a new "Chicken Soup" recipe within the undo window, click Undo on the original delete toast → expect a 409 with `name_collision` body and a frontend toast offering "Restore as 'Chicken Soup (restored)'?". Click the rename button and verify two distinct active items exist.
- **Lossy downgrade with NULL instructions:** create a recipe-backed item post-refactor with empty instructions, simulate Rev 3 break-glass downgrade, confirm the COALESCE empty string lets the row land in the recreated `recipes` table without a NOT NULL violation.
- **Soft-hidden visibility through ORM relationship:** verify that querying through `visible_meal_entries_stmt()` excludes soft-hidden rows even when an `Item` is fetched with `selectinload(Item.meal_entries)` from a different code path. This protects against accidental UI leakage of soft-hidden data.

## Affected Pages/Routes
- `/mealboard/planner` - Canonical Item-backed meal planner flow, edit-from-drawer, Jump to Today placement, day/date animation, food-item meal-card layout, delete/undo lifecycle.
- `/mealboard/recipes` - Unified item list/detail flow for recipe-type items, delete entry points, icon rendering, emoji search.
- `/lists` - Redirect destination for the removed Mealboard shopping subpage and shopping-card handoff target.
- `/mealboard/shopping` - Legacy route should no longer appear in Mealboard navigation and should redirect to `/lists`.
- `GET/POST/PATCH/DELETE /items` - Canonical item CRUD, including type filtering and soft-delete contract.
- `POST /items/{id}/undo` - Undo path must require the delete response token and fail clearly on stale/invalid attempts.
- `POST /uploads/item-icon` - Item icon upload path with PNG/JPEG/WebP-only policy.
- `POST /items/suggest-icon` - AI/cached emoji suggestion path with graceful degraded behavior.

## Key Interactions To Verify
- Open a recipe-backed meal from `/mealboard/planner`, click Edit from the detail drawer, and confirm the canonical item form opens populated with no blank-state flash during close/open transition.
- Enter `0.25` in a recipe ingredient quantity field and save without HTML step validation blocking the submission.
- Visit `/mealboard/shopping` directly and confirm the app redirects to `/lists` instead of rendering a dead Mealboard page or generic 404.
- Delete an item that is referenced by planned meals, confirm usage-aware copy appears, linked meal entries hide immediately, and the merged undo toast appears with a valid countdown.
- Click Undo within the valid window and confirm the same item and linked meal entries restore cleanly.
- Click Undo while offline and confirm the toast stays visible in a pending-retry state, reconnect triggers exactly one retry, and a failed reconnect exposes an explicit `Retry` action instead of silently giving up.
- Attempt Undo after expiry or with a stale token and confirm the UI shows an explicit "Undo window expired" style failure, not a silent no-op.
- Create or edit a food-item-type item with emoji mode, then switch to icon mode and confirm the emoji clears; repeat in reverse and confirm the icon URL/upload clears.
- Upload a valid PNG/JPEG/WebP icon and confirm it renders on cards and rows through the shared `ItemIcon` path.
- Search the emoji picker and confirm the result list filters live while the clear affordance remains adjacent to the search UI.
- Confirm food-item cards on the Food Items tab open edit on click and no longer rely on hover-only edit/delete affordances.

## Edge Cases
- Legacy Mealboard tabs during the Rev 2 soak should hit `410` refresh-required tombstones on old item endpoints, not generic 404/500 responses.
- Duplicate Undo clicks should resolve idempotently and never double-restore or error after a successful first restore.
- Duplicate offline Undo clicks should collapse onto a single queued retry, not fire parallel restore requests.
- `MEALBOARD_SOFT_DELETE_ENABLED=false` should hide or disable delete UI and the delete API should fail closed with `503`, never hard-delete.
- Invalid `undo_token`, mismatched token, or expired token should all produce the same clear failure path and leave the item deleted.
- SVG upload should be rejected explicitly; oversize or MIME-mismatched uploads should fail with clear client-visible errors.
- AI suggest `204` should quietly hide the suggestion affordance; AI suggest `503` should leave manual emoji/icon selection fully usable.
- Shopping sync after soft-delete, undo, and hourly hard-delete should not resurrect deleted item contributions or mutate checked/purchased tasks.

## Critical Paths
- Rev 1 additive rollout: old frontend + new backend with dual-write enabled, drift audit green, no user-visible regressions.
- Rev 2 switch rollout: new frontend + new backend on canonical `/items`, stale clients get refresh-required behavior, rollback remains code-first and safe.
- Rev 3 contract rollout: during the soak, stale clients still get refresh-required behavior from legacy tombstones; planner/recipes/delete/undo/upload flows still work; break-glass restore runbook remains available.
- End-to-end item lifecycle: create item -> edit item -> add to meal -> delete item -> undo within window -> allow server expiry -> verify hard-delete cleanup.
- End-to-end undo failure path: create item -> delete item -> click Undo while offline -> reconnect -> verify single retry restore or explicit Retry/expiry messaging.
- Planner + shopping coupling: add recipe and food-item meals, confirm shopping aggregation works, then soft-delete and undo without stale `source_meals` references.

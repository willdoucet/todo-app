## Edge cases
- `note` containing `=` (`--field note="closed in §3 = item 2"`) → stored whole (split on the
  first `=` only).
- Two `resolved` entries for the same review → the second is rejected ("already resolved").
- Resolution, then the original review re-runs and logs `issues_open` again → `--next` names it
  again with the failed reason; a second resolution by a review that ran after the **new**
  failure is accepted; the earlier resolver's entry (now older than the new failure) is not.
- Resolver named a review whose latest entry is itself `resolved` → rejected.
- A plan-stage failure while `ui_scope` is set and design is missing → `Next:
  /plan-design-review — required (ui_scope is set)` with the failure as an `Open:` line, never
  hidden.
- `--status resolved` on a branch with no plan and no `--plan` → the existing "no plan" error
  path; nothing appended.
- Log file absent → every reader behaves as today (empty); `review-log` creates it.
- An entry with a summary-named plan **and** no matching real plan file → attaches to the
  derived name; nothing crashes; the dashboard for that branch simply shows the row.
- Twelve pre-migration entries carry no `plan` at all → stay invisible (out of scope; the
  plan's §6c covers only summary names).
- `merge=union`: two branches each append one line from the same base → the merge keeps both
  with no conflict; `reviews_for_plan` orders by `ts`, not line position. Before the attribute
  exists on the receiving branch (M8's first merge, plan §12.2) → a conflict at the end of the
  file is resolved by keeping both sides, and `review-log` refuses to append until the
  markers are gone.
- Old 1.0.0 readers (a rollback of PR-T) on a log with `resolved` entries → they read as
  not-ok: a resolved CEO row shows `!` (harmless, the old behavior), a resolved gating tier
  blocks until re-run. Named in the plan's Failure modes; no silent pass.
- `office-hours` `issues_open` is the only entry on a fresh plan → `Next: /plan-eng-review —
  required (shipping gate)`, no `Open:` line.
- `--status resolved --field status=clean` (merged-entry smuggle) → rejected; log unchanged.
  <!-- plan-adversarial-review · harness: grok · model: grok-4.6 · 20260915-205728 -->
- `--field note=true` / `--field resolved_by=1` → rejected (must be non-empty strings after
  `parse_scalar`).
- A log file whose last byte is a newline after a valid object → `unreadable=0` (`splitlines`,
  not `split("\n")`).
- A blank line between two valid objects → skipped, not unreadable, line numbers still count it.
- CEO `issues_open` + eng `clean` (eng `ts` >= CEO `ts`) → `--next` reason contains

## Operational invariants
- `state/review-log.jsonl` only ever grows; `git diff` on it shows added lines only, on every
  branch, forever. No line is rewritten, reordered, or deleted by any helper or the upgrade.
- Every entry the CLI writes after 1.1.0 has a `status` in the four-word set; every `resolved`
  entry has `resolved_by`, `note`, and `resolves_ts`.
- For any plan, `workflow-state --next`, `--dashboard`, and the banner agree on which reviews are
  open (one `gate_state` computes all three, Eng review 2.1).
- The dashboard verdict is `CLEARED FOR IMPLEMENTATION` only when no plan-stage review is
  `failed`, and `CLEARED TO SHIP` only when no review of any gating tier is `failed`.
- `/ship` still refuses anything but `CLEARED TO SHIP`; `/execute-plan` refuses unless
  `--next --json` has `unreadable==0` and `next.skill` is exactly `/execute-plan`.
- The four review-gate helpers upgrade all-or-nothing; a mixed local-mod set is refused.
- The framework `tests/test_skill_lint.py` passes on every shipped payload; a skill cannot
  reintroduce `issues_found`, `fixed`, `pass`, or a bare `critical_gaps` field.

## Log hygiene
- `review-log` rejections print one JSON error object on stdout (the existing `run_main`
  envelope) naming the rule that failed and, for a vocabulary error, the four valid words.
- `workflow-state`'s `Warn:` line for unreadable log lines names the count and the file, never
  the line content (a conflict hunk may contain anything).
- Nothing new is logged anywhere else; the helpers write no files but the JSONL.
- No secret, token, or credential exists in this surface.

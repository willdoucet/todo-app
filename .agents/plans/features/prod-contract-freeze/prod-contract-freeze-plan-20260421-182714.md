# Design: todo-app v1 productionization — execution spec

Generated by /office-hours on 2026-04-21
Branch: prod-contract-freeze
Status: APPROVED (2026-04-21, pending formal review pipeline)
Mode: Startup (pure engineering/infra)

## Problem Statement

Take the `todo-app` repo from its current local-only dev state to a secure v1 production deployment. Architecture decisions are locked (Vercel frontend, Fly.io backend, Fly managed Postgres, Upstash Redis, Cloudflare R2, first-party email+password auth with JWT access + HttpOnly refresh cookie, single-tenant per household, gated first-account creation).

The question this doc answers is **execution sequencing**, not architecture:

- In what order do the milestones ship so that infra unknowns are discovered before committing to auth code?
- How are the milestone branches merged without parking `master` in a broken intermediate state?
- What is actually required for v1 vs deferred to v1.1?

## Demand Evidence

This is a single-family deployment — the operator is also the only customer — so classic demand-signal questions (paying users, churn, waitlists) do not apply. Evidence the work is worth doing:

- The app already ships meaningful product functionality (mealboard, responsibilities, calendar, lists). 24+ PRs merged in 2026 alone have extended it on top of a stack that has never been production-deployed.
- Current reach constraint: "works only on the laptop where `docker-compose up` is running." Productionization unlocks actual household use on mobile + desktop browsers across home network boundaries.
- The user has already invested in seed-brief, gap-checklist, implementation-plan, CI/CD-spec, and branch-strategy documents for this migration. Commitment signal is high.

## Status Quo

Current repo state as of branch cutoff:

- App stack runs via `backend/docker-compose.yml`: Postgres 5433, Redis 6379, FastAPI 8000, Vite 5173, Celery worker + beat
- **No auth.** `frontend/src/App.jsx` routes are all unprotected. No login UI.
- **Dev-only CORS.** `backend/app/main.py:144-154` allows `localhost:5173` and `localhost:3000` only.
- **Local filesystem uploads.** `backend/app/main.py:166` mounts `/uploads` as `StaticFiles(directory=UPLOAD_DIR)`; uploads die on container restart.
- **Localhost baked into frontend.** Many components do `import.meta.env.VITE_API_BASE_URL || 'http://localhost:8000'`.
- **Test-only CI exists.** `.github/workflows/test.yml` runs `backend-tests`, `frontend-tests`, `visual-tests`; already uses `CI_FERNET_KEY` repo secret.
- **No deploy infra.** No `fly.toml`, no `vercel.json`, no `.github/workflows/deploy.yml`, no `/healthz` endpoint.
- **Base branch is `master`** (one of the supporting docs refers to `main`; this conflict is resolved in M1).

Cost of staying here: the app is usable only by someone physically sitting at the operator's laptop.

## Target User & Narrowest Wedge

**Target user:** one household (the operator's). One shared login per deployment. Separate households get separate deployments — code is single-tenant by design.

**Narrowest correct v1 (revised after premise challenge):** 8 milestones, not 9. A shippable first production release does not require automated `deploy.yml` or Vercel PR previews; those can land in v1.1 once the manual release procedure has been exercised 2-3 times.

**Explicitly NOT v1:**

- Automated `.github/workflows/deploy.yml` (manual runbook instead)
- Vercel PR preview deployments (previews can't carry the refresh cookie across `*.vercel.app`)
- `visual-tests` as a required check on `master` (stays informational per current workflow)
- Multi-household, multi-user-per-household, invite flows, public signup
- Magic-link login, self-service password reset, OAuth/social login
- Native apps, PWA install, full staging environment, advanced observability (Sentry, structured JSON logging, app-layer rate limiting beyond the M2 Cloudflare edge rule)

## Constraints

Locked architectural decisions (do not reopen unless the repo reveals a hard technical blocker):

- **Hosting.** Vercel for frontend SPA; Fly.io for backend with one app, three process groups (`web`, `worker`, `beat`).
- **Data.** Fly managed Postgres, Upstash Redis (Celery broker/result only), Cloudflare R2 provisioned day one (exercised by app code starting in M7).
- **Tenancy.** Single household per deployment; separate deployments for other families.
- **Auth.** Custom first-party, email + password, JWT access token (15-min TTL, in-memory on frontend), HttpOnly refresh cookie (30-day TTL, `__Host-refresh`, `Secure`, `Path=/`, **no `Domain` attribute**, host-only on `api.todo.williamdoucet.dev`, rotated on login and refresh).
- **Bootstrap.** First account creation via the public create-account API, gated by `HOUSEHOLD_ACCESS_KEY` secret. Rejected once a shared login exists.
- **Domains.** `todo.williamdoucet.dev` → Vercel, `api.todo.williamdoucet.dev` → Fly. Note: the scheme is `<project>.<root>` rather than `app.<root>` because `williamdoucet.dev` is a developer portfolio hosting multiple projects. Each project (this one, future ones) gets its own subdomain namespace; within that, `api.<project>.<root>` is the backend origin.
- **Recovery.** No self-service password reset in v1. Operator CLI rotates the shared password.
- **Client.** Responsive web only. No PWA, no native.
- **Branch protection.** `master` is protected. PRs require status checks. Production deploy is approval-gated.
- **Portfolio context.** Root domain `williamdoucet.dev` also hosts the operator's developer portfolio. A second deployment of this app (demo instance with seed data for potential employers, lives at `demo.todo.williamdoucet.dev` / `api.demo.todo.williamdoucet.dev`) is deferred to v1.1+. The single-tenant-per-instance architecture supports this cleanly — two deployments, same codebase, separate Fly app + DB + Redis + R2 bucket + Vercel project.

## Premises

These were pressure-tested during the session. All stated here represent **accepted** positions after challenge.

1. **Deploy skeleton at M2, before building auth.** Split-origin cookies (`todo.williamdoucet.dev` talking to `api.todo.williamdoucet.dev` while the API issues a host-only `__Host-refresh` cookie), Fly migrations-on-release, Upstash connectivity from Fly, Vercel SPA rewrites, CORS with credentials — these fail in ways that cannot be validated locally. Deploying a healthz + skeleton stack with all real infra wired (Fly + Upstash + R2 + Postgres provisioned, DNS live, edge basic-auth gate protecting prod) surfaces those gotchas before committing to auth code that depends on them. Discovering a cookie-shape or origin-policy issue after 5 milestones of auth work would force rewrites across M3-M5.
2. **Hide `Create new account` on the unified auth portal once an account exists.** On portal mount, GET `/auth/status` and render the Create button only if `account_exists: false`. Backend still rejects defensively (10-line frontend override; zero backend change). Original spec's "leave it visible, let backend reject" ships a UI element that always errors — worse UX, no security gain.
3. **Vercel PR previews deferred to v1.1.** Preview URLs run on `*.vercel.app`, which cannot receive a cookie scoped to `api.todo.williamdoucet.dev` (cross-site). Previews would degrade to unauthenticated CSS smoke-checks only. Use local QA against `docker-compose` for PR review in v1. Revisit once the production domain flow is stable.
4. **Automated `deploy.yml` deferred to v1.1.** The spec's "production rollout remains manually controlled" requirement is satisfied by a documented manual runbook (`flyctl deploy`, verify `/healthz`, Vercel promote, smoke checklist). Running the runbook 2-3 times by hand before codifying it into YAML surfaces real procedure gaps that a GitHub Actions workflow would otherwise hide. Approval-gated deploy workflow lands in v1.1 as the first item.
5. **Incremental direct-to-master merge strategy.** Each milestone branch PRs directly to `master`. The edge basic-auth gate (established in M2, removed in M5) keeps production protected through the auth build-out. Combined with the production-deploy approval gate, this prevents a half-implemented auth state on `master` from reaching real users, without requiring a long-lived integration branch.

## Approaches Considered

**Approach A: Incremental direct-to-master (RECOMMENDED).** Each of 8 milestones PRs to `master`. Operator releases manually after each merge. Edge basic-auth gate from M2 protects prod until M5 cuts over to first-party auth. Matches the `Production Branch Strategy.md` doc.

- Effort: baseline (no new plumbing)
- Risk: Low-Med
- Pros: fast per-milestone feedback; solo-dev friendly; smallest deviation from stated branch strategy; approval gate + edge gate together defuse the "half-auth on master" concern
- Cons: master carries intermediate states during auth work (mitigated by the edge gate and the discipline not to deploy between M3-M5)
- Reuses: existing `Production Branch Strategy.md`, existing `.github/workflows/test.yml`, existing Docker-based dev workflow

**Approach B: Integration branch `prod-v1`.** All 8 milestone branches PR into `prod-v1`. When complete, FF-merge `prod-v1` → `master` for one atomic cutover.

- Effort: +1 long-lived branch + rebase overhead across 8 milestones
- Risk: Low on `master`; Med on merge coordination
- Pros: `master` stays pristine; one atomic v1 cutover
- Cons: delays real-production feedback until M8, which directly contradicts the skeleton-at-M2 premise; heavy rebase burden for a solo dev
- Rejected because: batching to master defeats the whole point of the skeleton milestone's infra de-risking.

**Approach C: Hybrid — skeleton + remainder incremental, auth bundled.** M1+M2 ship to master. M3-M5 collect in `prod-auth-v1` and merge atomically. M6-M8 ship incrementally.

- Effort: +1 bounded integration branch
- Risk: Low
- Pros: avoids intermediate half-auth on master without a full integration-branch burden
- Cons: slight deviation from the branch-strategy rule "one milestone per branch"; auth PR to master reviews ~3 milestones of code at once (mitigated by prior reviews of sub-milestones); edge basic-auth gate from M2 already makes this unnecessary
- Rejected because: adds coordination cost without additional safety beyond what the edge gate + approval gate already provide.

**M3. `prod-auth-backend-foundation`**

- Scope: backend auth foundation. Auth model + Alembic migration (backward-compatible: old image code must not break if the migration has run); password hashing (argon2 recommended); `POST /auth/login`; `POST /auth/refresh`; `POST /auth/logout`; `POST /auth/register` (gated by `HOUSEHOLD_ACCESS_KEY` + "no existing account" check); `GET /auth/status` (returns `{account_exists: bool}`, used by M4 for the P2 hide-button behavior); refresh-token persistence with revocation on logout/rotation; backend auth dependency/middleware helpers (not yet applied to existing routes).
- **Password rotation CLI is NOT in M3** — only the hashing primitive and the model support. The rotation CLI ships in M8, where operator recovery procedures live.
- **Security-sensitive implementation notes locked by CEO + Eng review** (not left to implementer discretion):
  - **JWT library + algorithm** (Eng review 2A): use `PyJWT >= 2.8` (`import jwt`) with `HS256` algorithm. Single-backend deployment means symmetric-key is correct. Secret is a 32-byte random value in `JWT_SECRET_KEY` Fly secret. Do NOT use `python-jose` (historically had `alg=none` CVEs). Access token TTL 15 min, refresh token TTL 30 days (matches plan constraints, line 68).
  - **Refresh token stored as SHA-256 hash, not plaintext** (Eng review 1A): the DB column stores `sha256(token_bytes)` — the plaintext token lives only in the HttpOnly cookie. On refresh, hash the incoming token and look it up; on rotation, write the new token's hash + mark old row `superseded_at = now()`. A DB compromise yields only hashes (useless for session hijacking). Standard practice.
  - **Password hashing parameters** (Eng review fold-in): `argon2-cffi` library with `argon2.PasswordHasher()` defaults (argon2id, memory_cost=65536 ≈ 64 MiB, time_cost=3, parallelism=4). OWASP 2024-recommended minimums. Do not roll custom params.
  - **Constant-time access-key compare** (CEO review 3A): use `hmac.compare_digest(submitted_key, HOUSEHOLD_ACCESS_KEY)`, never `==`. Prevents per-character timing side-channel on the register endpoint.
  - **Unique-constraint account race guard** (CEO review 2A): the "no existing account" check is enforced by a `UNIQUE` constraint on `users.email` (or a `users_singleton` table with a single-row constraint if the design is truly one-account-total). The register handler catches `IntegrityError` and returns the same "account already exists" error the SELECT-check would. No SELECT-then-INSERT window.
  - **60s refresh-token rotation grace window** (CEO review 6A): on refresh, the old token is marked `superseded_at = now()` but remains valid for 60 seconds. Any arrival within the grace window is accepted without re-rotating. After 60s, the superseded token rejects as revoked. Handles parallel in-flight refresh requests (multiple components mounting in parallel) without kicking the user to login.
  - **Password max length cap** (CEO review): reject passwords > 128 characters at validation time (Pydantic Field constraint). Argon2 has no built-in cap; hashing 100MB of input pins the VM. 128 chars is standard.
  - **CSRF on `/auth/logout`** (CEO review): logout requires the access token in `Authorization: Bearer ...` header, not just the refresh cookie. A cross-origin POST can carry the SameSite cookie but cannot read the in-memory access token → CSRF forgery fails.
  - **Refresh-token table index**: `CREATE INDEX ON refresh_tokens (user_id, token_hash)` in the same migration that creates the table.
  - **Expand-contract migration pattern** (CEO review, codifying the existing "backward-compatible" rule): any migration adding a NOT NULL column ships in three phases — (A) add nullable + backfill default, (B) deploy code that writes to it, (C) migration to add NOT NULL constraint. Never ship (A)+(C) as a single migration. Documented here to set the discipline for M3 and all later backend milestones.
  - **Public register/status behavior locked** (adversarial review): once the deployment is claimed, `/auth/register` returns the same generic public error shape for "wrong access key" and "account already exists". The portal still hides Create Account via `/auth/status`, but the register API itself must not become an account-existence oracle. `/auth/status` remains intentionally public in v1 because the portal needs it; keep its response body minimal (`{account_exists: bool}` only) and let the M2 Cloudflare `/auth/*` rule throttle abuse.
  - **Failed-auth status codes locked** (adversarial review 2): "same error shape" includes HTTP status, not just JSON. `POST /auth/login` failure returns one consistent status for wrong password vs unknown email. `POST /auth/register` failure returns one consistent status for wrong access key vs deployment already claimed. Do not vary status codes across those paired failure cases.
  - **Immediate post-rotation access revocation** (adversarial review 2): operator password rotation must invalidate already-issued access tokens immediately, not only refresh tokens. Implement with a server-side session/token-version check that protected routes enforce on every request; do not rely on the 15-minute JWT expiry window for break-glass recovery.
  - **Session-version storage shape locked to DB** (Eng review 3): the session/token version lives as a column on the single shared-household row (`users.session_version` integer, default `0`, NOT NULL). The auth dependency reads it via primary-key lookup on every protected request and compares against the version embedded in the JWT payload at issue time; mismatch → 401. Household-scale traffic (tens of requests/min peak) makes this a one-index-hit-per-request cost with no measurable latency impact. **Do NOT introduce a Redis cache tier for this in v1** — the complexity (invalidation on rotation, cache stampedes, staleness window) is unjustified at this scale. Revisit only if authenticated request p95 latency becomes user-visible.
- **Pytest coverage (explicit, per CEO review 7A):**
  - register success → shared-login row + refresh cookie set + access token returned
  - register rejected: invalid access key (constant-time requirement enforced by code-path verification that the handler uses `hmac.compare_digest`; do NOT gate CI on latency microbenchmarks)
  - register rejected: account already exists (HTTP status + JSON body match "wrong key" case exactly — no enumeration)
  - register race: 2 concurrent requests → exactly one succeeds; loser's HTTP status + JSON body are byte-identical to the wrong-access-key response
  - register rejected: password > 128 chars returns 422
  - login success + wrong password + unknown email (same HTTP status + body for latter two, prevent enumeration)
  - refresh success with fresh cookie; refresh success at T+30s with rotated-but-graced cookie; refresh rejected at T+90s with same cookie

  - auth dependency rejects missing token, expired token, malformed JWT, wrong signing key
  - password rotation invalidates access JWTs immediately via the server-side token/session version check; a request authenticated with a pre-rotation access token is rejected without waiting for normal JWT expiry
  - `/auth/status` returns `account_exists: false` on fresh DB, `true` after register

# Design: Mealboard hover-jitter fix — stabilize inner scrollbar gutter

Generated by /office-hours on 2026-04-20
Branch: mealboard-todos-042026
Status: DRAFT
Mode: Builder

## Problem Statement

On the Meal Planner page, hovering a food-item meal card (reproducible on "Blueberry Pancakes" in the current week) causes two visible regressions:

1. The card's title reflows from one line to two — "Blueberry Pancakes" splits onto "Blueberry" / "Pancakes".
2. The entire dashboard shifts horizontally on hover — the day/date row above the swimlanes and the swimlane grid itself visibly jump to the left by ~15px, then snap back on mouse-exit.

Expected behavior (verbatim from the task spec):

> "the only thing the user should see when hovering over a food item card is the bottom of the card expanding downwards, the buttons appearing in the newly created space, and the swim lane expanding to fit the new card size. nothing else on the dashboard should move."

The bug was not present in the design intent of `mealboard-meal-card-polish-plan-20260418-183015.md` (where the hover-expand animation was specified) — it is a layout-ambient regression that the polish plan did not anticipate.

## What Makes This A Clean Fix

Single root cause, two observable symptoms, and a small CSS-only fix localized to one scroll container. The only non-happy-path wrinkle is browser support: `scrollbar-gutter` needs a fallback if we want to preserve the project's documented Safari support range.

## Constraints

- CSS-only. Must not touch the hover-expand animation in `MealCard.jsx` — that design is explicitly wanted.
- Must not regress any other page's scroll behavior.
- Must verify in a real desktop browser against the visual invariants below. Use Playwright or browser automation if available, but do NOT couple the plan to a specific MCP server or tool name. This plan still does NOT stand up automated visual-regression infrastructure (that work is tracked separately as the P3 TODO in `.claude/TODOS.md` and is explicitly out of scope here).
- Must preserve the project's documented browser matrix from `.claude/TECH_STACK.md` (Chrome/Firefox/Edge 90+, Safari 14+). Because `scrollbar-gutter` does not cover that entire Safari range, the implementation must include a desktop fallback that keeps the mealboard container width stable when the property is ignored.
- **Desktop-only fix.** The mealboard has a compact-mode branch at `MealPlannerView.jsx:437-449` that renders `MobileDayView` instead of `SwimlaneGrid` below the `md` breakpoint. Touch/compact users don't see this bug (no hover state) and the fix is a no-op for them (`scrollbar-gutter: stable` is harmless when no scrollbar appears). Explicitly in-scope for desktop `SwimlaneGrid` only.

## Premises

All confirmed interactively before drafting:

1. **Root cause:** The mealboard's inner scroll container at `frontend/src/components/mealboard/MealPlannerView.jsx:430` (`<div className="flex-1 overflow-y-auto px-4 sm:px-6 lg:px-8 py-4">`) wraps both the `SwimlaneGrid` day/date header row AND the swimlane grid itself. When a card's hover-expand transition makes the swimlane tall enough to overflow the container's height, the browser renders a vertical scrollbar on that div. On desktop environments with **classic (gutter-consuming) scrollbars** — Windows Chrome/Firefox/Edge, many Linux DEs (X11 + GNOME pre-42, classic KDE), and macOS with "Show scroll bars: Always" — the scrollbar is 15–17px wide and reduces the container's content-width by that amount. Modern Wayland + GNOME 42+ and macOS defaults use overlay scrollbars and are not affected (see Premise 2).
2. **Reproduction environment implies classic scrollbars.** The user's observed symptoms (horizontal shift + text reflow) are only physically possible when the scrollbar consumes width. On macOS with default "Automatically based on mouse or trackpad" (overlay scrollbars), the scrollbar floats over content and the bug does NOT reproduce. Since the user reports seeing the bug, their environment is either (a) macOS with Always-show enabled, or (b) Windows/Linux. `scrollbar-gutter: stable` is the correct fix in any of those; it is a no-op under overlay scrollbars, which is also correct (no bug to fix there).
3. **Downstream symptom chain:** Container loses ~15px on the right (scrollbar appears) → the inner `<div role="grid">` tree shrinks to fit the new content-box → the header row `grid-cols-[80px_repeat(7,1fr)]` redistributes the shrunken width (1fr columns absorb all 15px loss; the 80px rail is fixed) → each day column is narrower by ~15/7 ≈ 2px. Two composable visual effects result:
   - **Title wrap:** The food-item card's body narrows by ~2px. The `line-clamp-2` on the name (`MealCard.jsx:208`) uses `-webkit-line-clamp` + `-webkit-box` which re-measures on box-size change — "Blueberry Pancakes" goes from fitting on one line to not, and wraps.
   - **Perceived ~15px dashboard shift:** The user's "15px shift" describes the right edge of the header row / swimlane grid retreating inward by ~15px on hover; content-centered elements (day labels, swimlane cells) also visually move because `text-center` recenters in the narrower columns. Taken together with the simultaneous card-expand animation, the overall motion reads as a jarring whole-page shift. The column-by-column shift is ~2px each; the right-edge shift is ~15px; those are the same event described at different scales.
4. **Hover-expand is fine.** The max-h / opacity / padding-bottom transitions on the `actionZoneClass` shared between recipe and food-item variants (`MealCard.jsx:182-190`) work as designed. The ambient page is what's fragile.
5. **Fixing the width-change eliminates both symptoms simultaneously.** No separate change to `line-clamp` is required — once column width stops oscillating on hover, "Blueberry Pancakes" stays on one line naturally.
6. **No backend changes; purely frontend CSS.**

Fix (Approach A) breaks the chain at the "content-width shrinks" step by reserving the gutter whether or not the scrollbar is rendered.

## Approaches Considered

### Approach A: stabilize the inner scroll container width with `scrollbar-gutter` plus desktop fallback (RECOMMENDED)

Use a small named utility on the `MealPlannerView.jsx:430` inner scroll container and define its behavior in `frontend/src/index.css`:

```css
@layer utilities {
  .mealboard-scroll-stable {
    overflow-y: auto;
    scrollbar-gutter: stable;
  }

  @supports not (scrollbar-gutter: stable) {
    @media (min-width: 768px) {
      .mealboard-scroll-stable {
        overflow-y: scroll;
      }
    }
  }
}
```

```jsx
<div className="mealboard-scroll-stable flex-1 px-4 sm:px-6 lg:px-8 py-4">
```

On browsers that support `scrollbar-gutter`, this reserves the gutter whether or not the scrollbar is currently rendering. On supported-but-older browsers that ignore the property (notably older Safari), the desktop fallback forces a permanent vertical scrollbar on this container so the width is still constant across hover-expand / hover-exit.

- **Effort:** human ~30 min (change + real-browser verification) / CC ~10 min
- **Risk:** Low
- **Pros:**
  - Targets the exact element that owns the offending overflow context.
  - Preserves the hover-expand animation and the "swimlane gracefully grows to fit" behavior.
  - Still a tiny diff: one class token in `MealPlannerView.jsx` plus one localized utility in `index.css`.
  - Idiomatic modern CSS — not a hack.
  - Preserves the browser matrix instead of silently regressing Safari support.
  - Fix applies equally under `prefers-reduced-motion: reduce` — those users get an instantaneous snap on hover-expand (no transition smoothing), which is the *worst* case for perceiving this jitter. They benefit most from the fix.
- **Cons:**
  - On short weeks / small families where content fits without scrolling, the reserved width still leaves a thin empty stripe on the right. Aesthetically minor; the surrounding `px-4 sm:px-6 lg:px-8` padding already provides visual breathing room.
  - On already-overflowing weeks (scrollbar present at rest), the fix is a no-op — scrollbar was already consuming width. That's fine: the bug also doesn't manifest in that case (no hover-triggered appearance).
  - On macOS with overlay scrollbars enabled (default trackpad setting), the `scrollbar-gutter` half is effectively a no-op. Also fine — the bug doesn't reproduce there either.
- **Tailwind v4 note:** Put the custom utility inside `@layer utilities` in `frontend/src/index.css`. Per `LESSONS.md`, unlayered custom CSS can be stripped by Tailwind v4's tree-shaker.
- **Reuses:** Existing container element and the project's global `index.css` utility layer — no new component, no new dependency, no global layout change.

### Approach B: `scrollbar-gutter: stable` globally on `html`

Apply the property in `frontend/src/index.css` under `@layer base { html { scrollbar-gutter: stable; } }`.

- **Effort:** human ~15 min / CC ~5 min
- **Risk:** Low
- **Pros:** Prevents the same bug class on any future page that introduces a scrollable container that crosses the viewport-height threshold mid-interaction.
- **Cons:** Does not fix THIS bug. The mealboard's `overflow-y-auto` container is nested; its scrollbar appears on the inner div, not on `html`. A global `html` rule would be orthogonal. If we want the belt-and-suspenders version, we'd combine with Approach A — but the global change alone does not solve the reported symptom.
- **Reuses:** index.css base layer.

### Approach C: Absolute-overlay hover action zone (refactor `MealCard.jsx`)

Change the hover action zone from `max-h` expansion to `position: absolute` overlay. Card stays one fixed height; overlay floats beneath on hover.

- **Effort:** human ~2 hours / CC ~30 min
- **Risk:** Medium
- **Pros:**
  - Impossible to regress this specific bug class — card height never changes, so the container never overflows on hover.
- **Cons:**
  - Breaks the "swimlane expands gracefully to fit the new card size" behavior the user explicitly keeps in the spec ("the swim lane expanding to fit the new card size").
  - On the last visible swimlane row, the overlay may clip below the scroll container.
  - Changes DOM focus flow (action buttons are no longer in document order under the card).
  - Larger diff, more surface area to review.
- **Reuses:** Nothing — this is a structural change to the hover pattern.

## Recommended Approach

**Approach A** — stabilize the inner mealboard scroll container with a small named utility: `scrollbar-gutter: stable` where supported, plus a desktop fallback for browsers that ignore that property.

Rationale:
- Smallest possible diff for a root-cause fix.
- Preserves the hover-expand design the user likes.
- Targets the exact element that owns the scroll context; no side effects on other pages.
- Preserves the documented browser matrix instead of quietly making this polish fix "desktop Chrome/Firefox only."
- Approach B doesn't actually fix the bug on its own; Approach C overbuilds for a CSS ambient-layout issue.

## Open Questions

1. **Should we also apply `scrollbar-gutter: stable` globally (Approach B) as a preventive measure?** Recommended posture: no for this plan — keep the fix surgical. If a similar bug appears on another page, address it there. Avoids an ambient change that might subtly alter pages that currently have no scrollbar at all.
2. **Should we also constrain `line-clamp-2` → `line-clamp-1` on the food-item title (`MealCard.jsx:208`)?** Recommended: no. Once the width stops oscillating, the title stays on one line for names that fit; longer food-item names (e.g., "Sweet Potato Hash Browns") still benefit from graceful 2-line wrap. Keeping `line-clamp-2` is the correct default — the bug was never about line-clamp semantics.
3. **Visual regression coverage.** This bug is exactly the class `.claude/TODOS.md` calls out as motivating the P3 "Visual Regression Test Infrastructure for Mealboard" item — class-assertion tests would not catch a ~15px horizontal reflow on hover. Out of scope for this plan but worth noting that a Playwright visual diff on the SwimlaneGrid in hover vs. rest state would have caught this.
4. **Cosmetic: spinner overlay recenters.** The loading spinner overlay at `MealPlannerView.jsx:467` uses `absolute inset-0` centered inside the `relative` wrapper (line 436). That wrapper is inside the scroll container whose content-box narrows by ~15px with the gutter reserved. Consequence: the spinner's center-of-mass shifts ~7-8px left *relative to the scroll container's outer edges* but remains visually centered on the grid content the user is actually looking at (the grid also shifted inward by the same amount). Cosmetic only; not a bug, flagged for completeness.

## Success Criteria

**Pre-flight reproduction check (MUST pass before touching code):**

0. **Bug reproduces pre-fix.** Preferred fixture: open the Meal Planner with "Blueberry Pancakes" visible in the current week, hover the card in a browser with classic scrollbars, and visually confirm both symptoms (title wraps to 2 lines, dashboard shifts). If that exact seed data is not present locally, use or create any equivalent **food-item** card whose title fits on one line at rest and whose hover-expand pushes the mealboard container across the overflow threshold; record which fixture you used. If the bug still does NOT reproduce in the implementer's environment (e.g., macOS with default overlay scrollbars), STOP and re-diagnose — do not ship a fix for a bug that wasn't observed. Options: switch macOS System Settings → Appearance → "Show scroll bars" to "Always" to force classic rendering and re-test; or reproduce on Windows/Linux.

Browser-verifiable in a real desktop browser (manual or automated; Playwright is optional if available, but no specific MCP server is required):

1. **Root-cause guardrail:** On desktop browsers that support `scrollbar-gutter`, computed styles on the mealboard scroll container show `scrollbar-gutter: stable`. On unsupported desktop browsers, the fallback keeps a reserved vertical scrollbar on that same container at rest. Do NOT rely only on the DOM class token.
2. **Title stability:** Hovering the target `MealCard` does NOT change the rendered line count of its name text. Before hover: 1 line. During hover: 1 line. After hover-exit: 1 line.
3. **Header row stability:** The bounding-box `x` coordinate of the day-header "Sun"/"Mon"/.../"Sat" labels does NOT change between rest and hover states (tolerance ≤1px for subpixel rounding).
4. **Swimlane grid stability:** The bounding-box `width` of the SwimlaneGrid container does NOT change between rest and hover states (tolerance ≤1px).
5. **Hover-expand still works:** The `actionZoneClass` element (the two-button action zone below the food-item body) transitions from `max-h-0 opacity-0` to `max-h-[48px] opacity-100` on hover (the existing hover-expand behavior is preserved).
6. **Scroll still works:** With many meals loaded such that the inner container legitimately overflows, the user can still scroll vertically within the mealboard container.
7. **Reduced-motion parity:** Re-run criteria 2-5 with the browser in `prefers-reduced-motion: reduce` mode (DevTools → Rendering → Emulate CSS media → "prefers-reduced-motion: reduce"). Expected: identical stability; hover-expand snaps instantly with no jitter.
8. **Already-overflowing week:** Populate or simulate a week with enough meals to force a scrollbar at rest. Hover a card — confirm no new jitter is introduced (fix is a no-op in this case, which is correct behavior).

Manual verification to pair with browser checks:

- **Short-week sanity check:** Load a week with few meals (no overflow). Confirm the reserved scrollbar gutter (~15px empty stripe on the right edge of the mealboard scroll area) is visually acceptable and does not look broken.
- **Fresh-bundle check:** After applying the fix, do a hard reload or open a fresh tab before judging the result. Do not let Vite HMR residue masquerade as a failed CSS fix.
- **Rollback criterion:** If pre-flight reproduction (Criterion 0) or any of Criteria 1-4 fail after the fix, revert the change and re-investigate before proceeding. Do not accumulate follow-up fixes on top of an unverified root cause.

## Rollout / Rollback

- **Rollout shape:** Frontend-only change. No schema, API, background-job, or feature-flag work required.
- **Mixed-version / stale-client risk:** During deploys or local development, some tabs may still be running the old CSS bundle. Before concluding the fix failed after ship, hard-refresh the page or reopen the tab so verification is against the new bundle.
- **Rollback sequence:** Revert the `MealPlannerView.jsx` class change plus the matching `mealboard-scroll-stable` utility in `frontend/src/index.css`, rebuild/restart the frontend, hard-refresh the browser, and rerun Success Criteria 0-4 to confirm the ambient layout behavior returned to the pre-fix state.

# Design: M4 — Frontend Auth Session (`prod-auth-frontend-session`)

Generated by /office-hours on 2026-05-03
Branch: `prod-auth-frontend-session`
Status: APPROVED
Mode: Builder (Learning subtype)

---

## Problem Statement

M3 shipped the backend auth foundation (#28, 2026-05-03): `/auth/register`,
`/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/status`, with a
`__Host-refresh` HttpOnly cookie carrying the refresh token, an in-memory
JWT access token model, a 60-second rotation grace window, and a
`session_version` column for instant access revocation. **The frontend
currently knows nothing about any of this.** All 28 frontend HTTP callers
still construct `const API_BASE = import.meta.env.VITE_API_BASE_URL` at
module scope and call axios directly. There is no central API client, no
auth state, no `/auth` route.

M4 wires the frontend into M3's contract:

- Centralized `frontend/src/lib/api.js` axios instance, with auth-aware
  request + response interceptors
- Module-scope auth state with React-tree subscription
- Boot-sequence refresh on page load
- Silent refresh on 401 with single-flight de-duplication for parallel
  in-flight requests
- Unified `/auth` portal — login + (rare) first-time household setup
- `return_to` redirect with open-redirect protection
- Mechanical migration of all 28 existing API callers to the central client

M4 does NOT enforce auth on backend routes — that's M5 PR #1. M4 ships
*ready* for enforcement.

---

## What Makes This Cool

**Most React auth tutorials are wrong.** Not wrong-wrong — the patterns
work — but they're conceptually muddled in the same place. They put the
access token in a React Context and then have to do an imperative dance
to "tell axios about the token," because axios interceptors live at module
scope, *outside* the React tree. The Context update fires; the interceptor
closure still has the old token; you `useEffect` a `setApiAccessToken(token)`
call to keep them in sync. It works, but you have two coordinated state
owners that drift apart any time someone refactors the wrong file.

React 18's `useSyncExternalStore` was added precisely for "external
stateful thing that components subscribe to." An in-memory access token
*is* an external stateful thing — it lives at module scope so axios can
read it directly, and React subscribes to it for UI re-renders. **One
source of truth, native primitive, learning value.**

The other interesting axis: **router loaders as the auth gate.**
React-router v7 (already a dep) has a `loader` concept that runs *before*
a route mounts. That's the modern primitive for "wait for `/auth/refresh`
before showing protected UI." The conventional alternative (an
`AuthProvider` with a `useEffect` and a global `isBooting` spinner) works
but is the older idiom. Switching the app to the data router is the
"refactor adjacent things just enough to use the right tool."

Together those two choices — module store + router loader — turn M4 from
"more JWT-handling code" into a tour of two underused-but-correct primitives.

## Constraints

- **Backend contract is locked.** M3 endpoints, cookie names, JWT shape,
  and rotation semantics ship as-is. Frontend conforms.
- **In-memory access token only.** Never `localStorage`, never
  `sessionStorage`. Refresh on every page load.
- **Single-family deploy.** One operator, one register event ever.
  Family members log in only.
- **Coexist with M2 plumbing.** `VITE_M2_SHELL=true` still swaps the
  whole app for `<PlumbingShell />`. M5 PR #2 removes both `PlumbingShell`
  and the `VITE_M2_SHELL` flag.
- **Coexist with visual tests.** During M4 → M5 transition, visual tests
  will go red (boot loader will redirect to `/auth`). M5 PR #1 introduces
  `AUTH_BYPASS_FOR_VISUAL_TESTS=1` on the *backend* to make `/auth/refresh`
  return a synthetic session in test mode. **M4 adds no frontend bypass
  flag and no test-only frontend code path.**
- **No new runtime deps.** TanStack Query (5.90), axios (1.13),
  react-router-dom (7.12) are all installed. We are not adding Zustand,
  jotai, redux, or any auth library.
- **Existing 28 callers must keep working.** Migration is mechanical
  base-URL swap; component code shape is preserved. (TanStack Query
  migration of those callers stays as Phase 3 Step 2.1, deferred.)
- **CSRF posture inherited from M3.** The `__Host-refresh` cookie is
  HttpOnly + Secure + Path=/ (required by the `__Host-` prefix) +
  `SameSite=Strict`. (Eng review 1: verified M3 currently sets
  `REFRESH_COOKIE_SAMESITE = "lax"` in `backend/app/auth/routes.py:33`;
  decision was to bump to `Strict` in a tiny pre-M4 backend PR rather
  than document Lax as the contract. Same-origin SPA on Vercel does not
  need Lax — there is no email-link sign-in flow that requires the
  refresh cookie to survive cross-origin top-level nav. **This is a
  prerequisite for M4 implementation: land the cookie change first, or
  bundle it into M4 PR #1 alongside `lib/api.js`.**)

## Premises

These were confirmed during the office-hours session. Subsequent reviews
should challenge them if they're wrong, not silently work around them.

1. **P1 — Visual tests during the M4 → M5 transition.** M4 ships, visual
   tests go red because the boot loader redirects to `/auth` with no
   cookie present. M5 PR #1 fixes them via the backend's
   `AUTH_BYPASS_FOR_VISUAL_TESTS=1` env (which makes `/auth/refresh`
   return a synthetic session when `APP_ENV=test`). M4 adds **zero**
   frontend bypass code. Visual tests is "informational, not required"
   per `IMPLEMENTATION_PLAN.md`, so transient red doesn't block merges.

2. **P2 — `/auth` is auto-discriminated by `/auth/status`.** On mount the
   `/auth` route calls `GET /auth/status`. If `account_exists: true` →
   render login form. If `false` → render first-time household setup
   form (with the `HOUSEHOLD_ACCESS_KEY` field). **No mode-toggle UI**
   is rendered. Single-family deploy → register is a one-time operator
   event; family members never see it.

3. **P3 — Refresh stays in axios infra, not in TanStack Query.**
   `POST /auth/refresh` is called from exactly two places: the root
   router loader (boot sequence) and the axios response interceptor
   (silent retry on 401). Single-flight is enforced by a module-scope
   `let refreshPromise: Promise<void> | null` — concurrent 401s `await`
   the same promise. TanStack Query handles the *app-level* auth ops
   (`/auth/status`, `/auth/login`, `/auth/register`, `/auth/logout`)
   only.

4. **P4 — M4 does NOT TanStack-Query-ify the existing 28 callers.** The
   migration is `const API_BASE = ...` → `import { api } from '@/lib/api'`
   and `axios.get(\`${API_BASE}/x\`)` → `api.get('/x')`. Each caller
   keeps its existing imperative shape, including any local state /
   error handling / loading flags. The proper TanStack Query migration
   stays as `IMPLEMENTATION_PLAN.md` §4 Phase 3 Step 2.1.

5. **P5 — `return_to` validates to a same-origin relative path.** Reject
   any value that contains `://`, starts with `//`, or doesn't start with
   `/`. **Also reject any path that starts with `/auth`** — otherwise a
   malicious or accidental `?return_to=/auth` creates a redirect loop on
   successful login. (CEO review 1, S3.) Open-redirect defense is
   non-negotiable, even on a single-family app. Implementation is a
   small utility (`isSafeReturnTo(path)`); test with a table of malicious
   inputs (full URL, protocol-relative, `javascript:`, `/auth`,
   `/auth/login`, control characters).

## Approaches Considered

### Approach A: Module-store + Router-loader (RECOMMENDED)

**Summary.** Token lives in a vanilla JS module-scope store
(`lib/auth/tokenStore.js`) exposing `getSnapshot/subscribe/setToken`.
React components read it via `useSyncExternalStore`. Axios reads it
directly (`tokenStore.getSnapshot()`). React Router v7 data router with
a root loader calls `/auth/refresh` before any protected route mounts.
TanStack Query handles `/auth/status`, login/register/logout mutations,
and global 401 routing via `QueryCache.onError` (delegates to the same
single-flight refresh).

- **Effort:** M (multi-file but bounded) — net adds `~12-15 files`,
  edits `~33` (28 callers + main.jsx + App.jsx + new RootLayout.jsx +
  a couple of test files).
- **Risk:** Med — requires migrating from `BrowserRouter` + `<Routes>`
  to `createBrowserRouter` + `<RouterProvider>`. Realistic LOC for the
  router migration alone: **~100-150 LOC across 3-4 files** (`main.jsx`,
  `App.jsx` → split into `RootLayout.jsx`, new `lib/router.jsx`, plus
  reconciliation of the existing `VITE_M2_SHELL` swap which currently
  wraps `<App/>` and must be re-homed inside the new layout). This is
  larger than a one-line BrowserRouter swap; budget accordingly.
- **Pros:**
  - One source of truth for the access token (no Context-axios drift).
  - Native React 18 primitive (`useSyncExternalStore`) used for its
    intended purpose — high learning value, no new deps.
  - Router loader is the modern way to gate routes; the same primitive
    is reusable for any future "wait for data before render" cases.
  - `QueryCache.onError` centralizes 401 handling for *all* TanStack
    Query reads, including future Phase 3.1 caller migrations.
- **Cons:**
  - The data-router migration is a real refactor of `App.jsx` +
    `main.jsx` (~100-150 LOC, 3-4 files). Provider stacking changes
    shape (providers move into a root layout route, not wrapping
    `<RouterProvider />`). The `VITE_M2_SHELL` swap also has to be
    re-homed.
  - `useSyncExternalStore` is a less-familiar hook than `useState` /
    `useContext`; future contributors may need a comment pointing to
    the React docs.
- **Reuses:** `axios`, `@tanstack/react-query`, `react-router-dom@7`
  already installed. No new deps.

### Approach B: Foundation but classic (`AuthContext` + spinner-on-boot)

**Summary.** Same scope. Token lives in a React Context. `AuthProvider`
runs `/auth/refresh` in a `useEffect` on mount, holds an `isBooting`
state, renders a single full-screen spinner during boot, then renders
either `<Routes/>` or redirects to `/auth`. Token is shared with axios
via a module-level `setApiAccessToken(token)` setter that `AuthProvider`
calls after a successful refresh / login. Mid-session 401: same
single-flight refresh in axios interceptor, then react-router
`navigate('/auth?return_to=…')` on terminal failure.

- **Effort:** M (slightly less than A because no router migration).
- **Risk:** Low — every step uses idioms the project already has
  (Context providers, useEffect-driven state).
- **Pros:**
  - No router refactor; keep `<Routes>/<Route>`.
  - Familiar pattern; any React dev recognizes it on sight.
- **Cons:**
  - Two coordinated state owners (Context + module setter). Refactors
    that touch one and forget the other are a class of bug we'd be
    inviting.
  - Boot sequence is "global spinner-then-app" rather than "router
    decides per-route." Less granular.
  - Loses the learning win (the user explicitly chose the API client
    architecture lens for its educational value).
- **Reuses:** Same deps. No new code beyond what A also uses.

### Approach C: Fetch-only, no axios (lateral)

**Summary.** Replace axios entirely with a thin `fetch` wrapper
(`apiFetch(path, opts)`) that reads the token from the module store and
handles 401 + single-flight refresh internally. TanStack Query queryFn
calls `apiFetch`. The 28 callers convert from
`axios.get(\`${API_BASE}/x\`)` to `apiFetch('/x')` — but the response
shape, error model, and headers convention all change subtly (axios
auto-throws on 4xx/5xx; fetch resolves; axios JSON-parses; fetch
doesn't; etc.). So caller migration becomes semantic rather than
mechanical.

- **Effort:** L — every caller's `try/catch` and response handling shifts
  shape.
- **Risk:** Med-High — caller migration is no longer mechanical;
  per-caller verification needed.
- **Pros:**
  - Zero runtime dep (`axios` removable entirely).
  - More modern; closer to what queryFn naturally takes.
- **Cons:**
  - Violates premise P4 (mechanical caller migration). M4's scope
    expands to "rewrite all 28 callers to fetch shape."
  - Less learning value relative to A — the interceptor pattern is what
    most production codebases run, so internalizing axios interceptors
    transfers more broadly.
  - Loses the axios helper conveniences the existing codebase relies on
    (auto-JSON, auto-throw on error status, `withCredentials` config
    convention).
- **Reuses:** Native fetch; TanStack Query.

---

## Recommended Approach

**Approach A.** Three reasons.

1. **The user picked Learning + the API-client architecture lens.** A is
   the approach where the architecture choices teach the most:
   `useSyncExternalStore` is the underused-but-correct primitive for
   external stores; data-router loaders are the modern way to gate
   routes; `QueryCache.onError` is the production pattern for centralized
   401 routing. B is a perfectly reasonable architecture but it teaches
   nothing the user doesn't already know.
2. **The data-router migration is bounded.** ~100-150 LOC across 3-4
   files (`main.jsx`, `App.jsx` → `RootLayout.jsx`, new `lib/router.jsx`).
   Worth doing once, then reusable for any future "wait for data before
   route mounts" need (e.g., the calendar prefetch we'll inevitably want).
3. **Premise P4 protects the scope from C-style runaway.** Mechanical
   caller migration keeps M4 a ~2-week-human / ~1.5-hour-CC milestone
   instead of a ~3-week-human / ~3-hour-CC one.

Risk to monitor: in pure CSR Vite (no hydration phase),
`getServerSnapshot` is never actually called by React — it exists for
SSR/hydration only. We still pass it to satisfy the hook signature and
match library expectations, but the rationale is "be explicit about the
contract," not "avoid a runtime warning." Returning `null` is fine.

### Cold-boot loader decision tree

```

                       │
                       ▼
                ┌─ tokenStore.getSnapshot() ─yes─→ return null → render protected ✓
                │   (already authenticated;
                │    e.g. back/forward nav)
                │
                no (cold boot or post-clear)
                │
                ▼
            performRefresh()
            (single-flight; raw axios; 10s timeout)
                       │
        ┌──────────────┼──────────────┬───────────────────┐
        │              │              │                   │
        ▼              ▼              ▼                   ▼
     success         401         5xx / network      malformed body
        │              │         / timeout              │
```

### Eng review 3: caller migration template

All 28 mechanical migrations follow this exact shape so the diff is easy
to audit in code review (one line removed, two lines changed at the call
site, one import added). Example using
`frontend/src/components/settings/MealboardSettings.jsx`:

```js
// BEFORE
const API_BASE = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8000'
// ... in some handler:
await axios.get(`${API_BASE}/meal-slot-types`)
await axios.post(`${API_BASE}/meal-slot-types`, payload)

// AFTER
import { api } from '@/lib/api'
// ... in same handler:
await api.get('/meal-slot-types')
await api.post('/meal-slot-types', payload)
```

Rules a migration must follow:
- The `const API_BASE = ...` line is **removed**, not retained.
- Every call site uses **relative paths only** (`/x`, never
  `${API_BASE}/x` and never an absolute URL).
- `withCredentials: true` is no longer set per-call (the central
  instance carries it).
- Local `try/catch`, loading flags, and toast-on-error code shape is
  **preserved verbatim**. M4 does NOT TanStack-Query-ify these callers.
- The 3 `fetch()` callers (`PhotoUpload.jsx`, `RecipeImageUpload.jsx`,
  `useRecipeImport.js` — verify list at implementation time) follow the
  same rule with `api.post('/...', formData)` instead of
  `fetch(`${API_BASE}/...`, { method: 'POST', body: formData })`.
- Image-rendering paths (`<img src={...}>`) move to `apiUrl(relativePath)`
  from `lib/apiBase.js`, NOT to the axios `api` instance. See SC #37.

### Token store contract (`lib/auth/tokenStore.js`)

```js
// Pseudo-shape, not literal code:
let accessToken = null;          // module-scope, in-memory only
const listeners = new Set();

export const tokenStore = {
  getSnapshot: () => accessToken,
  getServerSnapshot: () => null,           // CSR app; loader hasn't run yet
  subscribe: (listener) => {
    listeners.add(listener);
    return () => listeners.delete(listener);
  },
  setToken: (token) => {
    accessToken = token;
    listeners.forEach((l) => l());
  },
  clear: () => tokenStore.setToken(null),
};
```

`useAuth.js` becomes:

```js
const accessToken = useSyncExternalStore(
  tokenStore.subscribe,
  tokenStore.getSnapshot,
  tokenStore.getServerSnapshot,
);
const isAuthenticated = accessToken !== null;
return { accessToken, isAuthenticated };
```

### API origin + asset URL contract (`lib/apiBase.js`)

Adversarial review 2: centralizing HTTP requests is not enough. Several
existing callers use `VITE_API_BASE_URL` only to turn backend-relative
asset paths (`/uploads/...`) into absolute `<img src>` URLs. If M4 simply
removes those reads while migrating axios calls, uploaded family photos,
recipe images, food-item icons, and responsibility icons will silently 404
against the SPA origin.

```js
// Pseudo-shape, not literal code:
export const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || 'http://localhost:8000';

export function apiUrl(path) {
  if (!path) return path;
  if (/^https?:\/\//i.test(path)) return path;
  return `${API_BASE_URL}${path.startsWith('/') ? path : `/${path}`}`;
}
```

Rules:
- `api.js` imports `API_BASE_URL` for axios `baseURL`.
- `auth/refresh.js` imports `apiUrl('/auth/refresh')` for the raw axios
  refresh call, avoiding a circular import through `api.js`.
- Image/icon components (`MemberAvatar`, `ItemIcon`, `ItemCard`,
  `ResponsibilityCard`) use `apiUrl(relativeUploadPath)`.
- After migration, `VITE_API_BASE_URL` appears only in `lib/apiBase.js`;
  all request callers use relative URLs through `api.*`.

### API client contract (`lib/api.js`)

```js
import axios from 'axios';
import { API_BASE_URL } from './apiBase';
import { tokenStore } from './auth/tokenStore';
import { performRefresh } from './auth/refresh';
import { redirectToAuthOnce } from './auth/redirect';

export const api = axios.create({
  baseURL: API_BASE_URL,
  withCredentials: true,        // M3 contract: __Host-refresh cookie
  timeout: 15_000,
});

// Request interceptor — inject access token if present
api.interceptors.request.use((config) => {
  const token = tokenStore.getSnapshot();
  if (token) config.headers.Authorization = `Bearer ${token}`;
  return config;
});

// Response interceptor — single-flight refresh on 401, then retry once
api.interceptors.response.use(null, async (error) => {
  const original = error.config;
  // Eng review 1: guard error.config undefined. axios returns errors with no
  // `config` on certain pre-flight failures (request canceled, DNS failure
  // before send). Without this guard, `original._retried = true` below throws
  // a TypeError that masks the original error.
  if (!original || error.response?.status !== 401 || original._retried) {
    throw error;
  }
  // Don't refresh-loop on the auth endpoints themselves
  if (original.url?.startsWith('/auth/')) throw error;

  original._retried = true;
  try {
    await performRefresh();      // single-flight; see refresh.js
    original.headers.Authorization = `Bearer ${tokenStore.getSnapshot()}`;
    return api(original);
  } catch (refreshError) {
    // Adversarial review 1: only auth-terminal refresh failures redirect.
    // Non-401 refresh failures (backend down, timeout, malformed response)
    // stay as server errors; redirecting to /auth would lie to the user.
    if (axios.isAxiosError(refreshError) && refreshError.response?.status === 401) {
      tokenStore.clear();
      redirectToAuthOnce();
    }
    throw refreshError;
  }
});
```

### Single-flight refresh (`lib/auth/refresh.js`)

```js
import axios from 'axios';
import { apiUrl } from '../apiBase';
import { tokenStore } from './tokenStore';

let inFlight = null;             // shared promise; null when idle

export async function performRefresh() {
  if (inFlight) return inFlight;
  inFlight = (async () => {
    try {
      const { data } = await axios.post(
        apiUrl('/auth/refresh'),
        null,
        { withCredentials: true, timeout: 10_000 },  // CEO review 1: A1 — explicit timeout
      );
      // CEO review 1: defensive — guard malformed responses before touching tokenStore
      if (typeof data?.access_token !== 'string') {
        throw new Error('refresh: malformed response');
      }
      tokenStore.setToken(data.access_token);
    } finally {
      inFlight = null;
    }
  })();
  return inFlight;
}

export async function waitForRefreshToSettle() {
  if (!inFlight) return;
  try {
    await inFlight;
  } catch {
    // Logout is best-effort locally even if the in-flight refresh failed.
  }
}
```

Notes:
- Uses raw axios (not `api`) to avoid recursion through the response
  interceptor.
- **The 10-second timeout is mandatory.** Without it, a hung backend
  (5xx-with-no-response, dropped TCP connection) leaves the cold-boot
  loader awaiting forever and the user stuck on the HydrateFallback
  spinner. (CEO review 1: A1.)
- The 60-second M3 grace window means a stale cookie from a parallel
  tab still works — no extra coordination needed on the frontend.
- The `try/finally` guarantees `inFlight` resets even when refresh
  rejects (so the next 401 can try again instead of hanging on a stuck
  promise).
- **Failure classification is the caller's job, not performRefresh's.**
  performRefresh only `throws`; the loader and interceptor classify the
  thrown error (401 vs 5xx/network/timeout) and route accordingly.
  (CEO review 1: Q1A.)
- **Adversarial review 1: imperative callers must not be auth-dead ends.**
  Most M4-migrated callers keep their existing imperative shape, so they
  will not flow through TanStack Query's `onError`. The axios interceptor
  must call the same one-shot redirect helper on terminal refresh 401s.
  QueryCache/MutationCache are still useful for auth operations and future
  Query migrations, but they are not the only redirect path.
- **Adversarial review 1: all migrated call sites use relative URLs with
  the central client.** `api.get('/tasks')` is valid; `api.get(API_BASE +
  '/tasks')` is not. This keeps interceptor URL classification simple and
  avoids auth-endpoint guard drift.
- **Adversarial review 2: media URLs are not request URLs.** Components
  that render backend-uploaded images must use `apiUrl('/uploads/...')`
  rather than reading `VITE_API_BASE_URL` directly or accidentally treating
  asset rendering as an axios migration.

### Router (`lib/router.jsx`)

The loader is hoisted to a **pathless protected layout route** so it
runs once for any protected child rather than being copy-pasted onto
every `Route` definition. Adding a new protected page later is a
matter of dropping it inside the layout's children — no loader to
remember to wire.

```js
const router = createBrowserRouter([
  {
    path: '/',
    element: <RootLayout />,             // mounts providers
    hydrateFallbackElement: <HydrateFallback />,  // shown during loader runs
    children: [
      // /auth has no protected layout in the chain — accessible without a token.
      { path: 'auth', element: <AuthPortalPage /> },

      // Pathless protected layout — loader fires for ALL children below.
      {
        element: <ProtectedOutlet />,    // just <Outlet/>, nothing else
        loader: rootAuthLoader,
        errorElement: <BootErrorScreen />,  // CEO review 1 (Q1A): renders on non-401 refresh failure
        children: [
          { index: true,                element: <CalendarPage /> },
          { path: 'lists',              element: <ListsPage /> },
          { path: 'responsibilities',   element: <ResponsibilitiesPage /> },
          { path: 'settings',           element: <FamilyMembersPage /> },
          { path: 'mealboard/*',        element: <MealboardPage /> },
        ],
      },
    ],
  },
]);

async function rootAuthLoader({ request }) {
  // Already-authenticated short-circuit — back/forward nav, route changes
  // within an authenticated session, etc. We don't want to re-refresh on
  // every protected nav; we only refresh on cold boot (token === null).
  if (tokenStore.getSnapshot() !== null) return null;

  try {
    await performRefresh();
    return null;
  } catch (err) {
    // CEO review 1 (Q1A): classify the failure. 401 means "you need to log in";
    // 5xx / network / timeout / malformed means "the backend is broken." Lumping
    // both as "redirect to /auth" lies to the user and lands them on a /auth
    // page that ALSO can't reach the backend.
    const status = axios.isAxiosError(err) ? err.response?.status : undefined;
    if (status === 401) {
      const url = new URL(request.url);
      const returnTo = url.pathname + url.search;
      throw redirect(`/auth?return_to=${encodeURIComponent(returnTo)}`);
    }
    // Non-401: propagate as a Response so the route's errorElement renders
    // the "Can't reach the server. Retry." screen (router.revalidate() on
    // click). The route definition uses errorElement: <BootErrorScreen />.
    throw new Response('refresh failed', { status: 503 });
  }
}
```

Notes:
- `hydrateFallbackElement` is required when any route has a `loader` —
  it's what React Router renders during the loader's async work. We
  ship a small spinner in `lib/auth/HydrateFallback.jsx`. Without it,
  the user sees a blank page during boot refresh (~50-200ms).
- **CEO review 1 (A2): HydrateFallback renders OUTSIDE the RootLayout
  provider stack.** RR7 mounts `hydrateFallbackElement` while the root
  loader is still running, before RootLayout mounts. So the spinner
  CANNOT subscribe to `DarkModeProvider`, `ToastProvider`, etc. The
  spinner must read `prefers-color-scheme` and the persisted `darkMode`
  localStorage key directly and apply theme classes inline.
  **Eng review 3: pin the localStorage contract concretely.** The
  existing `frontend/src/contexts/DarkModeContext.jsx` writes string
  literals (`localStorage.setItem('darkMode', 'true')` /
  `'false'`), so HydrateFallback must use the same shape — `===` against
  the strings, no coercion, system-preference fallback only when the key
  is absent:

  ```js
  const stored = localStorage.getItem('darkMode');
  const isDark =
    stored === 'true'  ? true
  : stored === 'false' ? false
  : window.matchMedia('(prefers-color-scheme: dark)').matches;
  ```

  ~5 LOC of inline logic; the same shape applies to BootErrorScreen.
  Document the constraint in a comment so a future refactor doesn't
  "fix" the spinner by importing the dark-mode hook (which would crash
  because the provider hasn't mounted yet).
- **CEO review 1 (A3): provider stack lives INSIDE RootLayout, around
  `<Outlet/>`.** Not in `main.jsx` around `<RouterProvider/>`. RootLayout
  renders for both `/auth` and protected routes, so DarkMode + Toast +
  UndoToast are available to both surfaces. The only thing in `main.jsx`
  outside `<RouterProvider/>` is the `VITE_M2_SHELL` short-circuit (so
  PlumbingShell doesn't need the data router at all).
- The `tokenStore.getSnapshot() !== null` short-circuit means the loader
  fires `/auth/refresh` exactly **once per cold load** (or after a
  logout-induced clear). All subsequent in-session route navigation
  reuses the in-memory token. This avoids the "every-nav-hits-refresh"
  pattern that would balloon backend traffic.
- **Caveat: stale token after server-side `session_version` bump.** If
  the operator rotates a password (or some future admin action bumps
  `session_version`), the in-memory token in an open tab is now invalid
  but the loader's short-circuit returns `null` and renders the
  protected route. The first API call from that route will 401 → the
  interceptor refreshes → refresh also fails (session_version mismatch)
  → `redirectToAuthOnce` redirects. **Net UX: a brief flash of the protected
  route (~one round-trip) before the redirect.** Acceptable for v1
  given how rare server-side revocation is in a single-family deploy.
- **Adding a new protected page** is just adding a child under the
  `<ProtectedOutlet />` route. No loader plumbing required.

### Auth redirect helper (`lib/auth/redirect.js`)

```js
import { tokenStore } from './tokenStore';

let _router = null;
export function setRouter(router) { _router = router; }

// Module-scope guard — prevents N concurrent 401s from triggering
// N redirects to /auth. React Router dedupes identical navs but the
// `return_to` captured will be whichever fires last; using a one-shot
// flag makes the behavior deterministic and the captured URL the first
// failure's URL, not a race-winner's.
let redirecting = false;

export function redirectToAuthOnce() {
  if (redirecting) return;
  if (window.location.pathname.startsWith('/auth')) return;  // already there

  // Eng review 2: self-heal if router hasn't been bound yet. _router is null
  // between module-eval and main.jsx's setRouter() call — and in unit tests
  // that exercise this helper without bootstrapping the full router. Without
  // this guard, we'd set `redirecting = true`, then `_router?.navigate(...)`
  // would be a no-op, and the flag would never reset (no /auth mount fires
  // resetRedirectGuard). That deadlocks every subsequent redirect call —
  // silently in production, polluting state across cases in tests.
  if (!_router) {
    tokenStore.clear();
    if (import.meta.env.DEV) {
      console.warn(
        '[auth] redirectToAuthOnce called before setRouter(); skipping navigation'
      );
    }
    return;
  }

  redirecting = true;
  tokenStore.clear();
  const returnTo = window.location.pathname + window.location.search;
  _router.navigate(`/auth?return_to=${encodeURIComponent(returnTo)}`);
  // Reset the flag once the navigation settles. The /auth route's mount
  // effect calls `resetRedirectGuard()` exported from this module.
}

export function resetRedirectGuard() { redirecting = false; }
```

Notes:
- **Adversarial review 1: redirect ownership moved out of
  `queryClient.js`.** The 28 mechanically migrated callers are mostly
  imperative, not TanStack Query calls. If the redirect guard lived only
  in Query callbacks, a terminal refresh 401 from an imperative caller
  could be swallowed by that caller's local `catch` and leave the user on
  stale UI. `api.js` and `queryClient.js` both import this helper.
- **Eng review 1: late-bind the router via `setRouter()` to avoid a
  circular import.** `redirect.js` cannot import from `lib/router.jsx`
  directly because `router.jsx` defines routes whose page components
  depend on the QueryClient. `main.jsx` imports both modules and calls
  `setRouter(router)` once both are evaluated.
- **The `/auth` route's mount calls `resetRedirectGuard()`.** Mount is
  the natural moment because in React Router 7, `router.navigate(url)`
  resolves *as the destination route mounts* — there is no window where
  a protected route can render between `navigate('/auth')` and
  `<AuthPortalPage />`'s mount effect. So the guard reset is
  synchronous-with-respect-to-app-state, even though `navigate` itself
  is async. The guard does not need an earlier release path.
- **Eng review 2: self-heal when `_router` is null.** A separate fast
  path (above the `redirecting = true` line) handles calls that happen
  before `setRouter()` runs. It clears the token, logs a DEV warning,
  and bails *without* setting the guard. That keeps unit tests on
  `lib/queryClient.js` (SC #28) from polluting subsequent cases and
  removes a theoretical bootstrap deadlock. SC #35 pins the behavior.

### TanStack Query integration (`lib/queryClient.js`)

```js
import { redirectToAuthOnce } from './auth/redirect';

function handle401(error) {
  if (!axios.isAxiosError(error) || error.response?.status !== 401) return;
  redirectToAuthOnce();
}

const queryClient = new QueryClient({
  defaultOptions: {
    queries: { staleTime: 30_000, retry: false },
    mutations: { retry: false },
  },
  queryCache:    new QueryCache({    onError: handle401 }),
  mutationCache: new MutationCache({ onError: handle401 }),
});
```

Notes:
- **Both `QueryCache.onError` AND `MutationCache.onError` are configured.**
  Reads (queries) and writes (mutations) both have a centralized 401
  handler. Without `MutationCache.onError`, a 401 from a mutation
  (e.g., create-meal) still reaches the axios interceptor, but Query
  callbacks provide a second shared redirect path and keep future
  TanStack Query migrations from re-solving 401 handling per feature.
- **`redirecting` flag prevents N→N redirect storms.** With 5 concurrent
  401s after a stale-cookie boot, axios and Query callbacks may both
  observe terminal auth failure. The flag ensures exactly one
  `router.navigate('/auth?...')` fires.
- **`tokenStore.clear()` race.** `clear()` synchronously notifies all
  `useSyncExternalStore` subscribers, which can re-render and fire
  fresh authenticated requests inside the same microtask before
  `router.navigate` resolves. The `redirecting` flag protects against
  this: any new 401 inside that window is swallowed by `if (redirecting) return`.
  The race exists; the flag closes it.
- Query callbacks are a second line of defense, not the only auth-failure
  path. The axios interceptor owns terminal refresh-401 redirects for
  imperative callers.

`/auth/status` is a `useQuery`; login/register/logout are `useMutation`.
**All three auth mutations route through the wrapped `api` instance**
(not raw axios). The interceptor's `original.url?.startsWith('/auth/')`
guard prevents an `/auth/login` 401 (wrong password) from triggering a
refresh attempt — the 401 propagates through to the mutation's
`onError`, which renders the inline form error. Login `onSuccess` does
`tokenStore.setToken(data.access_token)` then
`navigate(safeReturnTo(...) ?? '/')`.

### `/auth` portal flow (`pages/AuthPortalPage.jsx`)

1. On mount (Eng review 1: `resetRedirectGuard()` MUST be in a top-level
   `useEffect(..., [])` at the start of the component body, BEFORE the
   already-logged-in short-circuit effect. This guarantees the guard is
   reset on every mount of `/auth`, including the short-circuit path
   where the form never renders. Test T9 pins this.):
   a. Call `resetRedirectGuard()` so subsequent 401-redirect cycles work.
   b. If `tokenStore.getSnapshot() !== null`, the user is already
      authenticated (e.g., they typed `/auth` directly while logged in).
      Navigate to `safeReturnTo(searchParams.get('return_to')) ?? '/'`
      immediately. Don't render the form.
   c. Otherwise, fire `useQuery(['auth', 'status'])` → `GET /auth/status`.
2. While `/auth/status` loads: skeleton.
3. `account_exists: true` → render login form (email, password).
4. `account_exists: false` → render setup form (email, password, password
   confirm, `HOUSEHOLD_ACCESS_KEY`). Mask the access-key input.
5. On submit: useMutation against `api.post('/auth/login')` or
   `api.post('/auth/register')`. On success: `tokenStore.setToken(data.access_token)`
   then `navigate(safeReturnTo(searchParams.get('return_to')) ?? '/')`.
   **Register `onSuccess` ALSO invalidates the `/auth/status` query**
   (Eng review 2): `queryClient.invalidateQueries({queryKey: ['auth', 'status']})`.
   Without this, a register-then-logout sequence inside the 30s default
   `staleTime` would briefly re-render SetupForm against the cached
   `account_exists: false` before the refetch flips to LoginForm. SC #36
   pins the behavior.
   On 401: render inline form error (the interceptor's `/auth/` guard
   means no refresh attempt and no redirect storm).

**Per-mutation error handling (CEO review 1):**

| Error | Login | Register |
|---|---|---|
| 401 | "Invalid email or password" | "Invalid household access key" |
| 409 | n/a | refetch `/auth/status` → flips to login form (G6) |
| 429 | "Too many attempts. Please wait a moment and try again." (G4) | same |
| 5xx / network / timeout | "Couldn't reach the server. Retry." | same |
| Malformed response | guarded the same way as `performRefresh` | same |

**Defensive rendering (CEO review 1, S3):**
- `AuthPortalPage` renders error messages as text nodes (React's
  default escaping). **No `dangerouslySetInnerHTML` anywhere in the
  auth portal.** Backend error strings are NOT trusted as HTML.
- The `HOUSEHOLD_ACCESS_KEY` value is never written to console logs,
  toast messages, or error payloads.

**Logout failure honesty (Adversarial review 1):**
- Frontend logout is fail-closed for local UI state, but an HttpOnly
  refresh cookie cannot be cleared by JavaScript if `POST /auth/logout`
  fails before the backend sends its clearing `Set-Cookie`.
- **Adversarial review 2: logout waits for any in-flight refresh before
  sending `/auth/logout`.** A refresh response that lands after logout can
  otherwise re-set `tokenStore` and may apply a stale `Set-Cookie` after
  the clearing cookie. The logout mutation calls `await
  waitForRefreshToSettle()` first, then posts `/auth/logout` with the
  latest bearer token if one exists. If the wait rejects or times out via
  the refresh timeout, logout still clears local UI state and navigates to
  `/auth`.
- On 5xx / network / timeout from logout, clear `tokenStore` and
  navigate to `/auth`, but show a non-blocking warning: "Signed out on
  this screen. The server could not confirm logout; retry if this is a
  shared device." Do not claim the server session was revoked.
- On logout 401, use the same local clear + `/auth` navigation. This
  usually means the access token was already stale or revoked; the user
  intent is still to leave the app.

**Submit-button disabled state (CEO review 1, Section 4):**
- Login + register submit buttons disabled while `mutation.isPending`
  (prevents double-submit) AND while `/auth/status` is still loading
  (prevents submitting the wrong form before the discriminator
  resolves).

**`/auth/status` defensive parsing (CEO review 1, G5):**
- If the response shape is unexpected (`account_exists` is not a
  boolean), the discriminator falls back to **render the login form
  by default**. Setup form requires a positive boolean false — never
  rendered on validation failure. Rationale: a malformed response
  should never accidentally expose the household setup surface.

**`/auth/status` 5xx / network (CEO review 1, G7):**
- The query's `error` state renders an inline "Can't reach the
  server. Retry." with a refetch button. Neither form renders until
  status resolves cleanly. Visual treatment defined under
  **§ UI Design — Boot / status-fetch error surface** below.

### User journey & emotional arc

| Step | User does | User feels | What supports it |
|---|---|---|---|
| Cold-boot login | hits app, lands on `/auth` | "ugh, log in" | fast familiar card; "Welcome back" headline; autofocus on email |
| First-time setup | hits app on a fresh deploy | "I'm starting our household" | "Set up your household" framing; no toggle UI; warmth in copy |
| Mid-session 401 bounce | was using app; lands on `/auth?return_to=…` | "wait, what?" | info banner: "Your session ended. Sign in to pick up where you left off." |
| Boot error (backend down) | hits `/`, sees BootErrorScreen | "is it broken?" | humane copy ("we can't reach our server right now"); retry button; cloud-with-slash icon (terracotta, not red — recoverable). Chromeless layout so the user reads "this is a system problem," not a regular page. |
| Logout (intentional) | clicks Sign out on `/settings` | "I'm done" | one-click; navigates to `/auth`; no confirm dialog |
| Logout failure | clicks Sign out, server returns 5xx | "did it work?" | local clear runs; navigate happens; warning toast appears with honest copy |

Time-horizon design (Norman): cold boot must hit the visceral 5-second
test (familiar warm-cream + terracotta = "this is my app"); first-time
setup must hit the behavioral 5-minute test ("create household" copy
makes the moment feel meaningful); the long arc is reflective ("this
app respects me — quick to get in, honest when something fails").

## Open Questions

These are real choices the design doesn't lock in. Eng review or
implementation can settle each:

- **OQ1 — `/auth` sub-routes.** This design uses a single `/auth` route
  that auto-discriminates via `/auth/status`. Alternative: `/auth/login`
  + `/auth/setup` as explicit sub-routes (cleaner URLs, slightly worse
  default UX). Eng review may push back.
- **OQ2 — Multi-tab session-loss UX.** Tab A logs out; Tab B is sitting
  on `/calendar` with no listener for cookie changes (HttpOnly cookies
  emit no `storage` event). Tab B will discover it on its next API call
  (401 → refresh → fail → redirect). Acceptable, but worth flagging
  that a "you've been logged out elsewhere" toast will not be possible
  without server-sent events or polling. Punt.
- **OQ3 — `/auth/status` cache policy.** Default `staleTime: 30s` for
  TanStack Query is reasonable, but `/auth/status` rarely changes
  (account_exists flips at most once per deploy). Could push to 5
  minutes or `Infinity` with explicit invalidation on register success.
- **OQ4 — Logout button placement.** Settings page (`FamilyMembersPage`,
  rendered at `/settings`) is the obvious spot. Header user-menu would
  be more discoverable but requires header redesign. Defer.
- **OQ5 — `session_version` propagation.** M3 backend revokes stale
  sessions immediately on next API call. Frontend learns about this
  exactly when the next `/api/*` call returns 401 (refresh attempts,
  also fails because session_version was bumped, then redirect). No
  active polling. Acceptable for v1; flag for future.

## Failure Modes and Rollback

Adversarial review 1 added this as the operator/QA contract for the
unhappy paths:

- **Cold boot, no valid refresh cookie:** loader receives refresh 401,
  redirects to `/auth?return_to=<current path>`, and no protected page
  renders.
- **Cold boot, refresh infrastructure failure:** loader receives 5xx /
  network / timeout / malformed response, renders `BootErrorScreen`, and
  does not redirect to `/auth`.
- **Mid-session API 401, refresh succeeds:** interceptor retries the
  original request once with the new bearer token.
- **Mid-session API 401, refresh returns 401:** interceptor clears the
  token and calls the shared one-shot redirect helper. This must work for
  both TanStack Query callers and still-imperative migrated callers.
- **Mid-session API 401, refresh has non-401 infrastructure failure:**
  interceptor does not redirect to `/auth`; it rethrows the refresh
  failure so the original feature can show its normal server/network
  error path.
- **Logout while refresh is in flight:** logout waits for the current
  `performRefresh()` promise to settle before posting `/auth/logout`, so
  a late refresh response cannot re-populate in-memory auth after the
  user has chosen to sign out.
- **Logout request fails:** frontend clears local auth state and moves to
  `/auth`, but the UI must not claim server-side revocation. The HttpOnly
  cookie may remain valid until a later successful logout or expiry.
- **Mixed old/new deployment:** old frontend works against the Strict
  cookie backend; new frontend works against M3 auth endpoints before M5
  route enforcement. No schema change is introduced in M4.
- **Rollback:** revert the Vercel frontend deployment. If the tiny
  SameSite=Strict backend prerequisite was bundled into M4, leave it in
  place unless a real cross-site sign-in flow is introduced; the app's
  same-origin SPA auth flow remains compatible. If users are stuck in a
  bad client state, instruct the operator to clear the site's cookies and
  redeploy the last known-good frontend.

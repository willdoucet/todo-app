## Problem Statement

Framework 1.1.0 (todo-app PR #53, 2026-09-17) made `workflow-state` block on a review that ran
and did not pass. Shipping it, and running its §12 on M8 (`prod-launch-release`), turned up
three more places where the workflow's state depends on a person happening to look.

1. **An approval can be overtaken and nothing records it.** M8's `/plan-design-review`
   (logged 2026-09-15T03:54:14Z) added a backend contract to item 15a — `stale` computed when
   the request is served, a new `jobs.read_at`, every beat task listed even with no row — and
   wrote into the plan that this "supersedes Eng review 1.2". `/plan-eng-review` had passed on

   The design review logged `clean, unresolved=0`, which is true of its own domain. The
   dashboard shows every row ✓, the verdict is `CLEARED FOR IMPLEMENTATION`, and `--next`
   names `/execute-plan`.
2. **The concern was written down where nothing reads it.** The design review put it in the
   plan's frontmatter `reason`. That field is one free-text string, overwritten by whichever
   skill sets it next, and `workflow-state` reads it in exactly one place: appended to
   "resolve the blocker first" when a plan is `blocked` (`workflow-state`, the `blocked` /
   `needs-context` branch of `decide()`). It was found on 2026-09-16 only because an agent ran
   `plan-metadata-get` while shipping a *different* plan.

   `/update-docs` call `date +%F` (local); and every `{date}` or "today's date" an agent fills
   in is whatever the agent believes. The parent plan's frontmatter reads
   `completed: "2026-09-16"` beside a ship entry stamped `2026-09-17T03:58:57Z`. `completed`
   is UTC when `obsidian-workflow` writes it and local when `/ship` does.

A fourth item arrived with a different answer than expected. `design-sync-check` reports
"DRIFT — 2 commit(s)" on every design-stage skill run. The user's words: **"i am not using it

## Status Quo

- An overtaken approval is noticed by a person reading the plan, or not at all. The interim
  habit is an agent reading `plan-metadata-get` output and mentioning the `reason` text.
- Date mismatches are reconciled by eye, with a note in the pull request ("UTC vs local").
- The drift warning is read and ignored, which trains the reader to ignore warnings.

Cost: the first is an ungated path to `/execute-plan` on an unreviewed contract, the same class
of hole the parent plan closed. The others are friction, and friction in a record is how a real
discrepancy gets waved through.

## Premises

Agreed 2026-09-17 (UTC), all nine. Premises 2 and 9 were amended during the spec reviews; the user

1. `--next` and the verdict stay the only real control. A concern that should stop work must
   change `--next`; everything else is displayed. Free text is never parsed and never gates.

   refusing a failed target lets a third review resolve it unseen, so §1 accepts any review

   leaves earlier approvals intact.

   fails as usual), or the operator waives it with a note, visible on the dashboard. Another

## Landscape findings

Searched with category terms only (stale approvals after changes; time zones in records;
re-approval in change control).

- **What everyone knows.** An approval goes stale when the approved thing changes; the standard
  control is "dismiss stale approvals when new commits are pushed". Store UTC, display local.
- **What the current discussion adds.** Blanket dismissal is widely resented: it voids every
  approval for a one-line fixup, and rebasing a stack dismisses reviews downstream; the standing
  request is for "intelligent" dismissal. Regulated change control works differently: whoever
  makes a change writes an impact analysis naming what it touches, and re-approval is routed
  only to those approvers. For logs and audit records the UTC rule is unanimous: a record is an
  absolute moment, not a wall-clock label.
- **Where the convention is wrong here.** (a) Automatic dismissal assumes the change author is
  untrusted and reviewers do not edit. Here reviewers edit the plan by design, and the editor
  is the one who knows which earlier approval they touched — so the pattern that transfers is
  change control's *declared, targeted* re-approval. Its known weakness, a reviewer who forgets,
  is why the declaration is mandatory even when empty. (b) "Display local" assumes a render
  layer between storage and reader. Here the records *are* the display: a date in `LESSONS.md`
  or a plan filename is committed text read by agents on a laptop, in CI, and in cloud sessions.
  With nowhere to convert, display-local collapses into storing local. UTC everywhere is the
  conventional rule applied correctly; the one true display surface, the dashboard, only needs
  a label. Both are recorded under LESSONS Decisions at approval.

## Approaches Considered

### Approach A: Fail the declarer (reuse what shipped)
- Summary: a review that changed what X approved logs its own entry as `issues_open` with
  `needs=X`; the 1.1.0 machinery blocks; X's clean re-run resolves it.
- Effort: M (human: ~1 day / AI-assisted: ~2 h), about 10 framework files
- Risk: Med
- Completeness: 7/10
- Pros: no new state; reuses `issues_open`, `resolved` and the completion handoff.
- Cons: `issues_open` would mean two things ("I found problems" and "someone else must look"),
  the defect the parent plan removed. The dashboard marks the row that needs no action while
  the row that does still shows ✓. Three patch rules are needed to close holes it creates: only
  X or operator may resolve; the declarer cannot clear itself by re-running clean; `--next`
  must be re-pointed at X.
- Reuses: `review_disposition`, `can_resolve`, the §6a handoff, `resolved_by=operator`.

### Approach B: Stale the target (chosen)
- Summary: the declaring review logs `clean` with `rereview=[X]`. On read, X's latest entry
  gets a fifth derived disposition, `stale`, whenever a later entry on the same plan demands
  it. `stale` is not ok: X blocks its stage, its row reads `stale !` with who demanded it, and
  `--next` names X. X running again clears it; so does an operator waiver. (Eng review 1.0:
  the waiver is deferred; in 1.2.0 only X running again clears it.)
- Effort: M–L (human: ~2 days / AI-assisted: ~3 h), about 14 framework files
- Risk: Med — touches the state machine that shipped the day before; all four gate helpers move.
- Completeness: 10/10
- Pros: each word keeps one meaning; the marked row is the row needing action; clearing is
  structural (only a newer entry from X, or operator, ends staleness); the mandatory
  declaration is validated on write, not only linted.
- Cons: a fifth disposition every reader must treat as not-ok; more tests; a larger diff to the
  gate cluster one day after 1.1.0.
- Reuses: the `superseded_by_failure` annotation pattern in `reviews_for_plan`; the two "is it
  ok" lists (`OK_DISPOSITIONS` in `workflow-state`, `review_ok` in `_lib`), which exclude a new
  disposition by construction; `gate_state`, `failed_reason`, the skill lint's per-skill checks.

### Approach C: Re-run inline, by procedure (lateral)
- Summary: no gate change. A review that changes what X approved may not finish until it has
  handed off to a scoped re-run of X in the same session; the lint checks the step exists.
- Effort: S (human: ~half day / AI-assisted: ~1 h), about 6 files, skills and lint only
- Risk: Low to build, High to rely on
- Completeness: 4/10
- Pros: smallest; no helper changes; the re-review happens while context is fresh.
- Cons: a rule written into skills, which premise 1 says is not enough — an interrupted session
  leaves nothing behind. Loses the cross-model independence the reviews rely on.
- Reuses: skill completion sections, `tests/test_skill_lint.py`.

### 1. Declaring (`payload/bin/review-log`)

- Two dedicated flags: `--rereview <skill>`, repeatable, once per review that must run again,
  or `--rereview none`; and `--rereview-note "<what changed>"`. Stored as
  `"rereview": ["plan-eng-review"]` (or `[]`) and `"rereview_note": "…"`. Flags rather than
  `--field 'rereview=[…]'` because a JSON list inside shell quoting is where agents fumble.
  `--field` refuses `rereview` and `rereview_note` (one way in), and refuses the keys only the
  tool or the reader may set: `waives_ts`, `stale_by`, `stale_ts`, `stale_note`, `stale_count`,
  `demanded_by`, `concern_ts`, `was` (spec review 1: `rereview_note` was both reserved and required through `--field`). The
  positional-JSON form accepts `rereview` and `rereview_note`, is validated identically on the
  merged entry, and is refused when it carries any tool-or-reader key.
  **Eng review 2A (DRY):** this list and §2's strip list are one tuple,
  `_lib.READER_ONLY_KEYS = ("was", "stale_by", "stale_ts", "stale_note", "stale_notes",
  "stale_count", "demanded_by", "concern_ts")`; `review-log` imports it for the refusal and
  `reviews_for_plan` for the strip, and the refusal runs on the merged entry beside the
  existing `disposition` / `resolves_ts` checks so both input forms are covered by one rule.
  **Adversarial review:** `stale_notes` is on the list so a hand-appended copy cannot
  invent the older-demand list the scoped re-run reads.
  `waives_ts` leaves the list with the waiver (Eng review 1.0).
  **Eng review, tests gap 4:** on the merged entry `rereview` must be a list of strings and
  `rereview_note` a string; positional JSON carrying `"rereview": "plan-eng-review"`,
  `["none"]`, a non-string member, or a non-string note is refused (`[]` is the JSON spelling

- **Required** when `skill` is one of the four plan reviews and `status` is `clean` or

## Appendix: the deferred operator waiver
<!-- Eng review 1.0: moved here verbatim, not for 1.2.0. Starting point for the P3 TODO

Deferred by `/plan-eng-review` on 2026-09-17 (UTC), user decision. Three holes were found in
this design across two reviews, so whoever builds it should start from them: (1) a waiver
validated against demands but not against X's own state (spec review 2, two union-merge
timelines); (2) the same, second timeline; (3) **"any entry carrying `waives_ts`" is set
aside** — a waiver must be an entry whose status is exactly `resolved` *and* that carries
`waives_ts`; any other entry with that key is an ordinary run and the key is ignored
(eng review 1). Design it together with the operator-declared demand and the concern
acknowledgement (TODOS.md) so the three operator records share one entry shape.

### From §2 (deriving)

- **Waiver.** X's own `resolved` entry with `resolved_by=operator`, a `note`, and `waives_ts`.
  Spec review 2 broke the first version with two union-merge timelines — a waiver that cleared
  an `issues_open` nobody saw, and a waiver that turned a clean re-run into `failed` — because
  it was validated against demands but not against X's own state. So: **a waiver is never part
  of X's latest-entry computation.** Pass 1 sets waiver entries (any entry carrying
  `waives_ts`) aside; Pass 2 computes X's 1.1.0 disposition from the rest, exactly as today.
  Only when that reads `passed` or `resolved` are waivers consulted, and a waiver **counts**
  only when all hold: `resolved_by` is exactly `operator`; `waives_ts` **equals** the `ts` of a
  kept demand naming X (the writer sets it exactly, so the reader requires it exactly — a
  hand-appended `waives_ts` in the future cannot pre-waive demands that merge in later);
  `waives_ts >= last_run(X).ts`; and the waiver's own `ts >= waives_ts`. A counting waiver
  **covers every demand naming X with `D.ts <= waives_ts`**, which settles two demands sharing
  a timestamp; a demand later than `waives_ts` is outstanding even if its line sits before the
  waiver's. A waiver that does not count is **ignored**, never read as a failure: X falls back
  to the state beneath it. When a counting waiver is what makes X ok, X's returned copy is the
  waiver entry, so the row reads `resolved ✓` with `resolved_by=operator`. An entry carrying
  both `waives_ts` and `resolves_ts` is ignored the same way.
- **Several counting waivers** (spec review 3): the returned copy is the one with the greatest
  `waives_ts`, then the greatest `ts`, then the later line.
- **One accepted exception to "a tie fails closed"** (spec review 3): a demand that
  union-merges in with exactly the `ts` a waiver names is covered by that waiver although the
  operator never saw it. Covering by `<=` is what settles two demands written in one second;
  the price is this one-second window, and it is accepted.

### From §3 (waiving, `payload/bin/review-log`)

`--status resolved` today requires the target's latest disposition to be `failed`. It becomes
`failed` or `stale`. When `stale`: `resolved_by` must be exactly `operator` (any other value is
refused with `a re-review demand clears only when <skill> runs again, or by operator`),
`waives_ts` is filled from the newest outstanding demand (so one waiver covers every demand the
operator could see) and a caller-supplied one is rejected, and `resolves_ts` is absent. When the
target is `failed` and also has outstanding demands, the ordinary resolution rules apply
unchanged and write `resolves_ts` only; the review then reads `stale` and needs its own run or
a waiver. The CLI never writes both keys, and refuses a caller-supplied `ts` earlier than `waives_ts`,
the check it already makes for resolutions. The existing resolver check already refuses a stale
resolver by accident — it requires the resolver's disposition to be `passed` — and §8 pins
that with a test. The skill rule is unchanged: `operator` only when the user said in the
session that they decided it.

**The honest cost** (spec review 2): this gives `resolved` a second use — clearing a demand on a
review that passed — and "one word, two meanings" is why Approach A lost. It is accepted here
for two reasons: the alternative is a fifth status word one day after the vocabulary shipped,

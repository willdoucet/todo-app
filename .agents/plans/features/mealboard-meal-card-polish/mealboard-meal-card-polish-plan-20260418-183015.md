# Design: Food-item meal card — vertical icon-on-top + hover-expand action zone

## Problem Statement

Two unchecked tasks on `todo-app-notes/Mealboard/Todo List.md`, both targeting the food-item variant of `frontend/src/components/mealboard/MealCard.jsx` (lines 113-187):

1. **`mealboard-food-item-hover-expand`** — On hover, the food-item meal card should extend its bottom downward and reveal a centered "Mark cooked" + "Delete" button row, matching the recipe card pattern shipped on 2026-04-18 (Chunk 2 of `mealboard-meal-card-polish-plan-20260417-213900.md`). Today the food-item variant uses 24×24 absolute-positioned overlay buttons in the top-right corner — visually inconsistent with the recipe variant and harder to discover.

2. **`mealboard-food-item-icon-overlap`** — On the swimlane food-item card for "Sweet Potato", the absolutely-positioned `ItemIcon` at `left-2.5` visually covers the first letter of the centered title text, producing the read "icon weet Potato" instead of "Sweet Potato". User wants the icon centered *above* the title (vertical stack) and explicitly accepts the card growing taller as a result.

## What Makes This Cool

- **Visual rhythm across the swimlane.** Today's grid mixes horizontal pill (food items) with vertical card (recipes), which reads as two unrelated UIs sitting next to each other. After this change, every meal card on the board shares the same outer chrome and hover-expand action-zone pattern — body sizing remains variant-specific (52px food-item vs. 100px recipe) and button sizes scale with the body (24×24 vs. 32×32), but the gesture and structure are unified. The grid feels like one coherent design language.
- **The icon becomes the visual anchor.** Right now the icon competes with the title for horizontal space and loses (literally — it covers it). Putting the icon on top makes the sweet potato 🍠 actually read as a sweet potato, and turns the card into a glanceable "what is this" anchor instead of a text-first row.
- **Hover affordance discoverability.** Top-right floating icons require users to know they exist. The recipe card's "expand-on-hover" gesture is self-revealing — the card visibly grows, so the buttons feel like they emerged from the card itself.

### Error feedback spec (new, both variants)

Replaces today's silent `console.error` on `handleToggleCooked` and `handleDelete` failure. Minimal, accessible, non-blocking.

```jsx
const [lastError, setLastError] = useState(null)
const errorTimerRef = useRef(null)

const flashError = (kind) => {
  if (errorTimerRef.current) clearTimeout(errorTimerRef.current)
  setLastError(kind)
  errorTimerRef.current = setTimeout(() => {
    setLastError(null)
    errorTimerRef.current = null
  }, 3000)
}

// On success in both handlers: if (lastError) setLastError(null) — stale
// error vanishes immediately once the next request works.
// On failure: flashError(err?.response?.status === 404 ? 'gone' : 'retry')
// Retry-after-retry resets the 3s window so the latest error gets a full read.
// Cleanup: useEffect(() => () => clearTimeout(errorTimerRef.current), [])
```

**Render as a sibling of the action-zone div, not a child** (Eng Review Pass 1). Rendering the error inside the action-zone container would make it invisible on desktop when the user's mouse leaves the card before the 3-second timer expires — the action zone uses `overflow-hidden` + `max-h-0` and would slide shut while the error timer is still running. Safari macOS doesn't move focus to a button on click, so hover is the only thing keeping the zone open. Rendering the error outside the action zone decouples visibility from hover/focus state — it always shows for the full 3-second window regardless of pointer position. Visual ordering is unchanged (card body → action-zone buttons → error text below).

```jsx
{lastError && (
  <div
    role="status"
    aria-live="polite"
    className="px-2 pb-1.5 text-[11px] text-terracotta-600 dark:text-red-400 text-center"
  >
    {lastError === 'gone' ? 'This meal was already deleted.' : "Couldn't save — try again."}
  </div>
)}
```

Button remains enabled after the error (isWorking resets in `finally`), so retry is a single re-tap. No toast primitive introduced — intentional: toast is a larger design decision deferred to its own plan.

`aria-live="polite"` (not `"assertive"`) because failure is informational, not urgent — matches Nielsen heuristic "Help users recognize, diagnose, and recover from errors" without hijacking the screen reader queue.

Desktop failure behavior is intentionally asymmetric: after a failed click, the action zone may retract when hover ends, but the inline error must remain visible for the full 3-second window. A slight temporary height bump from the error text is acceptable; hiding the failure state is not.

### Hover/focus expand motion (decided)

During the 180ms expand, the icon+name body stays visually stable and only the action-zone `max-height` animates from 0 → 48px. This is what the `min-h-[52px]` body + separate action-zone div already produces — no additional transforms. Matches recipe variant exactly. Codified as §Interaction States behavior so a future implementer doesn't "improve" it by adding a translate animation.

### Local JSX helpers (Eng Review Pass 2 — DRY)

Two tiny JSX-only consts inside `MealCard.jsx` (not exported, not a new file). Replace the 4 duplicated button call sites and 2 duplicated error `<div>`s.

```jsx
// Above the MealCard component in MealCard.jsx:

function CardActionButton({ onClick, disabled, label, variant, size, children }) {
  // variant: 'cooked' | 'delete'  — inner chip color
  // size: 'sm' | 'md'             — 'sm' = food-item 24px chip, 'md' = recipe 32px chip
  const chipSize = size === 'sm' ? 'w-6 h-6' : 'w-8 h-8'
  const chipColor = variant === 'cooked'
    ? 'bg-sage-50 dark:bg-green-900/20 text-sage-600 dark:text-green-400 group-hover/btn:bg-sage-100 dark:group-hover/btn:bg-green-900/30'
    : 'bg-terracotta-50 dark:bg-red-900/20 text-terracotta-600 dark:text-red-400 group-hover/btn:bg-terracotta-100 dark:group-hover/btn:bg-red-900/30'
  return (
    <button
      type="button"
      onClick={onClick}
      disabled={disabled}
      aria-label={label}
      title={label}
      className="group/btn w-11 h-11 flex items-center justify-center rounded-full disabled:opacity-50 focus-visible:outline focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-terracotta-500 dark:focus-visible:outline-terracotta-400"
    >
      <span className={`${chipSize} flex items-center justify-center rounded-full transition-colors ${chipColor}`}>
        {children}
      </span>
    </button>
  )
}

function CardErrorFlash({ kind }) {
  if (!kind) return null
  return (
    <div
      role="status"
      aria-live="polite"
      className="px-2 pb-1.5 text-[11px] text-terracotta-600 dark:text-red-400 text-center"
    >

    </div>
  )

```

Both call sites for each helper become one-liners. 4 button sites × ~14 lines saved = ~56 lines removed; 2 error sites × ~7 lines saved = ~14 lines removed. Net: MealCard.jsx gets *shorter* after this PR despite adding functionality.

Tests: these helpers have no logic of their own — they're pure JSX rearrangements. Existing aria-label, w-11 h-11, role=status, and className tests still assert the same rendered output. No helper-specific unit tests needed.

### Touch targets & focus (Design Review Pass 6)

**Hit-area expansion pattern (both variants).** Visible circle keeps today's diameter (24×24 on food-item, 32×32 on recipe) to preserve visual weight. Outer `<button>` grows to 44×44 — WCAG 2.5.5 Level AAA — by wrapping the visible circle in a larger clickable area:

```jsx
<button
  type="button"
  onClick={handleToggleCooked}
  disabled={isWorking}
  aria-label={entry.was_cooked ? 'Mark as not cooked' : 'Mark as cooked'}
  title={entry.was_cooked ? 'Mark as not cooked' : 'Mark as cooked'}
  className="group/btn w-11 h-11 flex items-center justify-center rounded-full disabled:opacity-50 focus-visible:outline-2 focus-visible:outline focus-visible:outline-offset-2 focus-visible:outline-terracotta-500 dark:focus-visible:outline-terracotta-400"
>
  <span className="w-6 h-6 flex items-center justify-center rounded-full bg-sage-50 dark:bg-green-900/20 text-sage-600 dark:text-green-400 group-hover/btn:bg-sage-100 dark:group-hover/btn:bg-green-900/30 transition-colors">
    <svg className="w-3 h-3" fill="none" viewBox="0 0 24 24" stroke="currentColor" strokeWidth={2.5}>
      <path strokeLinecap="round" strokeLinejoin="round" d="M5 13l4 4L19 7" />
    </svg>
  </span>
</button>
```

- **Food-item variant:** inner span `w-6 h-6` (24 visible).
- **Recipe variant:** inner span `w-8 h-8` (32 visible), same 44×44 outer button — the existing recipe code is edited in the same PR to gain the hit-area wrapper. Justified by AAA compliance, not aesthetics.
- **Action zone height stays 48px** — `w-11 h-11` (44px) fits inside 48 with 2px of vertical breathing room. Two buttons + `gap-1.5` = 94px wide, fits in the narrowest swimlane column (~120px+ in practice).
- **`focus-visible` only** (not plain `focus`) — mouse clicks don't show an outline; keyboard tabs do. Matches native browser behavior and avoids distracting sighted mouse users.
- **`group/btn` scope.** Named group prevents the button's hover state from leaking into the outer `group` that drives the action-zone expand. Without the name, hovering the button would re-trigger the expand on the parent group (already true, but stable), and would also match any ancestor-scoped `group-hover:` class by accident.

**Error-text contrast.** `text-[10px]` (food-item) on `bg-card-bg` (#FFFDFB) with `text-terracotta-600` (#C4613F) measures ~4.5:1 — passes AA for normal text but marginal for 10px. Plan bumps the food-item error text to `text-[11px]` (from 10px) to comfortably clear the small-text threshold. Recipe variant stays at `text-[11px]` already.

**Long-name + icon visual test.** Browser-verify step adds an explicit colorblind / reduced-motion check: (a) toggle macOS Accessibility → Display → "Reduce motion" and confirm expand is instant; (b) open Chrome devtools → Rendering → emulate CSS `prefers-color-scheme: dark` and confirm contrast holds in dark mode (sage-600 → green-400, terracotta-600 → red-400 swaps on error text).

### Emotional arc storyboard

1. **Resting (5-sec visceral).** Grid reads as one coherent rhythm — every card shares the same outer chrome. Food-item cards are shorter than recipes, but the visual vocabulary (icon + centered name) is the same.
2. **Hover-in (behavioral).** Card's bottom edge drops 48px over 180ms. Two buttons fade in. The gesture tells the user "this card is interactive" without a hover-hint tooltip.
3. **Click mark-cooked.** Button briefly disables (`opacity-50`). On success: name strikes through, sage pulse. On failure: inline error text appears below buttons; button re-enables; retry is one tap.
4. **Hover-out.** Action zone retracts. Icon+name stay in place throughout — no jank.
5. **Reflective (5-year).** User stops noticing the card design; it feels like part of the app's vocabulary. The highest compliment a meal card can earn.

## Approaches Considered

### Approach A: Single chunk — pattern-port (RECOMMENDED)
One commit. Restructure the food-item variant block in `MealCard.jsx` from a single horizontal pill (icon-absolute-left, name-centered, buttons-absolute-top-right) to a vertical layout (`flex flex-col overflow-hidden`) with a centered body div and a hover-expand action zone underneath that mirrors the recipe variant's structure. Keep the existing food-item tests green, then add the new layout + handler assertions in `MealCard.test.jsx` in the same commit. Browser-verify at 1280px and 720px before reporting complete.

- **Effort:** S (≈25 min CC, ≈1 day human)
- **Risk:** Low. Pattern is already proven in production by the recipe variant (shipped today). No new primitives.
- **Pros:**
  - Both tasks ship together — no half-broken intermediate state
  - Test updates land with the implementation that breaks them
  - Browser verification covers both fixes at once
- **Cons:**
  - Larger single diff (≈70 lines changed in MealCard.jsx food-item block + ~30 lines of test changes)
- **Reuses:** Recipe variant's hover-expand class string verbatim; existing `ItemIcon` component; existing `MemberAvatar` component; existing `containerBase` + `containerColor` outer chrome.

### Approach B: Two chunks — icon fix → hover-expand
Chunk 1 fixes only the icon overlap by moving from horizontal-pill to vertical layout (icon on top, name below), but keeps the action buttons in the existing top-right overlay. Chunk 2 ports the hover-expand pattern. Two commits, two browser-verify rounds.

- **Effort:** M (≈40 min CC, ≈1.5 days human)
- **Risk:** Low. Same surface area as A.
- **Pros:**
  - Bug fix lands in isolation, easier to bisect if a regression appears
  - Each commit is small and self-contained
- **Cons:**
  - Intermediate state (post-Chunk 1, pre-Chunk 2) has icon-on-top layout with awkward absolute-positioned buttons floating in unfamiliar territory
  - Procedural overhead: two test passes, two browser verifications, twice the workflow ceremony for a ~25-min change
- **Reuses:** Same as A.

### Approach C: Extract shared `MealCardShell` primitive
Refactor recipe and food-item variants to both use a new `MealCardShell` component that owns the `flex flex-col overflow-hidden` outer chrome, the body div, and the hover-expand action zone. Variants pass `body` and `actions` slots as children.

- **Effort:** L (≈1 hr CC, ≈2 days human)
- **Risk:** Medium. New component contract; need to design slot props carefully; risk of subtle behavioral drift if the recipe variant's existing tests don't fully cover the shell's invariants.
- **Pros:**
  - Eliminates duplication — single source of truth for the body+action-zone pattern
  - Easier to add a third variant (e.g., custom-meal card) later
- **Cons:**
  - Premature abstraction — only two variants exist today; YAGNI
  - Requires regression-testing the recipe variant (which already shipped today and is known to work)
  - Doesn't change the user-visible outcome at all
- **Reuses:** Same as A.

## Recommended Approach

**Approach A — Single chunk, pattern-port.**

Reasoning:
- Both tasks touch the same 70-line JSX block; splitting them creates a worse intermediate state, not a better one.
- The recipe-variant pattern shipped *today* in production and is proven — copying it verbatim is the lowest-risk path.
- A future third variant (custom meals?) hasn't appeared in the year+ this codebase has existed; no signal that the abstraction in Approach C would pay off.

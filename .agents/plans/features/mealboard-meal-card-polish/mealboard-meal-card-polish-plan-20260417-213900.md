# Design: Mealboard Meal-Card Polish (hover expand, undo delete, metadata cleanup)

Generated by /office-hours on 2026-04-17

## Problem Statement

Five unchecked tasks in `todo-app-notes/Mealboard/Todo List.md` under "Meal Planner Page" — all UI polish on the swimlane-grid recipe cards:

1. **mealboard-card-hover** — Replace the overlaid hover action icons with an **expand-downward reveal**: on hover, the card grows vertically and the action buttons fade into the new space below. On hover exit, buttons fade out and card retracts. Snappy motion.
2. **mealboard-remove-recipe** — Remove the "view recipe" button from hover actions. The card body is already clickable to open the recipe drawer, so the button is redundant. Remaining hover buttons: Mark cooked + Delete.
3. **mealboard-undo-delete** — After deleting a recipe card, keep the grid slot occupied for 5 seconds with an in-place "undo" card. Click = restore. Timeout = the delete becomes permanent.
4. **mealboard-remove-n** — Drop the "n servings" label from the recipe card metadata row. Center-align the remaining cook-time icon + number.
5. **mealboard-row-day** — The row containing weekday name, date number, and prep-time-sum currently shows the text-edit I-beam cursor on hover (because text is selectable). Suppress it — this row isn't a text editor.

## What Makes This Cool

The hover-expand + in-place undo pattern is rare in weekly-planner UIs (Google Calendar shows a popover, Airtable shows a toolbar, Notion hides everything behind `···`). Expanding the card itself keeps the action physically attached to what it acts on — no hunting, no disconnect. Pairing it with an in-place undo means the deletion animation *becomes* the undo affordance. Nothing jumps; nothing teleports; the user's focal point stays on the slot they just touched.

## Constraints

- **No UI framework churn.** React 19 + Tailwind v4 only — no `framer-motion` or similar. Existing keyframes in `index.css` (`meal-card-enter`, `bounce-in`, `fade-in`) are the animation toolkit.
- **Respect `prefers-reduced-motion`.** Existing code gates animations on this (see `SwimlaneGrid.jsx` day-entrance animation). New animations must do the same.
- **Mobile behavior (≤768px viewport):** the hover-expand is desktop-only. On mobile, recipe cards render at their expanded height permanently, with buttons always visible in the dedicated action zone. Matches current mobile UX (buttons always visible) just in a structured zone rather than overlaid.
- **Docker-only dev loop.** All builds, tests, and lint commands run through `docker-compose exec`. No host-side `npm` or `uv`.
- **Bundled rollout.** One plan, 3 chunks, one PR — consistent with prior Mealboard polish rollouts.
- **Food-item pill variant unchanged.** Tasks #1 and #2 apply only to the vertical (recipe + custom-meal) variant. Food-item pills retain their top-right icon layout.

## Premises

1. **Meal entries gain user-initiated soft-delete.** A new `undo_token` column is added to `meal_entries`. `soft_hidden_at` now has **two writers** distinguished by `undo_token` presence: (a) cascade-hide from item delete (existing behavior, `undo_token IS NULL`) and (b) user-initiated 5-second undo window (new, `undo_token IS NOT NULL`). Read filter at `crud_meal_entries.py:35` already applies `soft_hidden_at IS NULL` — no audit of read paths required (verified).
2. **Undo appears in-place, not as a toast.** The existing `useUndoToast` is NOT reused visually. However, the backend `undo_token` plumbing pattern is reused verbatim.
3. **Hover-expand is desktop-only.** Mobile gets permanently-expanded cards with visible buttons.
4. **"Remove n servings" means delete entirely.** Not relocated. The metadata row becomes just the cook-time pill, centered.
5. **Text-cursor fix is a one-line CSS tweak** on the day-header container in `SwimlaneGrid.jsx` (`cursor-default` class). Not a symptom of a larger problem.
6. **Parent-item-cascade vs user-undo precedence:** if the parent item is soft-deleted (`items.deleted_at IS NOT NULL`) at the moment the user tries to undo, the undo returns 410 Gone. The entry is truly gone because its parent is gone.
7. **Undo is atomic compare-and-swap, not read-then-write** (Eng review #1 Issue 3A). `undo_delete_meal_entry` issues a single `UPDATE meal_entries SET soft_hidden_at=NULL, undo_token=NULL WHERE id=? AND undo_token=? AND soft_hidden_at > now() - interval '6.5 seconds' RETURNING *`. Zero rows → 410. One row → 200 + re-dispatch celery. Eliminates the cross-tab/cross-device double-undo race (which would otherwise dispatch `sync_shopping_list_add` twice and duplicate groceries). Parent-deleted check still happens via a separate read on `items.deleted_at` because joining adds complexity for marginal benefit.

## Chunk 2 — Hover-expand recipe card animation (#1)

**Mockup:** `./mockups/expanded-meal-card-option-y-seamless.html` (Seamless action zone — chosen via Design Review Step 8 over Subtle Divider (X) and Tinted Tray (Z); rationale is consistency with the existing food-item variant hover-reveal pattern at `MealCard.jsx:148-181`, and subtraction-default — no new chrome where the existing hover shadow + border highlight already do the job).

**Scope:**
- `frontend/src/components/mealboard/MealCard.jsx` — recipe variant only (the second `return` block, identified by `flex flex-col items-center justify-center text-center px-2 py-3 min-h-[100px]`):
  - Current: card is `min-h-[100px]` with buttons `absolute bottom-2 left-1/2 -translate-x-1/2` overlaid on the card.
  - Target: card body holds its content at `min-h-[100px]`; an **action zone** below the body is collapsed at rest and expands to ~40px on hover. Buttons live inside the action zone (not absolute-positioned), horizontally centered.
  - Hover exit: action zone collapses back, buttons fade out.
- **Animation mechanism: commit to `max-height` transition** (not `grid-template-rows`). Rationale: grid-template-rows animation has Safari <16 bugs with `min-h-*` children — not worth the risk for this small gain. Use `max-h-0 overflow-hidden` collapsed, `max-h-[48px]` (or generous ceiling) expanded. Known caveat: max-height transitions ease to a ceiling, not content-height, so the motion is not perfectly linear — acceptable for a 180ms animation.
- Motion parameters: `transition-[max-height] duration-180 ease-out` on the action zone, `transition-opacity duration-120 delay-60` on the buttons inside. Retract mirrors (no delay).
- **Gate on `prefers-reduced-motion`**: when reduced, no `transition-*` classes applied — state changes are instant. Implement via `motion-reduce:transition-none` Tailwind modifier.
- **Mobile:** on `<md` viewports, the action zone is permanently expanded. Tailwind: base classes `max-h-[48px]` (always open); `md:max-h-0 md:group-hover:max-h-[48px] md:group-focus-within:max-h-[48px]` for desktop behavior.
- **Cooked badge ("✓ Cooked")** currently sits in the same vertical stack as the buttons. In the new layout, the badge stays in the card body (above the action zone); verify no overlap with the expanded zone.
- **Focus management:** keyboard Tab onto the card or its buttons expands the action zone via `md:group-focus-within:max-h-[48px]`. Preserves keyboard accessibility.
- **Scratch verification before finalizing:** spike the `max-h` approach in a throwaway component first in Safari + Chrome + Firefox. If Safari has visible flicker on the `overflow-hidden` clip during transition, fall back to opacity-only (no height animation) and document it as an open limitation.

**Success criteria:**
- Hovering a recipe card on desktop: card grows downward, buttons fade in within 200ms. No layout jump elsewhere on the grid.
- Hover exit: card retracts symmetrically. No flicker.
- Tabbing to the card (or a button inside it) triggers the same expansion.
- Mobile viewport: card is always expanded, buttons always visible.
- `prefers-reduced-motion: reduce` → no transition, just opacity toggle.
- Cooked badge remains visible in both states. No overlap with action zone.
- Clicking the body still opens the recipe drawer. Clicking the Cooked/Delete buttons still does their thing.

## Chunk 3 — Undo delete (#3)

### Backend

**Migration** (new Alembic revision):
- Add `undo_token VARCHAR(64) NULL` to `meal_entries` (indexed for lookup).
- `soft_hidden_at` column already exists — reuse.
- Partial index on `undo_token WHERE undo_token IS NOT NULL` for fast lookup.

**Changes to** `backend/app/crud_meal_entries.py`:
- `delete_meal_entry(db, entry_id)` currently hard-deletes. Change it to:
  1. Generate `undo_token` (uuid4 hex).
  2. Set `soft_hidden_at = now()`, `undo_token = <token>`.
  3. **Still dispatch `sync_shopping_list_remove.delay()`** — groceries leave the shopping list immediately on soft-delete (per CEO review Issue 1.1, option A).
  4. Add structured log: `logger.info("soft_delete meal_entry_id=%s undo_token=%s", entry_id, token[:8])`.
  5. Return `{entry: <updated>, undo_token: <token>, expires_at: <iso8601>}`.
- Add `_find_entry_for_undo(db, entry_id)` helper: queries by ID **without** the `soft_hidden_at IS NULL` filter (the undo endpoint must see hidden rows). Docstring must explicitly state this is the one intentional exception to the `visible_meal_entries_stmt()` convention.
- Add `undo_delete_meal_entry(db, entry_id, token)` — **atomic compare-and-swap, not read-then-write** (Eng review #1 Issue 3A; see premise 7):
  1. Pre-flight read: `_find_entry_for_undo` to detect 404 (entry never existed) vs 410 (expired or parent gone). If parent `item.deleted_at IS NOT NULL` → 410 reason=parent_deleted (per premise 6). This read is informational only — it does NOT decide whether to flip the row.
  2. Atomic flip: single statement
     ```
     UPDATE meal_entries
        SET soft_hidden_at = NULL, undo_token = NULL
      WHERE id = :entry_id
        AND undo_token = :token
        AND soft_hidden_at > now() - interval '6.5 seconds'
     RETURNING *
     ```
     The `> now() - 6.5s` window matches CEO review Issue 2.2 (5s client + slack). Zero rows returned → 410 (token_mismatch OR expired OR already-undone in a concurrent request). One row → success.
  3. Only on a successful flip: re-dispatch `sync_shopping_list_add.delay(entry_id)`. Wrap in `try/except kombu.exceptions.OperationalError` mirroring `delete_meal_entry` at line 204 — on Kombu failure, log warning and continue; user-visible entry is still restored.
  4. Structured logs: `logger.info("undo_success meal_entry_id=%s within_s=%s", entry_id, elapsed)` on success; `logger.info("undo_failed meal_entry_id=%s reason=%s", entry_id, reason)` on 404/410 (reason ∈ {not_found, token_mismatch, expired, parent_deleted}). Include only the first 8 chars of the token in logs.
  5. Return restored entry.
  6. Raise 404 if not found, 410 Gone if expired/token-mismatch/parent-deleted/race-lost.

  **Why atomic CAS:** without it, two concurrent undo requests (e.g. same user on phone + laptop, or rapid double-click that escapes the UI guard) both read the soft-hidden row, both validate the token, both write the cleared state, both return 200 — and `sync_shopping_list_add` fires twice, leaving duplicated groceries on the shopping list. The single-statement `UPDATE … WHERE undo_token = ?` makes Postgres pick exactly one winner. The H8 TODO in `.claude/TODOS.md` is the same module's documented history of shopping-sync race bugs; this avoids replaying that pattern.

**Update `update_meal_entry` (`crud_meal_entries.py:144`):**

A PATCH on a soft-hidden entry already returns 404 today. No code change needed. (CEO review Issue 5.1 — the original plan §155 proposed a redundant guard.)

The `_find_entry_for_undo` helper is the ONLY function that reads bypassing the filter — it must check `undo_token IS NOT NULL` to distinguish user-undo rows from cascade-hidden rows it must not touch.

**Hard-delete sweeper update** (pinned locations):
- Existing sweeper: `backend/app/tasks.py:569-619` (`hard_delete_expired_soft_deletes`), invoking `crud_items.hard_delete_expired_soft_deletes_async` at `backend/app/crud_items.py:28-75`.

### Frontend

**State ownership: `MealPlannerView`** (Eng review #1 Issue 1A) — NOT SwimlaneGrid. `MealPlannerView.jsx` is the actual owning component in the current codebase; do not invent a parallel `MealPlannerPage` wrapper just for undo state. Rationale: SwimlaneGrid is data-driven by the week's entries, so it remounts/refreshes on week navigation. Hoisting the pendingDeletes state one level up to `MealPlannerView` means the Map's lifecycle is tied to "user is on the meal-planner page" rather than "user is viewing this specific week." On week navigation, `MealPlannerView` runs an effect that clears pendingDeletes AND calls `clearTimeout` on every active timer (the user has navigated away from the slot they touched, so the in-place undo affordance is gone — backend soft-delete is already committed; data is consistent).

- Add local state in `MealPlannerView`: `pendingDeletes: Map<entryId, { entry, expiresAt, undoToken, timerId }>`. Using Map preserves insertion order.
- **Never mutate the Map in place.** Every add/remove/clear must clone (`new Map(prev)`) inside `setPendingDeletes(...)`; mutating the existing Map risks stale renders and stale cleanup closures.
- Pass `pendingDeletes` and the `onMealDeleted(id, undoToken, entry)` / `onUndo(id)` handlers down to both render paths:
  - desktop: `SwimlaneGrid` → `LaneCell`
  - mobile: `MobileDayView` → slot section list
- While touching `MobileDayView`, thread `onViewRecipe` through that path too so the "card body opens the recipe drawer" invariant matches desktop instead of silently regressing on `<768px`.
- On `onMealDeleted(id, undoToken, entry)` from `MealCard`, don't remove the entry from the list. Instead add to `pendingDeletes` with the captured `undo_token` and `entry` snapshot, start a 5s timer. Store the timer ID.
- When timer fires: remove entry from list and remove from pendingDeletes (it's already soft-hidden backend-side, sweeper will finish it within ~1 hour).
- When user clicks undo: call `POST /meal-entries/{id}/undo` with token, clear pending-delete state (including `clearTimeout(timerId)`), entry becomes live again in the list.
- **Cleanup on unmount:** `useEffect` cleanup iterates `pendingDeletes` and calls `clearTimeout(timerId)` for each. Prevents setState-on-unmounted warnings when user navigates away mid-window.
- **Cleanup on week navigation** (Eng review #1 Issue 1A): `useEffect` keyed on `currentWeek` (or whatever date prop drives the grid) runs cleanup on every change — clears all timers AND empties pendingDeletes. The backend delete is already committed, so this only forfeits the user's undo opportunity, never their data.
- **On 410 response from undo** (expired / token mismatch / parent item deleted): show a brief toast ("Too late — already deleted") and leave the entry removed from the list.

### Edge cases to verify

- **Rapid delete + navigate away:** user deletes a card, navigates to next week within 5s. Timer fires while component is unmounted. The delete was already soft-committed backend-side, so data is consistent; sweeper purges. But the undo opportunity is gone — document this.
- **Delete + immediate page reload:** soft-delete is backend-committed, entry doesn't appear on reload, sweeper eventually purges. Acceptable.
- **Delete + immediate edit of the same entry:** edit endpoint should respect `soft_hidden_at IS NULL` filter — an edit on a soft-hidden entry should 404 (treat as deleted).
- **Two users in same family delete same entry simultaneously:** first DELETE returns 200 with token, second DELETE finds the entry already soft-hidden. **Decision (CEO review Issue 4.2): return 404 Not Found** on the second DELETE — this is the natural behavior of `get_meal_entry`'s existing `soft_hidden_at IS NULL` filter. No extra code needed; matches "someone else deleted it" semantics.
- **Parent item deleted during user's undo window:** if item.deleted_at gets set while an entry is in its 5s undo window, cascade-hide is a no-op (entry is already soft-hidden) but the 410-on-parent-deleted check in `undo_delete_meal_entry` ensures the user can't restore an orphan.
- **Same slot, rapid consecutive deletes (delete A, then delete B 2s later):** pendingDeletes Map preserves insertion order. LaneCell renders UndoMealCards in the order they were added. Each has its own independent timer.

Both directions degrade gracefully.

# Design: M3 — prod-auth-backend-foundation

Generated by /office-hours on 2026-05-01
Branch: prod-auth-backend-foundation
Status: APPROVED
Mode: Builder

## Problem Statement

The Family Hub app currently has **no first-party auth**. Every backend route is unauthenticated, and production is held together by a Cloudflare Access edge gate (provisioned in M2) that lets exactly one operator email through. That gate is a temporary scaffold — it can't issue per-request identity, can't be rotated by the operator, and exists only because there was nothing else.

M3 builds the **backend** of the real auth system. Frontend (M4) and route-enforcement-with-edge-gate-removal (M5) follow in subsequent milestones. By the end of M3, the backend can:

- Create the single shared household account (gated by `HOUSEHOLD_ACCESS_KEY`)
- Authenticate that account with email + password
- Mint and rotate JWT access + HttpOnly refresh tokens
- Revoke all sessions immediately on operator password rotation
- Expose a status endpoint the M4 portal can use to know whether to show "Create account"

No existing routes are protected yet. The Cloudflare Access edge gate stays load-bearing through M3 → M5.

## What Makes This Cool

This is the milestone where the app stops being "behind a firewall" and starts being **trustworthy from the inside**. Every M3 design choice — argon2id at OWASP defaults, refresh-token hashes at rest, the 60-second rotation grace window, byte-identical error responses to defeat enumeration, session-version revocation that doesn't need Redis — is the kind of detail that separates "a login form" from "auth you would let your family use." Most solo apps cut corners here. This one doesn't.

## Constraints

- **Locked architecture (from contract-freeze plan):** PyJWT ≥ 2.8, HS256, 15-min access TTL, 30-day refresh TTL, `__Host-refresh` cookie (HttpOnly, Secure, Path=/, no Domain), argon2-cffi defaults, SHA-256 refresh-token hash at rest, 60s rotation grace window, `hmac.compare_digest` for access-key compare, byte-identical error responses for enumeration-prone failure pairs, session-version column read on every protected request.
- **Async SQLAlchemy throughout** (Eng review 1): codebase is fully async (`AsyncSession`, `await db.execute(select(...))`, `result.scalar_one_or_none()`). Auth code MUST follow this pattern; sync `db.query(...)` style is forbidden. Reference: `backend/app/crud_lists.py` and `backend/app/database.py`.
- **No frontend work in M3.** Auth dependencies exist but are not applied to existing routes.
- **No Redis cache for session-version.** DB column read is the design (Eng review 3).
- **Migration must be backward-compatible.** Old image code must still boot if the migration has already run (it will — the existing app simply ignores the new tables).
- **All app commands run through Docker Compose.** No direct `uv` / `pytest` / `alembic` on the host.
- **Single shared login per deployment.** Multi-user is explicitly v1.1+.
- **Fly `web` VM memory ≥1 GB** (Eng review issue 3): argon2 OWASP defaults consume 64 MiB per concurrent hash. Sustained hashing on a 256 MB shared-cpu-1x VM will OOM. Verify via `fly scale show --app <app>` before merging M3; if the VM is smaller, scale up via `fly scale memory 1024 --process-group web` (~$3-5/mo extra over baseline). Cloudflare's active `/auth/*` WAF rule limits per-IP burst (see `infra/cloudflare-state.md` for the exact free-tier rule), but distributed bursts are still possible.
- **Auth secrets fail closed (Adversarial review; criteria pinned by Eng review 2):** `JWT_SECRET_KEY` and `HOUSEHOLD_ACCESS_KEY` are required runtime config, not optional strings. Tests may override through the auth config helper, but production code must never silently substitute a default. Production startup MUST fail if any of the following hold for either secret:
   1. The variable is unset / `None`.
   2. The value, after `.strip()`, is empty.
   3. (`JWT_SECRET_KEY` only) `len(value) < 32`.
   4. The lowercased value contains any of: `"changeme"`, `"change-me"`, `"your-secret"`, `"your_secret"`, `"placeholder"`, `"example"`, `"replace-me"`, `"replace_me"`, `"todo"`, `"default"`, `"insecure"`, `"test-key"`, `"test_key"`. Substring match is intentional — a base64 secret happening to contain `"todo"` as a substring is astronomically unlikely; a placeholder slipping through is the realistic failure.
  
  Each rule above maps to its own assertion in `tests/unit/auth/test_config.py`.
  Config validation MUST NOT run at module import time. Production startup/lifespan validates the required auth config once, endpoint/service code reads config through the auth config helper, and tests override that helper without reading process env. Local/dev Docker may use explicit dev-only values in `.env`, but production must never fall back to built-in defaults.
- **Login rotation is same-client only (Adversarial review):** successful `/auth/login` may revoke the refresh token presented by that same request's `__Host-refresh` cookie, but MUST NOT revoke every active refresh token for the shared account. A household login should work on multiple devices unless the operator explicitly logs out or rotates the password.
- **Direct Fly origin bypass is blocked (Adversarial review run 2):** Cloudflare Access and the `/auth/*` WAF rule are load-bearing until M5, so production must not allow callers to bypass Cloudflare by hitting `*.fly.dev` directly. Add an app-level production host gate before auth/business routes: `/healthz` remains reachable for Fly checks, but every other backend path rejects requests whose `Host` is not the configured public API host (for example `api.mealy.dev`). Do not allow `mealy-app-prod.fly.dev` for browser/API traffic.

## Premises (confirmed in office-hours session 2026-05-01)

1. Scope is M3 only. Auth dependency helpers exist but are NOT applied to existing routes. Cloudflare Access edge gate remains load-bearing through M3-M5.
2. Single shared login per deployment — `users` table will only ever have 0 or 1 rows in v1.
3. No Redis cache for session-version. Per-request DB lookup is the design.
4. The beginner-friendly devops writeup is part of the M3 deliverable, committed in this PR, lives in `todo-app-notes/DevOps/`.
5. Test runtime is allowed to grow. Argon2 is intentionally slow; tests will use a fast-test profile via dependency override (production code path uses OWASP defaults).

## Approaches Considered

### Approach A: New `app/auth/` package + normal `users` table with `UNIQUE(email)` (RECOMMENDED — chosen)

**Summary:** Self-contained auth package alongside the existing flat layout. Standard `users` table with `UNIQUE(email)` enforces singleton via the register handler. Clear security surface; one place to audit.

- **Effort:** M
- **Risk:** Low
- **Pros:** Auth is the right place to break flat convention — every auditor expects to find auth code in one folder. Easy to evolve to multi-user in v1.1+ without a schema migration. Aligns with the "single security surface" pattern seen in mature FastAPI codebases.
- **Cons:** First package-shaped subsystem in this codebase. Requires registering the package's models with the shared `Base.metadata` so Alembic autogenerate sees them.
- **Reuses:** Shared `Base = declarative_base()` from `app/models.py`. Existing pytest fixtures + testcontainers infra. Existing Alembic migration pipeline. Existing `app/database.py` session factory.

### Approach B: Flat layout matching existing convention + same `users` table

**Summary:** `app/routes/auth.py`, `app/crud_auth.py`, `app/services/auth_service.py`, `app/utils/passwords.py`, `app/utils/tokens.py`. Auth logic is added to the existing `models.py` and `schemas.py`.

- **Effort:** M
- **Risk:** Low-Med
- **Pros:** Zero deviation from existing codebase convention. No package boundary to maintain.
- **Cons:** Auth logic spreads across 6+ existing files. `models.py` is already 500+ lines; adding auth pushes it past 600. No single audit surface — security review has to chase imports across the tree. The "where does the password get hashed?" question requires a grep, not a `cd`.
- **Reuses:** Same as Approach A.

### Approach C: New `app/auth/` package + `users_singleton` table with `CHECK (id = 1)`

**Summary:** Same package layout as A, but the schema-level constraint is "row id must equal 1" — making singleton enforcement structural rather than behavioral.

- **Effort:** M
- **Risk:** Low
- **Pros:** Self-documenting at the schema level. Impossible to misuse from raw SQL.
- **Cons:** One-way door. Evolving to multi-user in v1.1+ requires a real schema migration (drop CHECK, possibly rename table). The constraint also doesn't actually prevent multiple users — it just pins the single row to id=1 — so the "no second user" check still has to live in the register handler. The structural benefit is partly cosmetic.
- **Reuses:** Same as A and B.

## Recommended Approach

**Approach A** — `app/auth/` package + normal `users` table with `UNIQUE(email)`.

**Rationale:** Auth is the natural place to introduce a package boundary in this codebase. The audit surface argument outweighs convention-consistency. UNIQUE(email) is the right fence: it enforces "no duplicate accounts" at the schema level (the only actually-dangerous outcome), and lets the register handler enforce "no second account at all" at the application level — exactly where that policy lives. Approach C's CHECK constraint is partly cosmetic (you still need the handler check) and trades evolvability for self-documentation.

## Database Schema

### Singleton registration invariant (Adversarial review run 2)

The `UNIQUE(email)` constraint prevents duplicate emails, but it does **not** by itself enforce the v1 "0 or 1 users total" policy. `POST /auth/register` MUST acquire a transaction-scoped PostgreSQL advisory lock before checking whether any user exists and before inserting the user/refresh token. The check + user insert + refresh-token insert commit in one transaction.

Recommended lock shape: `SELECT pg_advisory_xact_lock(hashtext('auth_register_singleton'));`. The exact lock key can differ, but it must be stable, transaction-scoped, and shared by every registration attempt. The concurrent-register test must use two different emails so it proves singleton enforcement rather than only `UNIQUE(email)`.

### `users` table

| Column            | Type                       | Constraints                                              |
|-------------------|----------------------------|----------------------------------------------------------|
| `id`              | `BIGSERIAL` PK             |                                                          |
| `email`           | `CITEXT` (case-insensitive) | `NOT NULL`, `UNIQUE`                                     |
| `password_hash`   | `TEXT`                     | `NOT NULL` (argon2-cffi PHC string)                      |
| `session_version` | `INTEGER`                  | `NOT NULL`, `DEFAULT 0`                                  |
| `created_at`      | `TIMESTAMPTZ`              | `NOT NULL`, `DEFAULT NOW()`                              |
| `updated_at`      | `TIMESTAMPTZ`              | `NOT NULL`, `DEFAULT NOW()`, app-managed via SQLAlchemy `onupdate=func.now()` |

Note: `CITEXT` requires `CREATE EXTENSION IF NOT EXISTS citext;` in the migration. **Pre-flight check: run `SELECT * FROM pg_available_extensions WHERE name='citext';` against the Fly Postgres instance before writing the migration.** If unavailable, fall back to `TEXT` + a `CHECK (email = lower(email))` constraint and lowercase at the application boundary.

**Caveat on the fallback:** `UNIQUE` on plain `TEXT` is case-sensitive. The CHECK constraint guarantees no row stores a non-lowercase email, so combined with always-lowercasing on insert, case-sensitive UNIQUE is functionally equivalent to case-insensitive UNIQUE. This is acceptable for the singleton table (only ever 0-1 rows) but is a weaker fence than CITEXT — flag it during code review so nobody assumes the schema alone protects against `Foo@x.com` vs `foo@x.com` collisions if the application boundary is bypassed.

### `refresh_tokens` table

| Column           | Type             | Constraints                                                            |
|------------------|------------------|------------------------------------------------------------------------|
| `id`             | `BIGSERIAL` PK   |                                                                        |
| `user_id`        | `BIGINT`         | `NOT NULL`, `REFERENCES users(id) ON DELETE CASCADE`                   |
| `token_hash`     | `BYTEA`          | `NOT NULL` (32-byte SHA-256)                                           |
| `successor_id`   | `BIGINT`         | `NULL`, `REFERENCES refresh_tokens(id) ON DELETE SET NULL`, `use_alter=True` (Eng review 1) — set when this row is rotated; points to the new row that replaced it |
| `issued_at`      | `TIMESTAMPTZ`    | `NOT NULL`, `DEFAULT NOW()`                                            |
| `expires_at`     | `TIMESTAMPTZ`    | `NOT NULL`                                                             |
| `superseded_at`  | `TIMESTAMPTZ`    | `NULL` (set when rotated; +60s grace before reject)                    |
| `revoked_at`     | `TIMESTAMPTZ`    | `NULL` (set on logout, password rotation, or login-rotation)           |

**Indexes:**
- `CREATE UNIQUE INDEX ix_refresh_tokens_token_hash ON refresh_tokens(token_hash);`
- `CREATE INDEX ix_refresh_tokens_user_id ON refresh_tokens(user_id);`
- `CREATE INDEX ix_refresh_tokens_successor_id ON refresh_tokens(successor_id) WHERE successor_id IS NOT NULL;` (debug/chain-inspection helper; live traversal still follows primary-key lookups by row id)

**Why `successor_id` exists:** The 60-second rotation grace window has to be able to find the **current** valid token in the chain when an already-rotated cookie arrives. Without this column there is no way to traverse from "the cookie the client sent" to "the row that's actually live now."

**Refresh rotation concurrency invariant (Adversarial review):** The service MUST lock the incoming refresh-token row with `SELECT ... FOR UPDATE` before branching into Case A/B/C. Two simultaneous refreshes with the same fresh cookie must serialize so exactly one request performs Case A; the second waits, observes `superseded_at`, and follows Case B. Case B successor traversal must also lock each successor row with `SELECT ... FOR UPDATE` before evaluating `revoked_at`, `expires_at`, `superseded_at`, or `successor_id`. This serializes Case B against logout/password-rotation revocation: either the refresh wins before revocation commits, or revocation wins and refresh returns 401. Without these locks, refresh can mint from a terminal row that was revoked concurrently.

**No IP/user-agent columns in v1.** Single-user household; not useful for security analytics at this scale.

### Migration backward-compat

The migration only **adds** new tables (and the `citext` extension if available). Existing app code never references `users` or `refresh_tokens`. Old image code (post-migration but pre-deploy) continues to boot and serve. M3 verification includes deploying the migration, then booting the previous image against the migrated DB to confirm.

**Downgrade:** `op.drop_table("refresh_tokens")` then `op.drop_table("users")`. Do **not** drop the `citext` extension on downgrade (Adversarial review): the extension may have pre-existed in the database or be reused by future tables, and leaving an extension installed is safer than breaking unrelated schema objects during rollback.

**Production rollback note (Adversarial review run 2):** Code rollback is the default M3 rollback. Redeploy the previous image and leave `users`, `refresh_tokens`, and `citext` in place so claimed-account state is not destroyed. Run Alembic downgrade only if intentionally abandoning M3 auth state after taking a backup. The old-image smoke must cover a migrated DB **after** at least one user and refresh-token row exist, not just empty auth tables.

## JWT Payload Schema

Access tokens are JWTs (HS256). Refresh tokens are **opaque random bytes** (`secrets.token_urlsafe(32)`) — they are NOT JWTs and carry no embedded claims; their identity is the SHA-256 hash row in `refresh_tokens`.

**Access token claims:**
```json
{
  "sub": "<user_id as string>",
  "iat": 1730000000,
  "exp": 1730000900,
  "session_version": 0
}
```

- `sub`: user PK as string (per JWT spec)
- `iat` / `exp`: standard timestamps; `exp = iat + 900` (15 min)
- `session_version`: snapshot of `users.session_version` at issue time. The auth dependency compares this against the live DB value on every request.
- **`iss` / `aud`: not used in v1.** Single-deployment, single-issuer; no multi-audience use case.
- **`jti`: not used in v1.** Access-token revocation is via `session_version` bump, not a per-token blocklist.
- **Key rotation:** v1 has no `kid` header or dual-key support. Rotating `JWT_SECRET_KEY` means restart-with-new-secret invalidates every issued access token immediately. Acceptable for a single-operator household; intentional.

The `__Host-refresh` cookie set by `/auth/login`, `/auth/register`, and `/auth/refresh`:

| Attribute   | Value                                                         |
|-------------|---------------------------------------------------------------|
| Name        | `__Host-refresh`                                              |
| Value       | `secrets.token_urlsafe(32)` — opaque                          |
| HttpOnly    | `true`                                                        |
| Secure      | `true`                                                        |
| Path        | `/`                                                           |
| Domain      | **omitted** (host-only on `api.mealy.dev`)                    |
| Max-Age     | `2592000` (30 days)                                           |

Reject requests whose `Origin` is not in `CORS_ALLOW_ORIGINS`. Skip this if `SameSite=Lax` survives the matrix.

## Endpoint Contracts

All endpoints under `/auth/*`. CORS already configured by M2. Cloudflare's active `/auth/*` WAF rule covers this prefix; verify the exact rule against `infra/cloudflare-state.md` during pre-deploy because the free-tier rule shape can differ from the original 10/minute target.

**Status code policy:** All M3 endpoints return `HTTP 401 Unauthorized` on any auth-related failure, with byte-identical response bodies for paired enumeration-prone failures. 401 is the correct semantic for "credentials/access-key not accepted" and avoids the 403 "authenticated but forbidden" misnomer for what is fundamentally a public endpoint with credential checks. The contract-freeze rule is "same status across paired failures" — picking 401 for all auth-related failures satisfies that and is uniform across login/register/refresh.

Validation failures that are not auth decisions may still return `422` (for example, `/auth/register` password length >128). `/auth/login` is the exception: overlong, malformed, unknown-email, and wrong-password attempts all map to the same `401 {"detail": "invalid_credentials"}` and log `reason=bad_credentials`, so login cannot become a timing or response-shape oracle. The byte-identical register guarantee applies after request-body validation; malformed JSON/body shape may still be FastAPI/Pydantic `422`.

**Success statuses are pinned (Adversarial review run 2):**
- `POST /auth/register` → `200 OK`
- `POST /auth/login` → `200 OK`
- `POST /auth/refresh` → `200 OK`
- `POST /auth/logout` → `204 No Content`
- `GET /auth/status` → `200 OK`

### `POST /auth/register`

**Request body:**
```json
{ "email": "string", "password": "string", "access_key": "string" }
```

**Behavior:**
- Load `HOUSEHOLD_ACCESS_KEY` through `app/auth/config.py`; missing/blank/placeholder values fail closed before request handling in production.
- `hmac.compare_digest(access_key.encode("utf-8"), HOUSEHOLD_ACCESS_KEY.encode("utf-8"))` — constant-time compare. **Both inputs encoded to bytes** to avoid `compare_digest` raising on mixed types.
- Acquire the singleton registration advisory lock in the same transaction that checks for an existing user and inserts the user/refresh-token rows. See "Singleton registration invariant."
- If `users` table has any row → reject. Same HTTP status + JSON body as wrong-access-key case.
- Validate `password` length ≤ 128 chars (argon2 hard limit) → 422 if longer.
- Hash password with the injected `PasswordHasher` (production = OWASP defaults).
- `INSERT INTO users` — catch `IntegrityError` (race), return same generic-failure response.
- Generate access token (15 min, with `session_version: 0`).
- Generate refresh token via `secrets.token_urlsafe(32)`. Store `sha256(token_bytes)` in `refresh_tokens(token_hash)`.
- Set `__Host-refresh` cookie with the plaintext token (attributes per "Cookie Attribute Set" above).
- Return access token in response body: `{ "access_token": "...", "token_type": "bearer" }`.

**Failure responses (byte-identical — same HTTP status AND same body):**
- Wrong access key
- Account already exists
- Concurrent register race (loser)

All return: `HTTP 401`, body `{"detail": "registration_unavailable"}`.

### `POST /auth/login`

**Request body:**
```json
{ "email": "string", "password": "string" }
```

**Behavior:**
- Lookup user by email. **Always** call `password_hasher.verify(...)` on either the real hash OR a lazy-cached dummy hash if user not found — prevents timing oracle. The dummy hash is generated once on first cache-miss using the **same `PasswordHasher` instance** that's currently injected (so production-vs-test parameter mismatch can't leak timing). Cache lives in module scope and is invalidated when the hasher dependency changes.
- **Argon2 exception handling (Eng review 1):** wrap the `verify()` call to catch `argon2.exceptions.VerifyMismatchError`, `argon2.exceptions.VerificationError`, AND `argon2.exceptions.InvalidHashError`. All three map to the same byte-identical 401 response and log `reason=bad_credentials`. Distinguishing in logs would defeat enumeration defense.
- On success (entire success block runs in a single transaction — **Eng review 2:** either the revoke + new-row insert both commit or neither does; one `await db.commit()` at the end of step 4):
  1. **Same-client login rotation (Adversarial review):** if the request includes a `__Host-refresh` cookie and its SHA-256 hash matches a non-revoked refresh token for this same user, set only that row's `revoked_at = NOW()` before issuing the new token. If the cookie is absent, unknown, expired, already revoked, or belongs to no row for this user, ignore it and continue login. Do **not** revoke other active refresh tokens for the user; successful login from device B must not silently log out device A.
  2. Mint access token (with current `session_version`).
  3. Mint + persist new refresh token (new `refresh_tokens` row, no successor, fresh issued_at/expires_at).
  4. Set `__Host-refresh` cookie.
  5. Return access token in body.
- On any failure: same response.

**Failure response (byte-identical — same HTTP status AND same body):**
- Unknown email
- Wrong password

Both return: `HTTP 401`, body `{"detail": "invalid_credentials"}`.

### `POST /auth/refresh`

**Request:** No body. Reads `__Host-refresh` cookie.

**Behavior:**

1. Read `__Host-refresh` cookie. Compute `incoming_hash = sha256(cookie_bytes)`.
2. `SELECT * FROM refresh_tokens WHERE token_hash = incoming_hash FOR UPDATE`. If not found → reject with the uniform 401 / `refresh_failed` response defined below. The row lock is required; see the database-schema concurrency invariant above.
3. **Reject if `revoked_at IS NOT NULL`.** (Logout, password rotation, or login-rotation killed it.)
4. **Reject if `expires_at < NOW()`.** (Natural 30-day expiry.)
5. **Branch on `superseded_at`:**

   **Case A — Fresh token (`superseded_at IS NULL`):** This is the normal happy path.
   - INSERT a new `refresh_tokens` row with a fresh `secrets.token_urlsafe(32)` value, its SHA-256 hash, fresh `issued_at`, `expires_at = NOW() + 30 days`, `successor_id = NULL`.
   - UPDATE the current row: `superseded_at = NOW()`, `successor_id = <new row id>`.
   - Set new `__Host-refresh` cookie with the new plaintext token.
   - Mint new access JWT using `users.session_version` as it stands NOW (post any concurrent password rotation).
   - Return access token.

   **Case B — Superseded but within grace (`superseded_at IS NOT NULL` AND `NOW() < superseded_at + 60s`):** A parallel in-flight refresh already rotated this token. Don't re-rotate; serve the caller from the existing successor chain.
   - Walk `successor_id` forward, looking for the **live terminal row** — the one whose `successor_id IS NULL` AND `superseded_at IS NULL` AND `revoked_at IS NULL`.
   - Cap traversal at 10 hops and track visited row ids. If the cap is exceeded or a cycle is detected, log `reason=bad_refresh_chain` (no token values) and reject with the same 401 / `refresh_failed` response. This turns chain corruption into a visible log instead of an infinite loop or worker hang.
   - **If no live terminal exists** (e.g., a concurrent `/auth/login` or password rotation revoked everything in the chain mid-traversal) → reject with the same 401 / `refresh_failed` response as Case C.
   - Every successor row read during this traversal MUST be selected `FOR UPDATE` before evaluating whether it is live. After locking the terminal row, re-check `revoked_at IS NULL`, `expires_at >= NOW()`, `superseded_at IS NULL`, and `successor_id IS NULL` before minting. If a concurrent logout/password rotation wins first, reject; if refresh wins first, logout/password rotation waits and then revokes the new state.
   - Otherwise: do **NOT** issue a new cookie (the browser already has it from the parallel rotation; setting another would race), mint a new access JWT using current `users.session_version`, return access token only (no `Set-Cookie` header).
   - **Chain depth:** Two browser tabs racing produces a 1-hop chain. The Cloudflare `/auth/*` WAF rule bounds pathological depth for traffic through the public API hostname; the production host gate prevents direct Fly-origin traffic from bypassing that edge rule. In practice expect 1-2 hops.

   **Case C — Superseded past grace (`superseded_at IS NOT NULL` AND `NOW() >= superseded_at + 60s`):** Reject. Token is stale; client must re-login.

6. **Session-version handling:** Refresh tokens are opaque random bytes; they do NOT embed `session_version`. The defense against "refresh after password rotation" is `revoked_at` — operator password rotation explicitly sets `revoked_at = NOW()` on every active refresh-token row for that user (see "Operator Password Rotation" section). So step 3 above already handles it. The newly minted access JWT in Case A and Case B carries the **current** `users.session_version`, so any pre-rotation access JWTs that happen to still be in flight will fail the dependency check on next protected request.
7. **Timestamp source:** writes/comparisons for `issued_at`, `expires_at`, `superseded_at`, and `revoked_at` use timezone-aware UTC consistently; prefer DB-side `func.now()`/SQL expressions for comparisons inside refresh transactions. Tests should set DB timestamps directly for T+30/T+90 cases instead of sleeping or relying on wall-clock drift.

**Response on success:** `{ "access_token": "...", "token_type": "bearer" }`. Cookie reset only in Case A.

**Failure response:** `HTTP 401`, body `{"detail": "refresh_failed"}` (byte-identical for all rejection cases).

### `POST /auth/logout`

**Request:** Requires `Authorization: Bearer <access_token>` header. (CSRF protection — see contract-freeze line 180.)

**Behavior:**
- Validate the bearer access token with the same full semantics as `get_current_user`: decode JWT, validate claims, read live `users.session_version`, and reject stale/deleted-user tokens before any mutation. A stale token after operator password rotation must return 401 and must not revoke any newly issued valid refresh token.
- `UPDATE refresh_tokens SET revoked_at = NOW() WHERE user_id = $1 AND revoked_at IS NULL` — revokes ALL active sessions for that user.
- Clear the `__Host-refresh` cookie with the same deletion attributes browsers require to remove the original cookie: same name, `Path=/`, `Secure`, `HttpOnly`, same `SameSite` policy, no `Domain`, and `Max-Age=0`.
- Return `HTTP 204`.

**Note:** Does NOT bump `session_version` — that's reserved for password rotation. Logout intentionally leaves already-issued access tokens valid for their natural 15-min TTL. (If we wanted instant access-token revocation on logout we'd bump session_version. v1 doesn't need it.)

### `GET /auth/status`

**Public, no auth required.** Used by M4 portal.

**Response:**
```json
{ "account_exists": true|false }
```

That's it. No version/hostname/config leakage.

## Auth Dependency Helper (NOT applied in M3)

`app/auth/dependencies.py::get_current_user` exists and is fully functional, but is NOT added to any existing routes. M5 PR #1 wires it everywhere.

Behavior on every protected request:
1. Read `Authorization: Bearer <token>` header. Missing/malformed header → 401.
2. PyJWT decode (HS256, verify exp). **Catch ALL of:** `jwt.ExpiredSignatureError`, `jwt.InvalidSignatureError`, `jwt.DecodeError`, `jwt.InvalidTokenError`. All four map to 401 (Eng review 1).
3. Validate decoded claims before touching the DB: `sub` must parse to an integer user id, `session_version` must be an integer, and `exp` must have been verified by PyJWT. Missing, null, stringified non-int, negative, or otherwise malformed claims all map to the same 401. Do not let `ValueError` / `TypeError` escape as 500s.
4. `await db.execute(select(User.session_version).where(User.id == sub))` → scalar.
5. If row not found OR `db.session_version != token.session_version` → 401.
6. Return `User` object.

Cost: one indexed PK lookup per request. At household scale (tens of req/min) this is below noise floor.

## Operator Password Rotation (mechanism only — CLI ships in M8)

The `session_version` mechanism MUST be wired in M3 so that M8's CLI becomes a one-line change. The example below is **illustrative of the M3 building blocks**; it is NOT shipped as part of M3:

```python
# Illustrative — actual CLI ships in M8. Async patterns per Eng review 1.
from sqlalchemy import select, update, func
from sqlalchemy.ext.asyncio import AsyncSession

async def rotate_password(db: AsyncSession, new_password: str) -> None:
    user = (await db.execute(select(User))).scalar_one()
    user.password_hash = password_hasher.hash(new_password)
    user.session_version += 1   # invalidates every issued access JWT
    await db.execute(
        update(RefreshToken)
        .where(RefreshToken.user_id == user.id, RefreshToken.revoked_at.is_(None))
        .values(revoked_at=func.now())
    )  # invalidates every active refresh token
    await db.commit()
```

**Belt-and-suspenders rationale:** Bumping `session_version` alone kills access tokens; setting `revoked_at` alone kills refresh tokens. Doing both is intentional — `session_version` makes already-in-flight access requests fail immediately, and `revoked_at` makes any subsequent refresh attempt fail at the database level without needing to decode anything. Either alone is sufficient; together they make the failure modes orthogonal.

## Observability (CEO review 2026-05-01)

**Why this section exists:** Auth is a security boundary. Without telemetry we cannot tell whether someone is brute-forcing the login endpoint, whether refresh-token rotation is failing in production, or what happened during a "I can't log in" report 3 weeks post-ship. **What ships in M3:**

Every `/auth/*` request emits exactly one structured JSON log line at completion. Fields:

| Field         | Type    | Notes                                                                               |
|---------------|---------|-------------------------------------------------------------------------------------|
| `event`       | string  | One of `auth.register`, `auth.login`, `auth.refresh`, `auth.logout`, `auth.status`. |
| `outcome`     | string  | `success` or `failed`.                                                              |
| `reason`      | string  | On `failed`, a generic reason code: `bad_credentials`, `bad_access_key`, `account_exists`, `bad_refresh`, `bad_refresh_expired`, `bad_refresh_revoked`, `bad_refresh_superseded`, `bad_refresh_chain` (Eng review 2: covers Case-B cycle / >10-hop / no-live-terminal), `password_too_long`. **Note:** `bad_credentials` covers BOTH "wrong password" and "unknown email" — the log MUST NOT distinguish, since enumeration defense applies to logs as well as responses. |

- `auth.*` `outcome=success` → `INFO`
- `auth.*` `outcome=failed` → `WARNING`
- Unexpected exceptions caught in the auth path → `ERROR` with stack trace (never log secrets, hashes, or refresh-token plaintext)

- Persisted `auth_events` table
- Aggregated metrics (failed-login rate, refresh-rotation count)
- Dashboards / alerts
- IP-based anomaly detection

## Test Strategy

### Argon2 fast-test profile

`app/auth/passwords.py` exposes the hasher in **two forms** so both FastAPI-dependency code paths AND direct service-level unit tests can override it:

```python
# Module-level injectable (for direct calls in unit tests)
_password_hasher: PasswordHasher = PasswordHasher()  # OWASP defaults

def get_password_hasher() -> PasswordHasher:
    """FastAPI dependency. Overridable via app.dependency_overrides."""
    return _password_hasher

def set_password_hasher(hasher: PasswordHasher) -> None:
    """Test helper. Replaces the module-level instance for non-FastAPI code paths."""
    global _password_hasher
    _password_hasher = hasher
```

`tests/conftest.py` does **both**:
- `app.dependency_overrides[get_password_hasher] = lambda: fast_hasher` (for endpoint tests)
- `set_password_hasher(fast_hasher)` (for direct service-call tests)

Where `fast_hasher = PasswordHasher(memory_cost=8, time_cost=1, parallelism=1)`.

Result: tests run in seconds, not minutes. Production path is unchanged.

**Note on the timing-oracle defense:** the dummy-hash cache (used in `/auth/login` for "user not found" branch) is generated **lazily on first miss using the currently active hasher instance**, NOT precomputed at import time. This means production timing matches production hasher; test timing matches test hasher. The defense holds in production; in tests it's not load-bearing because the fast hasher's timing is dominated by network/DB latency anyway.

### Required test scenarios (locked by contract-freeze)

**Register:**
- Success → user row created, refresh cookie set, access token in body
- Wrong access key → byte-identical 401 body
- Account already exists → byte-identical 401 body (HTTP status + body match wrong-key)
- Concurrent register race (2 parallel requests with different valid emails) → exactly one succeeds, exactly one user row exists, and the loser's response is byte-identical to wrong-key
- Password > 128 chars → 422
- `compare_digest` is what's used (verify by source-code grep, not latency microbenchmark — Eng review note line 189)

**Login:**
- Success → cookie + access token
- **Login with a matching existing refresh cookie for the same user → only that cookie's DB row gets `revoked_at`; new token is issued; old cookie's value rejects on subsequent `/auth/refresh`** (Adversarial review, same-client login rotation)
- **Login from device B while device A has an active refresh token → device A's row remains non-revoked and can still refresh** (guards shared-household multi-device behavior)
- Login with an absent/unknown/expired/already-revoked refresh cookie but valid credentials → succeeds, issues a fresh cookie, and does not mutate unrelated refresh-token rows
- Unknown email → byte-identical 401 with wrong-password response
- Wrong password → byte-identical 401 with unknown-email response
- Overlong password on login (>128 chars) → byte-identical 401 with wrong-password response and `reason=bad_credentials` (not 422, not `password_too_long`)
- Verify `password_hasher.verify` is called on every login attempt (timing-oracle defense — assert via mock spy that `verify` is called even on unknown-email branch)

**Refresh:**
- Two simultaneous Case-A refreshes with the same fresh cookie → row lock serializes them; exactly one response sets a new cookie, the second follows Case B and returns an access token without `Set-Cookie`
- Case A — Fresh cookie → new cookie, new access token, old row `superseded_at` set, old row `successor_id` points to new row
- Case B — At T+30s with already-rotated cookie → returns NEW access token, **does NOT issue a new cookie** (no `Set-Cookie` header in response), traverses successor chain to terminal row
- **Case B — No live terminal in chain (Eng review 2):** within grace, but a concurrent `/auth/logout` or password rotation revoked every row in the chain mid-traversal → 401 with `reason=bad_refresh_chain` (or `reason=bad_refresh_revoked` if the terminal row is revoked rather than absent), byte-identical body. Distinct from "row already revoked at lookup" — this case requires concurrent revocation during the walk.
- **Case B — Concurrent terminal revocation (Adversarial review run 2):** Case B traversal races logout/password rotation against the terminal row lock. If revocation commits first, refresh rejects; if refresh commits first, revocation waits and then revokes. No refresh may succeed after observing a revoked terminal row.
- Case C — At T+90s with already-rotated cookie → 401
- Corrupt successor chain (cycle or >10 hops) → 401 + structured warning with `reason=bad_refresh_chain`, no token values logged
- Rejected after explicit logout (revoked_at set) → 401
- Rejected after operator password rotation (revoked_at set on all tokens) → 401, AND any access JWT issued before rotation fails the dependency check via session_version mismatch
- Expired refresh token (`expires_at < now()`) → 401
- Unknown cookie (no row matches) → 401, byte-identical to other rejection responses

**Logout:**
- Success → all refresh tokens for user marked `revoked_at`, cookie cleared, 204
- Cookie clearing response uses the original deletion attributes: `Path=/`, `Secure`, `HttpOnly`, same `SameSite`, no `Domain`, and `Max-Age=0`.
- **Concurrent-device case:** logout from device A revokes device B's refresh token at the DB level even though only A's cookie is cleared. Verify B's next `/auth/refresh` returns 401 even though its cookie is still locally present.
- Without Bearer header → 401 (CSRF defense)
- With expired Bearer → 401
- With stale bearer after simulated operator password rotation → 401 and does not revoke a newly issued valid refresh token

**Status:**
- Returns `{"account_exists": false}` on empty DB
- Returns `{"account_exists": true}` after register

- Manually call `get_current_user(token)` with stale session_version → raises 401

### Secret handling (CEO review 2026-05-01)

**Why this section exists:** On 2026-05-01 (during M2 Slice 3) an unfiltered `printenv` call dumped `JWT_SECRET_KEY`, `HOUSEHOLD_ACCESS_KEY`, `DATABASE_URL`, `FERNET_KEY`, and `REDIS_URL` into a Claude Code transcript.    fly secrets set HOUSEHOLD_ACCESS_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')" --app <app-name>

3. **The two cookies-and-tokens sentence.** "When you log in, the server hands your browser two things: a short-lived 'access token' that proves who you are for the next 15 minutes, and a long-lived 'refresh cookie' that lets the browser quietly get a new access token without bothering you. The cookie is special — it's `HttpOnly`, which means JavaScript can't read it, so even if someone snuck a script into the page they can't steal it."
4. **What argon2 is and why we use it.** Plain-English explanation: passwords are hashed (one-way scrambled) so even if someone steals the database, they don't get the passwords. Argon2 is the current best version of that scrambling.
5. **The "session version" trick.** Why we have an integer column on the user that goes up when the password changes, and how it kills every active session in milliseconds without needing Redis.
6. **The 60-second rotation grace window.** Why we don't immediately invalidate the old refresh token — and why "for 60 seconds, both the old and new are good" is the right answer for a multi-tab user.
7. **The error-shape rule.** Why "wrong password" and "no account with that email" return the **byte-identical** error — a footnote-sized explanation of enumeration attacks.
8. **What we didn't build (and why that's deliberate).** No password reset, no magic links, no OAuth. Operator rotates by SSH'ing into the box and running a CLI. Friend should understand this is *correct* for a single-household app.
9. **The "we wrote it but didn't wire it up" cliffhanger.** `get_current_user` exists; nothing uses it yet. M5 turns it on. Why it ships in two PRs.

**Tone:** Conversational, second-person ("when you log in..."), no acronyms without expansion, no code blocks longer than 5 lines, lots of "imagine if..." analogies.

**Length:** Aim for ~1500-2500 words. Long enough to actually teach; short enough to read in one sitting.

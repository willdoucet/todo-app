# Design: M7 — `prod-r2-storage`

Generated by /office-hours on 2026-07-15
Branch: prod-r2-storage
Status: APPROVED
Mode: Builder

## Problem Statement

M7 is the object-storage productionization milestone. Today the backend stores every user
upload (family photos, responsibility icons, item icons, recipe images) on **ephemeral local
disk** at `/app/uploads` (confirmed 2026-07-20: `backend/fly.toml` has no `[mounts]` block, so
this is the container filesystem, **not** a persistent Fly volume — prod uploads are already
lost on every deploy/restart), and serves them back through a public `StaticFiles` mount:

```python
# backend/app/main.py:183
app.mount("/uploads", StaticFiles(directory=UPLOAD_DIR), name="uploads")
```

That mount **bypasses the `protected` APIRouter entirely** — it is guarded *only* by
Cloudflare Access at the edge (`api.mealy.dev` is operator-gated). This is the single
load-bearing reason CF Access **Application 1** has survived since M5: the `protected`
wrapper can gate routes, but it cannot gate a StaticFiles mount.

M7 replaces local-disk storage with Cloudflare **R2** (S3-compatible, provisioned but
unused since M2), moves reads behind **first-party auth**, deletes the StaticFiles mount,
and clears the last exit-checklist item blocking the CF Access **Application 1** teardown.

Scope (IMPLEMENTATION_PLAN.md line 171): *storage abstraction; backend-proxied uploads with
atomic R2+DB transaction; UUID-keyed R2 objects; private-read with first-party auth; bundled
stock icons get an authenticated backend route (not R2); remove the `/uploads` StaticFiles
mount.* Exit item: tear down CF Access Application 1.

## What Makes This The Right Design

The elegant core insight, discovered during office hours: **the DB columns store *logical*
paths (`/uploads/item-icons/{uuid}.png`), not physical URLs, and the frontend resolves them
to absolute at render time via `apiUrl()`.** That indirection means we can swap the storage
*backend* (disk → R2) and the storage *access model* (public mount → auth proxy) **without a
data migration and without touching a single `<img>` consumer**, as long as the read route
keeps the same `/uploads/*` path. The whole milestone slides in behind an existing seam.

## Constraints

- **Docker-first:** all app builds/tests run through Docker Compose (`docker-compose exec
  frontend npm ...`, `docker-compose exec api uv run pytest`). No host `npm`/`uv`/`pytest`.
- **Single-family instance:** no multi-tenant / cross-family concerns. Perimeter auth still
  matters; IDOR/tenant-isolation does not. Scale is a handful of ≤5 MB images, ever.
- **Backend is async** (async SQLAlchemy); `boto3` is sync → must be called via
  `run_in_threadpool`.
- **Dev + visual-regression test stacks must not gain an R2 dependency.** `docker-compose`
  stays self-contained on local disk.
- **Same-site is load-bearing (NEW):** frontend `mealy.dev` and backend `api.mealy.dev`
  share eTLD+1 `mealy.dev`. The cookie-checked read path depends on this. Any future move of
  the frontend off a `mealy.dev` subdomain breaks image reads under `SameSite=Strict`.
- **Auth model recap (from M3/M4):** access token is in-memory JS, sent as
  `Authorization: Bearer` on XHR; `get_current_user` reads **only** that header
  (`auth/dependencies.py:14`). The refresh token is an httpOnly `__Host-refresh` cookie,
  `SameSite=Strict`, host-only to `api.mealy.dev`. **`<img>` tags cannot send a Bearer
  header — only cookies.** This is why reads need a cookie-based guard, not `get_current_user`.

## Premises

All confirmed during office hours (none vetoed):

1. **Entity columns keep storing the logical `/uploads/{key}` path.** The `assets` table is a
   side manifest keyed by that key. This preserves the zero-migration read win.
2. **`StorageBackend` abstraction:** `LocalDiskBackend` (dev/test) + `R2Backend` (prod),
   env-selected. Dev + visual-regression stay on local disk; **no R2 dep in `docker-compose`.**
3. **R2 via `boto3`** (S3-compatible client against the R2 endpoint), invoked from async
   routes through `run_in_threadpool`. New backend dep added via `uv`.
4. ⚠️ **Read guard validates the `__Host-refresh` cookie READ-ONLY** — hash-lookup + not-
   revoked + not-expired, **no rotation** — a new dependency distinct from `get_current_user`
   (Bearer) and from `/auth/refresh` (rotating). *Highest-risk piece; see Open Questions.*
5. **Stock icons stay bundled in the image**, served through the media proxy's `stock_icons/*`
   compat branch (same read-only cookie guard, **not** the Bearer-only `protected` router). The
   existing `/uploads/stock_icons/*.png` URL scheme is **kept** so already-adopted references
   keep resolving. *(Revised after spec review — the original "new `/stock-icons/{id}` route on
   `protected`" would have 401'd `<img>` loads and orphaned stored stock-icon columns.)*
6. **Teardown sequencing:** ship R2 writes + cookie-proxy reads + remove the mount + verify
   **first**; only **then** tear down CF Access Application 1. Never remove CF Access while
   the mount exists. CF teardown is an operator/platform step, not code.
7. ❓ **Existing prod uploads assumed near-zero** (recently-deployed single-family instance).
   Migration of existing disk files to R2 is trivial or unnecessary. *Verify before finalize.*

## Approaches Considered

Office hours resolved four independent forks. For each, the alternatives and the choice:

### Fork 1 — Read path (auth model for image `<img>` loads)
- **A ✅ Cookie-checked proxy** — keep `/uploads/*`, replace the mount with a real FastAPI GET
  route that validates the session cookie (no rotation) and streams bytes from storage.
  Zero DB migration, zero frontend change, matches scope's "backend-proxied". *Chosen.*
- B — Blob-fetch via Bearer: reuse `get_current_user`, but rework every `<img>` consumer to
  fetch-then-render with object-URL lifecycle. Rejected: frontend churn for no scale benefit.
- C — Presigned R2 URLs: `<img>` hits R2 directly. Rejected: expiring URLs break caching,
  weaken the "first-party auth" contract, expose the R2 endpoint to the browser.

### Fork 2 — Write side / orphan lifecycle ("atomic R2+DB")
- **B ✅ Dedicated `assets` table** — R2-first write + compensating delete on DB failure +
  explicit manifest + audit trail + clean GC by unreferenced rows. *Chosen* — the closest
  practical realization of the scope's "atomic R2+DB" (a compensating saga; true cross-store
  atomicity isn't possible), and the manifest makes orphan-GC tractable without listing R2.
- A — Columns-as-manifest (no table): same compensating pattern, entity columns as manifest,
  sweep by diffing R2 against columns. Viable and lighter; not chosen.
- C — Collapse upload into entity save (single transaction, no orphan gap): rejected — reworks
  every entity form's save path, couples storage into all CRUD.

### Fork 3 — File validation consolidation
> ⚠️ **Explicit scope addition beyond IMPLEMENTATION_PLAN.md line 171** (which is silent on
> validation). Deliberately folded in because M7 already routes every upload type through one
> new storage layer — the natural moment to close the gap. Carries a **user-facing behavior
> change: GIF uploads are rejected.** Called out here so it isn't a silent creep; drop this fork
> if a reviewer wants M7 held to the literal line-171 scope.

- **C ✅ Strong check, per-type caps** — magic-byte sniffing everywhere (delete the weaker
  extension-trusting validator), per-type size caps (icons 1 MB; photos/recipe images 5 MB).
  Only behavior change: GIF no longer accepted (allowlist PNG/JPEG/WebP). *Chosen.*
  *(Eng review 1: confirmed in-scope for M7, GIF rejected. The unified validator consolidates
  onto `item_icon_upload`'s streaming-abort reader — read 64 KB chunks, abort the moment the
  running total exceeds the per-type cap — NOT `save_upload`'s naive `await file.read()` which
  buffers the whole body before checking. Signature `validate_and_read(file, *, max_bytes, subdir)`.)*
- A — Fully unified single cap: rejected, forces one size limit across icons and photos.
- B — Preserve both validators as-is: rejected, leaves the filename-trusting gap in place.

### Fork 4 — Packaging
- **A ✅ Sliced, storage-first** — 2 code PRs + 1 ops step. *Chosen.* (Slice boundary corrected
  after spec review — see Slices: prod stays on local disk through PR1; R2 writes + read proxy
  flip together in PR2, so R2 is still proven in prod before CF Access comes down, at the
  PR2 → Ops boundary rather than PR1 → PR2.)
- B — Single PR: rejected, large diff, edge gate removed before writes independently verified.

## Recommended Approach

The synthesis of the four choices. Three slices, storage-first.

### Storage abstraction (`backend/app/storage/`)

A thin protocol — minimal by design (single-family scale):

```python
class StorageBackend(Protocol):
    async def put(self, key: str, data: bytes, content_type: str) -> None: ...
    async def get(self, key: str) -> bytes: ...   # bytes only; content_type comes from the assets manifest, not storage
    async def delete(self, key: str) -> None: ...  # idempotent; missing key is OK
```

- `LocalDiskBackend` — wraps the current `/app/uploads` disk writes. Dev + visual-regression.
- `R2Backend` — `boto3` S3 client against `R2_ENDPOINT` with the four `R2_*` secrets;
  `put/get/delete` via `run_in_threadpool`. Prod.
- Selected by env at startup (e.g. `STORAGE_BACKEND=r2|local`, defaulting to `local` so an
  unset dev/test env never reaches for R2). `key` is `{subdir}/{uuid4}.{ext}`.

> **Adversarial review (GPT-5.5) — key validation is a trust boundary.** Every media path must
> parse into exactly one of two shapes before touching disk, R2, or the manifest:
> `stock_icons/{filename}.png` from a fixed bundled allowlist, or
> `{family-photos|responsibility-icons|item-icons|recipe-images}/{uuid4}.{png|jpg|jpeg|webp}`.
> Reject absolute paths, `..`, empty path segments, encoded traversal, unexpected subdirs, and
> extension/content-type mismatches with 404/400 before `LocalDiskBackend.get()` can join paths
> or `R2Backend.get()` can fetch arbitrary keys. Add unit tests for traversal and malformed keys.

### `assets` table (new migration)

| column        | type        | notes                                            |
|---------------|-------------|--------------------------------------------------|
| `key`         | text PK     | `{subdir}/{uuid4}.{ext}` — matches the R2 object key AND the logical `/uploads/{key}` path |
| `content_type`| text        | validated MIME (`image/png` etc.). **Authoritative** — the read route serves this, not a storage-derived value (LocalDiskBackend has no stored content-type). |
| `size_bytes`  | integer     | post-validation byte count                       |
| `created_at`  | timestamptz | for the abandoned-upload sweep                   |
| `referenced`  | boolean     | `false` at insert; flipped `true` when an entity column adopts the key; a `false`-and-aged row is a sweep target |

*(`sha256`/de-dup was considered and cut — YAGNI at single-family scale with UUID keys that
can't collide. The table earns its keep on **operational** grounds, not pedagogy: an explicit
manifest gives GC-by-unreferenced-row without listing R2, plus an audit trail of what exists.)*

> **⚠️ Eng review 1 (A1) — `referenced` stays a boolean, NOT a refcount. Load-bearing
> 1:1 invariant: each managed key is adopted by AT MOST ONE entity column.** Replace/Delete
> hooks call `storage.delete(old_key)` unconditionally, so a key shared by two entities would
> be erased out from under the survivor (exactly the stock-icon sharing hazard, unguarded for
> managed keys). At single-family scale with per-upload UUID keys this can only happen via
> deliberate URL copy-paste, so we **accept the 1:1 invariant** rather than add refcount
> increment/decrement (with its row-lock race surface). Requirements: (a) name the invariant in
> an inline comment on the Replace/Delete hook, and (b) add a test documenting that a
> duplicated-key scenario is explicitly out of scope. Also resolves **Open Question 5**
> (maintained boolean, not computed-at-sweep). *Revisit if a "duplicate item / copy recipe"
> feature ever copies `image_url`.*

> **Eng review 1 (perf): add an index on `assets(referenced, created_at)`** in the same
> migration so the abandoned-upload sweep stays a cheap index scan, not a table scan.

### Write flow — a compensating transaction, not true atomicity

The scope calls this "atomic R2+DB", but R2 cannot enlist in a Postgres transaction. The real
guarantee is **no orphans on failure**, via a compensating (saga) pattern. Upload endpoints are
**standalone** (frontend uploads → gets a URL → *then* submits the entity form), so there is no
co-committed caller state at upload time — adoption happens later, in a separate request.

*Upload endpoint (per type):*
1. Stream-read + **magic-byte validate** (PNG/JPEG/WebP) against the per-type size cap.
2. Derive `key = {subdir}/{uuid4}.{ext}`.
3. `storage.put(key, data, content_type)` — **R2-first**.
4. Insert the `assets` row (`referenced=false`, `content_type`, `size_bytes`) and commit.
5. On DB failure after a successful `put`: **compensating `storage.delete(key)`** + log if the
   delete itself fails (the only residual-orphan path; the sweep is the backstop).
6. Return `{"url": "/uploads/{key}"}` — unchanged contract.

*Adoption / replace / delete (the entity write paths that must be wired — enumerated so no slice
misses one):*
- ⚠️ **`stock_icons/*` carve-out (all three hooks below skip it), symmetric with read-flow step 3.**
  Stock icons are bundled + unmanaged and have **no `assets` row**, yet they get adopted into the
  same columns (`icon_url = /uploads/stock_icons/foo.png`). Without the carve-out: adopt would
  flip a non-existent row (silent no-op or error); **replace/delete would call
  `storage.delete("stock_icons/foo.png")` — which on `LocalDiskBackend`, if stock files linger in
  the volume (Open Q3), deletes the SHARED bundled icon out from under every other entity still
  using it.** So: hooks match `stock_icons/*` → do nothing (no ref flip, no delete, no row drop).
- **Adopt:** when an entity PATCH/POST sets `icon_url`/`photo_url`/`image_url` to `/uploads/{key}`
  (and `key` is not `stock_icons/*`), row-lock the `assets` row, require it to exist, require
  `referenced=false` for newly adopted keys, then flip `assets.referenced = true` for that key.
  Paths: `responsibilities` (`icon_url`), `family_members` (`photo_url`), `items` (`icon_url`),
  recipe/item (`image_url`). If a PATCH repeats the entity's existing key, treat it as a no-op
  rather than a duplicate adoption. If a user copy-pastes another entity's managed `/uploads/*`
  path, reject it instead of silently violating the 1:1 key→entity invariant.
- **Replace:** when one of those columns changes **and the previous value is a managed
  (non-stock) key**, cleanup keys off the *previous* value alone — independent of what the new
  value is (managed upload, stock icon, or null) — so a managed→stock swap still reclaims the old
  object. Whether an **Adopt** also fires is a separate question decided by the *new* value.
  **Adversarial review ordering requirement:** never delete the previous object before the entity
  update commits. In the DB transaction: validate/adopt the new key and update the entity column;
  mark the previous asset row `referenced=false` (or otherwise enqueue it for cleanup). After the
  commit succeeds, call `storage.delete(previous_key)` and drop the old `assets` row; if storage
  deletion fails, keep the unreferenced row so the sweep retries it. If the DB commit fails, the
  old object remains live and the old column still points at valid bytes.
- **Entity-delete:** on delete of any of those entities, if its key is a managed (non-stock) key,
  commit the entity delete first and then perform the same post-commit object cleanup. A failed
  entity delete must never erase an object still referenced by a rolled-back row.
- **Abandoned-upload sweep** (Celery beat): delete `assets` rows + R2 objects where
  `referenced=false AND created_at < now()-24h` (covers "uploaded, closed the tab before saving").
  The sweep does **not** cover replaced/deleted *referenced* objects — those rely on the hooks
  above; the sweep is only the abandoned-upload backstop.

*Read-then-write races on replace are acceptable at single-family scale (no concurrent editors);
eng-review to confirm no locking is warranted.*

### Read flow (replaces the StaticFiles mount)

`GET /uploads/{key:path}` on a **new media router guarded by a read-only cookie dependency**
(the same dependency the stock-icon route uses — NOT the Bearer-only `protected` router, since
`<img>` cannot send a Bearer header):
1. Read the `__Host-refresh` cookie; 401 if absent.
2. SHA-256 it, look up the refresh-token row; 401 if unknown / revoked / expired / **superseded
   past the grace window**. **No rotation** (see "Read-guard mechanics" below).
3. **`stock_icons/*` compat:** if `key` starts with `stock_icons/`, serve the bundled file from
   the image (see Stock icons) with `content_type = image/png` (all bundled icons are PNG — the
   one deliberate exception to "content_type comes from the manifest", since stock icons have no
   `assets` row). This keeps *already-stored* `/uploads/stock_icons/*.png` column values live
   (they were never in R2) — without it, every responsibility/item that previously adopted a
   stock icon would 404. Everything else → step 4.
4. `data = await storage.get(key)` (bytes only); look up `content_type` from the `assets`
   manifest row (the single authority); **distinguish 404 (missing row/object) from 5xx
   (storage unreachable — e.g. R2 down/timeout): log the storage error distinctly so ops can
   tell "unknown key" from "R2 unreachable"** *(Eng review 1)*.
5. **`Response(data, media_type=content_type, headers={"Cache-Control": "private, no-cache",
   "ETag": f'"{key}"'})` + `If-None-Match` → 304.** *(Eng review 1 — ETag optimization built
   into PR2.)* `private` still forbids the Cloudflare edge from caching a private image (the
   load-bearing property — a `public`/`max-age` directive would let CF serve it to an
   unauthenticated client). Changed `no-store` → **`no-cache`**: `no-cache` lets the *browser*
   store the bytes but **revalidate on every use**, and the revalidation request carries the
   cookie and re-runs the guard — so auth is still enforced on every load, but a valid session
   gets an empty `304` instead of re-streaming a 5 MB image through Fly+R2. Keys are immutable
   UUIDs (a new upload = a new key), so `ETag = key` is always a safe validator and never
   serves stale content. (Verify end-to-end that CF still does not cache `/uploads/*` under
   `private, no-cache`.)

Same path (`/uploads/*`), so DB columns and `apiUrl()`/`<img>` consumers are untouched.
Then **delete `app.mount("/uploads", StaticFiles(...))`**.

*Accepted tradeoff (from rejecting presigned URLs, Fork 1/C): the backend is in the byte path —
every `<img>` load is at least one cookie/session lookup, and cache misses are an R2 GET streamed
through Fly. `private, no-cache` permits browser revalidation/304s but still prevents Cloudflare
edge caching of private bytes. At a handful of ≤5 MB images per family this is negligible; at
larger scale it would warrant reconsidering presigned reads.*

### Read-guard mechanics (the ⚠️ high-risk piece — eng-review must lock)

> **⚠️ Eng review 1 (CQ1) — DRY the validity predicate into ONE shared helper.** The read
> guard and `service.refresh` steps 2–4 must NOT re-implement "is this session valid?"
> independently — a security predicate that drifts between two copies silently re-opens the
> hole M7 exists to close. Extract a pure function in `auth/service.py` (or `auth/tokens.py`):
> ```python
> class RefreshStatus(Enum):
>     LIVE; REVOKED; EXPIRED; SUPERSEDED_IN_GRACE; SUPERSEDED_PAST_GRACE
> def refresh_row_status(row: RefreshToken, now: datetime) -> RefreshStatus: ...
> ```
> `service.refresh` branches on it (`LIVE`→Case A, `SUPERSEDED_IN_GRACE`→Case B, else reject);
> the read guard treats `{LIVE, SUPERSEDED_IN_GRACE}` as "serve" and everything else as 401.
> Single source of truth for session validity. `service.refresh`'s row-lock / rotation stays
> in `service.refresh` — only the pure predicate is shared.

- **Validity predicate** mirrors a strict subset of `service.refresh`: hash the cookie, indexed
  `token_hash` lookup, reject on `revoked_at` / `expires_at` / `superseded_at` (past grace).
  Including `superseded_at` keeps the read path's notion of "valid session" aligned with the
  refresh path's — otherwise a rotated-away cookie would authorize reads for its full 30-day TTL
  even though it can no longer refresh.
- **Revocation reliance (must stay true):** read-access revocation rides on the fact that logout
  and password/`session_version` bumps also revoke the refresh rows (`revoked_at`). The guard
  does not re-check `session_version` itself. Invariant to preserve: *any `session_version` bump
  must also revoke the user's refresh rows* — already true in M3, but now load-bearing for reads.

### Stock icons (auth-gated, not R2)

- Bundled files stay in the image (`/app/stock_icons_src`). They are served through the media
  proxy's **`stock_icons/*` compat branch** (Read flow step 3), reusing the same read-only
  cookie guard — **not** the Bearer-only `protected` router (`<img>` can't send Bearer).
- **Keep the existing `/uploads/stock_icons/{name}.png` URL scheme** so already-stored entity
  column values keep resolving. The `/upload/stock-icons` list endpoint's URLs therefore stay
  as `/uploads/stock_icons/*.png` — no change needed, and no migration of stored `icon_url`s.
  *(This supersedes the earlier idea of a new `/stock-icons/{id}` path, which would have orphaned
  every already-adopted stock-icon reference.)*
- Stock icons no longer need copying into the uploads *volume* at boot, since the proxy reads
  them straight from the image dir — simplifies the entrypoint copy step (flag for removal in
  PR2; don't silently drop, and confirm no stock files linger in the volume via Open Q3).

### Slices

**Corrected after spec review** to eliminate a broken-read window: PR1 must NOT flip prod writes
to R2 while reads still come from the disk mount (an R2-written file isn't on `/app/uploads`, so
it would 404 on read until PR2). Writes→R2 and reads→proxy flip **together** in PR2.

- **PR1 — Foundation (storage refactor + validation hardening):** `storage/` abstraction +
  `boto3` dep + `assets` migration + unified magic-byte validator + adopt/replace/delete hooks on
  the four entity write paths. Storage behavior is preserved; the **one intentional behavior
  change is GIF rejection** (Fork 3). **All environments (including prod) stay on
  `LocalDiskBackend`** — writes still land on `/app/uploads` and the existing mount still serves
  them, so there is no intermediate 404 window. *Verifiable: uploads still work end-to-end everywhere; validation
  rejects magic-byte fakes and GIF; `assets` rows written + `referenced` flips on adopt; old key
  deleted on replace/delete; sweep task unit-tested.*
  **Eng review 1 additions to PR1:** (1) **Bundle the `echo=True` env-gate** —
  `echo=os.getenv("SQLALCHEMY_ECHO","false").lower()=="true"` in `database.py`, default off in
  prod (TODO cross-ref; on-theme because the read guard adds a refresh-hash SQL lookup per image
  render — mark the TODOS.md entry done). (2) **`moto` as a test-only dev dependency** for
  `R2Backend` coverage (in-process S3 mock; docker-compose runtime stays R2-free). (3) **Index
  `assets(referenced, created_at)`** in the migration. (4) **Mandatory tests:** compensating-delete
  failure injection (DB insert raises after a successful `put` → assert `storage.delete(key)`
  called; + delete-also-raises → assert logged); the A1 duplicated-key out-of-scope doc-test.
- **PR2 — R2 + read cutover (atomic flip):** enable `R2Backend` in prod (`STORAGE_BACKEND=r2`),
  add the cookie-checked `/uploads/{key}` proxy route (incl. the `stock_icons/*` compat branch),
  **remove the StaticFiles mount**, and resolve dev/test media-auth handling — all in one deploy.
  *Verifiable: authed `<img>` loads succeed on `mealy.dev`; unauthenticated `/uploads/*` → 401;
  CF does not cache `/uploads/*`; new prod uploads land in R2 AND read back through the proxy;
  visual-regression suite still green.* **This is where R2 writes are first proven in prod — so
  the "prove R2 before the edge gate comes down" property now holds at the PR2 → Ops boundary.**
  **Eng review 1 additions to PR2:** (1) the read guard consumes the shared `refresh_row_status`
  helper (CQ1); (2) `Cache-Control: private, no-cache` + `ETag = key` + `If-None-Match`→`304`
  (perf); (3) media route logs storage-unreachable (5xx) distinctly from missing-key (404);
  (4) the visual suite gains a `context.route('**/uploads/**', …)` fixture-byte shim (A2).
  **Mandatory tests:** full read-guard rejection matrix (absent / unknown / revoked / expired /
  superseded-past-grace → 401; LIVE + in-grace → serve; `stock_icons/*` compat; manifest
  content_type; malformed/traversal key rejection; 404 missing row/object; storage-unreachable
  5xx distinct log; `Cache-Control` + `ETag`/`304` asserted); and the **session_version →
  read-access invariant integration tests** (login → image 200 → `logout()` → same cookie →
  image **401**; operator password rotation/session-version bump path → same cookie → image
  **401**).
- **Ops (post-merge, after PR2 verified in prod):** operator tears down CF Access Application 1;
  re-verify `api.mealy.dev` is protected by first-party auth alone.

### Rollback and reversal plan (Adversarial review, GPT-5.5)

PR2 changes the storage source of truth for new prod uploads. A blind rollback from PR2 code to
PR1 code after users create R2-backed uploads would strand those new `/uploads/{key}` references,
because PR1 reads only the local disk mount. Treat rollback in three windows:

1. **Before PR2 deploy:** normal rollback is safe; prod still writes to local disk and CF Access
   remains up.
2. **PR2 verification window, before ordinary household use:** keep CF Access Application 1 up
   and avoid creating real household uploads. Use only a throwaway smoke upload. If image reads
   fail, either forward-fix PR2 or redeploy PR1 and delete the throwaway DB reference/object.
3. **After PR2 has accepted real R2 uploads:** prefer forward-fix over rollback. If rollback is
   unavoidable, first export the affected `assets` rows and R2 objects created since PR2 cutover,
   restore compatible local files or accept documented broken image references, and only then
   redeploy PR1. Do not tear down CF Access until this window has passed and PR2 is verified.

Add the PR2 runbook checklist item: record the cutover timestamp, avoid real uploads during the
smoke window, and explicitly choose "forward-fix vs rollback with R2→disk recovery" if smoke
verification fails.

## Problem Statement

Provision all real production infrastructure (Fly app + Postgres, Upstash Redis, Cloudflare R2, Vercel, Cloudflare Access edge gate, DNS) and prove the split-origin cookie + CORS plumbing works end-to-end with a stub — **before** any auth code is written.

The parent plan's M2 section is dense and reviewed (3 eng + 1 CEO + 1 adversarial). This child plan does NOT relitigate those decisions. It does ONE thing: turn that 30-line spec into an executable, verifiable, vertical-slice implementation sequence on `prod-deploy-skeleton`.

## What Makes This Cool

The whole milestone is a bet that **infra unknowns are cheaper to discover before auth code is written than after**. The split-origin cookie scenario (`mealy.dev` → `api.mealy.dev` setting `__Host-refresh`) cannot be validated locally — no real eTLD+1, no real Cloudflare proxy, no real browser SameSite resolution. M2 is the milestone where the "does this actually work?" question stops being a thought experiment.

The split-origin cookie flow that M2 verifies (Eng review 1, issue 3; updated after adversarial + eng second-pass changes so the diagram stays current):

```
Browser at  mealy.dev
    │
    │ fetch('https://api.mealy.dev/plumbing-test',
    │        { method: 'POST', credentials: 'include' })
    ▼
Cloudflare proxy ──┐
    │              │ Slice-4 bypass policy:
    │              │ /plumbing-test
    │              │ /plumbing-test/read  → SKIP Access challenge
    │              │ everything else      → OAuth-style 302 to login
    ▼              │
Fly machine        │
    │              │
    ▼              │
FastAPI CORSMiddleware ◄── allow_credentials=True, max_age=3600
    │              │       allow_origins=[CORS_ALLOW_ORIGINS] ◄── fail-fast in prod (issue 4)
    ▼
/plumbing-test endpoint (POST)
    │
    ▼
Set-Cookie: __Host-plumbing-refresh=<probe>; HttpOnly; Secure; Path=/; SameSite=Lax
Headers: Cache-Control: no-store
Body: {"set": true, "probe": "<opaque-value>"}

Then on the next call to api.mealy.dev with credentials: 'include',
the browser auto-attaches __Host-plumbing-refresh:

GET /plumbing-test/read  →  {"value": "<probe>"}  + Cache-Control: no-store

Frontend success rule:
POST.probe === GET.value   ← cookie round-trip verified
```

The vertical-slice approach (Approach B, chosen during office-hours 2026-04-22) means each layer of the stack gets its own "did this work?" checkpoint instead of one all-or-nothing big-bang deploy. Failure mode goes from "debug everything at once at 11pm" to "this slice broke, rollback this slice, fix, re-deploy."

## Constraints

All locked decisions are inherited from the parent plan's M2 section. Re-stating only what `/execute-plan` and `/plan-eng-review` need at hand here:

- **Stack pieces, all Day-1 provisioned:** Fly app (web + worker + beat process groups), Fly managed Postgres, Upstash Redis, Cloudflare R2 bucket, Vercel project. Some are exercised later (R2 in M7); all credentials wired in M2 as Fly secrets.
- **Domains:** `mealy.dev` → Vercel; `api.mealy.dev` → Fly. DNS + proxy via Cloudflare (orange-cloud).
- **Edge gate (M2-M5):** Cloudflare Access policy on both subdomains, restricted to operator email `willdoucet@gmail.com`. Removed in M5 PR #2.
- **Cookie shape under test in M2:** `__Host-plumbing-refresh`, `HttpOnly=true`, `Secure=true`, `Path=/`, **NO `Domain` attribute**. The important browser-security invariant is the `__Host-` prefix + attributes, not the literal auth cookie name. M2 intentionally uses a distinct probe-cookie name so the publicly bypassed `/plumbing-test*` endpoints cannot overwrite the future real auth cookie during mixed M2/M3/M4 rollout. SameSite=Lax tried first; fall back to None only if browser matrix demonstrably fails.
- **Probe cookie semantics are intentionally non-auth:** the plumbing cookie value is a fresh opaque throwaway probe, never persisted server-side, never accepted as auth/session state, and safe to echo back only because it is not a credential. Do NOT reuse any future M3 refresh-token generator, session table, or auth dependency for `/plumbing-test*`. The point of M2 is transport verification only.
- **Cache headers (locked Eng review 3 of parent):** `index.html` → `Cache-Control: public, max-age=0, must-revalidate`; `/assets/*` → `Cache-Control: public, max-age=31536000, immutable`. Vite hashes asset filenames so long-cache is safe.
- **Fly scaling:** `auto_stop_machines = false` and `min_machines_running = 1` for **both** `web` and `beat` (web: cold-start would break M4's <300ms refresh budget; beat: must always be running to fire the 10-min iCloud sync schedule — auto-stop would create gaps where no scheduled tasks fire). `worker` keeps Fly defaults (jobs queue in Redis; workers can cold-start on demand). **Beat must be exactly one process** in production. (Fix from spec review issue 7 — earlier draft incorrectly let beat keep auto-stop.)
- **Migrations:** `[deploy.release_command]` runs `alembic upgrade head` before web becomes healthy. Migrations must be backward-compatible (release_command failure → previous image keeps serving).
- **DB pool sizing per process group:** `SQLALCHEMY_POOL_SIZE=3`, `SQLALCHEMY_MAX_OVERFLOW=2`. Web + worker + beat × 5 = 15 peak vs. ~20 Postgres limit.
- **Upstash TLS:** Celery `broker_url` and `result_backend` use `rediss://...` not `redis://`. Local docker-compose uses `redis://` — schemes must be swappable via `REDIS_URL` env alone.
- **CORS env var name locked:** `CORS_ALLOW_ORIGINS` (matches existing `backend/app/main.py:32` and `backend/tests/unit/test_cors_config.py`). Do NOT introduce a new `ALLOWED_ORIGINS`.
- **CORSMiddleware `max_age=3600`** so OPTIONS preflight is cached.
- **Cloudflare rate-limit:** 10 req/min/IP on `api.mealy.dev/auth/*` (covers M3 from day 1, before any /auth code lands).
- **`/healthz` behavior (Eng review issue 6, decision 6A — shallow probe):** Returns `{"status": "ok"}` (HTTP 200) **unconditionally** as long as the FastAPI process can serve a request. Does **NOT** ping DB or Redis. Body discipline: only the `status` key — no version/config/hostname (CEO body-discipline rule from parent line 154). **Deviation from parent line 147** (which says "returns 200 once DB + Redis check out") is intentional: with `min_machines_running=1` for web, deep probes turn 5-second dep flaps into total user-facing downtime instead of graceful degradation. DB/Redis health surfaces via `fly logs` and per-request errors instead of pulling the only machine out of rotation. (Single-instance Fly inverts the conventional-wisdom calculus that assumes multi-instance + load-balancer routing around bad instances.)
- **CORS production fail-fast (Eng review issue 4, decision 4A):** Modify `_parse_cors_origins` in `backend/app/main.py:18-26` so that when `APP_ENV=production` AND `CORS_ALLOW_ORIGINS` is unset OR resolves to an empty list, the function raises `RuntimeError("CORS_ALLOW_ORIGINS must be set when APP_ENV=production")` at import time. Prevents the silent localhost-fallback failure mode where a production deploy with a missing secret returns 200 from `/healthz` but rejects every cross-origin XHR. Existing dev/test behavior (returns localhost defaults when env unset) is preserved when `APP_ENV != "production"`.
- **`APP_ENV` is a NEW env var introduced in M2 (Eng review 2, issue 1):** Set ONLY on Fly (`APP_ENV=production`). MUST stay unset in local docker-compose, CI workflows, and the visual-test stack — those rely on the existing dev-default CORS behavior. Default behavior when unset = development (localhost origin fallback). A future operator adding `APP_ENV=production` to CI secrets would cause CI to fail-fast at import time until `CORS_ALLOW_ORIGINS` is also set there. Rule: treat `APP_ENV=production` as a Fly-only marker — never copy it into other environments.
- **Existing `/uploads` StaticFiles mount (Eng review issue 2 clarification):** `backend/app/main.py` mounts `/uploads` as `StaticFiles(directory=UPLOAD_DIR)` for legacy local-disk uploads. **NOT modified in M2.** The mount stays publicly accessible at the FastAPI level during M2-M5 because Cloudflare Access edge-gates the entire `api.mealy.dev` subdomain (operator-only). M5 PR #1 swaps to first-party auth-gated reads (parent plan line 230); M7 swaps storage to R2 with the same auth contract (parent plan line 265). M2 leaves it alone — flagging here so reviewers don't wonder why a publicly-readable upload mount is shipping to prod.
- **`migration-upgrade` CI job:** New job in `.github/workflows/test.yml` — clean Postgres, `alembic upgrade head` from base, then `alembic downgrade -1 && alembic upgrade +1` for newest revision.
- **Secrets durability:** `FERNET_KEY` ported intact from CI (changing it makes stored iCloud creds undecryptable). `JWT_SECRET_KEY` and `HOUSEHOLD_ACCESS_KEY` generated fresh in pre-flight — these are M3 concerns; provisioning them in M2 is a deliberate small scope expansion to avoid a mid-milestone Fly secret PR (parent plan M2 spec doesn't list them; flagged by spec review issue 6 as acceptable).
- **Visual-test docker-compose healthcheck (`backend/docker-compose.yml` `api-test`):** **NOT modified in M2.** Parent plan line 235 explicitly assigns this update to M5 PR #1, where unauthenticated `GET /` becomes 401 and the current healthcheck breaks. M5 is the right home; M2 leaves it alone. (Resolves spec review issue 2.)
- **Lock-heavy migration quiesce enforcement:** the M2 `migration-upgrade` CI job verifies up/down symmetry only. Quiesce-marker enforcement (parent line 162) lives in the M8 runbook + Alembic revision header convention, not in M2 CI — no lock-heavy revisions exist yet in this codebase, so there is nothing to enforce against today. (Resolves spec review issue 5.)
- **Cloudflare Access bypass policy on `/plumbing-test*`:** the Access challenge uses an OAuth-style redirect that an XHR cannot complete from a different origin. Without a bypass, the `mealy.dev` → `api.mealy.dev/plumbing-test` `fetch()` would receive a 302 to the Access challenge instead of the cookie response. M2's Access policy must therefore include an explicit bypass rule for the two exact plumbing paths only: `^/plumbing-test$` and `^/plumbing-test/read$` (or one equivalent exact-match rule such as `^/plumbing-test(?:/read)?$`). Do NOT use a broader prefix match that accidentally exposes unrelated future routes. The bypass is removed alongside the endpoints in M5 PR #2. (Resolves spec review issue 3 — critical.)
- **Plumbing-test responses are never cacheable:** both `POST /plumbing-test` and `GET /plumbing-test/read` must return `Cache-Control: no-store` so browser/devtools/proxy caching cannot make the cookie probe look healthy when it is actually stale or missing.
- **Cloudflare config has a checked-in snapshot (Eng review 3, issue 1):** `infra/cloudflare-state.md` is the canonical intent file for all Cloudflare dashboard state during M2-M5. PR-body capture freezes a moment; the snapshot file outlives the M2 PR and is updated in the same commit as any slice that touches Cloudflare. M5 PR #2 must also remove the bypass section from this file when it removes the bypass policy from the dashboard. Real drift-detection (Cloudflare API or Terraform) is intentionally deferred to the M8 runbook (TODOS.md). The M2-only mitigation is: diffable intent in repo + Slice 7 manual eyeball reconciliation against the live dashboard. Required schema:

## Premises

These are the load-bearing assumptions for M2. All inherited from the parent plan and confirmed intact during the 2026-04-22 office-hours session (assignment recap was "smooth — nothing surprising").

1. **Provision-infra-first is the right sequencing.** Auth-code-first would force rewrites across M3-M5 if the cookie shape, CORS rules, or origin policies turn out wrong in real browsers. — confirmed, parent plan §Premises.1
2. **Cloudflare Access is the right edge gate** for M2-M5. Single gate covers both subdomains via Cloudflare's auth plane. — confirmed, parent plan Open Q #2.
3. **SameSite=Lax should be tried first** because `api.mealy.dev` and `mealy.dev` share eTLD+1. Fall back to None only if browser matrix fails. — confirmed, parent plan M2 SameSite rule.
4. **Vertical-slice ordering** beats provision-then-wire because it localizes failure surface to one layer at a time. — confirmed, office-hours 2026-04-22.
5. **All M2 work ships in one PR to master** (parent plan §Premises.5). The branch carries multiple deploys across slices, but only one PR.
6. **Account setup is done.** All 5 platform accounts created, regions chosen, tokens captured. — confirmed, office-hours 2026-04-22.

## Approaches Considered

### Approach A: Provision-then-wire (literal parent-plan order)
- **Order:** Provision all 5 platforms in their UIs → DNS → Cloudflare Access → backend code (`/healthz` + `/plumbing-test`) → frontend code → one big deploy → browser matrix → rate-limit + CI.
- **Effort:** M (human ~3-5 days / CC: ~4 hours)
- **Pros:** Matches parent plan literally. One big deploy. Simplest mental model.
- **Cons:** First failed deploy debugs ALL infra at once. If `fly.toml` is wrong AND CORS is wrong AND DNS hasn't propagated, you can't tell which is biting you.
- **Reuses:** Existing `backend/docker-compose.yml` as local-parity reference.

### Approach B: Vertical slice — RECOMMENDED
- **Order:** Pre-flight inventory → Slice 1 (Fly + Postgres + /healthz) → Slice 2 (Upstash + worker + beat) → Slice 3 (R2 secrets) → Slice 4 (Vercel + DNS + Cloudflare Access on both subs) → Slice 5 (/plumbing-test + browser matrix) → Slice 6 (rate-limit + migration-upgrade CI) → Slice 7 (final sweep + PR).
- **Effort:** M (human ~3-5 days / CC: ~4-5 hours; ~5 deploys vs 1)
- **Pros:** Each slice has its own pass/fail checkpoint. Failures localize to one layer. First prod deploy under the belt early. Branch can be paused mid-slice without leaving infra in an inconsistent state.
- **Cons:** ~5 deploys instead of 1. Branch open longer. Requires discipline that each slice is additive (don't rip-and-replace `fly.toml` between slices).
- **Reuses:** Same as A.

### Approach C: Critical-path first (cookie verify before infra) — REJECTED
- **Order:** Implement `/plumbing-test` against local docker-compose first; verify cookie shape; THEN provision.
- **Why rejected:** Cross-subdomain cookies CANNOT be validated locally. No real domains, no real eTLD+1 split, no real Cloudflare proxy. Local cookie testing tells you nothing about whether prod will work. This rejects the M2 premise.

## Recommended Approach

**Approach B — Vertical slice.**

Rationale: M2 exists because "discover infra issues before they cascade into auth code" is the highest-value bet of the entire 8-milestone plan. A single big-bang deploy at the end of M2 turns that bet into "discover ALL infra issues simultaneously at the worst possible moment." Slicing converts one debugging session into 5 small "did this layer work?" checkpoints. With CC the marginal cost of extra deploys is minutes, not days.

- Cloudflare → Security → WAF → Rate limiting rules → new rule

  - Action: **Block**. Do NOT use Managed Challenge here: `/auth/*` will become machine-driven XHR/fetch traffic in M3/M4, and a challenge page is the wrong failure mode for API clients.

Two-step verification because Cloudflare's WAF rate-limit ordering vs. Access/origin resolution is implementation-dependent:
  1. Obtain one valid authenticated path through Access for the API origin before the burst. Acceptable options:
     - export a fresh `CF_Authorization` cookie from an already-authenticated browser session for `api.mealy.dev`, or

     for i in {1..15}; do curl -s -o /dev/null -w "%{http_code}\n" \
       -X POST https://api.mealy.dev/auth/login \
       -H "Content-Type: application/json" \
       --cookie "CF_Authorization=<value>" \
       -d '{}'; done

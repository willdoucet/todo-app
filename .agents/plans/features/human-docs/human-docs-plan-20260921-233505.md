## Problem Statement

In the user's words: the last time nothing readable existed, the question was **"What does
feature X do now?"**, and the answer came from asking an agent or from memory. The repository
holds every fact needed to answer it (an approved plan, a summary with deviations, two code
reviews, a pull request) but all of it is written for agents and reviewers, is long, and is
organized per plan, not per feature. There is no page a person opens to learn what a feature
does today, and no dated record of what each ship changed that a person would read.

## Status Quo

Ask a session, or remember. Cost: one session per question, and "the answer is never the same
twice." Small, real, recurring. The Learning summaries, the plan summaries and the PR bodies are
the raw material; nobody reads them for this question.

## Target User & Narrowest Wedge

The user: the builder, six months from now, and the same person in a fresh clone or on GitHub
(feature pages and log entries are committed by `/ship`, so they travel; a brief is local until
someone commits it; the vault never travels). Secondary: anyone the repository is shared with.

The wedge (Q4): **the feature page is the product.** `docs/human/features/<slug>.md` answers
"what does X do now" in one screen. `docs/human/log/` exists so the page can be rewritten on every
ship without losing history. `docs/human/briefs/` is the parking lot for office-hours prompts that
are not ready to run, with one intake row so they can be run from where they sit.

## Premises

Agreed by the user on 2026-09-21 (UTC), all ten:

1. The problem is "I can't find out what feature X does now without asking an agent". The
   feature page is the product; the log exists so the page can be rewritten without losing
   history.
2. Doing nothing costs a session per question: real but small, so v1 stays small. No new skill,
   no new helper, nothing in the review-gate cluster.
3. A feature is not a plan. The feature slug names a capability the way a person would say it
   (`mealboard`, `household-login`), never a branch or plan name. No command can derive that, so
   `/ship` lists the existing pages and proposes one of: update this page / new page `<slug>` /
   log-only. It goes in ship step 1's existing ASSUMPTIONS block, so it costs no extra round trip.
4. The log slug is mechanical: `log/<utc-date>-<safe-branch>.md`. Log-only ships have no feature
   slug, so the branch is the only rule that works for every ship. One entry per pull request: a
   re-run of an interrupted ship updates the entry that names that PR, never writes a second.
5. Hook: written in ship step 8 (PR_URL and the shipped record exist; beside the Learning
   summary), committed by step 9's record commit, so it is in the pull request before merge.
   Failure is soft: by step 8 the code is pushed and the PR is open, so a hard fail cannot
   un-land anything; a missed write is `DONE_WITH_CONCERNS` naming the file.
6. Plan link: `/ship` refuses without a plan, so one always exists at write time. The link is
   always written, repo-relative Markdown. The page retells; it never copies plan text.
7. Learning summaries stay exactly as they are (vault, per plan, the why, optional, local). The
   feature page holds what-it-does-now and links the plan for the why. The README describes the
   vault as "intake, plus optional local learning summaries", which is what ship already does.
8. `briefs/` keeps its name (office-hours already calls its input the "seed brief"). v1 gives it
   a template, a README paragraph, and one office-hours intake row so
   `/office-hours docs/human/briefs/<slug>.md` works. The brief's text goes verbatim into the
   plan under `## Source brief` when the plan is written, and on approval the file is removed on
   the branch, so `briefs/` always equals what is still parked. (Spec review 1: the copy happens
   at plan-writing time, step 12; only the removal waits for approval, §4.)
9. A `modules.human_docs` switch gates the ship step, as `learning_summaries` is gated. On by
   default for new projects; the upgrade turns it on where the key is absent.
10. Rot is made visible, not prevented: every feature page opens with "As of `<utc-date>` ·
    PR". A page that says how old it is beats one that pretends to be current.

## Landscape findings

Searched with category terms only (changelog conventions; AI-generated docs pitfalls;
docs-as-code and Diátaxis).

- **What everyone knows.** Changelogs are for humans: one line per change, imperative mood,
  link out for detail, exclude noise, never paste commit messages or PR titles
  (keepachangelog.com; common-changelog.org). Docs live in git and are reviewed in pull
  requests. Diátaxis separates *reference* (what it is) from *explanation* (why) and both from
  history; mixing them is what makes a page unreadable.
- **What current discourse says.** AI-written docs fail in a specific way: no audience is
  named, so the model outputs everything; they rot faster because code now changes faster; "a
  person still has to choose what's notable". The standing advice is: do not let the AI write
  the human docs (passo.uno, "What's wrong with AI-generated docs"; dev.to and Mergify posts on
  auto-generated docs).
- **Why the convention is wrong here.** That advice assumes the generator has only code to read
  and nobody reviews the output. At ship step 8 the opposite holds: there is an approved plan
  with the problem in the user's words, a summary with deviations, two code reviews, and a pull
  request the user merges by hand. Generation is safe under four constraints: written only at
  ship, only from reviewed material, one screen with the audience fixed by the template, and
  visible in the PR diff before merge. Two further points the convention does not cover: there
  are no release versions, so the unit is the ship and one file per ship beats a single
  `CHANGELOG.md` that every concurrent branch would conflict on; and rot is not preventable in
  v1 (quickfixes are out of scope), so it is made visible instead. Recorded under LESSONS
  Decisions at approval.

## Approaches Considered

All three share the skill-side work (§3, §4, §8) and differ in where template bodies live and
how folders and config reach a consumer.

### Approach A: Lazy and inline

Template bodies inline in `ship/references/human-docs.md`, as `learning-summary.md` does today;
`mkdir -p` on first write; no installer change; each consumer hand-edits `config.json` for the
flag and the exempt line. Effort S (human ~1 day / AI-assisted ~1.5 hours). Risk Low.
Completeness 6/10. Pros: fewest files, nothing in `bin/framework` changes. Cons: hand-edited
config per consumer; `briefs/` does not exist until someone creates it; a consumer cannot adjust
a template without editing the skill reference, which upgrade then refuses to overwrite; drops
the templates and upgrade scaffolding the user asked for.

### Approach B: First migration

Templates as files under `payload/templates/human/`; `migrations/001_human_docs.py` creates the
folders and README, adds the exempt line and the flag; a separate function for `init` because a
fresh init never runs migrations; doctor warns on a missing folder. Effort M (human ~3 days /
AI-assisted ~4 hours). Risk Med. Completeness 9/10. Pros: uses `migrations/` for what its README
says; runs once. Cons: `load_migrations` and the upgrade loop have zero tests, so this PR must
write the first ones; two code paths do one scaffold and can drift; a migration's `run()` gets no
`Report`, so `upgrade --dry-run` prints only the migration's name and not what it would write
(the user was bitten once by a dry-run that showed less than the truth).

### Approach C: Shared install step, no migration (chosen)

Same templates as B. The scaffold is one idempotent function in `bin/framework`'s "Shared install
steps" block, called by `init`, `migrate` and `upgrade` the way `copy_payload` is. It uses
`write_if_absent`, `render` and `Report`, so dry-run lists every file and config change. Effort M
(human ~2 days / AI-assisted ~3 hours). Risk Low. Completeness 9/10. Pros: one code path for three
callers; honest dry-run for free; tests follow the existing `test_init_*` / `test_upgrade_*`
patterns; matches precedent (the vault folder and its README are scaffolded by
`install_harness_files`, not by a migration). Cons: `migrations/` stays unproven; upgrade
re-checks on every run and re-creates a folder deleted while the flag is on.

## Recommended Approach

C. A migration transforms state that already exists (rename a key, rewrite a value, raise
`schema_version`); an install step ensures something is present. Creating folders and adding an
optional key with a default is the second kind. The tell is that B needs the same logic twice.
When one piece of logic needs two homes it is in the wrong category. Proving the migration
machinery is worth doing on a change that transforms something, with a contract that can report
its dry-run.

### 1. Layout in a consumer repository

```
docs/human/
├── README.md              # rendered from templates/human/README.md; write-if-absent
├── features/<slug>.md     # one page per capability; rewritten on every ship that touches it
├── log/<utc-date>-<safe-branch>.md   # one entry per pull request; never rewritten after merge
└── briefs/<slug>.md       # parked /office-hours prompts; deleted on plan approval
```

Empty folders carry a `.gitkeep` so the scaffold is visible in the upgrade pull request. A
consumer that already has a `docs/` directory gets `docs/human/` nested inside it; nothing else
under `docs/` is read or written.

Eng review 1: the installer also appends `.obsidian/` to `.gitignore` the first time
`ensure_human_docs` runs with the flag on (§5). The README tells a person to open this folder
as an Obsidian vault, and Obsidian writes its workspace state to `<vault>/.obsidian/`, which
ship step 9's `git add -A` would otherwise sweep into every record commit (neither todo-app's
`.gitignore` nor `harness/gitignore.snippet` ignores it today; the notes vault never needed it
because the whole vault is ignored). The line is unanchored, so a vault opened at the
repository root (open question 2) is covered too.

Installed by the payload (never read by a person directly):

```
.agents/templates/human/README.md    # {{PROJECT_NAME}}, {{VAULT_PATH}} rendered by the installer
.agents/templates/human/feature.md   # filled by /ship
.agents/templates/human/log.md       # filled by /ship
.agents/templates/human/brief.md     # copied by a person; read by /office-hours
```

A consumer may edit any of the four; `framework upgrade` then leaves that file alone with the

### 2. Templates (exact bodies)

Slot conventions, stated once in the `## Rules` section (spec review 3): `{{…}}` is filled by
the writer named in the file; `<…>` inside a slot is a sub-slot; `a | b` inside a slot means
choose one; `<utc-date>` is the output of `date -u +%F`; `{{one line}}` in a History row is
the log entry's H1 without its date. The fenced bodies below are the payload files, verbatim,
and nothing else;
each "Rules" paragraph that follows a body goes into `ship/references/human-docs.md` under a
`## Rules` heading (spec review 2), except the brief's, which goes into
`office-hours/references/brief-intake.md`.

**`templates/human/feature.md`** (written by `/ship`; the reader is a person who does not have
the code open)

```markdown
# {{FEATURE_NAME}}

As of <utc-date> · [PR #{{PR_NUMBER}}]({{PR_URL}}) · [plan]({{PLAN_RELPATH}})

## What it does

{{Two to five sentences. The whole capability as it behaves now, not this ship. Say what it
does, not what it is called: no function, file, table or route names. Written fresh on every
ship that touches this page.}}

## What changed in this ship

- {{One line per change a person would notice, imperative mood ("Add…", "Fix…"), this ship only.
Replaced, not appended, on the next ship.}}

## History

- {{LOG_DATE}} — [{{one line}}](../log/{{LOG_FILE}})
{{Newest first, at most ten rows; the oldest row drops off, the log folder keeps everything.
Links only; the log entry holds the detail.}}
```

Rules for the page (spec review 1: placeholders named, caps split): `{{FEATURE_NAME}}` is the
capability's name as a person would say it, proposed at ship step 1 beside the slug (free text,
title case: "Household login", not the slug); the page is at most 40 lines excluding `## History`,
and History at most ten rows; "What it does" is a retelling from the plan's problem statement and
the summary, never an excerpt; no frontmatter (GitHub renders it as a table, and the header line
already carries the date); relative links only, so the page works on GitHub and in Obsidian;
`{{PLAN_RELPATH}}` is `../../../` followed by the repo-relative `_PLAN_FILE` (whatever
`paths.plans` is; `../../../.agents/plans/features/<dir>/<file>.md` by default). `{{LOG_FILE}}`
and `{{LOG_DATE}}` are the log entry's actual filename and the date parsed from it (§3 step 4),
never recomputed. `{{PR_NUMBER}}` is the trailing integer of `PR_URL`; when a pull request could
not be opened (no `gh`), `PR_URL` is the compare URL `pr-body.md` already sets, and the PR cell
of this header and of the log entry's is written as `[PR pending](<that compare URL>)` (one
form, spec review 2); the ship's `DONE_WITH_CONCERNS` names both files for a hand edit unless
the user hands back the real URL inside the run (§3 step 4).
Eng review 2 (user decision): on a part that does not complete its plan (`PARTIAL=1`), "What
it does" describes what works once this part merges, never the plan's end state (the plan's
problem statement describes the whole plan, so retelling it would claim the unshipped
parts); one closing sentence may say more is coming, without part labels. "What changed in
this ship" is this part's changes.

### 3. The ship hook (`payload/skills/ship/SKILL.md`, `references/human-docs.md`, `references/pr-body.md`)

All gated on `modules.human_docs` being `true` in `$REPO_ROOT/.agents/config.json`; when it is
not, steps 1 and 8 each print one skip line in the transcript and nothing else changes (spec
reviews 2 and 3).

Eng review 2 (user decision, 2026-09-23 UTC): every part of a plan that ships in parts is a
ship here. Each part writes its own log entry (premise 4: one entry per pull request) and
follows its own step 1 page decision; unlike the Learning summary, nothing waits for the last
part. Rejected: the page on the last part only (the page is stale or missing while earlier
parts are live, and its History would link only the last entry without another lookup), and
nothing until the last part (breaks premise 4; an earlier part can be live for weeks with no
record a person reads).

**Step 1, the ASSUMPTIONS block** gains one line. Before writing the block, the skill lists the
existing pages (`ls "$REPO_ROOT/docs/human/features/" 2>/dev/null`; an empty or missing folder
lists nothing) and proposes exactly one of:

- `update features/<slug>.md` when an existing page names this capability (title or intake words
  match; the skill says which words);
- `new page features/<slug>.md` when no page does, with the slug and the capability's name
  (`{{FEATURE_NAME}}`, free text) it proposes;
- `log-only` when the ship adds nothing a person would name as a capability (an infrastructure
  change, a dependency bump, a refactor; spec review 3 removed "a framework upgrade" from the
  examples because a workflow upgrade that gives people something new, like this plan's, is a
  capability of the repository).

plus the log entry's path: the lookups of step 8's item 4 run here too (one `grep` each), and a
hit shows `update log/<existing file>` (an interrupted ship, or one that crossed midnight);
otherwise the planned `log/<utc-date>-$SAFE_BRANCH.md`. The user corrects it in the same reply
they already give for the part, the sync convention, tests, commit split and PR title (the
part line is 1.4.0's; Eng review 2).

**Slug rule.** `^[a-z0-9]+(-[a-z0-9]+)*$`, 2 to 40 characters: lowercase, digits, single
hyphens, no leading or trailing hyphen. Named for the capability as a person would say it (for
example `household-login`, `recipe-import`, `calendar-sharing`), never for a branch, plan or
milestone. (The skill text keeps "for example" on that line and never uses a product name: the
convention lint's `FORBIDDEN` list includes `mealboard` and `todo-app`, and only a line with
an `ALLOW_LINE` word such as "example" escapes it; spec review 3.) A proposed slug that fails
the rule is corrected before the block is shown; one the user types in the correction reply
that fails the rule is refused with the rule quoted and the block is re-shown with that line

# Design: Optional to run, not optional to resolve — one review-status vocabulary and a resolution gate

Generated by /office-hours on 2026-09-15
Branch: workflow-review-resolution
Status: APPROVED (2026-09-15)
Mode: Startup (intrapreneurship; pure engineering and infrastructure)
Spec review: 3 rounds (6 → 8 → 9/10), 35 issues fixed in place

## Problem Statement

The workflow's next-step helper can route an agent past a review that ran and left problems
open. `workflow-state` asks one question of each review — "is its latest log entry a passing
status?" — and a review that **never ran** and a review that **ran and failed** both answer "no".
For a review the pipeline treats as optional, both then produce the same optional suggestion,
and the implementation verdict ignores both. Nothing records that a later review closed an
earlier one's open item, so the only way to clear the flag is to re-run the original review.

It surfaced on M8 (`prod-launch-release`) on 2026-09-14. `/plan-ceo-review` logged
`issues_open` with one critical gap left open (a break-glass flag nothing detected); `/plan-eng-
review` closed that gap in the plan's text the same day; the dashboard kept showing
`CEO | issues_open !` and `--next` printed "Optional: /plan-ceo-review — not yet run" for a review
that had run. The verdict said `CLEARED FOR IMPLEMENTATION` throughout.

Reading the code turned up the same failure in a sharper form. The status words themselves do not
mean one thing:

- `issues_found` means **fixed** for `plan-adversarial-review` ("the plan or artifact was
  hardened") and **not fixed** for `qa` and `design-review` ("`done` when … every found issue was
  verified fixed; otherwise `issues_found`"). `workflow-state` puts all three in `FIX_IN_PLACE` and
  counts `issues_found` as passing for each. A QA run that left bugs unfixed shows ✓.
- At the ship stage, `decide()` suggests `/qa` and `/design-review` only when they are *absent*
  (`if not reviews.get("qa")`). Once either has run, a failing result is never mentioned again.
- `review-log` accepts any status string. This repository's log already contains
  `review-implementation` and `final-review` entries with `issues_found`, a word neither skill
  defines.
- `critical_gaps` means "found" in the CEO review's entry (5) and "still open" in the eng
  review's (0, alongside `critical_gaps_found_and_closed=3`).

In the user's own words, answering how open review items get closed today: **"Agents handle it, I
don't check."** That makes `workflow-state --next` and the dashboard verdict the only control in
practice. A path where they route past an open review is an ungated path to `/ship`.

## Status Quo

Agents follow `workflow-state --next`; the operator approves questions and does not track review
status. When a plan review has logged `issues_open` in the past, the fix has been to re-run that
review until it logs `clean` — every earlier CEO, eng and adversarial plan-review entry in this
repository's log that was `issues_open` was later superseded by a `clean` entry for the same plan
and skill. M8 is the first
case where a *different* review closed the item, and there was no way to say so.

Cost of the status quo: a re-run of a long review (a CEO review in SELECTIVE_EXPANSION mode is
the better part of an hour and can reopen scope) purely to clear a flag another review already
closed; and, for QA and the design audit, no signal at all when a run leaves problems open.

Interim guard, recorded 2026-09-14 in LESSONS.md on the `prod-launch-release` branch (uncommitted
there, not on this branch): before trusting `CLEARED FOR IMPLEMENTATION`, run `review-read` and
treat every plan-stage `issues_open` entry as open.

## Target User & Narrowest Wedge

**Target user:** the agent that runs the next skill because `--next` named it, and the single
operator who does not check. The design has to be correct for someone who never reads the log.

**Narrowest wedge** (decided in Q4): a gate plus a resolution record. `workflow-state` blocks on
any review that ran and did not pass, and a `resolved` entry is the one way to clear it without
re-running. Done with one status vocabulary (Approach B), because premise 3 requires it.

## Constraints

- **Where the code lives.** Canonical source is `../framework/payload` (framework 1.0.0, a git
  repository with PRs; the zsh pin-SHA fix landed there as PRs #1 and #2 on 2026-09-15, `main`
  clean). Projects receive it through `framework upgrade`, which replaces files whose hash matches
  `.agents/manifest.json` and refuses to overwrite locally modified ones. The framework has no
  `.agents/` pipeline of its own, which is why this plan lives in todo-app.
- **Nothing under todo-app's `.agents/bin`, `.agents/skills` or `.agents/tests` is hand-edited.**
  PR-T is `framework upgrade` output only. `.agents/**` is exempt in the doc map.
- **Framework conventions** (`payload/skills/CONVENTIONS.md`, enforced by `tests/test_skill_lint.py`):
  SKILL.md at most 500 lines; no copying of `_shared` blocks; no hardcoded project, stack, test
  command, base branch or harness tool name; canonical tool verbs; never compute the next step in
  prose.
- **Helpers are host-side, standard-library Python.** Framework tests run with
  `python3 -m pytest tests payload/tests -q`; in todo-app with `python3 -m pytest .agents/tests -q`.
- **The review log is append-only.** No entry is ever rewritten or deleted, including legacy
  ones; new meaning is applied on read.
- **The review log is a committed JSONL file shared by every branch.** git does not union-merge it
  (`git check-attr merge` reports `unspecified`), so appends made on two branches from the same base
  conflict at the end of the file. The resolution is always to keep both sides; entries are ordered
  by `ts`, never by line position. PR-T adds `merge=union` for it in todo-app's `.gitattributes`
  (§11).
- **Separation of duties** (from the landscape search): a review never resolves its own failed
  entry — that is a re-run.
- **No `skipped` or neutral status.** GitHub counts skipped and neutral required checks as
  passing, which is widely called out as the hole that makes a required check not required.

## Premises

Agreed 2026-09-15:

1. `workflow-state --next` and the verdict are the real control, because agents follow them and
   the operator does not check. The fix makes routing past a failed review impossible in the tool
   itself; a rule written into the skills alone is not enough.
2. "Never ran" and "ran and did not pass" are different. Optional governs only never-ran. A review
   that ran and did not pass blocks its stage's gate, at the plan stage (CEO, eng, adversarial,
   design) and at the ship stage (implementation, QA, design audit, final).
3. Every status word means one thing in every skill, and `review-log` rejects unknown words when
   writing. The QA/design-audit `issues_found` inversion is a bug fixed in the same change. Old log
   entries are read through a compatibility mapping, never rewritten.
4. A `resolved` record is the only way to clear a failed review without re-running it. It names the
   review it resolves, `resolved_by` (a different skill or `operator`, never the review itself) and
   a note saying where the plan closed the issue, and it applies only to that plan file. No expiry,
   and it is not dismissed when the plan is edited.
5. Scope is the gate plus the resolve record. `--next` itself tells the agent what to do ("re-run
   X, or verify the plan closes each item and log `resolved`"), backed by one short shared-doc note.
   **Amended at approval (2026-09-15):** the user chose to build all four deferred items here rather
   than file them — the handoff step and REVIEW REPORT mirroring (§6a), the `critical_gaps` split
   (§6b), `adversarial-subagent` as a tier plus the legacy summary-name normalization (§6c), and
   `office-hours` as a display-only dashboard row (§6d). Scope is therefore the gate, the resolve
   record, and the four amendments; nothing is left in TODOS.md from this plan. Premise 7 (the VRT
   TODO stays out) is unchanged.
6. The code ships in `../framework` on its own branch and PR, with a CHANGELOG entry and version
   bump, then reaches todo-app through `framework upgrade` on this branch. After the upgrade, M8's
   stale CEO row gets a real `resolved` entry on the M8 branch.
7. The P3 TODO "Add VRT-gate check to `/plan-eng-review`" is out of scope: same file, different
   concern.

## Landscape findings

Searched with category terms only (quality-gate waivers, required status checks, stale-approval
dismissal).

- **What everyone knows.** Required checks gate merges. Exceptions are first-class records that
  name the control they override, who approved them and why, scoped narrowly and often expiring.
  Stale approvals are dismissed when the content changes.
- **What the current discussion adds.** GitHub distinguishes `MISSING` from `FAILED` among
  required-check dispositions — exactly the distinction `workflow-state` collapses — and counts
  `skipped` and `neutral` as success, which is the named hole: a check that can pass without
  running protects nothing. `FIX_IN_PLACE`'s "`issues_found` counts as passing" is that hole in this
  vocabulary.
- **Where the convention is wrong here.** Dismiss-on-change does not transfer: every review edits
  the plan by design, so the rule would void each resolution the moment the next review saved.
  Expiry does not fit short-lived plans; superseding a plan already resets its dashboard.
  Separation of duties transfers intact. Recorded under LESSONS Decisions at approval.

## Approaches Considered

### Approach A: Reader-side meaning table (minimal)
- Summary: leave every skill as is. `_lib` gets one table of what each (skill, status) pair means —
  `qa`+`issues_found` = failed, `plan-adversarial-review`+`issues_found` = passed — and
  `workflow-state` gates on it; `review-log` accepts `resolved` and rejects pairs outside the table.
- Effort: M (human: ~1 day / AI-assisted: ~1.5–2 h), about 7 framework files
- Risk: Low
- Completeness: 7/10
- Pros: matches the Q4 sizing; no skill text changes; fixes the QA inversion where it is read.
- Cons: contradicts premise 3 — `issues_found` still means opposite things, now written into a
  table the next skill author will not find; `review-read` keeps showing raw words to the plan
  reviews that call it.
- Reuses: `review_ok` and `FIX_IN_PLACE` (replaced by the table), `review_log_append`,
  `reviews_for_plan`.

### Approach B: One status vocabulary, gated and linted (chosen)
- Summary: a closed set of statuses with one meaning each; `_lib` owns the vocabulary, a
  compatibility map for legacy entries, and the disposition of each review (missing, passed,
  failed, resolved); `workflow-state` gates both stages on dispositions; `review-read` shows them;
  `review-log` validates writes; the skills that wrote ambiguous words switch to canonical ones; a
  skill-lint test fails any skill whose review-log call uses a non-canonical word.
- Effort: L (human: ~3 days / AI-assisted: ~5 h), about 25 framework files. Spec review round 1
  added the ship-stage gating, provenance snippets and verdict docs; the four approval amendments
  (§6a–§6d) added the handoff step, the `critical_gaps` split, a new gating tier with the legacy
  summary-name fix, and a display-only tier flag. Eng review's Step 0 complexity check should expect
  this size.
- Risk: Med — every review skill's completion text is touched, and the gate gets stricter on
  upgrade (a failed review that used to be ignored now blocks).
- Completeness: 10/10
- Pros: premise 3 holds structurally, enforced by a test; plan reviews that already call
  `review-read` see "failed" rather than a raw word; legacy entries read correctly with no rewrite.
- Cons: larger than the Q4 sizing; a project with locally modified skills keeps writing legacy
  words until it upgrades them, and those writes are rejected (see open question 2).
- Reuses: `tests/test_skill_lint.py`'s convention checks, `review_extra`'s envelope,
  `reviews_for_plan` unchanged (a `resolved` entry is logged under the original skill, so
  latest-per-skill already picks it up), the framework's PR and CHANGELOG precedent.

### Approach C: Gate on counts, not words (lateral)
- Summary: skills log `open=N`; `workflow-state` passes a review only when `open` is 0 after
  resolutions; the status word becomes display text; `resolved` zeroes `open` for one review.
- Effort: M–L (human: ~2 days / AI-assisted: ~3 h), about 12 files
- Risk: Med
- Completeness: 8/10
- Pros: a number cannot be inverted the way `issues_found` was; fits counts skills already log.
- Cons: moves the agreement problem to a field no one can validate for truth; plan reviews must
  sum unresolved decisions and critical gaps consistently (the `critical_gaps` ambiguity again);
  legacy entries have no `open`, so a word-based fallback is needed anyway.
- Reuses: existing count fields, `review_extra`.

## Recommended Approach

**Approach B**, chosen by the user on 2026-09-15, shipped as two pull requests from this plan
(decided at the shape gate): **PR-F** in `../framework` on branch `review-resolution`, then
**PR-T** from this branch in todo-app. A lost to premise 3 — it keeps the ambiguity and hides it in
a table. C lost because it still needs A's word mapping for every existing entry and trades a
checkable vocabulary for an uncheckable number.

### 1. The vocabulary

One definition, in `payload/skills/_shared/obsidian-sync.md` under `## Review log` (replacing its
current `STATUS` paragraph); `payload/WORKFLOW.md` points at it beside its review-log paragraph
(not in the State table, which lists plan frontmatter keys); `payload/bin/_lib.py` holds the
constants. Four words (spec review round 1: `fixed` is dropped — five reviews already fix in place
and log `clean`, so a separate `fixed` would have contradicted premise 3 for all of them; the
counts carry the detail):

| Status | Meaning | Disposition | Written by |
|---|---|---|---|
| `clean` | Nothing the review found is left open: it found nothing, or every finding was fixed in place, recorded in the plan as a decided and accepted limitation, or deferred to TODOS.md with the user's approval. Counts (`found`, `fixed`, `deferred`, `critical_gaps_found_and_closed`, …) carry the detail | passed | every review |
| `issues_open` | Something the review found is neither fixed nor decided | failed | every review |
| `resolved` | A later record closing a failed review's open items | resolved | `review-log`, on behalf of a resolver other than the review itself (§3) |
| `done` | The step completed; no findings semantics | passed | `ship` only |

Throughout this section, **ok** means disposition `passed` or `resolved`. No `fixed`, `skipped`,
`neutral`, `pass`, `cleared` or `issues_found` is valid for a new write.

Eng review 1.8a (open question 1, decided 2026-09-16): a finding the review records in the plan
as a named, accepted limitation is closed; `plan-adversarial-review` logs `clean` with
`remaining=N` carrying the count. Only a finding that still needs someone's decision makes it
`issues_open`. Eng review 1.8b (open question 2, decided): `review-log` rejects legacy words from
any caller, including a locally modified skill; the error names the four words, so the agent
recovers in one retry.

### 2. Dispositions and the compatibility map (`_lib.py`)

- `REVIEW_STATUSES` (the four words), `LEGACY_STATUS_MAP`, and `review_disposition(entry) ->
  "passed" | "failed" | "resolved"`; a review absent from `reviews_for_plan` is `"missing"`.
- `REVIEW_TIERS` moves from `workflow-state` into `_lib.py` (spec review round 2): `review-log`
  validates `resolved_by` against it and cannot import `workflow-state`.
  Eng review 1.3: each tier is a dict with keys `label`, `short`, `skill`, `invoke`, `gates`
  (not a 3-tuple — every current `for label, short, skill in REVIEW_TIERS` unpack site
  breaks; grep is the completion check). `invoke` is the slash command that runs it, separate
  from the log skill name — `adversarial-subagent` is invoked as `/review-implementation`,
  `office-hours` as `/office-hours` (never `next`, since `gates=False`). `--next` prints
  `invoke`, never the log name, so it can never name a skill that does not exist; the JSON
  field stays `next.skill` and its value is that invoke string including the leading slash
  (Adversarial review: pin the key so `/execute-plan`'s guard cannot parse a different shape).
  The lint asserts every `invoke` is a real skill directory.
- `LEGACY_STATUS_MAP` is applied on read only, keyed by `(skill, status)` with a `(None, status)`
  fallback:
  - `(plan-adversarial-review, issues_found)` → passed (that skill's definition was "hardened").
  - `(qa, issues_found)`, `(design-review, issues_found)` → failed (their definition was "not every
    issue fixed").
  - `(None, issues_found)` → failed: `review-implementation` and `final-review` never defined it, so
    the conservative reading wins.
  - `(None, cleared)`, `(None, pass)`, and `done` from any skill → passed (today's `OK_STATUSES`;
    covers legacy `qa`/`design-review` `done` and old fixtures).
  - Any other unknown word → failed. An unreadable status never passes.
  - `resolved` without a `resolved_by` (a hand-edited line; the CLI never writes one) → failed,
    and a missing `status` → failed (Eng review 1.6).
- `FIX_IN_PLACE`, `OK_STATUSES` and `review_ok` in `workflow-state` are replaced by
  `review_disposition`.
- `_lib.review_log_append` stays permissive: the framework's test helper (`R.log_review`) writes
  legacy words through it to build fixtures, and the legacy migration in `bin/framework` writes raw
  lines. Validation lives in the CLI (§3).
- `_lib.review_log_read(root, cfg) -> tuple[list[dict], int]` returns `(entries, unreadable)`
  (Eng review 1.5; Adversarial review: the return type is a tuple, not a list-plus-attribute,
  and it never raises on parse or decode failure). Today the function drops bad lines silently,
  so a `<<<<<<<` conflict marker — the state §12.2 predicts for M8's first merge — hides
  whichever failed entry sits inside the hunk, and the gate opens.
  Rules, so two implementers parse the same file the same way:
  - Iterate with `str.splitlines()` (a trailing newline does **not** create an extra record;
    `str.split("\n")` does, and would fail-close every well-formed log).
  - Blank / whitespace-only lines are skipped and are **not** unreadable.
  - A line is unreadable when `json.loads` fails **or** the value is not a `dict`
    (`json.loads("1")` succeeds today and then `.get("plan")` blows up later).
  - `UnicodeDecodeError` on the file: return `([], 1)` — the whole file is unreadable.
  - Never raise on those cases. The session banner's `except Exception: pass` would otherwise
    swallow the failure and print nothing, which is an open gate (Adversarial review: a
    fail-silent wrapper around a fail-closed check is an open gate).
  Every caller unpacks both values: `reviews_for_plan` uses `entries` and ignores the count;
  `review-log`, `review-read`, and `workflow-state` fail closed on `unreadable > 0` (§3, §4,
  §5). `gather()` stores `st["unreadable"]`. There is no second reader that still skips.

### 3. Writing (`payload/bin/review-log`)

Validation applies to both the flag form and the positional-JSON form, **and to the fully
merged entry after JSON + flags + `--field` are applied** (Adversarial review: `--field
status=` / `--field skill=` currently overwrite the flag values in `build_entry`, so
validating `args.status` before the merge lets `--status resolved --field status=clean`
smuggle a passing write that skips every `resolved` rule).

- `status` must be one of the four words, matched exactly and lowercase (`Clean` is rejected,
  not normalized — Eng review 2.4), else exit non-zero with `unknown status 'issues_found';
  use one of: clean, issues_open, resolved, done`. `done` is accepted only with skill `ship`. Which
  of `clean` and `issues_open` a given skill writes is advisory here and enforced by the skill lint
  (§8).
- `status resolved` additionally requires:
  - `resolved_by`: a non-empty string, exactly `operator` (lowercase, no alias) or the log name
    of a `gates=True` tier from `REVIEW_TIERS` with no leading `/`, and not equal to `skill`
    (Eng review 1.6: `office-hours` cannot vouch). `parse_scalar` JSON-parses `--field` values,
    so `true` / `1` / `null` / an object is rejected — it must be a string after parse
    (Adversarial review);
  - `skill` (the review being resolved) is itself a `gates=True` tier; otherwise
    `nothing gates on '<skill>'` (Eng review 2.2);
  - `note`: a non-empty string after `parse_scalar` — the plan section, report path, or commit
    SHA where each open item is closed. Same type rule as `resolved_by` (Adversarial review);
  - the current latest entry for that skill and plan has disposition `failed` (resolving a missing,
    passing, or already-resolved review is an error);
  - when `resolved_by` is a skill, that skill's latest entry on the same plan has disposition
    `passed` — not `resolved`, so a review that was itself only cleared by resolution cannot vouch
    for another — **and** its `ts` is **not earlier** than the failed entry's `ts` (`>=`, Eng
    review 1.1): the resolver must actually have run after the failure, so an agent cannot name a
    review that never looked. `>=` and not `>` because `ts` has one-second resolution and one
    skill step writes two entries: this log holds ten pairs where the failed `adversarial-subagent`
    entry and the passing `review-implementation` or `final-review` entry share the exact second,
    and §6c's natural resolution would be rejected every time under a strict comparison;
  - a caller-supplied `resolves_ts` is rejected (it is filled from the failed entry), and a
    caller-supplied `ts` earlier than the failed entry's `ts` is rejected (the resolution must
    become the latest entry; on an equal `ts` the later line wins, as `reviews_for_plan` already
    does).
- Re-running the original review later appends a new entry as today; if it fails again, it blocks
  again.
- The log must be fully readable before any append (Eng review 1.5): if `review_log_read`
  reports unreadable lines, `review-log` exits 2 naming the line numbers and writes nothing.
  Line numbers are 1-based over the file as `splitlines()` returns it (blank lines still
  occupy a number even though they are not unreadable).
- `resolved_by=operator` needs no extra flag (Eng review 2.8, open question 3): a flag the same
  agent passes is ceremony, not a check. The control is visibility — the dashboard row and
  `review-read` show `resolved_by=operator` and the note, so a false claim is visible to the user
  at the next banner. The skill rule (§7) stays: `operator` only when the user said in the session
  that they decided the item.

### 4. Reading (`payload/bin/review-read`)

- JSON: every review (plan mode) and every entry (`--all`) gains `disposition`; no existing key
  changes.
- Text: disposition goes directly after status — plan mode `skill|ts|status|disposition|extra`,
  `--all` `plan|skill|ts|status|disposition|extra`, per entry.
  The module docstring spells this format and is updated with it (Eng review 2.5); so are
  `workflow-state`'s docstring (dispositions and the Open list) and `review-log`'s usage block
  (the `resolved` form).
- Unreadable lines (Adversarial review): `review-read` fails closed the same way `review-log`
  does. If `unreadable > 0`, exit 2 naming the line numbers; do not print a successful plan-mode
  or `--all` parse as if the log were complete. JSON includes `"unreadable": N` only on that
  error envelope (the success payload's keys stay unchanged). A handoff step that trusted a
  partial parse would miss a failed review sitting inside a conflict hunk.
- Provenance: `final-review` (step 1's `review-read --json` snippet) and `plan-adversarial-review`
  (its eng-review provenance snippet) read the latest entry's `model` and `harness`. When that entry
  is `resolved`, both snippets report provenance as unknown rather than the resolver's.

### 5. Gating (`payload/bin/workflow-state`)

One rule, applied in `REVIEW_TIERS` order (Office hours, CEO, Eng, Adversarial, Design, Impl
review, Adv subagent, QA, Design audit, Final, Ship), computed **once** by a pure
`gate_state(reviews, fm, status, unreadable)` that returns `dispositions`, `open`, `missing`,
`missing_to_ship`, `verdict`, and `unreadable` (Adversarial review: the count is an argument,
not a side read, or `--next` and the dashboard disagree the moment the log is dirty).
`decide()`, `dashboard()`, and `fmt_reviews()` all read from it, so `--next`, `--dashboard`,
and the banner cannot disagree (Eng review 2.1). Tiers with `gates=False` are skipped by every
list below. Both `--next --json` and `--dashboard --json` always include `"unreadable": N`
(integer, 0 when clean).

When `unreadable > 0` the function short-circuits: `verdict` is
`NOT CLEARED — review log unreadable`; `open` and `optional` are empty; `next` is
`{"skill": null, "args": null, "required": true, "reason": "review log has N unreadable line(s); resolve the conflict (keep both sides) before any review command"}`
with N filled in; parseable rows may still render on the dashboard for visibility, but they
do not drive `next`, `missing`, or `missing_to_ship`. `--next` text prints that reason and

### 6a. The handoff step in every plan review (approval amendment)

> Run `"$BIN/review-read"`. For every earlier review whose disposition is `failed`, read its open

adversarial already do. The procedure text itself lives once in `_shared/dashboard.md` (§7), so the
skills reference rather than copy it (`SHARED_SIGNATURES` would fail a copy).

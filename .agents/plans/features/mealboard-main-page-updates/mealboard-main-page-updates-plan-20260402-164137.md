# Design: Mealboard Flexible Slots + Per-Person Meals + UI Overhaul

Generated by /office-hours on 2026-04-02
Branch: mealboard-main-page-updates
Status: APPROVED
Mode: Builder

## Problem Statement

The current mealboard has three fixed slots per day (Breakfast, Lunch, Dinner) with a single-meal-per-slot model. This is too rigid for real family meal planning:

- **Family of 4 (2 parents, 2 kids):** Kids eat different lunches, family shares dinner. Can't represent per-person meals.
- **Roommates:** Only need weekday dinners. 14 empty B/L slots per week are visual noise.
- **Couple with variable sharing:** Sometimes eat together, sometimes separate. No way to model "shared breakfast on weekends, separate on weekdays."
- **Parent of 1-year-old:** Baby eats 5+ times/day, often simple items (banana, yogurt) not full recipes. Three slots insufficient, recipe-only model doesn't fit.

Additionally, the progress tracker only counts dinners (hardcoded), and the UI needs a visual refresh — more color, vibrancy, and crispness aligned with the recent lists page update.

## What Makes This Cool

This solves a problem **no meal planning app handles well today**. Research across 15+ apps (Eat This Much, MealBoard, Plan to Eat, Paprika, Mealie, Samsung Food, Solid Starts, Little Lunches, etc.) reveals:

- Most apps offer fixed B/L/D or fully-custom slots, but none combine **smart defaults** with **progressive customization**
- **No app handles "shared dinner but separate lunches"** as a first-class concept. Mumsnet threads confirm real family frustration with this gap.
- Baby feeding apps treat simple items as first-class, but don't integrate with family meal planning
- The "Smart Defaults + Override" approach (works immediately, customize when needed) is genuinely novel in this space

## Constraints

- Must work within existing tech stack (FastAPI + React 19 + Vite + PostgreSQL + TailwindCSS v4)
- Must use existing FamilyMember model for per-person assignment (already has id, name, photo_url, color)
- All commands through Docker Compose
- Responsive: desktop (>=1200px with side panel), mobile-first
- Keep the mealboard side panel menu as-is (Meal Planner, Recipes, Shopping, Recipe Finder)
- Must migrate existing meal plan data (B/L/D entries) to new model
- Smart features (auto-fill rules, food-group tracking, AI generation) designed for in data model but NOT built in V1

## Premises

1. **Per-person meals use existing FamilyMember model** — add a many-to-many relationship between meal entries and family members. No new system needed.
2. **User-defined meal slot types** (settings) provide structure over unstructured "add meal" buttons. Structure enables scannability ("What's for baby's morning snack?").
3. **Simple items are first-class** alongside recipes — not shoehorned into the recipe system. A meal entry can be a recipe, a simple item ("banana"), or a custom name.
4. **Smart features (auto-fill, food-group tracking) are Phase 2+** — data model supports them, UI ships without them.
5. **Progress tracker reimagined** to track completion against user-configured slots, not hardcoded dinners.
6. **Data model migration** — MealCategory enum replaced by MealSlotType table. Existing B/L/D data migrated to default slot types.

## Approaches Considered

### Approach A: "Structured Slots" — Settings-Driven Configuration
Users define all meal slot types in settings before using the planner. Maximum flexibility but requires configuration upfront. Like Eat This Much.
- Effort: L | Risk: Medium
- Pro: Handles all use cases. Clean data model.
- Con: Empty settings = empty mealboard. Setup friction.

### Approach B: "Freeform Days" — Minimal Structure
No predefined slots. Just add meals to days with optional labels and family member tags. Like a Kanban board.
- Effort: M | Risk: Medium
- Pro: Zero config. Handles baby's 5-meals naturally.
- Con: Loses weekly scannability. Progress tracking hard. Visual mess at scale.

### Approach C: "Smart Defaults + Override" (CHOSEN)
Ships with intelligent defaults that work immediately. Users CAN customize but don't HAVE TO. Progressive disclosure of complexity.
- Effort: L | Risk: Low
- Pro: Works out of the box AND scales to complex cases. Best of both worlds.
- Con: Two paths (defaults vs. custom) means more frontend states.

## Recommended Approach: C — Smart Defaults + Override

### Core Concept

The system ships with sensible defaults (Breakfast, Lunch, Dinner, Snack) that require zero configuration. Users see a working mealboard on first visit. When they need more flexibility, they customize slot types in settings. Per-person assignment defaults to "everyone" but can be overridden per meal.

### Data Model Changes

#### New: `MealSlotType` table
```
meal_slot_types
  id: Integer PK
  name: String (e.g., "Breakfast", "Kid Lunch", "Baby Morning Snack")
  sort_order: Integer (display ordering)
  color: String (hex, for category badge — e.g., "#F59E0B" for amber)
  icon: String (optional emoji or icon name)
  is_default: Boolean (true for system defaults, false for user-created)
  is_active: Boolean (show/hide without deleting)
  default_participants: JSON array of family_member_ids (who typically eats this; stale IDs from deleted family members are filtered out at read time and cleaned up lazily)
  created_at: DateTime
  updated_at: DateTime
```

**Default seed data on first run:**
| name | sort_order | color | default_participants |
|------|-----------|-------|---------------------|
| Breakfast | 1 | #F59E0B (amber) | [] (everyone) |
| Lunch | 2 | #6B8F71 (sage) | [] (everyone) |
| Dinner | 3 | #E8927C (peach) | [] (everyone) |
| Snack | 4 | #B8A9C9 (lavender) | [] (everyone) |

Empty `default_participants` array = "everyone in the household."

#### New: `FoodItem` table
```
food_items
  id: Integer PK
  name: String (indexed, unique — e.g., "Banana", "Yogurt", "Crackers")
  emoji: String (nullable — e.g., "🍌", "🥛")
  category: String (nullable — e.g., "fruit", "dairy", "grain", "protein", "vegetable")
  is_favorite: Boolean (default False)
  created_at: DateTime
  updated_at: DateTime
```

Lightweight model for non-recipe food items. Reusable across meal entries. The `category` field prepares for Phase 5 food-group tracking. Browsable on the Recipes page via a "Recipes | Food Items" tab toggle.

**Emoji auto-suggestion:** A constants file (`frontend/src/constants/foodEmojis.js`) maps ~100 common food names to emojis (e.g., `{banana: "🍌", yogurt: "🥛", apple: "🍎", ...}`). When the user types a food item name, the emoji field auto-fills from this lookup. Override via a **curated food emoji grid** (~40-50 emojis grouped: Fruits, Vegetables, Protein, Dairy, Grains, Drinks, Sweets).

#### Modified: `MealPlan` table → `MealEntry` table
```
meal_entries (renamed from meal_plans)
  id: Integer PK
  date: Date, indexed
  meal_slot_type_id: FK → meal_slot_types (replaces category enum, ON DELETE RESTRICT)
  recipe_id: FK → recipes (nullable, ON DELETE SET NULL)
  food_item_id: FK → food_items (nullable, ON DELETE SET NULL)
  custom_meal_name: String (nullable — fallback free-text for one-off items not worth saving)
  item_type: Enum("recipe", "food_item", "custom") — "recipe" = has recipe_id, "food_item" = has food_item_id, "custom" = free-text custom_meal_name only
  servings: Integer (nullable, override recipe default when item_type="recipe"; ignored for simple_item)
  was_cooked: Boolean (default False)
  notes: String (nullable)
  sort_order: Integer (ordering within a slot on a day, for multiple items)
  created_at: DateTime
  updated_at: DateTime
```

#### New: `meal_entry_participants` junction table
```
meal_entry_participants
  meal_entry_id: FK → meal_entries (ON DELETE CASCADE)
  family_member_id: FK → family_members (ON DELETE CASCADE)
  PK: (meal_entry_id, family_member_id)
```

**Participant Resolution Algorithm (3-level fallback):**
1. Check `meal_entry_participants` for this entry. If rows exist → those are the participants.
2. If no rows, check `meal_slot_type.default_participants`. If non-empty → those are the participants.
3. If empty → meal is for "everyone" in the household.

This avoids requiring participant assignment on every meal. To simplify querying (especially filtering by family member), **eagerly materialize participants at write time**: when creating/updating a meal entry with no explicit participants, populate the junction table from the slot type defaults (or all family members if no defaults). This trades a slightly larger junction table for dramatically simpler queries — no 3-way conditional SQL needed.

#### Modified: `Task` model (existing)
Add these nullable fields (only populated for auto-generated mealboard shopping items):
```
  source_meals: JSON (nullable)
  aggregation_key_name: String (nullable — normalized ingredient name, e.g., "ground beef")
  aggregation_unit_group: String (nullable — "weight", "volume", "count", or "none")
```
- `source_meals`: Tracks which meal entries contributed to this task and their quantities. Structure: `[{meal_entry_id, quantity, base_unit}]`. Null for manually-added tasks.
- `aggregation_key_name` + `aggregation_unit_group`: Deterministic aggregation bucket. Used to enforce a **unique constraint**: `UniqueConstraint("list_id", "aggregation_key_name", "aggregation_unit_group", name="uq_task_ingredient_aggregate")`. This prevents duplicate shopping items even under concurrent Celery workers — if two workers try to INSERT the same ingredient, the second hits the constraint, catches the violation, and retries as an UPDATE instead.
- These columns are null for all non-mealboard tasks (manual tasks, iCloud-synced tasks, etc.)

#### Modified: `MealEntry` — add shopping sync status
```
  shopping_sync_status: Enum("synced", "pending", "failed") (nullable, default null)
```
Tracks whether this meal's ingredients have been synced to the shopping list. Set to "pending" on meal creation, updated by Celery task to "synced" or "failed" (after 3 retries). Null for meals with no shopping list linked.

#### Updated references
- `Recipe` model — rename relationship from `meal_plans` to `meal_entries` (and `back_populates` on MealEntry side)
- `FamilyMember` model — no schema changes, just referenced by new junction table

### Migration Strategy

**This migration MUST be hand-written** (not autogenerated). Alembic's autogenerate interprets a table rename as drop+create, which loses data. Test against a copy of production data before running.

1. Create `meal_slot_types` table and seed 4 default rows (B/L/D/Snack) via `op.bulk_insert()`
2. Create `food_items` table
3. Create `meal_entry_participants` junction table
4. Add `meal_slot_type_id`, `food_item_id`, `item_type`, `servings`, `sort_order` columns to `meal_plans`
5. Migrate data: map existing `category` enum values to corresponding `meal_slot_type_id`; set `item_type` = `"recipe"` where `recipe_id` is not null, else `"custom"`
6. Rename table using `op.rename_table('meal_plans', 'meal_entries')`
7. Drop `category` column and `MealCategory` enum
8. Update Recipe model relationship: `meal_plans` → `meal_entries`
9. Add `mealboard_shopping_list_id` to AppSettings table

**Default seeding:** The 4 default slot types are created in the Alembic migration (runs for both new installs and existing DBs). The `POST /meal-slot-types/reset` endpoint re-inserts these 4 rows (delete user-created + upsert defaults) with confirmation required.

### API Changes

All endpoints are at the API root (matching existing convention — `/recipes`, `/meal-plans` are root-level, not prefixed).

**New endpoints:**
```
GET    /meal-slot-types              — list all slot types (active + inactive)
POST   /meal-slot-types              — create custom slot type
PATCH  /meal-slot-types/{id}         — update (rename, recolor, reorder, toggle active)
DELETE /meal-slot-types/{id}         — check `EXISTS(meal_entries WHERE meal_slot_type_id = id)`: if yes, soft-delete (set is_active=false); if no entries, hard-delete
POST   /meal-slot-types/reset        — restore defaults (for "I messed up my config")

GET    /food-items                   — list all food items (supports ?search=banana&category=fruit)
POST   /food-items                   — create food item { name, emoji?, category? }
PATCH  /food-items/{id}              — update food item
DELETE /food-items/{id}              — hard-delete (ON DELETE SET NULL on meal_entries.food_item_id)
```

**Modified endpoints (meal-plans → meal-entries):**
```
GET    /meal-entries?start_date=...&end_date=...&family_member_id=...
POST   /meal-entries  { date, meal_slot_type_id, recipe_id?, custom_meal_name?, item_type, servings?, participant_ids?, notes? }
PATCH  /meal-entries/{id}  { meal_slot_type_id?, recipe_id?, custom_meal_name?, was_cooked?, participant_ids?, notes? }
DELETE /meal-entries/{id}
```

**New query parameter:** `family_member_id` on GET filters to meals where that person is a participant (or meal has no participants = everyone).

### Frontend: Mealboard UI Overhaul

**Design Reference:** `.claude/plans/features/mealboard-main-page-updates/mockups/05-playful-swimlanes.html` is the approved mockup. **Use this file as the source of truth for all visual decisions** — layout, colors, spacing, card styles, typography, and interaction patterns. The mockup includes the full app chrome (sidebar + mealboard nav panel) and all interaction states described below.

#### Layout: Horizontal Swimlanes

The planner uses a **horizontal swimlane layout** (rows = meal slot types, columns = days) — NOT vertical day columns. This layout enables scanning "all dinners this week" or "all breakfasts" at a glance.

```
              Mon     Tue     Wed     Thu     Fri     Sat     Sun
           ┌───────┬───────┬───────┬───────┬───────┬───────┬───────┐
☀ Breakfast│ card  │ card  │ card  │ card  │  +    │ card  │  +    │
           ├───────┼───────┼───────┼───────┼───────┼───────┼───────┤
🥪 Lunch   │ 2cards│  +    │ 2cards│  +    │ card  │  +    │  +    │
           ├───────┼───────┼───────┼───────┼───────┼───────┼───────┤
🍽 Dinner  │ card  │ card  │ card  │ card  │ card  │  +    │ card  │
           ├───────┼───────┼───────┼───────┼───────┼───────┼───────┤
🍌 Snack   │ food  │ food  │ 2foods│  +    │ food  │  +    │  +    │
           └───────┴───────┴───────┴───────┴───────┴───────┴───────┘
```

**Grid structure:** `grid-template-columns: 100px repeat(7, 1fr)` — 100px left rail for the slot type label, then 7 equal day columns.

**Breakpoints:**
- Desktop (>=1200px): Full swimlane grid + app sidebar (80px) + mealboard nav panel (224px). Content offset `margin-left: 304px`.
- Tablet (768px-1199px): Full swimlane grid, no mealboard nav panel (MealboardNav switches to dropdown). Sidebar remains.
- Mobile (<768px): **Day-focused swipeable cards.** Shows ONE day at a time as a vertical card stack (slot type sections with meal cards, matching the mockup's day column layout but full-width). Day navigation via:
  - Horizontal day pills at the top (Mon/Tue/Wed/Thu/Fri/Sat/Sun, today highlighted, scrollable)
  - Swipe left/right to move between days (using `react-swipeable`, already in the project's dependencies)
  - Add meal popover becomes a bottom sheet or full-screen modal (already noted in plan)
  - Progress tracker collapses to a single row with 4 mini progress bars (no encouraging messages — space constraint)

#### Accessibility

- **Keyboard navigation:** Arrow keys move between swimlane cells (up/down = slot types, left/right = days). Enter on a cell opens the add meal popover. Enter on a meal card opens edit. Escape closes popovers/modals. Tab cycles through interactive elements within a cell.
- **ARIA landmarks:** Swimlane grid has `role="grid"`, each swimlane row has `role="row"`, each cell has `role="gridcell"`. Slot type labels serve as row headers (`role="rowheader"`). Day headers serve as column headers (`role="columnheader"`).
- **Screen reader labels:** Each meal card has `aria-label` combining meal name + slot type + day (e.g., "Pasta Bolognese, Dinner, Monday"). Cooked state announced via `aria-label` update. Empty cells announce "No meals planned, [slot type], [day]. Press Enter to add."
- **Touch targets:** All interactive elements (add buttons, meal cards, participant toggles, filter chips) minimum 44×44px tap area per WCAG 2.1 Success Criterion 2.5.5.
- **Color contrast:** All text meets WCAG AA minimum (4.5:1 for normal text, 3:1 for large text). Slot type colors are decorative only — no information conveyed by color alone (always paired with text labels).

#### Swimlane Structure

Each meal slot type is a horizontal band (`.swimlane`) with:
- **Left rail label:** Emoji + slot type name (e.g., "☀ Breakfast"), centered vertically. Color matches slot type.
- **Gradient background per band:** amber gradient for breakfast, sage for lunch, peach for dinner, lavender for snack.
- **Rounded container:** `border-radius: 20px` with colored border matching the slot type.
- **7 lane cells:** One per day, each containing meal cards or an empty state.

#### Day Header Row

A fixed header row above the swimlanes with the same grid structure:
- Day name (uppercase, 11px, letter-spacing 1px)
- Day number (22px, 800 weight)
- **Today highlight:** Day number rendered inside a gradient terracotta circle (`border-radius: 12px`, `box-shadow`), day name in terracotta color.

#### Interaction States (All Visible in Mockup)

**1. Empty cell (no meals planned for this day/slot):**
- Full-size dashed border container (`border: 2px dashed`, `border-radius: 12px`)
- Muted "+" text centered
- Hover: border turns terracotta, "+" turns terracotta, subtle white background, `scale(1.03)`

**2. Filled cell with recipe card:**
- White card, `border-radius: 12px`, subtle shadow (`0 2px 6px rgba(0,0,0,0.05)`)
- No left border accent — the swimlane band background already communicates the slot type. Cards are clean white within the colored band.
- Card content: name (12px, 600 weight), cook time with clock emoji, optional notes (italic, muted)
- Hover: `translateY(-2px)`, deeper shadow (`0 5px 14px`)

**3. Filled cell with food item (simple item):**
- Lighter treatment than recipe cards — translucent white background (`rgba(255,255,255,0.65)`), `border-radius: 10px`
- Emoji prefix + food name (11px, 500 weight)
- Hover: background brightens to `rgba(255,255,255,0.9)`, `scale(1.02)`

**4. Multiple items in one cell (e.g., Mon lunch: Turkey Wrap + PB&J):**
- Cards stack vertically within the cell with 5px gap
- Each card shows its own participant avatars
- The inline "+" add button appears below the last card

**5. Inline add button (filled cells only):**
- Small dashed pill below the last card in any filled cell
- Hidden by default (`opacity: 0`), appears on cell hover (`opacity: 1`)

- Card background changes to sage-50 (`#F4F7F4`), border to sage-100

- Badge has `box-shadow` for depth

**7. Today column highlight:**
- All cells in today's column get `background: rgba(255,255,255,0.45)` — a subtle white wash over the swimlane gradient
- Combined with the terracotta date circle in the header, makes today visually distinct

**8. Favorite recipe badge:**
- Gradient pill (`linear-gradient(135deg, terracotta-500, #E8927C)`) with white text "★ FAV"
- Sits inline in the card-meta row next to cook time

**9. Per-person participant avatars:**
- 20px circles with white initial letter (8px, 800 weight)
- **Important:** The mockup uses hardcoded placeholder gradients for demo purposes. In the real implementation, avatar colors MUST be derived from each `FamilyMember.color` field (a hex value from `FAMILY_MEMBER_COLORS` in `frontend/src/constants/familyColors.js` — e.g., `#D4695A` Soft Red, `#5A80B0` Steel Blue, `#8A60B0` Lavender). Use the family member's stored color as the avatar `background-color`. The gradient effect from the mockup is a nice-to-have — can be achieved by lightening the stored color ~10% for the second gradient stop.

- Small beige pill with family emoji + "Everyone" text (9px, 700 weight)

**11. Notes on cards:**
- Italic, muted text (10px), shown below the meta row
- Example: `"Extra garlic tonight"`

**12. Family member strip (top of page):**
- Horizontal bar with family member pills (photo/initial + name)
- Clickable — clicking a family member pill filters the swimlane grid to show only meals where that person is a participant. Click again to deselect (show all). Backend already supports `?family_member_id=` on GET /meal-entries.

### Predefined Unit System

Recipe ingredients currently use freeform text for `unit`. Replace with a **predefined unit dropdown** to enable reliable aggregation and conversion.

**Unit groups (constants file: `frontend/src/constants/units.js` + `backend/app/constants/units.py`):**

| Group | Units | Base unit | Conversion factors |
|-------|-------|-----------|-------------------|
| Weight | lb, oz, g, kg | g | lb=453.6, oz=28.35, kg=1000 |
| Volume | cup, tbsp, tsp, ml, l, fl oz, quart, pint, gallon | ml | cup=236.6, tbsp=14.8, tsp=4.9, l=1000, fl oz=29.6, quart=946.4, pint=473.2, gallon=3785.4 |

### Automatic Sync: Meals → Shopping List

When a meal entry is added to the planner, its items are **automatically** written to the linked shopping list with **ingredient aggregation**. When removed, its contributions are subtracted.

**Sync is async via Celery** — meal creation returns immediately, shopping sync happens in a background task. This matches the existing iCloud sync pattern. On meal creation, set `shopping_sync_status = "pending"`, dispatch Celery task. Task retries 3x with exponential backoff. On success → "synced". On failure after 3 retries → "failed".

**If sync fails, the UI must tell the user which meal failed.** The shopping card in the top bar shows a warning indicator (e.g., orange dot) when any meal on the current week has `shopping_sync_status = "failed"`. Clicking the warning shows the specific meal name (e.g., "Shopping sync failed for Pasta Bolognese on Monday") and offers a "Retry" action.

**Concurrency safety:** Uses an aggregation key + unique constraint on the Task model (`list_id`, `aggregation_key_name`, `aggregation_unit_group`). The sync flow uses SELECT FOR UPDATE on existing rows, and catches unique constraint violations on INSERT to retry as UPDATE. This prevents both update-race and insert-race conditions regardless of Celery concurrency.

**Aggregation flow (on meal add):**
1. For each ingredient in the meal, normalize: lowercase name → `aggregation_key_name`, determine unit group → `aggregation_unit_group`
2. SELECT FOR UPDATE: search the linked shopping list for an existing task with the **same `aggregation_key_name` + `aggregation_unit_group`**
3. If match found:
   - Convert both quantities to the base unit (grams or ml)
   - Sum the quantities
   - Convert back to the user's display preference (imperial/metric)
   - Update the task title: e.g., `"1 lb ground beef"` → `"2 lb ground beef"`
   - Append the meal entry to the task's `source_meals` JSON array
4. If no match: INSERT a new task with the formatted title, `aggregation_key_name`, `aggregation_unit_group`, and `source_meals`
   - If INSERT hits the unique constraint (concurrent worker beat us), catch the violation, SELECT FOR UPDATE the winning row, and UPDATE it instead
5. If quantity/unit are null (pantry staple like "olive oil"): write just the name, deduplicate by name only (`aggregation_key_name` = "olive oil", `aggregation_unit_group` = "none")

**Recipe meals — title format:**
- `"{quantity} {unit} {name}"` — e.g., `"2 lb ground beef"`, `"5 cloves garlic"`, `"400g pasta"`
- Quantity displayed in user's preferred measurement system
- If no quantity/unit: just the name — `"olive oil"`, `"salt"`

**Food items (simple items like "banana"):**
- Written as a task with just the food item name as title: `"Banana"`, `"Yogurt"`
- Deduplicated by name: if "Banana" already exists on the list, don't create a duplicate

**Custom meals (free text):**
- NOT auto-added to shopping list (no structured data to derive items from)

**Tracking provenance — multi-source contributions:**
- Replace the single `source_meal_entry_id` FK with a JSON field on Task: `source_meals`
- Structure: `[{meal_entry_id: 1, quantity: 453.6, base_unit: "g"}, {meal_entry_id: 2, quantity: 453.6, base_unit: "g"}]`
- Stores each meal's contribution in base units so subtraction is precise
- Null/empty for manually-added items

**On meal removal — subtraction rules:**
- When a meal entry is deleted from the planner:
  - Find all tasks on the linked shopping list whose `source_meals` JSON contains the deleted meal's ID
  - For each matching task:
    - If the task is **checked** (already bought): leave it completely alone
    - If the task is **unchecked**: subtract the deleted meal's contribution from the total quantity
    - If remaining quantity is 0 (or no other sources remain): delete the task
    - If remaining quantity > 0: update the task title with the new quantity and remove the meal from `source_meals`
  - Tasks where `source_meals` is null/empty (manually added) are never touched

**Edge cases:**
- If no shopping list is linked, adding meals does NOT queue items. Items are only synced while a list is linked. However, when a list is **first linked**, all current-week meal entries are backfilled (Celery tasks dispatched for each).
- If the linked list is deleted (from the Lists page), the `mealboard_shopping_list_id` reference becomes stale. The existing ShoppingListView already handles this (404 → unlink). The shopping card should also detect this and revert to State 1.
- If a user manually edits an aggregated task title on the shopping list (e.g., changes "3 lb ground beef" to "5 lb ground beef"), the `source_meals` JSON still tracks the original contributions. Next removal will subtract normally — the manual bump is effectively "extra" that won't be auto-removed.
- Rounding: display quantities rounded to sensible precision (1 decimal for weight/volume, whole numbers for count). E.g., 1.5 lb not 1.4999 lb.

## Problem Statement

The Mealboard feature just finished a 4-phase overhaul (commits `90cb121`, `8c72e7e`, `b5c4754`, `e6d34ea`). It works, but the overhaul left six pieces of visible and invisible polish debt:

1. **Deprecated components and CSS** left behind from earlier-phase patterns.
2. **Meal planner loading state** flashes a spinner for a fraction of a second and then vanishes — reads as "broken" rather than "loading".
3. **Day/date bar** pops into existence abruptly at the same instant as the spinner disappears, producing a visually noisy first paint.
4. **Recipes tab loading state** renders two full rows of skeleton placeholders (10 cards) but the database currently holds only 7 recipes, so the last 3 placeholders are never replaced and the screen finishes in a jagged state.
5. **Recipe tag pills** materialize instantly with no entrance animation, breaking the craft bar set by the rest of the recipe card redesign.
6. **Food Items tab** is missing the `"x food items"` count indicator between the search bar and the grid/list toggle — a small symmetry gap with the Recipes tab.

All six are owned by the user and targeted at the user's own family app. The user has chosen a learning-mode framing: the goal is not "ship the fixes" but "practice codebase hygiene and refactor discipline using this batch as the workbench."

## What Makes This Cool

The interesting part of this batch is that **Task 1 (dead-code removal) is the anchor, and the other five tasks are exercises in the same discipline**: diagnose the wrongness precisely, prove the diagnosis, apply the minimum fix, verify the result. Every task gets a before/after artifact.

A second coolness: **Task 2's fix is deletion, not replacement.** The "broken" spinner isn't a spinner-quality problem — it's a visibility problem. Sub-200ms loads should render nothing at all; any indicator that flashes and vanishes reads as broken to the human eye. This is the kind of insight that turns a "make it prettier" task into a "remove a thing" task, and dissolves Task 3 as a side effect (no spinner/bar overlap means nothing to smooth out).

A third coolness: the batch introduces exactly **one** reusable pattern (`useDelayedFlag`), **one** factored subcomponent (`ToolbarCount`), and **one** new dev tool (`knip`). None of them are invented just for this batch — each one earns its keep by being used twice within the same plan and compounding from there.

## Constraints

- **Scope discipline:** Mealboard only. Do not backport patterns to Lists, Responsibilities, Calendar, or Dashboard in this plan. A follow-up Obsidian task can cover that.
- **Branch:** all changes land on `mealboard-main-page-updates`. One bundled PR.
- **Docker discipline:** all builds, tests, and lint runs go through `docker-compose exec frontend ...`. Nothing runs directly on the host.
- **Test surface:** Phase 4 tests are green at 355/356 (one pre-existing failure, not ours). Must stay green; any new component/hook must arrive with matching tests.
- **No new runtime dependencies.** `knip` is a dev dependency, nothing ships to users. `useDelayedFlag` is a 10-line hook, not a library.
- **Accessibility:** reduced-motion users must not see new animations. Every keyframe introduced here needs a `@media (prefers-reduced-motion)` guard.

#### Step 3 — Introduce `useDelayedFlag` hook (enables Tasks 2 and 4)
- Create `frontend/src/hooks/useDelayedFlag.js`:
  ```js
  import { useEffect, useState } from 'react'

  // Returns true only after `flag` has been true for at least `delayMs`.
  // Intended use: gate a loading indicator so it never appears for fast loads.
  // For loads faster than delayMs, the return value stays false the entire time,
  // because `flag` flips back to false (load finished) before the timer fires.
  export default function useDelayedFlag(flag, delayMs = 200) {
    const [delayed, setDelayed] = useState(false)
    useEffect(() => {
      if (!flag) { setDelayed(false); return }
      const id = setTimeout(() => setDelayed(true), delayMs)
      return () => clearTimeout(id)
    }, [flag, delayMs])
    return flag && delayed
  }
  ```
- Create `frontend/tests/hooks/useDelayedFlag.test.js` using vitest's `vi.useFakeTimers()`. Cover four cases:
  (a) flag=true, advance <200ms → returns false;
  (b) flag=true, advance ≥200ms → returns true;
  (c) flag→false before timer fires → returns false, timer is cancelled (no delayed flip);
  (d) unmount before timer fires → no "setState on unmounted" warning.
- Run `docker-compose exec frontend npm run test:run` — expected delta: +4 passing tests.
- **Artifact:** none yet — hook gets its before/after in the steps that use it.
- **Commit:** `feat(frontend): add useDelayedFlag hook`

#### Step 4 — Delete the meal-planner spinner (Tasks 2 + 3)

**Current code (the thing we're fixing).** `MealPlannerView.jsx:269` renders:
```jsx
{(!initialLoaded || loading) ? (
  <div className="... animate-spin" />  // inline spinner div, not a named component
) : isCompactMode ? (
  <MobileDayView ... />
) : (
  <SwimlaneGrid ... />
)}
```
The day/date bar is rendered as a separate grid *before* the data rows inside `SwimlaneGrid`, so it only appears when `initialLoaded` is true and `loading` is false — which is exactly why it "pops" into existence when the branch flips. The spinner flashes because `initialLoaded` goes true within ~100ms on a warm network, so the spinner mounts and immediately unmounts.

**The fix.** Remove the three-way branch so both `SwimlaneGrid` (desktop) and `MobileDayView` (mobile) render from the first frame, with the spinner as a delayed overlay. [ENG REVIEW: Updated to cover both desktop AND mobile paths per Issue 3A.]

1. Import the hook: `import useDelayedFlag from '../../hooks/useDelayedFlag'`.
2. Derive: `const showSpinner = useDelayedFlag(!initialLoaded || loading, 200)`.
3. Always render the content view unconditionally based on `isCompactMode`: `MobileDayView` for mobile (**the real codepath is `<768px`**) or `SwimlaneGrid` for desktop. When `mealEntries` is empty and `!initialLoaded`, both views naturally render empty cells — the day/date bar and the swimlane structure are stable from frame zero. No new "empty shell" component is needed.
4. Render the spinner as an absolute-positioned, pointer-events-none overlay gated on `showSpinner`. **Visual treatment (design review decision 1A): bare spinner, no backdrop.** Use the existing `w-8 h-8 border-2 border-terracotta-500 dark:border-blue-500 border-t-transparent rounded-full animate-spin` pattern, centered in the content area with `flex items-center justify-center`. No background color or opacity backdrop — the grid structure (day headers + swimlane rows with dashed cells) is fully visible behind the spinner, reinforcing that the layout is ready and data is on the way. For sub-200ms loads `showSpinner` never goes true, so nothing flashes. For genuinely slow loads the overlay appears after 200ms and disappears on completion.
5. Animation rule: use a small opacity transition only in motion-safe mode (`motion-safe:transition-opacity motion-safe:duration-150`). Under reduced motion, the overlay appears/disappears instantly so the plan stays consistent with the "no new animations" constraint. No new keyframes needed.

**Task 3 resolves here** because the day/date bar is now rendered from the first frame via `SwimlaneGrid`/`MobileDayView`, so there is no pop-in moment at all. If empirical verification shows any residual flicker (e.g., day labels recomputing after `weekDates` updates), add an `opacity-0` → `opacity-100` transition on the bar element bound to `initialLoaded` (150ms), but start without it — simpler is better if it works.

- Hard reload `/mealboard` at mobile viewport (**<768px**) (expected: no spinner, `MobileDayView` visible from first frame). [Independent GPT 5.4 review: fixed breakpoint to match actual code.]

#### Step 6 — Recipe tag pill entrance animation (Task 5)
- In `frontend/src/index.css`, add a new keyframe `tag-pill-enter` modeled on the existing `recipe-card-enter` for pattern symmetry.
- **Animation constraints (enforced):**
  - Duration: 200ms.
  - Only `transform` and `opacity` are allowed. No `width`, `height`, `margin`, `padding`, or `top/left` — these cause reflow and the whole point of the animation is that it should not shift layout. The pill must occupy its final box from frame zero.
  - From: `opacity: 0; transform: translateY(4px);`. To: `opacity: 1; transform: translateY(0);`.
  - Easing: `cubic-bezier(0.2, 0.8, 0.2, 1)` (matches existing keyframes).
- **Stagger budget:** cap total entrance at 400ms (animation duration + max stagger). With a 200ms animation, that leaves 200ms of stagger. At `index * 30ms`, that means the 7th pill and beyond all start at the same 200ms offset — clamp the delay: `animationDelay: \`${Math.min(index, 6) * 30}ms\``.
- Guard the keyframe behind `@media (prefers-reduced-motion: no-preference)` so reduced-motion users skip the entrance entirely (pills appear instantly in final position).
- Apply via inline `style={{ animationDelay: ... }}` inside the existing tag pill `.map((tag, index) => ...)` in `RecipesView.jsx`. The `index` is the position in the currently-filtered tag array — not the database ID — which is the desired behavior (visual stagger should follow rendered order).
- **Verify:** open devtools Layers panel during the animation — only `transform` and `opacity` should appear as composited properties. No reflow events.

## Premises

These premises reverse or extend decisions from the shipped 20260413 plan. Each one was confirmed interactively during Phase 3 of this office-hours session. They are the explicit, documented trail so that a future office-hours round doesn't rediscover them the hard way.

1. **Jump-to-Current-Week becomes a primary-styled button.** Shipped plan §1203/§1662 made it secondary because "Add meal" is the primary planner action. Override rationale: the user wants navigation discoverability more than they want to protect Add meal's visual primacy on the planner header. The planner header does not actually host an Add meal affordance — meal adds happen inline inside swimlanes — so the competition concern was theoretical. — **agreed 2026-04-15**

2. **Label becomes "Jump to Current Week", not "Today".** This is a *third* label, not the shipped "Jump to Today" and not the original task 3 "Today". Rationale: "Today" alone is ambiguous (could mean "insert today's date" or "filter to today"); "Jump to Today" is fine but has two meanings depending on context; "Jump to Current Week" is unambiguously "scroll the week selector to the current week". Longer label is fine at desktop; mobile word-wrap tolerated. — **agreed 2026-04-15**

3. **The button gets hidden (not disabled) when `isOnCurrentWeek` is true.** Shipped plan §1145 kept a disabled visual state. New premise: hiding is cleaner because the button is purely navigational with no meaningful disabled affordance. Layout collapse is fine — the week selector can breathe. — **agreed 2026-04-15**

4. **The food-item card is being redesigned, not tweaked.** Tasks 7/8/9 collectively reverse three shipped-pill decisions: (a) centered `max-w-5xl` → left-aligned full-width, (b) ~40% vertical-space reduction → increased vertical height + icon size, (c) right-side category dot → right-side category stripe. These are not compatible with the shipped pill mockup `food-items-pill-option-a.html`. A new mockup is required before implementation. — **agreed 2026-04-15**

5. **`@emoji-mart/react` is happening now.** Shipped plan §1746 planned it for Chunk 5 but deferred via TODOS.md on 2026-04-14 ("revisit if a user asks for search by name"). The user has now asked for emoji search (task 10), which is the exact revisit trigger. Gates A (≤250KB gzipped) and B (keyboard a11y) from shipped plan §2008 still apply as this plan's implementation gates. Tasks 4 and 10 merge into a single chunk. — **agreed 2026-04-15**

6. **The undo toast bug is a real bug, not missing behavior.** The `UndoToast.jsx` code *reads* correct: `show()` sets a 15s `setTimeout` that calls `hide()` which sets `toast` to `null`. No tests exist (`**/UndoToast*.test.*` returns zero files). A repro-first spike is required before a fix can be chosen. — **agreed 2026-04-15**

**Installation command (Docker-only):**
```
docker-compose exec frontend npm install @emoji-mart/react @emoji-mart/data
```

**Lazy-import strategy (sidesteps Gate A):** Before wiring the lazy boundary, verify the export shape of the installed `@emoji-mart/react` version. **Colocate both imports in a single `React.lazy()` call** using `Promise.all` so the Picker always has data when it mounts — no timing gap, no useEffect race:
```jsx
const LazyPicker = lazy(async () => {
  const [emojiMart, { default: data }] = await Promise.all([
    import('@emoji-mart/react'),
    import('@emoji-mart/data'),
  ]);
  const Picker = emojiMart.Picker ?? emojiMart.default;
  return { default: (props) => <Picker data={data} {...props} /> };
});
```
The `Picker ?? default` fallback handles both named and default export shapes without a separate verification step. This moves both packages into a separate chunk that's not loaded at app boot. Bundle impact on the main chunk is expected to be ≤2KB (the `lazy` + `Suspense` wrapper) — confirm at Gate A with the post-install `npm run build` comparison. The user only pays the emoji-mart download cost the first time they open the picker in a session — and the result is cached by the browser for subsequent opens. (Eng review #2, issue 1A: colocated lazy import replaces separate useEffect approach.)

### Chunk 4: Undo toast dismiss bug — spike + fix

Source: `mealboard-undo-toast`.

**Files:**
- `frontend/src/components/shared/UndoToast.jsx` — diagnosis target
- `frontend/tests/components/shared/UndoToast.test.jsx` — new file (no test currently exists — verified via glob)

**Step 4.1 — Reproduce:**
- Start the dev stack: `docker-compose up`
- Delete a food item, watch the toast, wait 15 seconds, observe the bug
- Capture: does the countdown ring complete? Does the toast stay visible? Does any console output appear?
- Try with dev-tools open vs closed, tab focused vs backgrounded
- Note during the spike that current production callers may omit `onExpire`; expiry correctness still depends on the timer calling `hide()`, not on `onExpire` being present.

**Step 4.2 — Hypotheses** (ordered from most to least plausible; two have been eliminated during planning):

1. **~~CSS keyframe duration mismatch~~** — **ELIMINATED AT PLANNING TIME.** `frontend/src/index.css:173-176` defines `@keyframes undo-countdown` with no hardcoded duration (only `stroke-dashoffset` from 0 to 37.7). The duration is injected from JS at `UndoToast.jsx:192` as `undo-countdown ${UNDO_WINDOW_MS}ms linear forwards`, so CSS and JS share the same constant and cannot drift. This hypothesis cannot fire; no need to re-check during the spike.

2. **~~React Strict Mode double-mount clearing the timer~~** — **ELIMINATED AT PLANNING TIME.** StrictMode is active (`main.jsx:11`), so double-mount runs in dev. But `UndoToastProvider`'s `expireTimerRef` is a per-instance `useRef`; each Strict-Mode mount gets its own ref, so the cleanup from discarded-mount A cannot affect the timer set on surviving-mount B. The mechanism doesn't apply. This hypothesis cannot fire.

3. **setTimeout drift when the tab is backgrounded.** Browsers throttle `setTimeout` in backgrounded tabs to ≥1s. If the user switches tabs during the 15s window, the JS timer can fire noticeably later than the CSS animation completes — creating a "ring done but toast still visible" window that matches the user's description. **Plausible.** Investigate first. Fix pattern: record `expiresAt = Date.now() + UNDO_WINDOW_MS` in the ref; on `visibilitychange` when the page becomes visible, check if `Date.now() >= expiresAt` and call `hide()` immediately if so.

4. **The `<Transition>` component from `@headlessui/react` not unmounting the leave.** If the leave transition is interrupted (e.g., React re-renders and briefly flips `show` back to true), the DOM can retain the toast. Check by inspecting the DOM at t=16s and at t=30s — if the outer `<div>` is still attached, Transition is the culprit; if it's detached but something else is keeping state, look elsewhere. **Medium probability.**

5. **A stale-closure bug in the `hide` callback.** `hide` is `useCallback(() => { clearTimers(); setToast(null); setRestoring(false); }, [])` with an empty dep array. `clearTimers` reads `expireTimerRef.current` — that's fine (refs are always current). But if React 19's state-batching reorders the setState calls in a way that leaves `toast` non-null when the Transition evaluates `show={toast !== null}`, the toast stays. **Lower probability, but worth a quick console.log of `toast` value inside the Transition during the spike.**

**Step 4.3 — Fix:** Based on the diagnosed root cause. Order of attack: hypothesis 3 → 4 → 5. If the landed fix relies on `visibilitychange` / `document.hidden` catch-up, treat that path as a first-class codepath and add explicit regression coverage for it rather than relying only on fake timers.

**Step 4.4 — Regression test:**
- Create `frontend/tests/components/shared/UndoToast.test.jsx`
- Test 1: "toast auto-hides 15s after show() is called" — use `vi.useFakeTimers()`, call `show`, advance past the 15s timer **and** the 150ms Headless UI leave transition (or `waitFor` removal), assert toast is gone
- Test 2: "onExpire callback fires once on auto-hide" — spy on `onExpire`, advance timer, assert called once
- Test 3: "hide() before timer fires cancels the timer" — call `hide` at 5000ms, advance to 16000ms, assert `onExpire` NOT called
- Test 4: If the landed fix uses `visibilitychange`, simulate hidden-tab expiry and visible-again catch-up so the background-tab path cannot slip past unit coverage

**Success criteria:**
- Bug reproduces reliably in manual QA
- Root cause identified and documented in the plan's "Review" section
- Fix lands in `UndoToast.jsx` with no new lint warnings
- Three required regression tests pass, plus visibility-change coverage if that path is used
- Toast auto-hides at t=15s in manual QA

**Effort:** ~30 min CC (15 spike, 15 fix+tests). Could go over if the bug is a subtle race.

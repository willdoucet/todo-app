## Problem Statement

The mealboard overhaul (4 phases, 60 files, shipped 2026-04-04) is on-screen and functional, but review revealed nine UX gaps and a recipes page that hasn't kept up. The central complaint: the meal card doesn't transmit "what's for dinner" at a glance — it buries the meal name under clutter (participant avatars, small type, hover-only actions). Meanwhile the shopping aggregation system has latent data bugs (unit-group matching is too coarse, plural/singular mismatches silently duplicate rows, no story for swap/unlink/check). And the recipes page has no read-mode, cards too big, filter bar wasting space, placeholder book icon out of place.

This plan addresses all of that in a phased delivery.

## What Makes This Cool

The scan-the-card-and-know experience: glance at Tuesday dinner → you see the meal name, a real thumbnail, cook time, and you can one-click open the recipe drawer to read it while the grid stays on screen. The shopping list becomes deterministic — "Grapes (1 bunch)" and "Grapes (1 bunch)" merge, while "Corn (1 ear)" and "Corn kernels (2 cups)" honestly stay separate. Purchased items are sacred. Swap shopping lists, and your planned items follow. The recipes page becomes a real browse surface: denser, more info, tap-to-read. Whole thing feels like a recipe app that respects its user.

## Constraints

- Must work on current stack: FastAPI + React 19 + Postgres + Docker Compose
- All dev via Docker (never host npm/pytest/uv)
- Must keep existing migration intact (this builds on top of `603854e284dd_mealboard_overhaul.py`)
- No third-party fuzzy-matching libraries (keep backend deps lean)
- Mobile must still work (<768px day-focused view)
- Family app scale (~100 recipes, ~10 meals/week) — no need to optimize for scale

## Premises

Confirmed with user:
1. **Scannability > info density.** Meal card's dominant element is the meal name.
2. **Recipes page = browse/pick.** Reading happens in the drawer.
3. **Auto shopping items = computed view of meal entries + linked list pointer.** Deterministic, regenerable.
4. **Food items are first-class with shopping metadata** (`shopping_quantity`, `shopping_unit`).
5. **V1 aggregation is boring and correct.** No fuzzy matching, no synonyms, no ingredient ontology.
6. **Purchased is sacred.** Checked auto-items flip to manual, stay purchased.

## Approaches Considered

### Approach A: Single PR (bundle everything)
- All backend + frontend in one branch. One review, one deploy, one rollback risk.
- **Pros:** Fastest to merged. Nothing ships half-done.
- **Cons:** Huge diff, hard to review, giant rollback if anything fails.
- **Reuses:** n/a

### Approach B: Phased — backend → mealboard UX → recipes (CHOSEN)
- Three PRs, sequentially dependent but individually reviewable.
- **Phase 1:** Backend aggregation spec + food item units + canonical_name + unlink/swap/check logic + data migration
- **Phase 2:** Mealboard UX — drawer, taller rows, hide participants, always-visible icons, unlink UI
- **Phase 3:** Recipes page redesign — new cards, toolbar, placeholder fix
- **Pros:** Backend bugs ship ASAP. Each phase validated against a real week of meals before the next starts. Reviews stay manageable.
- **Cons:** 3 PRs to land.
- **Reuses:** Drawer component shared across Phase 2 + Phase 3.

### Approach C: Ship backend fix only
- Just the aggregation rework. Defer UX indefinitely.
- **Pros:** Minimal diff, fixes real bugs.
- **Cons:** Leaves all the UX concerns in the wind. User's original nine concerns mostly untouched.
- **Reuses:** n/a

## Recommended Approach

**Approach B** (user-selected). Phased delivery. Backend fixes the latent data bugs first — they exist today and silently corrupt shopping lists. Frontend polish follows, one surface at a time.

## Aggregation Spec (Locked)

Source: user-authored, accepted verbatim. Binding.

**Goal:** Answer one question consistently: "What total amount of this thing do I need to buy?"

**Structured Contribution Model** — every shopping contribution normalized to:
- `list_id`
- `source_kind` (recipe_ingredient | food_item)
- `display_name` (original user-facing name)
- `canonical_name` (normalized for matching)
- `quantity`, `unit`, `unit_group`
- `base_quantity`, `base_unit` (when convertible)
- `source_reference` (provenance: meal_entry_id, recipe_id, food_item_id)

**FoodItem model gains:**
- `shopping_quantity` (required, default 1)
- `shopping_unit` (required, default "each")

**Aggregation rules:**
1. **Normalize names conservatively:** lowercase, trim, collapse spaces, singularize common plurals, ~20-entry irregulars table. No fuzzy matching, no synonyms.
2. **Units must be explicit.** Missing unit → does not participate in quantitative aggregation.
3. **Aggregate only when name AND unit semantics match:** same list_id, same canonical_name, same aggregation_source, compatible unit semantics.
4. **Convert within compatible families:** weight → base `g`, volume → base `ml`. Count-style units aggregate only when specific normalized unit matches (ear ≠ bunch ≠ each).
5. **Incompatible units stay separate.** "Corn + ear" ≠ "corn kernels + cup". Separate rows > fake math.
6. **Display is derived, identity is not.** Identity = structured fields. Never parse `Task.title`.

**Aggregation bucket:** `(list_id, aggregation_source, aggregation_key_name, aggregation_unit)`
  — where `aggregation_key_name` is the column that stores the computed `canonical_name`.

**New Task fields (minimum viable set):**
- `aggregation_source` (nullable string; `"mealboard_auto"` or NULL for manual)
- `aggregation_key_name` (nullable; canonical normalized name — output of `canonicalize_name()`)
- `aggregation_unit` (nullable; specific normalized unit used for bucket identity, e.g. `each`, `bunch`, `ear`, `lb`, `g`, `cup`)
- `aggregation_unit_group` (helper for display/conversion; e.g. `weight`, `volume`, `count`)
- `aggregation_base_quantity` (authoritative summed quantity in base unit for weight/volume, or direct quantity for count-style units)
- `aggregation_base_unit` (the base unit that `aggregation_base_quantity` is expressed in: `g` for weight, `ml` for volume, or equals `aggregation_unit` for count-style)
- `source_meals` (JSON provenance ledger — see shape below)

**`source_meals` JSON shape:**
```json
[
  {"meal_entry_id": 42, "source_kind": "recipe_ingredient", "recipe_id": 7, "ingredient_name": "Bananas", "quantity": 2, "unit": "each"},
  {"meal_entry_id": 51, "source_kind": "food_item", "food_item_id": 3, "display_name": "Banana", "quantity": 1, "unit": "each"}
]
```

**Unique constraint:** `(list_id, aggregation_source, aggregation_key_name, aggregation_unit)` — guarantees one aggregate row per bucket per list. Because Postgres treats NULL as distinct in unique constraints, manual tasks (`aggregation_source=NULL`) are automatically exempt and can share names/units freely.

**Pantry-staple NULL-unit caveat:** unitless pantry-staple rows (where both `quantity` and `unit` are absent → `aggregation_unit=NULL`) would *also* be treated as distinct by Postgres, allowing duplicates per (list, name). To prevent this, the sync service does an explicit pre-insert lookup for rows matching `(list_id, 'mealboard_auto', aggregation_key_name, aggregation_unit IS NULL)` and updates in place if found. The unique constraint handles the non-NULL case; code handles the NULL case.

**Default unit inference:** If a recipe ingredient has `quantity > 0` but no unit specified, its `aggregation_unit` defaults to `"each"` (count-style). If a recipe ingredient has no quantity AND no unit (pantry staple), it produces a shopping row with `aggregation_unit = NULL` and does NOT participate in quantitative aggregation — name-only match.

**Concurrency:** unique constraint + `with_for_update()` — different problems, both needed.

**V1 non-goals:** typo correction, synonym matching, ingredient ontology, "corn vs corn kernels" smart merging, "ground beef vs mince" merging, user-driven merge UI.

**Example outcomes:**
- Banana (1 each) + 2 bananas → **3 bananas**
- Grapes (1 bunch) + 1 bunch grapes → **2 bunch grapes**
- Corn (1 ear) + 2 cups corn kernels → **two rows** (honest)
- 1 lb ground beef + 16 oz ground beef → **2 lb ground beef** (weight conversion)

## Phase 1 — Backend Aggregation Rework

**Database migration (Alembic):**
- Add `shopping_quantity` (numeric, default 1), `shopping_unit` (string, default "each") to `food_items`
- Add `aggregation_source` (nullable string) to `tasks`
- Add `aggregation_unit` (nullable string) to `tasks` — new column for specific-unit bucket matching
- Add `aggregation_base_unit` (nullable string) to `tasks`
- Add `synced_to_list_id` (nullable FK to lists.id) to `meal_entries` — provenance for remove task. Data migration backfills this for existing meal_entries: set `synced_to_list_id = AppSettings.mealboard_shopping_list_id` for any meal_entry with `shopping_sync_status="synced"`, else NULL.
- Retain existing `aggregation_unit_group` column (used as a display/conversion helper)
- Drop old unique constraint on tasks, create new: `(list_id, aggregation_source, aggregation_key_name, aggregation_unit)`
- **Data migration for existing auto rows:** identify all tasks where `source_meals IS NOT NULL` (these are the 6 known mealboard-auto rows). For each:
  - Set `aggregation_source = "mealboard_auto"`
  - Inspect `source_meals` JSON to recover the original ingredient unit: use the `unit` field of the first entry if present. (The existing backend code writes `unit` into `source_meals` entries — verify this during migration authoring.)
  - If `source_meals` lacks unit data for any row, fall back to the unit_group's default: `{weight: "g", volume: "ml", count: "each"}`.
  - Set `aggregation_base_unit` = `g` for weight group, `ml` for volume group, else equal to `aggregation_unit`.
  - Set `aggregation_base_quantity` from the existing row: for weight/volume, convert the row's current quantity to the base unit; for count-style, copy the row's current quantity verbatim.
  - Because only 6 rows exist today, the migration can also be authored as a deterministic per-row UPDATE if the generic approach proves unreliable during authoring.
- **source_meals JSON shape migration (Eng review, added):** existing rows store `source_meals` entries as `{"meal_entry_id", "quantity", "base_unit"}`. The new shape adds `source_kind`, `recipe_id`/`food_item_id`, `ingredient_name`/`display_name`, and renames `base_unit` → `unit`. The same Alembic data-migration pass rewrites each entry in `source_meals[]` on the 6 existing rows:
  - `source_kind = "recipe_ingredient"` (all old rows came from recipes)
  - `recipe_id` — look up from the meal_entry FK (`SELECT recipe_id FROM meal_entries WHERE id = :meal_entry_id`)
  - `ingredient_name` — use the task's `aggregation_key_name` (best-effort; displays may differ slightly from original but aggregation still works)
  - `unit` — copy from old `base_unit` field
  - Drop `base_unit` field from the entry (superseded by top-level `aggregation_base_unit`)

**Alembic `downgrade()` (explicit):**
- Drop new unique constraint `(list_id, aggregation_source, aggregation_key_name, aggregation_unit)`
- Restore prior unique constraint on `(list_id, aggregation_key_name, aggregation_unit_group)`
- Drop columns: `tasks.aggregation_source`, `tasks.aggregation_unit`, `tasks.aggregation_base_unit`, `food_items.shopping_quantity`, `food_items.shopping_unit`, `meal_entries.synced_to_list_id`
- No data un-migration needed — the 6 rows retain their original `aggregation_key_name` + `aggregation_unit_group` from Phase 1's prior migration.
- Must be tested locally via `alembic downgrade -1` before merging.

**Code changes:**
- `backend/app/services/shopping_sync.py`: rewrite aggregation to match on `(canonical_name, aggregation_unit)`. Implement `canonicalize_name()` (lowercase, trim, collapse spaces, singularize, irregulars table). **Note: `_upsert_shopping_item()` signature changes significantly** — old params `(ingredient_name, quantity, unit)` become `(canonical_name, display_name, aggregation_unit, aggregation_unit_group, aggregation_base_quantity, aggregation_base_unit, source_kind, source_id, meal_entry_id)`. Treat this as a rewrite of the function, not an extension. The food-item call site must read `entry.food_item.shopping_quantity` and `entry.food_item.shopping_unit` (not pass `None`).
- `backend/app/crud_tasks.py`: in `update_task` (around line 138-142 where completed-transition is already detected), when `update_data["completed"]` becomes True AND `db_task.aggregation_source == "mealboard_auto"`, call `on_item_checked(db, db_task)` from shopping_sync. Single colocated hook; no SQLAlchemy event listeners.
- `backend/app/constants/irregulars.py` (new): ~20-entry table — tomato/tomatoes, potato/potatoes, leaf/leaves, knife/knives, berry/berries, etc.
- `backend/app/services/shopping_sync.py`: add `on_item_checked()` hook — when a `mealboard_auto` task's `completed` flag goes true, flip `aggregation_source` to NULL. **Retain** `aggregation_key_name`, `aggregation_unit`, `aggregation_unit_group`, `aggregation_base_quantity`, `aggregation_base_unit`, `source_meals` on the row (provenance is preserved even after the row becomes manual). **Concurrency:** the flip must acquire a `with_for_update()` row lock on the task before nulling; concurrent sync writes to the same bucket will block on that lock, then (finding `aggregation_source=NULL` post-flip) fall through to the "create new aggregate row" path — meaning new demand after a check creates a fresh `mealboard_auto` row alongside the purchased-manual one.

**Race-condition handling for async Celery sync (CEO + Eng reviews):**
- Add `"skipped"` value to `ShoppingSyncStatus` enum (backend + schemas.py).
- **New column on MealEntry: `synced_to_list_id` (nullable FK to lists.id)** — provenance tracking. Records the list_id where this meal_entry's shopping rows currently live. Set to NULL on entry creation; populated by add-sync; maintained by swap/unlink; cleared by remove.
- **ADD task guard** (`sync_shopping_list_add`) — gated by status AND list:
  1. Load `meal_entry` (lock with `with_for_update`). If `shopping_sync_status != "pending"` → log + no-op (handles double-execute + post-swap already-synced cases).
  2. Else read `AppSettings.mealboard_shopping_list_id`. If NULL → set meal_entry status to `"skipped"`, `synced_to_list_id=NULL`, log warning, return.
  3. Else proceed with sync against current linked list; on success set `status="synced"`, `synced_to_list_id=<current linked list>`.
- **REMOVE task guard** (`sync_shopping_list_remove`) — gated by provenance, NOT by status:
  1. Load `meal_entry` (lock with `with_for_update`). Read `synced_to_list_id`.
  2. If `synced_to_list_id IS NULL` → no-op (meal was never synced, OR was already cleaned up by unlink).
  3. Else call `remove_meal_from_shopping_list(db, meal_entry_id, target_list_id=synced_to_list_id)` — scoped to the specific list the meal was last synced to.
  4. After successful removal, set `synced_to_list_id=NULL` on the meal_entry.
  5. The remove function is idempotent by construction (source_meals scan finds 0 matches on re-run).
- `swap_mealboard_list(old_id, new_id)` (runs atomically inside a DB transaction):
  1. For all meal_entries where `synced_to_list_id=old_id`, set `synced_to_list_id=new_id`, `status="synced"`.
  2. Delete all `mealboard_auto` rows from `old_id`.
  3. Recompute fresh rows on `new_id` from the meal_entries (populates unique-constraint-protected aggregate rows).
  4. Pending add-sync Celery tasks for these entries will no-op on guard step 1 (status="synced").
- `unlink_mealboard_list(list_id)` (runs atomically inside a DB transaction):
  1. Delete all `mealboard_auto` rows from `list_id`.
  2. For all meal_entries where `synced_to_list_id=list_id`, set `synced_to_list_id=NULL`, `status="skipped"`.
- **This kills both failure modes:** double-count race (add-sync runs after swap → status guard catches it), and orphan rows on remove-after-unlink (remove sees `synced_to_list_id=NULL` and no-ops).

**Atomic list-link transition (Eng review, added):**
- List-link changes (`mealboard_shopping_list_id` updates) are a **stateful workflow**, not stateless field mutation. They belong in a domain service, not generic CRUD. New function `change_mealboard_list(db, new_list_id)` in `shopping_sync.py` owns the full transition atomically:
  1. Lock AppSettings singleton row `with_for_update`.
  2. Read `old_list_id` from settings.
  3. Dispatch the appropriate subroutine based on transition:
     - `old=NULL, new=X` → link (no pre-existing rows to clean up; if meal_entries exist, recompute fresh on X)
     - `old=X, new=NULL` → `unlink_mealboard_list(X)`
     - `old=X, new=Y` (X != Y) → `swap_mealboard_list(X, Y)`
     - `old=X, new=X` → no-op
  4. Update `AppSettings.mealboard_shopping_list_id = new_list_id`.
  5. Single `db.commit()` covering all of the above.
- `backend/app/routes/app_settings.py` PATCH handler: if `mealboard_shopping_list_id` is in the update payload, extract it and call `change_mealboard_list(db, new_list_id)` FIRST. Apply all other field changes via existing `update_settings` CRUD after. This ensures linked-list changes go through the atomic service while other AppSettings fields continue using generic CRUD.
- Rationale: generic CRUD is correct for stateless field mutations (measurement_system, week_start_day). Stateful workflows with side-effects (moving shopping rows) require a dedicated service abstraction.
- `backend/app/services/shopping_sync.py`: add `swap_mealboard_list(old_list_id, new_list_id)`, `unlink_mealboard_list(list_id)`, `change_mealboard_list(db, new_list_id)` (see "Atomic list-link transition" above).
- `backend/app/schemas.py`: FoodItem schemas gain `shopping_quantity: float = Field(default=1.0, gt=0)` (enforces positive via Pydantic) and `shopping_unit: str` with a `field_validator` that checks against `VALID_UNITS` (follow existing pattern at schemas.py:255 for Ingredient.unit). Zero/negative quantities rejected at the schema layer.
- `backend/app/routes/food_items.py`: accept new fields on create/update.
- `backend/app/routes/app_settings.py`: detect `mealboard_shopping_list_id` in PATCH payload, call `change_mealboard_list()` service for that field, call existing `update_settings` for all other fields.

## What Makes This Cool

- Two of three bugs are one-line root causes once identified; the third (edit-from-drawer) is ~15 lines because `MealPlannerView` needs its own `RecipeFormModal` render. Plan front-loads all three so the user stops hitting papercuts within an hour or two of implementation starting.
- The emoji-vs-icon XOR on food items unlocks visual variety the emoji-only constraint prevents. Household members can have a custom avatar-style icon per food (family photo of the actual container, brand logo, cartoon) instead of settling for the nearest Unicode approximation.

- Cascading recipe delete means the user can confidently prune their recipe collection without manually cleaning up meal plans first.

### 0.1 — Data Model

**New tables:**

```sql
CREATE TABLE items (
    id SERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    item_type TEXT NOT NULL CHECK (item_type IN ('recipe', 'food_item')),
    icon_emoji TEXT,
    icon_url TEXT,
    tags JSONB NOT NULL DEFAULT '[]'::jsonb,
    is_favorite BOOLEAN NOT NULL DEFAULT false,
    deleted_at TIMESTAMP NULL,  -- reused by Expansion B soft-delete
    created_at TIMESTAMP NOT NULL DEFAULT now(),
    updated_at TIMESTAMP NOT NULL DEFAULT now()
);

CREATE TABLE recipe_details (
    item_id INT PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,
    description TEXT,
    ingredients JSONB NOT NULL DEFAULT '[]'::jsonb,
    instructions TEXT,
    prep_time_minutes INT,
    cook_time_minutes INT,
    servings INT,
    image_url TEXT
);

CREATE TABLE food_item_details (
    item_id INT PRIMARY KEY REFERENCES items(id) ON DELETE CASCADE,
    category TEXT NOT NULL DEFAULT 'Other',
    shopping_quantity NUMERIC NOT NULL DEFAULT 1.0,
    shopping_unit TEXT NOT NULL DEFAULT 'each'
);

-- XOR check constraint on the parent (from Expansion C security hardening)
ALTER TABLE items ADD CONSTRAINT items_icon_xor_check
    CHECK (NOT (icon_emoji IS NOT NULL AND icon_url IS NOT NULL));

-- Unique name per type (prevents cross-type collision on rename)
-- Adversarial review concern: existing recipes.name and food_items.name may or may not have
-- unique constraints today. Decision: enforce UNIQUE (name, item_type) on items so a recipe
-- and a food item can share a name (e.g., "Chicken") but two recipes cannot both be named
-- "Chicken". This is a relaxation if prior uniqueness was global by table, but it matches
-- the household use case.
CREATE UNIQUE INDEX items_name_type_uniq ON items(name, item_type)
    WHERE deleted_at IS NULL;

-- Indexes
CREATE INDEX items_item_type_idx ON items(item_type);
CREATE INDEX items_is_favorite_idx ON items(is_favorite) WHERE is_favorite = true;
CREATE INDEX items_deleted_at_idx ON items(deleted_at) WHERE deleted_at IS NOT NULL;
CREATE INDEX recipe_details_ingredients_gin ON recipe_details USING GIN (ingredients);

-- updated_at propagation trigger: changes to recipe_details or food_item_details
-- bump items.updated_at so cache invalidation keyed on items.updated_at stays correct.
CREATE OR REPLACE FUNCTION bump_item_updated_at() RETURNS TRIGGER AS $$
BEGIN
    UPDATE items SET updated_at = now() WHERE id = COALESCE(NEW.item_id, OLD.item_id);
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER recipe_details_bump_parent
    AFTER INSERT OR UPDATE OR DELETE ON recipe_details
    FOR EACH ROW EXECUTE FUNCTION bump_item_updated_at();

CREATE TRIGGER food_item_details_bump_parent
    AFTER INSERT OR UPDATE OR DELETE ON food_item_details
    FOR EACH ROW EXECUTE FUNCTION bump_item_updated_at();
```

**meal_entries changes:**

- Drop `recipe_id` FK column (eventually — see expand-and-contract migration in 0.2)
- Drop `food_item_id` FK column (eventually)
- Drop `item_type` enum column (eventually; must first audit all readers — see 0.2 pre-drop audit step)
- Add `item_id INT REFERENCES items(id) ON DELETE RESTRICT` (nullable — must still allow `custom_meal_name` to stand alone)
- **FK behavior is RESTRICT, not CASCADE** (adversarial review concern). Rationale: a hard `DELETE FROM items` must NOT silently wipe meal history. The supported deletion path is the Expansion B soft-delete flow, which sets `items.deleted_at` and mirrors `meal_entries.soft_hidden_at` — meal history is preserved through the undo window and only purged via the Celery beat hard-delete job which explicitly handles meal_entries via the cascade-in-code transaction (see Expansion B and Eng Review #3 Issue 3). A raw DELETE bypassing that flow should fail loudly with an FK violation so the developer notices.
- **Item ↔ MealEntry relationship spec (Eng Review #3 Issue 6):** at Rev 3, the existing `MealEntry.recipe` and `MealEntry.food_item` SQLAlchemy relationships are removed. Add `MealEntry.item: Mapped["Item | None"] = relationship("Item", back_populates="meal_entries", lazy="selectin")` to mirror `Item.meal_entries`. **Never use `item.meal_entries` directly to render UI** — it loads ALL rows including soft-hidden ones. The relationship exists for ORM-level back-population only; UI/CRUD reads must go through `visible_meal_entries_stmt()` from `crud_meal_entries.py`.
- Keep `custom_meal_name`, `custom_meal_emoji`, `custom_meal_color` as-is for ad-hoc meals that aren't Items
- Add constraint: `CHECK (item_id IS NOT NULL OR custom_meal_name IS NOT NULL)`
- Keep `soft_hidden_at TIMESTAMP NULL` from Expansion B
- Keep `was_cooked`, `participants`, `shopping_sync_status` as-is

**Rationale for the split-table design (Item + subtype details) instead of one fat `items` table:**

- Recipe and food item detail fields are cleanly separable and unlikely to be queried together.
- Keeps the `items` core table small and fast for list queries that only need name + icon + favorite + tags.
- Avoids NULL pollution (recipe-only columns don't clutter food item rows and vice versa).
- JOIN on primary key is fast; we only join when the detail fields are needed.
- Future subtypes (e.g., "meal_plan_template" or "grocery_bundle") can be added as new `{type}_details` tables without touching existing ones.

**Alternative considered and rejected:** single fat `items` table with all columns nullable. Rejected because (a) it creates a long wide row with many NULL columns per entity, (b) it makes schema validation harder at the ORM level, and (c) it doesn't gracefully extend to future subtypes.

### 0.2 — Alembic Migrations (Expand-and-Contract, Three Revisions)

**Why three revisions instead of one atomic revision:** CEO review follow-up 2026-04-13. User chose "expand-and-contract over three Alembic revisions" for maximum safety. The atomic approach was correct for single-instance deployment but lost recoverability if a post-migration bug surfaced days later. The three-revision approach creates a dual-write window where both old and new schemas are live and the application writes to both, so any revision can be rolled back without data loss for recent writes.

**Timeline:** Each revision must run for at least one full cycle of testing (local → staging → production, plus one day of real usage on each) before the next revision starts. Total calendar time: ~3-5 days across all three revisions in a personal-project context, longer in production.

**Pre-migration hard gates (BLOCKERS — do not start Revision 1 until all pass):**

1. **Run migration against production snapshot locally.** Take a `pg_dump` of production, load it into a local Postgres, run Revision 1 against it, verify row counts match expected values, verify semantic correctness assertions (see 0.5). Record output. If any assertion fails, FIX before proceeding.
2. **Verify the `pg_dump` restore actually works on a disposable clone.** Do the drill on a throwaway restore target (local Postgres, staging clone, or provider snapshot clone), not by dropping the live production database in place. Verify the restored DB matches the original via row counts + sample queries. Schrödinger backups (untested backups) are worse than no backups. This is a one-time gate per environment.
3. **Audit all readers of `meal_entries.item_type` column.** Grep the entire backend for references to `meal_entries.item_type`, `MealEntry.item_type`, or any equivalent ORM access. Every reader must either (a) move to reading `items.item_type` via JOIN or (b) not run until Revision 3 drops the column. Document the audit results in the implementing PR.
4. **Audit all hardcoded IDs.** Grep for any backend or frontend code that hardcodes a numeric ID against recipes or food_items (unit tests, seed data, migrations, fixtures). None should exist in a well-structured codebase; any found must be updated to use name-based lookups or be post-migration-aware.
5. **Stop Celery workers + beat during every upgrade() execution.** The migrations take `ACCESS EXCLUSIVE` locks on `recipes`, `food_items`, and `meal_entries`. Celery writes during that window cause lock timeouts. Document in the rollout checklist: `docker-compose stop celery_worker celery_beat` before the migration, start after verification.

**Revision 1: EXPAND — Create new schema, backfill, start dual-write**

```python
"""create item model, backfill, start dual-write

Revision ID: <timestamp>_item_model_expand
"""

def upgrade():
    bind = op.get_bind()

    # Acquire exclusive locks up front to prevent concurrent writes racing the backfill.
    # Stop Celery workers + beat before running this migration (see pre-migration gate 5).
    op.execute("LOCK TABLE recipes IN ACCESS EXCLUSIVE MODE")
    op.execute("LOCK TABLE food_items IN ACCESS EXCLUSIVE MODE")
    op.execute("LOCK TABLE meal_entries IN ACCESS EXCLUSIVE MODE")
    op.execute("LOCK TABLE tasks IN ACCESS EXCLUSIVE MODE")  # Phase 6 rewrites Task.source_meals

    # Eng Review #2 (2026-04-13): capture the food_item ID offset ONCE and bind it into every
    # phase that needs it. The earlier draft tried to "reconstruct" the offset inside each SQL
    # statement using `MAX(items.id) - COUNT(*) FILTER (WHERE item_type='food_item')`, which is
    # only correct when food_items.id is dense (no gaps). Production almost certainly has gaps
    # from past deletes, so the reconstruction silently overshoots and corrupts FK references.
    # The dev DB already shows recipes max=8 / count=7, so the bug would fire on day one.
    food_id_offset = bind.execute(
        sa.text("SELECT COALESCE(MAX(id), 0) FROM recipes")
    ).scalar()

    # Phase 0: Pre-flight duplicate-name audit (fails loudly if we can't create the unique index).
    # Eng review 2026-04-13 added this gate. The new UNIQUE(name, item_type) partial index
    # adds a constraint that didn't exist on recipes before. If recipes or food_items have
    # duplicate names today, the index creation later in this migration will fail with an
    # obscure error. Detect it here with a clearer message.
    result = op.get_bind().execute(sa.text("""
        SELECT 'recipe' AS type, name, COUNT(*) AS cnt FROM recipes GROUP BY name HAVING COUNT(*) > 1
        UNION ALL
        SELECT 'food_item' AS type, name, COUNT(*) AS cnt FROM food_items GROUP BY name HAVING COUNT(*) > 1
    """))
    duplicates = result.fetchall()
    if duplicates:
        details = "; ".join(f"{t}: '{n}' ({c}x)" for t, n, c in duplicates)
        raise RuntimeError(
            f"Cannot migrate: duplicate names found that violate the new UNIQUE(name, item_type) "
            f"constraint. Resolve (rename or merge) these rows before retrying: {details}"
        )

    # Phase 1: Create new tables + constraints + indexes + triggers
    op.create_table(
        'items',
        sa.Column('id', sa.Integer(), primary_key=True),
        sa.Column('name', sa.Text(), nullable=False),
        sa.Column('item_type', sa.Text(), nullable=False),
        sa.Column('icon_emoji', sa.Text(), nullable=True),
        sa.Column('icon_url', sa.Text(), nullable=True),
        sa.Column('tags', postgresql.JSONB(), nullable=False, server_default=sa.text("'[]'::jsonb")),
        sa.Column('is_favorite', sa.Boolean(), nullable=False, server_default=sa.false()),
        sa.Column('deleted_at', sa.TIMESTAMP(), nullable=True),
        sa.Column('created_at', sa.TIMESTAMP(), nullable=False, server_default=sa.func.now()),
        sa.Column('updated_at', sa.TIMESTAMP(), nullable=False, server_default=sa.func.now()),
    )
    op.create_check_constraint('items_item_type_check', 'items', "item_type IN ('recipe', 'food_item')")
    op.create_check_constraint('items_icon_xor_check', 'items', 'NOT (icon_emoji IS NOT NULL AND icon_url IS NOT NULL)')
    op.create_index('items_item_type_idx', 'items', ['item_type'])
    op.create_index('items_is_favorite_idx', 'items', ['is_favorite'], postgresql_where=sa.text('is_favorite = true'))
    op.create_index('items_deleted_at_idx', 'items', ['deleted_at'], postgresql_where=sa.text('deleted_at IS NOT NULL'))
    op.create_index('items_name_type_uniq', 'items', ['name', 'item_type'], unique=True, postgresql_where=sa.text('deleted_at IS NULL'))

    op.create_table(
        'recipe_details',
        sa.Column('item_id', sa.Integer(), sa.ForeignKey('items.id', ondelete='CASCADE'), primary_key=True),
        sa.Column('description', sa.Text(), nullable=True),
        sa.Column('ingredients', postgresql.JSONB(), nullable=False, server_default=sa.text("'[]'::jsonb")),
        sa.Column('instructions', sa.Text(), nullable=True),
        sa.Column('prep_time_minutes', sa.Integer(), nullable=True),
        sa.Column('cook_time_minutes', sa.Integer(), nullable=True),
        sa.Column('servings', sa.Integer(), nullable=True),
        sa.Column('image_url', sa.Text(), nullable=True),
    )
    op.create_index('recipe_details_ingredients_gin', 'recipe_details', ['ingredients'], postgresql_using='gin')

    op.create_table(
        'food_item_details',
        sa.Column('item_id', sa.Integer(), sa.ForeignKey('items.id', ondelete='CASCADE'), primary_key=True),
        sa.Column('category', sa.Text(), nullable=False, server_default='Other'),
        sa.Column('shopping_quantity', sa.Numeric(), nullable=False, server_default='1.0'),
        sa.Column('shopping_unit', sa.Text(), nullable=False, server_default='each'),
    )

    # updated_at propagation trigger (addresses adversarial review WARNING dimension 7)
    op.execute("""
        CREATE OR REPLACE FUNCTION bump_item_updated_at() RETURNS TRIGGER AS $$
        BEGIN
            UPDATE items SET updated_at = now() WHERE id = COALESCE(NEW.item_id, OLD.item_id);
            RETURN NULL;
        END;
        $$ LANGUAGE plpgsql;
    """)
    op.execute("""
        CREATE TRIGGER recipe_details_bump_parent
            AFTER INSERT OR UPDATE OR DELETE ON recipe_details
            FOR EACH ROW EXECUTE FUNCTION bump_item_updated_at();
    """)
    op.execute("""
        CREATE TRIGGER food_item_details_bump_parent
            AFTER INSERT OR UPDATE OR DELETE ON food_item_details
            FOR EACH ROW EXECUTE FUNCTION bump_item_updated_at();
    """)

    # Phase 2: Backfill items + recipe_details from existing recipes
    # Use NULLIF to normalize empty-string icon values (adversarial review dimension 2)
    op.execute("""
        INSERT INTO items (id, name, item_type, icon_emoji, icon_url, tags, is_favorite, created_at, updated_at)
        SELECT id, name, 'recipe', NULL, NULL, COALESCE(tags::jsonb, '[]'::jsonb), COALESCE(is_favorite, false), created_at, updated_at
        FROM recipes
    """)
    op.execute("""
        INSERT INTO recipe_details (item_id, description, ingredients, instructions, prep_time_minutes, cook_time_minutes, servings, image_url)
        SELECT id, description, COALESCE(ingredients::jsonb, '[]'::jsonb), instructions, prep_time_minutes, cook_time_minutes, servings, image_url
        FROM recipes
    """)

    # Phase 3: Backfill items + food_item_details from existing food_items
    # ID offset = food_id_offset (captured once at top of upgrade(), bound as a parameter
    # into every statement that needs it). Eng Review #2 (2026-04-13) replaced the previous
    # SQL "reconstruction" formulas with this single Python-side capture because the
    # reconstruction was wrong whenever food_items.id was sparse.
    # NOTE: current food_items column is `emoji`, NOT `icon_emoji` (verified against
    # backend/app/models.py:224 during eng review). Do not rename in the SELECT below.
    op.execute(
        sa.text("""
            INSERT INTO items (id, name, item_type, icon_emoji, icon_url, tags, is_favorite, created_at, updated_at)
            SELECT
                f.id + :food_id_offset,
                f.name,
                'food_item',
                NULLIF(f.emoji, ''),
                NULL,
                '[]'::jsonb,
                COALESCE(f.is_favorite, false),
                f.created_at,
                f.updated_at
            FROM food_items f
        """).bindparams(food_id_offset=food_id_offset)
    )
    op.execute(
        sa.text("""
            INSERT INTO food_item_details (item_id, category, shopping_quantity, shopping_unit)
            SELECT
                f.id + :food_id_offset,
                COALESCE(f.category, 'Other'),
                COALESCE(f.shopping_quantity, 1.0),
                COALESCE(f.shopping_unit, 'each')
            FROM food_items f
        """).bindparams(food_id_offset=food_id_offset)
    )

    # Phase 4: Resync the sequence using pg_get_serial_sequence (adversarial review dimension 7)
    # Never hardcode 'items_id_seq' — use pg_get_serial_sequence so Alembic-renamed sequences still work.
    op.execute("""
        SELECT setval(pg_get_serial_sequence('items', 'id'), (SELECT COALESCE(MAX(id), 1) FROM items))
    """)

    # Phase 5: Add item_id column to meal_entries as a shadow column.
    # DO NOT drop recipe_id/food_item_id yet — Revision 2 flips reads, Revision 3 drops the old columns.
    op.add_column('meal_entries', sa.Column('item_id', sa.Integer(), nullable=True))
    op.create_foreign_key(
        'meal_entries_item_id_fkey', 'meal_entries', 'items',
        ['item_id'], ['id'],
        ondelete='RESTRICT'  # Adversarial review dimension 7: NOT CASCADE. Soft-delete is the supported path.
    )
    op.create_index('meal_entries_item_id_idx', 'meal_entries', ['item_id'])

    # Backfill meal_entries.item_id from the old columns using the same captured ID offset
    op.execute("""
        UPDATE meal_entries SET item_id = recipe_id WHERE recipe_id IS NOT NULL
    """)
    op.execute(
        sa.text("""
            UPDATE meal_entries
            SET item_id = food_item_id + :food_id_offset
            WHERE food_item_id IS NOT NULL
        """).bindparams(food_id_offset=food_id_offset)
    )

    # Phase 6: Rewrite Task.source_meals JSON to use item_id instead of recipe_id/food_item_id.
    # Identified by eng review on 2026-04-13: shopping_sync.py stores source tracking as JSON
    # inside Task.source_meals with embedded recipe_id and food_item_id fields. After the refactor,
    # these stale field names reference tables that no longer exist (post-Revision-3) and the
    # food_item_id values don't match the new offset-adjusted item IDs.
    #
    # Rewrite each source_meals entry atomically:
    #   {recipe_id: 7, food_item_id: null, source_kind: 'recipe_ingredient', ...}
    #     → {item_id: 7, source_kind: 'recipe_ingredient', ...}
    #   {recipe_id: null, food_item_id: 3, source_kind: 'food_item', ...}
    #     → {item_id: 3 + offset, source_kind: 'food_item', ...}
    #
    # The offset used MUST be the same one used in Phase 3 above. We bind food_id_offset
    # (captured at the top of upgrade()) directly into the statement instead of
    # recomputing it from the live items table. The previous CTE was off by
    # -count(food_items) regardless of density and would have silently scrambled
    # every food-item shopping task source reference.
    op.execute(
        sa.text("""
            UPDATE tasks
            SET source_meals = (
                SELECT jsonb_agg(
                    CASE
                        WHEN entry->>'source_kind' = 'recipe_ingredient' THEN
                            jsonb_build_object(
                                'meal_entry_id', entry->'meal_entry_id',
                                'source_kind', entry->>'source_kind',
                                'item_id', entry->'recipe_id'
                            ) || COALESCE(entry - 'recipe_id' - 'food_item_id' - 'meal_entry_id' - 'source_kind', '{}'::jsonb)
                        WHEN entry->>'source_kind' = 'food_item' THEN
                            jsonb_build_object(
                                'meal_entry_id', entry->'meal_entry_id',
                                'source_kind', entry->>'source_kind',
                                'item_id', to_jsonb((entry->>'food_item_id')::int + :food_id_offset)
                            ) || COALESCE(entry - 'recipe_id' - 'food_item_id' - 'meal_entry_id' - 'source_kind', '{}'::jsonb)
                        ELSE entry
                    END
                )
                FROM jsonb_array_elements(source_meals) AS entry
            )
            WHERE source_meals IS NOT NULL AND jsonb_typeof(source_meals) = 'array'
        """).bindparams(food_id_offset=food_id_offset)
    )

    # Phase 7: Application-level dual-write + source_meals code update marker.
    # After this migration, the backend MUST be updated to:
    #   (a) write to BOTH old tables and new tables on every create/update/delete
    #   (b) shopping_sync.py must write `item_id` (not recipe_id/food_item_id) into
    #       Task.source_meals for new entries created after the migration
    # Both changes ship in the SAME PR as this migration. Dual-write and the old field-name
    # writers are removed in Revision 3.


def downgrade():
    """Full, round-trippable downgrade. NOT lossy during Revision 1 because the old tables
    and columns are still intact. Items created post-Revision-1 in the new schema that
    don't have corresponding rows in the old tables WILL be lost by this downgrade —
    which is acceptable because dual-write means they should exist in both schemas.
    """
    op.execute("LOCK TABLE recipes IN ACCESS EXCLUSIVE MODE")
    op.execute("LOCK TABLE food_items IN ACCESS EXCLUSIVE MODE")
    op.execute("LOCK TABLE meal_entries IN ACCESS EXCLUSIVE MODE")
    food_id_offset = op.get_bind().execute(
        sa.text("SELECT COALESCE(MAX(id), 0) FROM recipes")
    ).scalar()
    # Reverse Phase 6 before dropping the new-schema-only references. After a Rev 1 downgrade,
    # pre-refactor shopping-sync code expects legacy `recipe_id` / `food_item_id` keys inside
    # Task.source_meals. Leaving `item_id` in place would make the schema look rolled back while
    # the JSON payload shape silently stayed on the new contract.
    op.execute(
        sa.text("""
            UPDATE tasks
            SET source_meals = (
                SELECT jsonb_agg(
                    CASE
                        WHEN entry->>'source_kind' = 'recipe_ingredient' AND entry ? 'item_id' THEN
                            jsonb_build_object(
                                'meal_entry_id', entry->'meal_entry_id',
                                'source_kind', entry->>'source_kind',
                                'recipe_id', entry->'item_id',
                                'food_item_id', to_jsonb(NULL::int)
                            ) || COALESCE(entry - 'item_id' - 'meal_entry_id' - 'source_kind', '{}'::jsonb)
                        WHEN entry->>'source_kind' = 'food_item' AND entry ? 'item_id' THEN
                            jsonb_build_object(
                                'meal_entry_id', entry->'meal_entry_id',
                                'source_kind', entry->>'source_kind',
                                'recipe_id', to_jsonb(NULL::int),
                                'food_item_id', to_jsonb((entry->>'item_id')::int - :food_id_offset)
                            ) || COALESCE(entry - 'item_id' - 'meal_entry_id' - 'source_kind', '{}'::jsonb)
                        ELSE entry
                    END
                )
                FROM jsonb_array_elements(source_meals) AS entry
            )
            WHERE source_meals IS NOT NULL AND jsonb_typeof(source_meals) = 'array'
        """).bindparams(food_id_offset=food_id_offset)
    )
    op.drop_index('meal_entries_item_id_idx', table_name='meal_entries')
    op.drop_constraint('meal_entries_item_id_fkey', 'meal_entries', type_='foreignkey')
    op.drop_column('meal_entries', 'item_id')
    op.execute("DROP TRIGGER IF EXISTS food_item_details_bump_parent ON food_item_details")
    op.execute("DROP TRIGGER IF EXISTS recipe_details_bump_parent ON recipe_details")
    op.execute("DROP FUNCTION IF EXISTS bump_item_updated_at()")
    op.drop_index('recipe_details_ingredients_gin', table_name='recipe_details')
    op.drop_table('food_item_details')
    op.drop_table('recipe_details')
    op.drop_index('items_name_type_uniq', table_name='items')
    op.drop_index('items_deleted_at_idx', table_name='items')
    op.drop_index('items_is_favorite_idx', table_name='items')
    op.drop_index('items_item_type_idx', table_name='items')
    op.drop_table('items')
```

**Revision 1 safety profile:** Forward-only destructive operations: NONE. The old `recipes`, `food_items`, and `meal_entries.recipe_id`/`food_item_id` columns remain untouched. Downgrade is fully reversible. Only risk is a bug in the dual-write application code that misses an update on the new schema — caught by the verification steps below.

**Overall migration safety summary:**

- **PK collision handling:** Food item IDs get offset by `food_id_offset = MAX(recipes.id)`, captured ONCE at the top of `upgrade()` and bound as a parameter into every Phase 3, 5, and 6 statement that needs it. Eng Review #2 caught and fixed three earlier draft formulas that tried to "reconstruct" the offset from the live `items` table — those reconstructions were wrong whenever `food_items.id` was sparse (production almost always has gaps from past deletes). `pg_get_serial_sequence` is still used for the post-backfill sequence resync.
- **Lock acquisition:** Every upgrade() and downgrade() acquires `ACCESS EXCLUSIVE` locks on the affected tables up front. Celery workers + beat must be stopped during each migration run (rollout gate 5).
- **Dual-write window:** Revisions 1 and 2 keep both schemas live. Revision 3 drops the old one only after dual-write has validated the new schema for at least 24h.
- **Downgrade:** Revision 1 and Revision 2 downgrades are non-lossy. Revision 3 downgrade is lossy but documented as break-glass only.
- **Backup:** `pg_dump` taken before each revision, restore verified (rollout gate 2).
- **Atomicity:** Each revision runs in a single transaction. Alembic config sets `transaction_per_migration = True`.

### 0.3 — Backend Model + CRUD + Route Refactor (Canonical /items API)

**Decision:** The façade pattern is rejected per CEO review concern 5. `/recipes` and `/food-items` routes are DELETED. The canonical API surface is `/items` with type filtering. One API shape, one mental model, one code path. This is the cleanest, most future-proofed approach.

```python
    id: Mapped[int] = mapped_column(primary_key=True)

    item_type: Mapped[str]  # 'recipe' | 'food_item'

    item: Mapped["Item"] = relationship(back_populates="food_item_detail", lazy="selectin")
```

**Query builders** — `backend/app/crud_items.py` owns all Item CRUD. Every Item query uses `selectinload` explicitly even though `lazy="selectin"` is set, because explicit is safer than relying on default lazy modes across async callers. The project uses the async `select(...)` idiom, not `session.query(...)`:

```python
from sqlalchemy import select
from sqlalchemy.orm import selectinload

def active_items_stmt(item_type: str | None = None):
    """Canonical statement builder for non-deleted items with detail eager-loaded.
    All list/detail/search endpoints build off this."""
    stmt = (
        select(models.Item)
        .where(models.Item.deleted_at.is_(None))
        .options(
            selectinload(models.Item.recipe_detail),
            selectinload(models.Item.food_item_detail),
        )
    )
    if item_type is not None:
        stmt = stmt.where(models.Item.item_type == item_type)
    return stmt


async def list_items(db, item_type: str | None = None) -> list[models.Item]:
    result = await db.execute(active_items_stmt(item_type))
    return list(result.scalars().all())
```

Same pattern in `backend/app/crud_meal_entries.py` for meal entries, using `soft_hidden_at IS NULL` instead of `deleted_at IS NULL`:

```python
def visible_meal_entries_stmt():
    """Canonical statement builder for non-hidden meal entries."""
    return (
        select(models.MealEntry)
        .where(models.MealEntry.soft_hidden_at.is_(None))
        .options(selectinload(models.MealEntry.item))
    )
```

**Why not a mixin?** Eng review 2026-04-13 rejected the mixin-style pattern because (a) Item uses `deleted_at` but MealEntry uses `soft_hidden_at`, so a shared mixin would branch on subclass; (b) the project's async select idiom doesn't compose well with classmethod builders; (c) explicit statement helpers at module level match engineering preference "explicit over clever" and align with the existing CRUD file structure.

### 0.4 — Frontend Refactor (Path A: Full Merge)

**Decision:** Path A — full merge. `RecipeCard` + `FoodItemCard` collapse into one `ItemCard`. `RecipeRow` + `FoodItemRow` collapse into one `ItemRow`. `RecipeFormModal` + `FoodItemFormModal` collapse into one `ItemFormModal`. `useRecipes` + `useFoodItems` collapse into one `useItems({type})` hook.

Rationale (per CEO review concern 3 + adversarial review dimension 4): Path B (thin wrappers) was the short-term pragmatic choice and explicitly a "5-year optimization target" miss. Wrappers-whose-only-job-is-passing-props are the definition of premature abstraction in the opposite direction — they tend to accumulate divergent logic over time until a future refactor "just finishes the merge." Since Claude-Code effort is not a constraint and you want the cleanest, most future-proofed end state, Path A is strictly better.

### 0.4C — AI Slop Risk Guardrails (Design Review 2026-04-13, Pass 4)

This plan is classified as **App UI** (workspace-driven, data-dense, task-focused). The AI slop blacklist scan finds zero high-risk patterns, but two LOW-risk drift points need explicit guardrails so an implementer doesn't accidentally introduce them:

1. **Empty states are LEFT-aligned, not centered cards.** The empty-state cells in §0.4A ("No recipes yet — [Add recipe]") MUST render as left-aligned content within a normal grid container, NOT as a centered card with a decorative icon-in-circle. Concretely:
   ```jsx
   <div className="px-1 py-8 max-w-md">
     <h3 className="text-base font-medium text-text-primary">No recipes yet</h3>
     <p className="mt-1 text-sm text-text-secondary">Add your first recipe to start building meal plans.</p>
     <button className="mt-4 px-4 py-2 bg-terracotta-500 text-white rounded-lg">+ Add recipe</button>
   </div>
   ```
   No `text-center`. No `flex items-center justify-center` wrapper. No decorative SVG illustration. No `bg-warm-sand rounded-xl` card chrome around it. Reads like "the page is empty and the next step is right there", not like a marketing card.

2. **Food item `ItemDetailDrawer` uses SVG icons, not emoji-as-icon prefixes.** The existing recipe drawer renders meta chips as `⏲ 30m prep` and `👥 4 servings` — emoji used as icon substitutes. This is a known concession from prior rounds; the plan must NOT propagate it to the new food-item drawer body. The food-item drawer's category badge and shopping-unit line use inline SVG icons from the existing project icon vocabulary (the same pattern as `RecipesView` and `FoodItemsView` toolbar icons), styled with `text-text-muted w-4 h-4`. Concretely:
   - Category line: `[shopping-bag SVG] Fruit` (NOT `🛒 Fruit`)
   - Shopping unit line: `[scale SVG] 0.25 cups per meal` (NOT `⚖ 0.25 cups`)
   Recipe drawer chips are NOT being changed in this batch — that would be scope creep — but new surfaces inherit the SVG-only rule.

3. **No new motion vocabulary.** All new motion (UndoToast countdown ring, day/date entrance, restored-item flash, AI suggest scale-in, Custom image drop zone highlight, cooked-state pulse) reuses an existing keyframe (`fade-in`, `scale-in`, `view-crossfade`) or a Framer Motion spring with the same `duration: 200-300ms`, `ease-out` profile already used elsewhere. Do NOT introduce a new bezier easing curve, a new spring stiffness, or a new keyframe. Variety inside one app feels generative; coherence feels designed.

4. **Section headings stay utility.** The food-item drawer's section labels are "Category", "Shopping unit", "Tags" — not "About", "Pantry stats", "Lifestyle". Utility language only.

5. **No icon-in-colored-circle for decoration.** The existing `ConfirmDialog` uses `bg-red-100 rounded-full` around an exclamation icon — that's a semantic warning marker, not decoration, and stays as-is. New surfaces must NOT add icon-in-circle patterns for category dots, status pills, or section headers. The Food Items tab category dot stays as the existing `w-2 h-2 rounded-full` (no icon inside).

### 0.6 — Rollout + Safety

**Pre-migration hard gates (all must pass before Revision 1 runs):**

1. `pg_dump` of production taken and stored to `.claude/backups/pre-item-refactor-{timestamp}.sql` (gitignored). Never use `DROP DATABASE` against the live production DB as part of a restore drill.
2. **Verified restore** — actually run the restore command against a throwaway DB and confirm row counts match. Untested backups are Schrödinger backups.
3. **Local dry run against production snapshot.** Load the pg_dump into a local Postgres, run Revision 1, execute the migration smoke test suite, verify semantic correctness assertions pass. Record results in the PR description.
4. **`meal_entries.item_type` reader audit.** Grep the entire backend (and any frontend reference) for the column; document every reader and confirm each is updated to use `items.item_type` via JOIN before Revision 3.
5. **Hardcoded ID audit.** Grep for numeric literals against `recipes.id` or `food_items.id` in tests, seed data, fixtures. Document findings.
6. **Celery workers + beat are stopped** via `docker-compose stop celery_worker celery_beat` before each revision's upgrade() runs. Start them after verification. Document in the runbook.
7. **If more than one API instance exists, all replicas are drained or put behind maintenance mode** before the Rev 1 migration window. The "stop the API" safety fix only works if *all* write paths are actually quiesced.

### 0.6B — Silent Failure / Stale State Rules

- **Dual-write drift is a release blocker, not just a dashboard datapoint.** Any non-zero drift audit on row counts, checksums, or stale `recipe_id` / `food_item_id` writes must emit a structured error log, increment a metric, and block promotion from Rev 1 → Rev 2 or Rev 2 → Rev 3 until the mismatch is explained and fixed. **Promotion gate is numeric, not vibes-based:** Rev 1 → Rev 2 requires ≥ 24 consecutive clean `audit_dual_write_drift` runs (= ~2 hours of green at the every-5-min cadence) AND zero structured-error logs from the audit task in the soak window. Rev 2 → Rev 3 reuses the same threshold against the post-switch state.
- **Stale clients must fail clearly.** During Rev 2 and the Rev 3 soak, old Mealboard clients hitting tombstoned legacy endpoints must receive a refresh-required response that the frontend maps to a visible "Mealboard updated. Refresh required." message instead of a generic error toast. The user-visible copy is exact; do not fork it into multiple near-identical messages.
- **Soft-delete / undo must be user-visible and idempotent.** Duplicate undo clicks while the item is already restored should resolve successfully without double-restoring; expired undo, invalid `undo_token`, or a hard-delete race must return a clear `410 Gone` path that renders as "Undo window expired" rather than a silent no-op.
- **Feature-flag fallback must fail closed.** If `MEALBOARD_SOFT_DELETE_ENABLED` is disabled during rollout or incident response, delete buttons disappear (or render disabled with explanatory copy) and `DELETE /items/{id}` returns `503`; the system must not silently fall back to a hard delete path.
- **Shopping sync side effects must be explicit.** Soft-delete subtracts the item's contributions from aggregated shopping tasks and records the hidden state in `Task.source_meals`; undo restores the exact contributions for the same still-active meal entries; hourly hard-delete removes any remaining hidden meal-entry source references so aggregation cannot resurrect deleted items later.
- **Upload and AI suggest failures must not be invisible.** Invalid MIME / oversize uploads return clear 4xx responses, SVG is rejected explicitly, Claude suggest `204` hides the suggestion block quietly, and `503` shows no suggestion UI but leaves manual emoji/icon selection fully functional.

**Feature flags:** The refactor itself does NOT use a feature flag — the revision sequence IS the rollback mechanism. The downstream feature flags from Expansions B (`MEALBOARD_SOFT_DELETE_ENABLED`) and C (`MEALBOARD_AI_SUGGEST_ENABLED`) remain in place for their respective features.

**Maintenance window:** Revision 1 intentionally takes the API fully down during the upgrade window (connection-refused / maintenance behavior is expected). Revision 2 is a schema no-op and should not create DB downtime. Revision 3 keeps the API up but may surface brief 500/timeout responses during the `ACCESS EXCLUSIVE` lock window after the code-first deploy step. Typical lock window for household-sized data: 1-5 seconds. Schedule each revision during a low-traffic window (late evening).

## CEO Review Scope Expansion (2026-04-13)

The CEO review added scope that remains valid, but the implementation language below is rewritten in canonical post-Chunk-0 terms so it no longer conflicts with the unified `Item` direction.

### Expansion A — Delete symmetry now lives inside the single Item lifecycle

- The old asymmetry between recipe delete and food-item delete is gone after Chunk 0 because both are `items` distinguished by `item_type`.
- There is no surviving standalone `meal_entries.food_item_id` cascade migration after Chunk 0. The relevant lifecycle is `items.deleted_at`, `meal_entries.soft_hidden_at`, and later hard-delete handling against `item_id`.
- The UI requirement survives: both recipe-like and food-item-like item surfaces expose the same delete flow, confirm copy, and usage messaging.

### Expansion B — Soft-delete + merged undo toast

- Soft-delete is canonicalized as `DELETE /items/{id}` returning `{undo_token, expires_at}` and `POST /items/{id}/undo` clearing both `items.deleted_at` and the matching `meal_entries.soft_hidden_at` values.
- `POST /items/{id}/undo` requires the opaque `undo_token` from the delete response. The backend must verify the token matches the item and the current soft-delete window before restoring; item-id-only undo is not allowed. Invalid, stale, or mismatched tokens return `410 Gone` so stale clients fail clearly instead of silently restoring the wrong thing.
- **Undo collision against the partial unique index (Eng Review #3 Issue 4):** if a same-named item was created between the original soft-delete and the undo attempt, restoring the deleted item would violate `UNIQUE(name, item_type) WHERE deleted_at IS NULL` and surface as a 500. The undo handler MUST catch the unique constraint violation and return `409 Conflict` with body `{error: "name_collision", existing_id: <int>}`. The frontend toast renders item-type-aware copy, for example: *"Could not restore: a food item named 'X' already exists. Restore as 'X (restored)'?"* with a one-click rename-and-restore button that retries undo with a `?rename_to=` query param. The backend handles `?rename_to=` by renaming the restored row in the same transaction as the deleted_at clear. Test rows added to §0.5 cover the collision detection, the 409 response, and the rename-and-retry path.
- Storage is post-refactor: `items.deleted_at TIMESTAMP NULL`, `meal_entries.soft_hidden_at TIMESTAMP NULL`, plus partial indexes where useful.
- The hourly job `hard_delete_expired_soft_deletes` operates on Items, not separate recipe/food-item tables.
- **Hard-delete cascade-in-code, not schema (Eng Review #3 Issue 3):** the `meal_entries.item_id` FK is `ON DELETE RESTRICT` so raw `DELETE FROM items` cannot silently wipe meal history. But this means a naive `DELETE FROM items WHERE deleted_at < now() - INTERVAL '24 hours'` will crash on the FK whenever soft-hidden meal_entries still reference the item. The Celery job `hard_delete_expired_soft_deletes` MUST run as an explicit two-step transaction:

  ```python
  async def hard_delete_expired_soft_deletes(db):
      cutoff = datetime.utcnow() - timedelta(hours=24)
      # Step 1: gather expired item IDs
      expired = (await db.execute(
          select(Item.id).where(Item.deleted_at.is_not(None), Item.deleted_at < cutoff)
      )).scalars().all()
      if not expired:
          return
      async with db.begin():
          # Step 2a: delete soft-hidden meal_entries that reference expired items
          # (these must already be soft_hidden_at IS NOT NULL — anything still active
          # is a bug and should fail loudly)
          await db.execute(
              delete(MealEntry).where(
                  MealEntry.item_id.in_(expired),
                  MealEntry.soft_hidden_at.is_not(None),
              )
          )
          # Step 2b: assertion gate — if any active meal_entries still reference
          # an expired item, ABORT the transaction and alert. This means soft-delete
          # didn't propagate hidden state correctly and we must NOT proceed.
          remaining = (await db.execute(
              select(func.count(MealEntry.id)).where(MealEntry.item_id.in_(expired))
          )).scalar()
          if remaining > 0:
              raise RuntimeError(
                  f"Hard-delete aborted: {remaining} active meal_entries still "
                  f"reference {len(expired)} expired items. Soft-delete propagation bug."
              )
          # Step 2c: now delete the items (FK is satisfied)
          await db.execute(delete(Item).where(Item.id.in_(expired)))
  ```

  This preserves `ON DELETE RESTRICT` as a safety latch against raw SQL deletes (the original adversarial review concern), while letting the explicit cleanup path work. The assertion gate ensures a propagation bug fails loudly via Celery error handling instead of silently leaving orphan rows. Test rows added to §0.5 cover the happy path, the assertion-gate failure, and the partial-failure transaction rollback.

- The frontend still uses a merged undo toast: deletes within 2 seconds merge into one toast, 15-second client countdown, 24-hour server grace window, optimistic restore with rollback on failure.

- **`UndoToast` component (Design Review 2026-04-13, IA pass, Issue 2B):** The undo flow uses a NEW dedicated singleton component, NOT an extension of the existing `frontend/src/components/shared/ToastProvider.jsx`. Rationale: existing ToastProvider is a fire-and-forget bottom-right stack with no action button, no countdown, no merging — extending it to support all four would turn it into the project's notification primitive forever and couple every future toast change to delete/undo logic. Keeping it unmodified preserves the simple-error-toast contract the rest of the app relies on.

  **File:** `frontend/src/components/shared/UndoToast.jsx` (placed in `shared/` because the same primitive may later host other "you have N seconds to undo" flows like checked-task undo on the Lists page).

  **Position:** `fixed bottom-6 left-1/2 -translate-x-1/2 z-[110]` on desktop (≥768px), `fixed bottom-4 inset-x-4 z-[110]` on mobile (<768px) so the entire viewport width is usable as a thumb target. `z-[110]` is one layer above the existing `ToastProvider` z-[100] so an unrelated error toast cannot occlude the undo affordance.

  **Singleton:** there is at most ONE `UndoToast` visible at any time — the merge behavior absorbs new deletes into the existing toast instead of stacking. If a Chunk 6 future feature also wants an undo toast (for e.g. checked-task undo), it queues until the current one resolves; the queueing rule is documented as a follow-up TODO, not implemented in this batch.

  **Slots (left → right on desktop, top → bottom on mobile):**
  1. **Item icon** — small `ItemIcon` (24px) showing the deleted item's emoji or image. For a merged toast (`count > 1`), shows the FIRST deleted item's icon with a `+N` badge indicating additional items.
  2. **Label** — single line:
     - `count === 1, type='recipe'`: "Recipe deleted"
     - `count === 1, type='food_item'`: "Food item deleted"
     - `count > 1`: "{count} items deleted" (item-type mixing is allowed; the label flattens to the generic "items" form)
  3. **Countdown ring** — circular SVG progress indicator showing time remaining out of 15s. Hidden when state ≠ `active`.

  5. **Dismiss** — small ✕ icon button (`p-1.5 rounded-full text-white/70 hover:text-white`). Dismissing does NOT cancel the server-side soft-delete; it only hides the toast and locks in the deletion (the user can still recover via the 24h server grace window if they fish for it, but there is no UI for that — only the toast countdown is exposed).

  **Visual style:** dark surface for high contrast (`bg-text-primary text-white dark:bg-gray-800` — i.e. the warm-charcoal `#3D3833` used elsewhere as primary text becomes the toast's background, mirroring the existing dark error/success toasts). Rounded `rounded-xl`, padding `px-4 py-3`, max width `max-w-md` desktop / full-width mobile, shadow `shadow-xl`. Entrance: `fade-in` from below with `translateY(8px) → 0` over 200ms (existing `fade-in` keyframe).

  **States:** see Pass 2 interaction state matrix below — `active`, `offline-retrying`, `collision-rename`, `expired`, `error`. The component swaps slot 4 (action button) and slot 3 (countdown vs spinner vs nothing) per state without re-mounting, so the entrance animation only fires on the first appearance.

  **Mobile behavior:** on viewports <768px, the toast spans full width with `inset-x-4`, the countdown ring stays inline with the action button, and the action button is enlarged to `min-h-[44px]` to meet the 44px touch target requirement.

  **A11y:** `role="status" aria-live="polite"` on the toast container so the deletion announces without interrupting screen reader speech. The Undo button has an explicit `aria-label="Undo deletion of {item name}"` (or "Undo deletion of {count} items" when merged). Keyboard: Tab focuses the Undo button on appearance; Esc dismisses (does not undo).

  **State matrix (Design Review 2026-04-13, Pass 2 issue 1):** the toast swaps slot contents on transition without re-mounting. Each state defines slots 1-5 from the shell above (icon / label / countdown / action / dismiss):

  | State | Trigger | Icon (1) | Label (2) | Countdown (3) | Action (4) | Dismiss (5) |
  |---|---|---|---|---|---|---|
  | `active` | Delete request returned 200 with `undo_token` | ItemIcon (24px) of first deleted item, +N badge if `count > 1` | "Recipe deleted" / "Food item deleted" / "{N} items deleted" | Visible 15s circular ring counting down | "Undo" (terracotta-500) | ✕ |
  | `optimistic-restoring` | User clicked Undo | Same icon | "Restoring…" | Hidden | Spinner (replaces button) | hidden |
  | `offline-retrying` | Undo click while `navigator.onLine === false` OR retry attempt failed network | Same icon | "Restoring when back online…" | Hidden | Small "Retry now" link button (visible only after first reconnect attempt fails) | ✕ |
  | `collision-rename` | Undo returned `409 {error: "name_collision", existing_id}` | Same icon | "A {recipe\|food item} named "{name}" already exists." | Hidden | "Restore as "{name} (restored)"" (single button, retracts to second line on mobile) | ✕ |
  | `expired` | Undo returned `410 Gone` (server window expired) | Same icon, but desaturated `opacity-60` | "Undo window expired" | Hidden | hidden | ✕ (auto-dismisses after 4s) |
  | `error` | Undo returned 5xx OR offline-retry exhausted | Same icon | "Couldn't restore — please try again" | Hidden | "Try again" (terracotta-500) | ✕ |
  | `success` | Undo returned 200 (restored) | Same icon | "{Recipe\|Food item} restored" (or "{N} items restored") | Hidden | hidden | hidden (auto-dismisses after 1.5s, fades out) |

  **Transition rules:**
  - `active` is the entry state for any new toast.
  - A new delete arriving within 2 seconds of an existing `active` toast: increments `count`, restarts the countdown ring at 15s, swaps icon to a `+N` badged variant. Stays in `active`.
  - A new delete arriving while toast is in any non-active state: queues a NEW toast that mounts after the current one resolves (singleton queue).
  - The visual continuity from `active` → `optimistic-restoring` → `success` reads as one motion: the user clicks Undo, the button becomes a spinner in place, the spinner becomes the success label, then the whole toast fades out.
  - A page reload during `offline-retrying` clears the in-memory queue (per Expansion B); the toast does NOT reappear after reload. The 24h server window is still open, but the UI does not surface it — accepted tradeoff.

  **`+N` merged badge style:** small terracotta circle overlaid on the bottom-right of the ItemIcon, `text-[10px] text-white font-semibold w-4 h-4`. Reads "+2" for 3 deletes, "+9+" for ≥10. Caps at "+9+" so the badge stays one character.

  **Countdown ring:** 16px circular SVG, 2px stroke, `stroke-white/20` track + `stroke-white` progress. Animation is a CSS `@keyframes` `stroke-dashoffset` interpolation over 15000ms, paused if the user hovers (desktop only — gives a moment to read merged-count). The white-on-charcoal contrast inherits from the dark toast background and avoids introducing a new token (the existing terracotta scale skips 300/400 — see `frontend/src/index.css`).
- If the browser is offline when Undo is clicked, keep the same toast open in a pending-retry state, queue exactly one in-memory retry keyed by `{item_id, undo_token}`, and fire it automatically on the `online` event. If that reconnect attempt still fails, keep the toast visible with an explicit `Retry` action. Duplicate undo clicks collapse onto the same queued request instead of spawning parallel restores. A full page reload clears the client-side queue; after reload, the user can still retry manually if the server window has not expired.
- If `MEALBOARD_SOFT_DELETE_ENABLED=false`, the system fails closed: destructive Item UI entry points are hidden or disabled, `DELETE /items/{id}` returns `503`, and there is no hard-delete fallback on the primary user path.
- Query safety follows the eng-review decision: use explicit async item/meal-entry select helpers that filter out soft-deleted rows instead of reintroducing an `active_only()` mixin abstraction.

## Eng Review #3 Findings (2026-04-13)

Run by `/plan-eng-review` after the second adversarial pass. Verified plan claims against actual code state in `backend/app/models.py`, `backend/app/services/shopping_sync.py`, `backend/app/routes/`, and `frontend/src/`. Surfaced 7 issues plus 1 TODO. All resolved before this writeup.

**Issue 1 — Rev 1 deploy-window data hole (P0, fixed):** Stopping only Celery during `alembic upgrade <rev1>` left the API container running and writing meal_entries with `recipe_id`/`food_item_id` populated but `item_id = NULL`. Those rows would later violate Rev 3's `CHECK (item_id IS NOT NULL OR custom_meal_name IS NOT NULL)` and abort the upgrade. The drift audit detected the gap but had no repair path. **Fix:** §0.6 Rev 1 sequence now stops the API container alongside Celery for the migration window. Outage budget: ~30s-2min, scheduled in a low-traffic window. Test row added: ER#3 Issue 1 in §0.5.

**Issue 2 — Rev 3 deploy ordering caused write failures (P0, fixed):** The previous sequence ran `alembic upgrade <rev3>` BEFORE deploying the code that disables dual-write. Between alembic and code deploy, the existing Rev 2-era backend (still `DUAL_WRITE_ENABLED=True`) tried to `INSERT INTO recipes ...` against tables that no longer existed → every mutation 500'd. **Fix:** §0.6 Rev 3 sequence now deploys the code with `DUAL_WRITE_ENABLED=False` first, verifies writes, then runs alembic. Reads were already on the new schema since Rev 2, so this gap is safe. Test rows added: ER#3 Issue 2 (happy path + reversed-order regression) in §0.5.

**Issue 3 — Hard-delete crashed on `ON DELETE RESTRICT` FK (P0, fixed):** The plan kept `meal_entries.item_id` FK as RESTRICT (correctly, per the original adversarial review) but the hourly `hard_delete_expired_soft_deletes` Celery job did a naive `DELETE FROM items WHERE deleted_at < cutoff`. Soft-hidden meal_entries still referenced those items, so RESTRICT blocked the delete and the Celery task crashed every hour without ever cleaning up. **Fix:** Expansion B now spells out the cascade-in-code pattern: gather expired item IDs, delete soft-hidden meal_entries first, assert no active meal_entries still reference, then delete items — all in one transaction. The RESTRICT FK is preserved as the safety latch against raw SQL deletes. Three test rows added: happy path, assertion-gate failure, partial-failure rollback.

**Issue 4 — Undo collision against the partial unique index (P1, fixed):** `UNIQUE(name, item_type) WHERE deleted_at IS NULL` allows a same-named item to be created after a soft-delete. When the user clicks Undo on the original within the 24h window, the restore violates the unique index → 500 to the user on a feature whose entire selling point is confidence. **Fix:** Expansion B now requires the undo handler to catch the unique constraint violation and return `409 Conflict` with `{error: "name_collision", existing_id}`. Frontend renders a "Restore as 'X (restored)'?" button that retries undo with `?rename_to=` to rename in the same transaction. Two test rows added covering the 409 detection and the rename-and-retry path.

**Issue 5 — Rev 3 lossy downgrade aborted on `recipes.instructions` NOT NULL (P1, fixed):** The current `recipes.instructions` column is `nullable=False`. The new `recipe_details.instructions` is nullable. Items created post-refactor with no instructions populated would NULL-fail the lossy downgrade INSERT. **Fix:** Rev 3 downgrade SQL now uses `COALESCE(rd.instructions, '')`. One-line edit in §0.2. Test row added: ER#3 Issue 5.

**Issue 6 — `MealEntry.item` back-population unspecified (doc gap, fixed):** §0.3 specified `Item.meal_entries` but never showed the `MealEntry` side. **Fix:** §0.1 now spells out: at Rev 3, remove `MealEntry.recipe` and `MealEntry.food_item` relationships, add `MealEntry.item: Mapped["Item | None"] = relationship("Item", back_populates="meal_entries", lazy="selectin")`.

# Design: M5 — prod-auth-enforcement

Generated by /office-hours on 2026-05-04
Branch: prod-auth-enforcement
Status: APPROVED
Mode: Builder

## Problem Statement

After M3 (backend auth foundation) and M4 (frontend auth session), the app has all the *machinery* to authenticate users — but **no route, frontend or backend, actually requires authentication.** Today, only the Cloudflare Access edge gate is preventing the world from hitting `api.mealy.dev/tasks` and `mealy.dev/`. The backend's `app/auth/dependencies.py::get_current_user` exists, is fully unit-tested across all four PyJWT exception classes, but is wired to zero routes (M3 plan L407: "M5 PR #1 wires it everywhere"). The frontend's `frontend/src/lib/router.jsx::rootAuthLoader` (L59-71) already implements the redirect-on-401 — it just doesn't trip today because the backend doesn't actually return 401s.

M5 is the milestone that flips the lock from "off" to "on." It ships in two PRs:

- **PR1** wires `get_current_user` across all 14 protected backend routers via a wrapping `protected` APIRouter, updates 18 backend integration tests to authenticate, refactors the integration-test conftest to transaction-rollback isolation (per Eng review 1, Issue 2C), updates the visual-regression test seed layer to authenticate, and confirms the M4-shipped frontend gate works end-to-end against the now-enforcing backend. CF Access stays up as defense in depth during this PR's soak.
- **PR2** removes the Cloudflare Access policy, deletes `backend/app/routes/plumbing_test.py`, removes the corresponding `app.include_router(plumbing_test.router)` line and import from `main.py`, and deletes `frontend/src/PlumbingShell.jsx` (the M2 plumbing-flow probe surface).

## What Makes This Cool

- **The "wrapping protected APIRouter" pattern.** The FastAPI-canonical move is to add `dependencies=[Depends(get_current_user)]` to each `app.include_router()` call — 14 declarations. Our auth split is binary (everything is protected except a small allowlist), so a single wrapping `protected = APIRouter(dependencies=[Depends(get_current_user)])` gives us **one declaration site, one place to audit**, and structurally makes "I forgot to add auth to my new router" impossible — you'd have to register it on `app` directly instead of `protected`, which is grep-able in one place.
- **The Playwright `route()` bypass design.** Most teams ship visual tests with a "skip auth in test mode" branch in their auth dependency. We don't need that. The visual-test stack already seeds data through the real API (`seed.js::seedKnownWeek()`); we teach `globalSetup.js` to login-or-register first, attach the JWT to seed calls, and use Playwright's `context.route()` to intercept `/auth/refresh` in the test browser and return the cached access_token. **Zero production code paths exist for bypass — frontend OR backend.** A senior security engineer would not flinch.
- **The "we wrote it but didn't wire it up" cliffhanger from M3 finally closes.** This is the moment.

## Constraints

- **CF Access stays through PR1.** The CF Access policy + `production_host_gate` middleware (`main.py` L98-115) are load-bearing alongside the new app-layer auth during PR1's soak. CF Access is removed only in PR2.
- **No changes to `get_current_user` internals.** It's already unit-tested across all four PyJWT exception classes + stale `session_version` (M3 plan L570). Bug fixes inside `get_current_user` would be a separate PR.
- **No changes to `frontend/src/lib/router.jsx::rootAuthLoader` (M4 already shipped it).** PR1 only verifies the existing loader behaves correctly when the backend starts returning 401s instead of 200s.
- **Visual-regression CI must stay green.** The `visual-tests` GitHub Actions job runs on every push/PR and exercises 5 specs against a `vite preview` bundle in Docker. The `seedKnownWeek()` flow writes through the real API and will return 401 from minute one of PR1 unless the seed layer authenticates.
- **The `__Host-refresh` cookie has `secure=True` hardcoded** in `backend/app/auth/routes.py` L43, L59. Browsers reject `Secure` cookies on `http://`. The visual-test stack uses `http://api-test:8000` and `http://frontend-preview:4173`. This means the refresh cookie cannot survive into the test browser via Playwright's `storageState` mechanism — the test design must work around this without touching `routes.py` (the cookie's hardening is correct for production).
- **`production_host_gate` middleware stays untouched.** It's a separate concern (rejecting direct *.fly.dev traffic when `APP_ENV=production`) and remains load-bearing after PR2.
- **M3's 60s refresh grace window must continue to work.** `Depends(get_current_user)` already supports it via `validate_bearer` (the underlying check); wiring it into routes does not change that path.
- **Single-family deployment model.** Per project memory: code is single-family; sharing means separate instances, not multi-tenant. No IDOR/cross-tenant concerns to worry about in M5.
- **Adversarial review (2026-05-06): FastAPI's automatic docs are not on the public allowlist.** `/docs`, `/redoc`, and `/openapi.json` are registered directly by `FastAPI(...)`, not by any application router, so the wrapping `protected` APIRouter will not gate them. PR1 must disable them explicitly; otherwise PR2 would expose the full API schema on the open internet after CF Access removal.

## Approaches Considered

### Gate Placement

**Approach A — Per-router `dependencies=[Depends]` at each include_router call**
- Summary: 14 individual dependency declarations.
- Effort: S. Risk: Low.
- Pros: Tutorial-canonical; per-router auth visible at registration site.
- Cons: 14 declarations to keep in sync; easy to forget on a new router.

**Approach B — Wrapping `protected` APIRouter (CHOSEN)**
- Summary: One `protected = APIRouter(dependencies=[Depends(get_current_user)])`; all 14 protected routers included via `protected.include_router(...)`. Public routers registered directly on `app`.
- Effort: S (~5 lines added, 14 changed). Risk: Low.
- Pros: ONE auth declaration, ONE point of auditability. Forgetting a router structurally requires registering on `app` directly — grep-able. Best fit for our binary protected/public shape.
- Cons: Slightly less tutorial-conventional, so a future contributor unfamiliar with this pattern needs a one-line code comment.

**Approach C — Middleware allowlist**
- Summary: One middleware that auth-checks every request, with a hard-coded path allowlist.
- Effort: M. Risk: Med.
- Cons: Less idiomatic; routes can't easily declare `Depends(get_current_user)` and instead read from `request.state.user`; community consensus is negative for FastAPI.

### Visual-Test Bypass Mechanism

**Approach A — Env flag short-circuits get_current_user**
- Effort: S. Risk: Med.
- Cons: Production code path now has a test-only branch; security smell.

**Approach B — Real login + Playwright `context.route()` intercept of `/auth/refresh` (CHOSEN)**
- Summary: `globalSetup.js` does login-or-register-on-401 against the real `/auth/*` endpoints in `api-test`; saves the access_token. The Playwright base test fixture installs `context.route('**/auth/refresh', ...)` that returns the cached access_token + 200 status whenever the test browser tries to refresh. The M4 `rootAuthLoader → performRefresh → tokenStore.set` chain runs unmodified.
- Effort: M (~50 LOC test setup change, 0 LOC production code).
- Pros: ZERO production code paths for bypass. Most production-faithful overall — backend gets real auth headers from real users; the only thing intercepted is the refresh endpoint, which is replaced with a token the backend just minted.
- Cons: Visual tests don't exercise the M4 boot-refresh round-trip itself. Acceptable: the M4 plan's spec coverage didn't include that path either; it's tested by frontend unit tests (`vitest`) with MSW.

**Approach C — Header-based magic token**
- Cons: Same code-smell as A; magic tokens are an anti-pattern.

**Why not direct in-memory token injection via `addInitScript`?** Considered. Would require writing `tokenStore` from outside, which means tokenStore.js would need a "read from window.__VRT_TOKEN__ if set" branch — i.e., a test-only branch in production code. Rejected.

**Why not relax `secure=False` when `APP_ENV=test`?** Considered. Same problem — production code branches on test mode. Rejected.

**Why not run api-test over HTTPS with a self-signed cert?** Considered. Significant infrastructure work (cert generation, Caddy/Nginx terminator, frontend trust config) for a one-time test concern. Rejected.

**Approach B (gate placement) + Approach B (bypass mechanism), shipped in two PRs per IMPLEMENTATION_PLAN.md L169.**

#### Step 1.2 — Backend: programmatic enumeration of `app.routes` (Eng review 1: Issue 1C)

> **Eng review 1 (2026-05-06): Step 1.2 rewritten.** Original spec tested FastAPI's mechanic in a separate test app — would NOT have caught the failure mode the wrapping pattern was designed to prevent (a future contributor adding `app.include_router(X)` instead of `protected.include_router(X)`). Replaced with a programmatic enumeration test against the production `app` instance.

Add `backend/tests/unit/test_protected_router_propagation.py`. It walks `app.routes`, skips the public allowlist, and asserts every other route's dependency tree contains `get_current_user`:

```python
# tests/unit/test_protected_router_propagation.py
from app.auth.dependencies import get_current_user
from app.main import app
from fastapi.routing import APIRoute
from starlette.routing import Mount

PUBLIC_PREFIXES = ('/auth/', '/plumbing-test')
PUBLIC_EXACT = {'/', '/healthz'}
PUBLIC_STATIC_MOUNTS = {'/uploads'}
FORBIDDEN_PUBLIC_DOCS = {'/docs', '/redoc', '/openapi.json'}


def _is_public(path: str) -> bool:
    return path in PUBLIC_EXACT or path.startswith(PUBLIC_PREFIXES)


def _has_dep(deps, target) -> bool:
    return any(d.call is target or _has_dep(d.dependencies, target) for d in deps)


def test_every_protected_route_requires_auth():
    failures = []
    for route in app.routes:
        if not isinstance(route, APIRoute):
            continue
        if _is_public(route.path):
            continue
        if not _has_dep(route.dependant.dependencies, get_current_user):
            failures.append(route.path)
    assert not failures, f"Routes missing auth: {failures}"


def test_only_expected_static_mounts_are_public():
    mounts = [route.path for route in app.routes if isinstance(route, Mount)]
    unexpected = sorted(set(mounts) - PUBLIC_STATIC_MOUNTS)
    assert not unexpected, f"Unexpected public mounts: {unexpected}"


def test_fastapi_docs_are_not_public():
    paths = {getattr(route, "path", None) for route in app.routes}
    assert paths.isdisjoint(FORBIDDEN_PUBLIC_DOCS)
```

This test is the structural guard that makes the wrapping `protected` APIRouter pattern's value proposition real. A future contributor adding a router via `app.include_router(X)` instead of `protected.include_router(X)` causes this test to fail with the path name in the error, not silently ship.

**Adversarial review hardening (2026-05-06):** do NOT put `/upload`, `/uploads`, or `/uploads/` in the APIRoute public allowlist. The public static file surface is the `StaticFiles` mount at `/uploads`, which appears as a `Mount`, not an `APIRoute`. The protected upload APIs (`/upload/*` and `/uploads/item-icon`) must fail the test if they ever lose `get_current_user`.

**Public allowlist maintenance:** if a NEW public surface is ever added, update `PUBLIC_PREFIXES` / `PUBLIC_EXACT` here in lockstep. Do not add protected APIs to these allowlists merely because they share a path prefix with a public static mount.

> **Eng review 1 (2026-05-06): Step 1.3 expanded.** Three plan-correctness issues surfaced and folded in here:
> - **Issue 1B — `auth_config.configure()` is never called for integration tests.** Integration tests use `ASGITransport(app=app)` (`conftest.py:114`), which does NOT run FastAPI's lifespan, so `_initialize_auth_config` from `main.py:46-49` never fires. The first `tokens.encode_access_token` call in the new `auth_headers` fixture would raise `AuthConfigError("Auth config not initialized…")`. Adding an autouse session fixture mirrors the unit-test pattern at `tests/unit/auth/test_dependencies.py:29-37`.
> - **Issue 2C — session-scoped `auth_user` collides with the existing schema-rebuild pattern.** Existing `db_session` fixture is function-scoped and runs `Base.metadata.drop_all` after each test (`conftest.py:90-92`). A session-scoped `auth_user` row inserted at session start gets dropped after test 1, and every subsequent test's `validate_bearer` 401s on the live-DB lookup. Decision: refactor `db_session` to **transaction-rollback isolation** so the schema persists for the whole session and per-test data rolls back automatically. Trade-off acknowledged: M5 PR1's blast radius widens to include this refactor; CI red on PR1 may surface as auth bug, isolation bug, or interaction. All 18 existing integration tests must stay green under the new isolation as a hard gate.
> - **Password hash:** `User.password_hash` is `Column(Text, nullable=False)` with no schema-level argon2 validation. Computing real argon2 in the fixture would add ~700ms-1s × test count to the suite (M3's argon2 is configured for ≥1GB-memory hardness). Use a literal placeholder string — the JWT path never validates the password.

Plan for `backend/tests/integration/conftest.py`:

```python
# 1. Autouse session fixture — installs auth config so encode_access_token
#    works without FastAPI lifespan. Mirrors tests/unit/auth/test_dependencies.py.
@pytest.fixture(autouse=True, scope="session")
def install_auth_config():
    from app.auth import config as auth_config
    auth_config.configure(auth_config.AuthConfig(
        jwt_secret_key="x" * 64,
        household_access_key="dev-access-key",
    ))
    yield
    auth_config.reset()


# 2. Session-scoped engine + transaction-rollback isolation. Replaces the
#    existing function-scoped engine + drop_all pattern at conftest.py:67-95.
@pytest_asyncio.fixture(scope="session")
async def test_engine(postgres_url):
    engine = create_async_engine(postgres_url, echo=False)
    async with engine.begin() as conn:
        await conn.execute(text("CREATE EXTENSION IF NOT EXISTS citext"))
        await conn.run_sync(Base.metadata.create_all)
    yield engine
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.drop_all)
    await engine.dispose()


@pytest_asyncio.fixture
async def db_session(test_engine):
    """Per-test transaction; rolls back at teardown.

    `join_transaction_mode='create_savepoint'` keeps existing
    `await db_session.commit()` calls transparent — the commit ends
    the inner SAVEPOINT instead of releasing the outer transaction,
    so cross-test isolation holds.
    """
    async with test_engine.connect() as conn:
        outer = await conn.begin()
        session = AsyncSession(
            bind=conn,
            expire_on_commit=False,
            join_transaction_mode='create_savepoint',
        )
        try:
            yield session
        finally:
            await session.close()
            await outer.rollback()


# 3. Session-scoped fixture user. Survives across tests because the
#    schema persists for the session.
@pytest_asyncio.fixture(scope="session")
async def auth_user(test_engine):
    from app.auth.models import User
    # Connect via test_engine directly — bypasses the per-test transaction
    # so this user persists across tests.
    async with test_engine.begin() as conn:
        result = await conn.execute(
            text(
                "INSERT INTO users (email, password_hash, session_version) "
                "VALUES (:email, :hash, :sv) RETURNING id"
            ),
            {
                "email": "auth-test@local",
                # password_hash is never read on the JWT path; literal is fine.
                # Avoids ~700ms argon2 cost per session.
                "hash": "argon2-placeholder-not-validated-on-jwt-path",
                "sv": 1,
            },
        )
        row = result.fetchone()
    yield {"id": row[0], "email": "auth-test@local", "session_version": 1}


@pytest.fixture
def auth_headers(auth_user):
    """Mint a fresh access JWT for auth_user; return {'Authorization': 'Bearer <jwt>'}."""
    from app.auth import tokens
    # tokens.encode_access_token signature per app/auth/tokens.py L35:
    #   encode_access_token(user_id: int, session_version: int) -> str
    # Internally stringifies user_id for the JWT `sub` claim.
    token = tokens.encode_access_token(
        user_id=auth_user["id"],
        session_version=auth_user["session_version"],
    )
    return {"Authorization": f"Bearer {token}"}
```

Each integration test file gets one `auth_headers` parameter added to its async client calls. Total effort: ~90 LOC test-file changes + ~80 LOC new conftest fixtures (engine refactor + auth_user + auth_headers + install_auth_config) = ~170 LOC.

We mint the JWT directly via `tokens.encode_access_token` (rather than calling `/auth/login`) because:
- Tests already need `tokens` to be importable for unit tests.
- Skips a full registration + login round-trip per test session.
- The auth dependency itself is exhaustively unit-tested at the JWT layer; integration tests only need a valid Authorization header to exercise downstream behavior.

**Hard gate before PR1 merges:** all 18 existing integration tests must stay green under the new transaction-rollback isolation. If any test relied on `db_session.commit()` actually committing across connections, refactor the test (NOT the isolation pattern).

async function loginOrRegister() {

  const loginRes = await fetch(`${API_URL}/auth/login`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },

    return body.access_token
  }

  if (!HOUSEHOLD_KEY) {
    throw new Error('globalSetup: HOUSEHOLD_ACCESS_KEY env var not set')

    headers: { 'Content-Type': 'application/json' },

      email: FIXTURE_EMAIL,
      password: FIXTURE_PASSWORD,
      access_key: HOUSEHOLD_KEY,
    }),
  })
  if (!regRes.ok) {
    throw new Error(`globalSetup: register failed ${regRes.status}`)
  }
  const loginRes2 = await fetch(`${API_URL}/auth/login`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ email: FIXTURE_EMAIL, password: FIXTURE_PASSWORD }),
  })
  const body = await loginRes2.json()

}

# Design: Inline Task Editing & Card Redesign

Generated by /office-hours on 2026-04-01
Branch: lists-ui-update-inline-edits
Status: APPROVED
Mode: Builder

## Problem Statement

The current task list UI uses a modal dialog for all task creation and editing. This creates friction — every edit requires opening a full modal, making changes, and closing it. The goal is to replace this with inline editing that matches Apple Reminders' feel: click a task to edit its title in place, expand for full field editing, zero modal interruptions on desktop.

## What Makes This Cool

The "no modals" paradigm. Every interaction happens right where you're looking. Click to type, expand for details, empty-and-enter to delete. It's the difference between "edit a task" (3 clicks + modal) and "just type" (1 click). The polish IS the feature — smooth expand animations, crisp visual separation between title and action areas, and a responsive behavior split where mobile gets inline title editing but keeps the modal for full fields.

## Visual Direction

**"Crisp Defined" variant** (Mockup B), characterized by:
- Bordered action area container with separator line between indicators and buttons
- Round checkboxes — change from current rounded-square (`rounded`) to fully round (`rounded-full`)
- Inset expansion panel with border + subtle inner shadow
- Active expand button fills terracotta to signal expanded state
- Clean bordered pills for priority and assignment

Reference mockup: `.claude/mockups/inline-edit-mockup-b.html`

## Constraints

- Must not break future drag-and-drop reordering (click = edit, click-and-hold = drag)
- Mobile: inline title editing only, modal for full field editing (no expand/contract)
- Desktop: full inline editing + expand/contract, modal removed entirely
- Must work with existing subtask/parent-child nesting
- Must use existing design system colors (warm-cream, warm-beige, terracotta, etc.)
- All commands run through Docker Compose

## Premises

1. The task creation/editing modal is removed on desktop. It becomes dead code for desktop breakpoints. Mobile retains it for full field editing.
2. Mobile gets inline title editing (click task → edit title in place) but uses the existing modal for expand/detail editing. The expand/contract button on mobile opens the modal instead.
3. Click-and-hold (~200ms threshold) for future drag-and-drop is standard and compatible with single-click-to-edit.
4. Delete-on-empty-enter is a power-user shortcut. The always-visible delete button is the safe/primary path.
5. The expanded detail view fits within the task card's width, rendered as an inset bordered panel below the title row.
6. Existing subtask/parent-child nesting continues to work unchanged.

## Approaches Considered

### Approach A: "Card Grows" (Minimal Viable)
Task card expands downward. Expanded fields render inside the same card with a thin divider. Single component manages both states.
- **Effort:** M
- **Pros:** Fewest new components, most Apple Reminders-like, smooth CSS grid animation
- **Cons:** Cards can get tall, nested subtask expansion could look cluttered

### Approach B: "Detached Panel" (Ideal Architecture)
Expanded fields render in a visually distinct panel below the card — inset, bordered, shadow. Card stays fixed height.
- **Effort:** M
- **Pros:** Clear visual hierarchy, easier to style independently, better drag-and-drop separation
- **Cons:** More complex DOM, need to manage visual connection between card and panel

### Approach C: "Hybrid" (Creative / Chosen)
Card row stays compact with inline title. Expanded area uses a distinct visual treatment (bordered inset panel) but renders as a continuation of the card. Combines A's simplicity with B's visual distinction.
- **Effort:** M
- **Pros:** Best of both, matches spec exactly, clean drag-and-drop story
- **Cons:** Requires careful color/spacing work

## Recommended Approach

**Approach C (Hybrid)** — matches the user's spec most precisely and the "Crisp Defined" mockup direction. The visual separation naturally supports future drag-and-drop (card top = drag handle, expansion = edit zone).

## Interaction Specification

### Task States

**1. Contracted (default)**
```
┌─────────────────────────────────────────────────────────────────────┐
│ ○  Task Title                  [🏴 Pri] [📅 Date] │ [🗑] [▼]       │
│                                ← indicators →      │← actions →    │
│                                ─────────────────────────────────────│
│                                bordered action area, bg: #f8f6f1   │
└─────────────────────────────────────────────────────────────────────┘
```
- Click anywhere on task text → activates inline edit
- Checkbox click → toggle complete
- Action area is visually separate (bordered container, different bg)
- Delete button always visible (no more hover-reveal on desktop)
- Save/Cancel buttons hidden (space reserved)
- Expand/contract button (▼ chevron) is rightmost

**2. Inline Edit Active (contracted)**
```
┌─────────────────────────────────────────────────────────────────────┐
│ ○  [editing: Task Title____]   [🏴] │ [🗑] [Save][Cancel] [▼]     │
│                                      │                              │
│    terracotta underline on input     │ save/cancel now visible      │
└─────────────────────────────────────────────────────────────────────┘
```
- Input has terracotta bottom border
- Save/Cancel buttons appear in action area
- Enter → save, Escape → cancel
- If text is emptied: Save button becomes "Delete" (red bg), Enter → deletes task
- If text is re-added: button reverts to "Save"
- **Blur behavior:** auto-save on blur (matches Apple Reminders). If title is empty on blur, cancel instead of delete (safety net — delete-on-empty requires intentional Enter).
- **Concurrent edits:** Only one task can be in inline-edit mode at a time. Clicking another task auto-saves the currently editing task first.
- **Save error handling:** If the API call fails, keep the input active, show a brief inline error toast ("Failed to save — try again"), let the user retry or cancel. Same error pattern applies to all auto-save calls (title + expanded fields).
- **Toggle complete while editing:** Auto-save current title, then toggle complete, then exit edit mode. Checkbox is never disabled during editing.

### Save Semantics (CEO Review Finding)

**Title:** Auto-save on blur (Enter confirms + exits edit mode, Escape cancels).

**Expanded fields (description, due date, assignee, priority):** Auto-save each field independently on blur/change. Each field triggers a debounced (500ms) PATCH call. No "Save All" concept — changes persist as you make them.

**Implication:** The Save button's role is "confirm title edit + exit edit mode," NOT "persist all changes." Expanded field changes are already saved by the time the user clicks Save. This eliminates data loss on navigate-away and removes the need for navigation guards.

**Debouncing:** Each expanded field has an independent 500ms debounce timer. Rapid changes to the same field batch into one PATCH. Different fields can save concurrently.

**Field clear payloads (Eng Review Finding).** The backend uses `exclude_unset=True` when applying PATCH updates, so omitting a field means "don't change it." Clearing a field requires actively sending `null`. The schema also has `min_length=1` on `description` and `ge=1` on `assigned_to`, so empty strings and zero are rejected. InlineTaskFields must normalize cleared values as follows:

| User action | PATCH payload | Reason |
|---|---|---|
| Clear description (empty textarea on blur) | `{description: null}` | `""` fails `min_length=1`; omitting = no change |
| Clear due date (clear date input) | `{due_date: null}` | Omitting = no change |
| Clear assignee (deselect all member pills) | `{assigned_to: null}` | `0` fails `ge=1`; omitting = no change |
| Set priority "None" | `{priority: 0}` | `0` is a valid value meaning "no priority" — NOT `null` |
| Set description text | `{description: "text"}` | Standard |
| Set due date | `{due_date: "2026-04-10"}` | Date-only string from `<input type="date">`; Pydantic coerces to `datetime(2026,4,10,0,0)`. Matches existing TodoForm behavior. |
| Select assignee pill | `{assigned_to: 3}` | Standard |

Note: the existing `TodoForm.jsx` uses `description || undefined` which works for modal create/edit (undefined is omitted, backend defaults to null on create). InlineTaskFields must NOT use this pattern — it must send explicit `null` for cleared fields so the backend knows to clear them.

### Concurrent Auto-Save Strategy (Eng Review Finding)

**Problem:** The backend returns a full task object for each partial PATCH (`crud_tasks.py:update_task` → `return await get_task()`). If two field PATCHes are in-flight concurrently, naive wholesale replacement (`setTasks(prev => prev.map(t => t.id === id ? response.data : t))`) causes the last response to overwrite the other field's update with stale data. The DB is always correct — this is a frontend-only state race.

**Strategy: Field-level merge + silent reconcile (two layers)**

**Layer 1 — Immediate field-level merge.** When a PATCH response arrives, only merge the fields that were in that specific PATCH payload into local state. Do NOT replace the entire task object:

```js
// In ListsPage.onUpdateTask(taskId, fieldData):
const response = await axios.patch(`${API_BASE}/tasks/${taskId}`, fieldData)
setTasks(prev => prev.map(t =>
  t.id === taskId
    ? { ...t, ...Object.fromEntries(
        Object.keys(fieldData).map(k => [k, response.data[k]])
      )}
    : t
))
```

**Safe fields for field-merge** (the only fields the user directly edits inline): `title`, `description`, `due_date`, `priority`, `assigned_to`.

**Fields that need reconcile** (server-side derived, not in user's PATCH payload): `completed_at`, `family_member` (relationship object), normalized dates, any future server-side derived fields.

**Layer 2 — Debounced silent reconcile.** 1 second after the last PATCH response settles, do a full refetch to pick up immediate server-derived fields (e.g., `completed_at` timestamps, relationship objects, normalized dates). This does NOT catch async Celery worker transitions like `PENDING_PUSH → SYNCED` — those happen on a 30-second countdown via `push_task_to_icloud_task.apply_async(countdown=30)`. ListsPage currently has no polling for `sync_status` changes (unlike `useCalendarData.js` which polls every 10s for calendar events with PENDING_PUSH). This means the "Syncing..." badge on TaskItem may remain stale until the user navigates away and back. If real-time sync badge accuracy on the lists page matters, a follow-up polling hook (similar to `useCalendarData`'s pattern) would be needed — but that is a pre-existing gap, not introduced by this feature.

```js
// In ListsPage:
const reconcileTimerRef = useRef(null)
const selectedListIdRef = useRef(selectedListId)

// Keep ref in sync:
useEffect(() => { selectedListIdRef.current = selectedListId }, [selectedListId])

// Inside onUpdateTask, after the field-level merge:
clearTimeout(reconcileTimerRef.current)
reconcileTimerRef.current = setTimeout(
  () => loadTasks(selectedListId, { silent: true }),
  1000
)
```

**Guard 1 — Silent refetch (no spinner flicker).** `loadTasks()` currently sets `isLoadingTasks(true)` which triggers a full-page spinner via `TaskListView`. The reconcile refetch must be silent. Silent reconcile failures are swallowed — user data is already field-merged, and the next edit or navigation will refetch.

```js
const loadTasks = async (listId, { silent = false } = {}) => {
  if (!silent) setIsLoadingTasks(true)
  if (!silent) setError(null)
  try {
    const response = await axios.get(`${API_BASE}/tasks?list_id=${listId}`)
    // Ignore stale responses if user switched lists while request was in-flight
    if (listId !== selectedListIdRef.current) return
    setTasks(response.data)
  } catch (err) {
    if (!silent) {
      setError(err.response?.data?.detail || 'Failed to load tasks')
    }
    console.error('Error loading tasks:', err)
  } finally {
    if (!silent) setIsLoadingTasks(false)
  }
}
```

**Guard 2 — Cancel timer + cleanup on list switch.** Clear pending reconcile timers when the user switches lists so stale timers don't fire for the old list:

```js
useEffect(() => {
  clearTimeout(reconcileTimerRef.current)
  if (selectedListId) loadTasks(selectedListId)
  return () => clearTimeout(reconcileTimerRef.current)  // cleanup on unmount
}, [selectedListId])
```

**iCloud synced tasks:** Auto-save works identically for synced tasks. No confirmation dialog for inline edits (the iCloud badge on the card provides awareness). PENDING_PUSH + Celery push happens automatically as with the current modal flow.

### State Ownership (CEO Review Finding)

TaskItem owns all local edit state (input value, expanded/collapsed, dirty flags). ListsPage owns only `editingTaskId` (which task is in edit mode). Since each field auto-saves via direct PATCH calls from TaskItem, there is no need to lift edit state to ListsPage. The callback pattern between them is: ListsPage tells TaskItem "you are the active editor" (via prop), TaskItem handles all save/cancel/auto-save internally.

### Dual Expand Controls (Eng Review Finding)

Tasks with subtasks have TWO independent expand/collapse controls. These are completely separate in position, appearance, state ownership, and what they reveal:

```
SUBTASK CHEVRON (existing)          DETAILS CHEVRON (new)
─────────────────────────           ─────────────────────
Position:  Left of checkbox         Position:  Rightmost in action area
Icon:      ▶ right-pointing, 3x3px  Icon:      ▼ downward, 13x13px
Rotation:  0° → 90° (right→down)   Rotation:  0° → 180° (down→up)
Active bg: None                     Active bg: Fills terracotta
Reveals:   Child task rows BELOW    Reveals:   Detail panel INSIDE card
State:     TaskListView             State:     TaskItem (internal)
           (expandedTasks Set)                 (isDetailsExpanded bool)
ARIA:      "Expand subtasks" /      ARIA:      "Show details" /
           "Collapse subtasks"                 "Hide details"
Only if:   task.children.length > 0 Always:    Yes (all tasks)
```

**Layout when both are active (task with children, both expanded):**

```
┃▶ ○  Parent Task           [🏴] │ [🗑] [Save][Cancel] [▲]     │
┃  ← subtask chevron (left)       │              details chevron →│
├─────────────────────────────────────────────────────────────────┤
│    ┌── DUE DATE / DESCRIPTION / ASSIGNEE / PRIORITY ──┐        │
│    └──────────────────────────────────────────────────-┘        │
│    ↑ detail panel renders INSIDE the parent card               │
├─────────────────────────────────────────────────────────────────┤
│  ○  Child Task 1             [📅] │ [🗑] [▼]                   │
│  ○  Child Task 2                  │ [🗑] [▼]                   │
│  ↑ subtask rows render BELOW the parent card (via TaskTree)    │
```

**Key rules:**
- Both can be open simultaneously — they don't conflict because they control different DOM regions.
- Subtask chevron only renders when `hasChildren` (same as today). Detail chevron renders on ALL tasks.
- State is fully independent: toggling one has no effect on the other. Collapsing subtasks does not close the detail panel, and vice versa.
- The subtask chevron uses `onToggleExpand` (callback to TaskListView). The detail chevron uses internal `isDetailsExpanded` state in TaskItem. No naming collision — different props/state.

**Keyboard focus:** The task title is not a standalone tabbable element in contracted mode. Tab focuses the subtask chevron (if present), checkbox, then action area buttons. Enter or Space on the title text region activates inline title edit, at which point focus moves into the input. When the details panel is open, Tab continues from the action area into the panel fields (due date → description → assignee pills → priority pills).

**Click-target precedence:** Clicking the left chevron only toggles subtasks. Clicking the right chevron only toggles the details panel. Clicking the title text region activates inline title edit and never toggles either expand control. The three zones are physically separate DOM regions — no `stopPropagation` judgment calls needed between the two expand controls.

### Accessibility Spec (Design Review)

**ARIA:**
- Inline edit input: `aria-label="Edit task: {title}"`. When Save button morphs to Delete: `aria-label="Delete task"`.
- Toast messages: `role="alert"` and `aria-live="assertive"` for error toasts.
- Expand button: `aria-expanded="true|false"`, `aria-label="Show details" / "Hide details"`.

**Focus management:**
- Click task text → focus moves to inline input.
- Enter/Escape (exit edit) → focus returns to the task row.
- Expand → focus moves to first field (due date) in the expansion panel.
- Toast dismissal → focus returns to the field that triggered the error.

**Touch targets:**
- Action buttons are visually 26x26px but have 44x44px minimum tappable area on mobile via padding (`min-h-[44px] min-w-[44px]` on `<640px`). Desktop retains 26x26px hit area.
- Save/Cancel buttons: minimum 44px touch height on mobile.

**Reviewer decisions:**

1. **Auto-save per field on blur** — Expanded fields (description, date, assignee, priority) auto-save independently on blur with 500ms debounce. Eliminates data loss on navigate-away. Save button = "confirm title + exit edit mode."

6. **Error handling** — Same pattern for all saves: keep field active, inline error toast, retry or cancel. Debounce prevents rapid PATCHes.

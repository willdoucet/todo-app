## Inherited constraints

rollback checklists, password-rotation CLI, backup-restore drill.
Depends on: M7 (shipped 2026-09-11, PR #44). Dependency satisfied.

### Locked decisions (from the epic, verbatim)

1. Frontend: Vercel SPA at `mealy.dev`
2. Backend: Fly.io with `web`, `worker`, and `beat` process groups at `api.mealy.dev`
3. Database: Fly managed Postgres
4. Broker and result backend: Upstash Redis over TLS (`rediss://`)
5. File storage: Cloudflare R2, single provider, no S3 fallback
6. Tenancy: single-tenant per household, one deployment per family
7. Auth: first-party email and password, JWT access token plus `__Host-refresh` HttpOnly cookie
8. Merge strategy: squash-and-merge on `master`; direct push blocked by branch protection
9. Sequencing rule: infra unknowns are discovered before auth code depends on them

### Done when (from the milestone, verbatim)

- A manual release runbook is committed, smoke and rollback checklists exist, the operator
  password-rotation CLI works over `fly ssh console`, a backup-restore dry-run has been executed
  against a scratch Postgres, and the two criteria below are met.
- **Process-group counts are reconciled, not merely checked.** `fly scale show` must agree with
  `fly.toml` and the docs. Production runs `web=2` today, not the `web=1` this milestone
  assumed (`worker=1` and `beat=1` are correct). Nothing pins the count: `fly.toml` sets
  `min_machines_running = 1`, which is a floor, not a cap. M8 either scales `web` back to 1, or
  keeps 2 deliberately and updates `fly.toml`, TECH_STACK, and this criterion to match. Each web
  VM is 1024 MB (sized for argon2), so running 2 doubles that spend; a second machine also
  widens the window in which a restart leaves two machines briefly holding different secret
  values, which is what made the 2026-09-11 rollout hard to diagnose. `beat=1` is the invariant
  that must not change — a second beat double-fires the iCloud sync schedule.
- **The production host gate records which check rejected a request.** One log line per
  rejection naming the failed check (host vs origin-verify, absent vs mismatched), never the
  secret value, and with the 421 response body unchanged so the two failure modes stay
  indistinguishable to a caller. They are currently indistinguishable to the operator as well:
  during the origin-lock rollout, a drifted secret and a mis-deployed Cloudflare rule looked
  identical from outside, and telling them apart cost a production experiment. This is one line
  on an existing gate for operability — not the broader structured-logging story deferred
  below.

## Problem Statement

Production has been live since 2026-05-01 and has taken 22 merges to `master` since — 12 of
them touching `backend/`, and because Vercel auto-deploys on merge every one of the 22 was a
frontend production release. None of them ran against a written procedure — every one was
improvised from memory and from whichever milestone runbook happened to exist at the time. M8 is the milestone that turns "the operator
remembers how this works" into an artifact that survives the operator forgetting.

The specific failure this milestone exists to prevent is not data loss. It is the **silent
failure that nobody is looking for** — which is precisely the shape of both production incidents
this deployment has had.

## Demand Evidence

Not hypothetical. Six pieces of evidence, all from this repo's own record:

1. **The 103-day silent worker outage (2026-09-11).** The Celery `worker` machine had been
   stopped since at least the end of May. iCloud sync, the soft-delete purge, and the
   abandoned-upload sweep never ran; 32,136 jobs queued in Upstash. Nothing surfaced it — web
   stayed healthy, beat kept queueing, and the M7 deploy updated the stopped machine without
   starting it. It was found only because an M7 runbook step happened to look at worker logs
   for an unrelated reason.
2. **The M7 runbook's abandoned-upload sweep check was left open and nothing tracked it.** Its
   execution log says so in as many words: "Still open: the sweep's worker `succeeded` line."
   (The `fly status` box in the same runbook is also unchecked, but corrected during spec
   review: `git log -S` places that check's introduction in `651ff27` / PR #49, *after* the
   runbook's only execution in `3f14222` / PR #45. It has never had an opportunity to be run,
   so it is not evidence of anything.)
3. **The origin-lock rollout cost a production experiment (2026-09-11).** A drifted secret and a
   mis-deployed Cloudflare rule produce an identical 421 from outside. Telling them apart
   required changing production to see what happened.
4. **Nothing states the intended `web` count anywhere.** Corrected during spec review: `fly.toml`
   has no per-group machine count at all — `[processes]` maps names to commands, `[[vm]]` maps
   sizes to groups, and `min_machines_running = 1` is a floor on one service, not a cap.
   TECH_STACK names the three process groups without counts. Production runs 2. Nobody noticed
   until the M8 criterion was written. This is why item 7 below needs a new file to pin against:
   there is no existing place to put the number.
5. **Backups have never been restored.** Fly Postgres snapshots exist; no restore has ever been
   performed. By the standard definition, the backups are untested and therefore unproven.
6. **The locked deploy order is inverted by construction.** The parent plan's CEO review locked
   "backend first, then frontend." TECH_STACK records Vercel as git-integration auto-deploy, and
   Fly is deployed by hand — so the frontend ships on merge and the backend whenever someone
   runs `fly deploy`. The M7 execution log shows exactly this: PR #44 merged 10:48 PDT, Fly
   cutover 10:49 PDT. Every release since M2 has violated the rule, and no release has noticed.

7. **The production database was moved to a new volume and its entire snapshot history went
   with it — and nothing surfaced that either.** Found 2026-09-12 while executing The Assignment
   (below). The machine `6835444b795398` was created `2026-09-11T23:31:01Z` in zone `d2a4`; the
   previous volume sits in `pending_destroy` in zone `76a8`. Data survived (`/auth/status`
   returns `{"account_exists":true}`), but a moved volume starts a fresh snapshot timeline, so
   `fly volumes snapshots list` returned **"No snapshots available"** — production had **no
   restore point at all**, and `fly pg backup` (continuous/point-in-time backups) was found
   disabled. This is the milestone's own thesis happening in real time: not data loss, but a
   silent change to the recovery posture that no check was watching. It is also the single
   strongest argument that the drill in item 3 is worth the effort — a drill run the day before
   would have had nothing to restore from and would have said so.

## Status Quo

Today a release is: merge the PR (Vercel auto-deploys the frontend), then `cd backend && fly
deploy -a mealy-app-prod` from memory, then look at the app in a browser. Health verification is
`/healthz` returning 200, which proves only that one uvicorn process is alive. There is no
rollback procedure written down, no smoke checklist outside the two milestone-specific runbooks
(`r2-cutover-runbook.md`, `cloudflare-state.md`), no way to change the household password except
by hand-editing a hash, and no evidence any backup is restorable.

What it costs: the 103-day outage is the direct price already paid. The next one is unbounded —
nothing in the current procedure would catch a dead `beat`, a drifted secret, a Cloudflare rule
someone disabled, or a migration that half-applied.

## Target User & Narrowest Wedge

**The user is the operator, six months from now, who has forgotten everything.** Not a team, not
an on-call rotation — one person, by design, on a deployment whose whole premise is
one-household-one-instance.

This inverts the standard restore-drill advice, which universally says "train at least two
people; single-person ownership is a dangerous gap." That mitigation is structurally unavailable
here. The compensating control is different: the drill's value is not in cross-training, it is
in the **observed numbers written into the artifact** — how long the restore actually took, what
the row counts were, how old the snapshot was. The document, not the operator's memory, is what
has to survive.

**Narrowest wedge:** a release procedure the operator can follow cold, whose mechanical checks
fail loudly on their own rather than relying on the operator to remember to look.

## Constraints

- **Single-tenant, single household.** One operator, one account. Multi-user, invite flows and
  public signup are PRD non-goals; nothing here should anticipate them.
- **Command policy.** App commands run through Docker Compose (`backend/`); `.agents/bin/`
  helpers are host-side. `fly` and `vercel` are operator-side CLIs, run from the host.
- **Never run unfiltered `env` / `printenv`** on any machine (LESSONS.md). Every check in every
  artifact this plan produces must filter on the remote side. Names only, existence checks, or a
  single redacted variable.
- **The secret is never written down.** `ORIGIN_VERIFY_SECRET` appears in no document, no script
  output, no log line, no transcript.
- **`beat=1` is invariant.** A second beat double-fires the iCloud sync schedule.
- **The new backend must serve the previous frontend bundle unchanged.** The parent plan states
  the deploy-order rule as a pair: backend first, *and* "backend supports both old and new
  clients at any given moment." Turning off Vercel auto-promotion (item 8) makes that window
  operator-controlled rather than seconds long, so this constraint gets stricter, not looser.
- **Migrations must be backward-compatible** (`fly.toml [deploy] release_command`): a
  `release_command` failure leaves the previous image serving, so the new migration must not
  break old app code.
- **Shallow `/healthz` only** (LESSONS Decisions, 2026-04-23). Deep DB+Redis probes on a
  single-instance deployment turn a 5-second dependency flap into total downtime. This plan adds
  liveness checks to the *runbook*, never to the health endpoint.
- **Runbook checks must be runnable, and meaningful, where they sit** (LESSONS.md, 2026-09-11).
  A check must fail when the thing it guards is broken, and must be able to pass at the point in
  the sequence where it is written.
- **This repository is public.** GitHub disables scheduled workflows on public repos after 60
  days with no repository activity (commits, PRs — workflow *runs* do not count). The daily
  `ops-check.yml` watchdog dies silently on that timer, which is the 103-day outage in
  miniature. Monthly releases reset the clock; a 50-day gap since the last commit is a
  documented re-arm, not a surprise. Adversarial review: 60-day trap named.
- **Deferred to v1.1 by the epic, and out of scope here:** `deploy.yml` release workflow, Vercel
  PR previews, `visual-tests` as a required check, Sentry, structured JSON logging beyond the
  single host-gate line, app-layer rate limiting, password-rotation CLI as `workflow_dispatch`.

## Premises

Agreed by the user, 2026-09-11:

1. M8's deliverable is a runbook that has been **executed** at least once, not one that has been
   written. Everything else in M8 is subordinate to that.
2. A release is not "green" on web health alone. The smoke checklist must prove `worker` and
   `beat` actually **ran a job** — not that `fly status` says `started`. Anything less
   reproduces the 103-day outage.
3. The password-rotation CLI is the only meaningful new application code in M8, plus one log
   line on the host gate. The rest is documentation, operator procedure, and executed drills.
   M8 is therefore unusually doc-heavy for a plan-tier milestone; reviewers should expect that.
4. `web=2` is drift to be **decided**, not a bug to be reflexively fixed. Either number can be
   right; what is wrong today is that nothing pins it and three sources disagree.
5. The parent plan's open item 8 (`prod-contract-freeze-plan-20260421-182714.md` § Open
   Questions, item 8) — "plan the v1.1 scope during M8, not after launch" — is this plan's
   responsibility. It lands here as a written scope contract or is explicitly dropped with a
   reason.
6. The two Cloudflare drift-detection TODOs both name "the M8 runbook" as their home. They get
   promoted here or explicitly declared out of scope. Not silently ignored.

## Landscape findings

Searched with category terms only; the product, domain, and proprietary concepts never left the
session.

**Conventional wisdom.** Runbooks fail from length, not from missing edge cases; the good ones
are short, imperative, one failure mode each, with exact commands and expected output, explicit
stop-and-escalate points, and a **last-tested date**. Mixing runbook types (deploy, diagnose,
remediate, maintain) into one document is named as the most common failure mode in growing
teams. A completed backup job is not proof of recovery — teams "trust the wrong signal." On
rollback, the field has largely settled on forward-only migrations with compensating migrations,
especially for single-instance deployments.

**Where it is sound, and we build on it:** forward-fix over rollback, already locked
independently by the parent plan's adversarial review on 2026-04-22. Split by runbook type. Put
a last-tested date on every artifact.

**Where it is wrong here, and why:**

1. "Train at least two people" is structurally unavailable on a single-operator deployment. The
   compensating control is the written observed numbers, not cross-training. → recorded under
   LESSONS Decisions.
2. "Write shorter" is the wrong correction for this repo. `cloudflare-state.md` and
   `r2-cutover-runbook.md` are long and heavily annotated, and those annotations demonstrably
   paid for themselves during the 2026-09-11 rollout. The advice that applies is **split by
   type, not by length**.
3. Rollback is not one doctrine here, it is two: Vercel is genuinely one-command reversible;
   Fly plus Postgres is not. The parent plan's "roll the frontend back first" rule implies this
   but never says it.
4. The industry's canonical backup story is not this repo's actual incident. Both 2026 failures
   were **liveness** failures nobody was looking for, not data loss.

## Approaches Considered

### Approach A: One runbook, manual throughout

- Summary: a single `infra/release-runbook.md` holding the deploy sequence, smoke checklist,
  rollback checklist, SPOF diagnostics and execution log. Password-rotation CLI. Host-gate
  rejection log line. Scale decision pinned in `fly.toml`. Execute one real release and one
  restore drill against it.
- Effort: M (human: ~2 days / AI-assisted: ~3-4 h) + operator execution ~2-3 h, human only
- Risk: Low-Med
- Completeness: 7/10
- Pros: smallest surface; no new credentials; ships fastest; meets every M8 done-when literally.
- Cons: one document mixing four runbook types is the exact failure the field names; every check
  stays human discipline — and the M7 runbook's sweep check was left open with nothing tracking
  it, which is the evidence that discipline alone did not hold here.
- Reuses: `r2-cutover-runbook.md` structure and execution-log table; `ROLLOUT.md`'s
  `pg_dump` → restore-probe → count-verify drill; `Secret Rotation Guide.md`'s rotation-order
  format.

### Approach B: Runbook set split by type + an executable release gate + drift detection

- Summary: three documents, one per runbook type — release, incident diagnostics, and the
  backup-restore drill with its execution log. Plus `infra/release-smoke.py`, which mechanically
  asserts the checks a human skips and exits non-zero. Plus the Cloudflare drift script both
  TODOs ask for. Plus the CLI, the gate log line, the scale decision, the executed release, the
  executed drill, and the v1.1 scope contract.
- Effort: L (human: ~5-6 days / AI-assisted: ~10-13 h) + operator execution ~3-4 h, human only.
  Re-estimated upward after spec review: three documents, two scripts, a CLI with tests, five
  gate-reason branches with tests, a new scale-expectation file, doc_map rules, and
  `fly.toml`/TECH_STACK/epic edits across two PRs. PR1 lands as two pull requests, 1a (docs,
  scripts, config) and 1b (application code and UI) — Eng review 0: decided, see Recommended
  Approach.
- Risk: Med — scope, and one new read-only Cloudflare API token
- Completeness: 10/10
- Pros: turns the two checks that actually failed in 2026 into assertions that cannot be
  silently skipped; closes both Cloudflare drift TODOs at the home they name; splitting by type
  keeps the release doc short enough to read under pressure while the diagnostics stay as deep
  as this repo's precedent.
- Cons: largest M8, realistically two PRs; a Cloudflare API token is a new credential surface
  launch does not strictly require; some checks (browser same-site, stale-tab chunk load) can
  never be scripted and stay manual.
- Reuses: everything A reuses, plus `cloudflare-state.md` as the drift script's diff target and
  `slice6-rate-limit-burst-test.sh` as the shell-script precedent.

### Approach C: Script-first — the script IS the runbook, markdown is its log

- Summary: invert the artifact. Write the executable verification first and keep the markdown
  thin: an ordered command list where the script performs every assertion, and prose only where
  a script cannot go. No Cloudflare drift automation.
- Effort: M-L (human: ~3 days / AI-assisted: ~5-6 h) + operator execution ~3 h, human only
- Risk: Med
- Completeness: 9/10
- Pros: directly serves this repo's own lesson that runbook checks must be runnable where they
  sit; both 2026 failures were unrun checks, not badly written ones.
- Cons: the operator still has to remember to run the script, so the discipline problem moves
  rather than disappearing; the rationale that made `cloudflare-state.md` pay off has no natural
  home in a script; heavy automation for a roughly monthly procedure is hard to justify alone.
- Reuses: same as B minus the Cloudflare API surface.

## Recommended Approach

**Approach B, shipped as two PRs on `prod-launch-release`** — chosen by the user, 2026-09-11.

The two-PR split is structural, not stylistic: premise 1 says the deliverable is an *executed*
runbook, so PR2 cannot be written until PR1 has been merged and actually run in production. M5
(#34, #36) and M7 (#41, #44) both shipped this way; this is the branch's own precedent.

**Eng review 0 (2026-09-12): PR1 lands as PR1a and PR1b.** The scope stays exactly as chosen;
the split is sequencing. PR1a carries everything with no application code — items 1, 2, 3, 4 (the
smoke script, its `infra/tests` suite and CI job), 7, 9, 10, 12's documentation, the `vercel.json`
build command and `index.html` meta tag for check 8's frontend tier, the host-side exception in
AGENTS.md and development-commands.md, the TECH_STACK truth fixes (Vercel promotion, Postgres Flex
17.2), and the expired break-glass line in `cloudflare-state.md`. PR1b carries the code — items 5,
6, 13, 14, 15, the `GATE_BREAK_GLASS` flag, the `job_heartbeats` migration, and every test. Two
properties fall out for free: PR1a is a real no-migration release, so criterion 8's rollback
dry-run runs on it, and PR1b is a real migration release, so criterion 19's migration-listing step
is exercised on the first execution rather than on paper. The "Between the PRs" window is
re-sequenced below accordingly.

A and C lost for the same underlying reason: A leaves every check as human discipline, which is
the failure already on the record twice; C automates well but has nowhere to put the rationale
that makes this repo's existing infra docs valuable, and it still depends on the operator
remembering to run the script.

- Cloudflare is a single point of failure in three places (DNS, proxy, WAF rate limit). If
  "nothing works" and Fly plus Vercel look healthy, check cloudflarestatus.com first; the
  documented fallback is temporarily grey-clouding the proxy to route direct to Fly and Vercel.
  **The trap, and why it is still open.** Grey-clouding also removes the origin lock's Transform
  Rule, so the app 421s every request — the fallback is self-defeating unless paired with a step,
  and that interaction is written down nowhere today. It also removes the `/auth/*` WAF rate
  limit. This plan tried to close the question with `cloudflare-state.md`'s "redeploy the

  longer removes it — the operator would have to roll back past #46, reverting every subsequent
  change against an already-migrated database. Every other lever fails closed by design:
  blanking `ORIGIN_VERIFY_SECRET` makes the app refuse to boot, and blanking `PUBLIC_API_HOST`
  421s everything through the `not allowed` branch. The only live escape today is
  `APP_ENV != production`, which also loosens auth config and re-derives CORS. This is open
  question 6, and PR1 must land a real answer with its blast radius enumerated — the deployment
  currently has a break-glass procedure that does not work.
- **The database moved hosts, and the snapshot history did not follow.** Found 2026-09-12. A
  Fly host migration creates a new volume in a new zone, marks the old one `pending_destroy`,
  preserves the data, and silently resets the snapshot timeline to zero. Nothing warns you, and
  `fly volumes list` will not even show the old volume without `--all`. Symptom: none — the app
  is perfectly healthy and `/auth/status` still returns `{"account_exists":true}`. The only
  signal is `fly volumes snapshots list <vol> -a mealy-app-prod-db` returning nothing, which is
  why smoke check 9 exists. Recovery: nothing to recover; the action is to confirm continuous
  backups are on and wait for the first scheduled snapshot, then record the gap.
- **Break-glass when Cloudflare is unavailable**, in two modes — Mode A (proxy or WAF degraded,
  DNS resolving) is solvable with the `GATE_BREAK_GLASS` flag; Mode B (Cloudflare DNS down)

**The two unobservable reasons**, named in the diagnostics doc as things an operator will never

**Test work is larger than "one new test."** All **eight** existing 421 tests
(`tests/integration/auth/test_host_gate.py` :73, :84, :103, :119, :128, :141, :165, :177 — Eng
review 2.2 recounted; the plan said five) assert only `status_code == 421` and, mostly,

(REVIEW_CHECKLIST → pytest: "byte-identical failure responses have a test that compares bodies
across every failure reason"), plus one new `host_absent` test (defined as "the `Host` header is missing *or* empty" —
`request.headers.get("host", "").strip()` yields `""` for both).

**Do not reuse `emit_log_line`, and do not wrap it either.** It calls `resolve_client_ip`
*inside its body*, which returns `CF-Connecting-IP` or the first `X-Forwarded-For` entry
verbatim — and on a request that went *around* the edge, the only interesting rejection, both
headers are attacker-controlled. It also binds a module-level
`logger = logging.getLogger("app.auth")` and documents itself as "structured logging for
/auth/\* endpoints", but the gate is middleware, not an auth endpoint. **A wrapper cannot change
either of those** — round 3 of spec review was right that round 2's "thin wrapper" decision was
not implementable. So: a **separate emitter** that reuses the payload *shape* and the field names
but not the function, resolving the IP from `request.client.host` (the Fly peer) and logging
under `app.gate`. It lives in `backend/app/gate_logging.py`, which **must be added to the
doc_map** (item 10) or it ships unrouted. **Shape** (Eng review 2.2): `gate_logging.py` holds the
six reason constants so tests import them from one place, and `emit_gate_rejection(request,
reason)` logs under `app.gate` with `event="host_gate"`, `outcome="rejected"`, `reason`, `ip`
from `request.client.host`, `request_id` via the existing `resolve_request_id`
(allowlist-validated, safe to import even though `emit_log_line` is not), `path` from
`request.scope["path"]` truncated to 128, and the presence and length of the `Host` and
`X-Origin-Verify` headers. The gate itself is restructured into a pure
`gate_reason(request) -> str | None` in `main.py` — ordered checks returning the first failing
reason — so the six branches get unit tests on a fake request and the HTTP tests assert the body;
with `GATE_BREAK_GLASS` on, `gate_reason` skips only the origin-verify check and the emitter logs
`outcome="bypassed"` per admitted request. The alternative — a `trust_edge_headers: bool = True`
parameter on `resolve_client_ip` — stays rejected: it defaults to the unsafe behavior and a
future caller can forget it.

**A logging failure must never change the response** (CEO review 2A, CRITICAL GAP). The emitter
is wrapped so that any exception inside it is swallowed and the gate still returns 421 with the
unchanged body. This exact class has bitten this gate once already: LESSONS records that
`hmac.compare_digest` raises `TypeError` on a non-ASCII `str`, which "would turn a forged header
into a 500 instead of a 421" — and item 5 adds a second code path that reads attacker-supplied
header data inside the same middleware. `test_gate_logging_failure_does_not_change_response`
patches the emitter to raise and asserts the 421 survives; it is the single most valuable test in
this plan, because it proves an observability bug cannot take down the auth boundary.

Never log the secret, and never log the incoming header value either — presence and length, not
content. The 421 body stays exactly `{"detail": "host_not_allowed"}` so the failure modes remain
indistinguishable to a caller.

     question 4 says the Postgres primary stops hourly. --> The web process runs a **background
refresher** started in the lifespan: every 30 s it reads `job_heartbeats` under
`asyncio.wait_for(..., 1.0)` and writes module state; on timeout or error it keeps the last-known
value and sets `read: "stale"` (or `"unavailable"` when nothing has ever been read); it handles
`CancelledError` at shutdown. The `/healthz` handler reads memory only and never awaits the store,
so `test_healthz_issues_no_database_queries` asserts exactly that, and a second test proves the
endpoint answers within the probe budget while the store is stubbed to hang. Without this, Fly's
10-second probe would query Postgres forever and a DB flap would start killing machines —
precisely the deep-probe pattern the 2026-04-23 LESSONS decision forbids.

**The signal must not lie in the reassuring direction, and it must distinguish its own breakage**
(CEO review 2B-A). The `task_postrun` handler writes **only when `state == "SUCCESS"`** (Eng
review 3: the signal fires on failure too, and an unfiltered write would record a failed task as a
success) **and only when `sender.name` is a `beat_schedule` task** (Adversarial review).
`backend/app/tasks.py` has sixteen `@celery_app.task`s; `beat_schedule` names four
(`app.tasks.sync_all_icloud_integrations`, `sync_all_reminders`,
`hard_delete_expired_soft_deletes`, `sweep_abandoned_uploads`). The other twelve — including
`health_check`, which smoke check 4 fires on every release — are one-shot. Rows are keyed by
Celery **task name** (`entry["task"]`), not by beat-entry key (`sync-icloud-calendars`). Interval
lookup walks `beat_schedule.values()`. An unfiltered writer plus "worker dead = every row stale"
marks the worker dead the first time someone imports a recipe: `extract_recipe_from_url`
succeeds, gets a row, has no interval, and sits stale forever. Belt and suspenders: the writer
drops unknown names, **and** the reader derives staleness only for the four beat tasks. `health_check`
SUCCESS must not insert a row (test).

The handler runs through `run_async` because the task's own loop is already closed by then, catches
everything — it never taints a task result — logs at WARNING with the store error, and increments
a failure counter that `/healthz` also reports. **A later successful upsert zeros `error_count`
and clears `last_error`.** Without that, one network blip permanently paints "can't record job
runs" even after writes recover. "Recent write errors" means `last_error` is within one
refresher interval, not `error_count > 0` historically. A stale timestamp *with* recent write
errors reads "the writer is broken"; a stale timestamp *without* them reads "the worker is dead".
The cron's failure message names which.
Two states beyond those (CEO review 4A): `last_success_at` is NULL on a fresh deploy and after a
restore drill, and that is **"no data yet", not "stale"** — the cron tolerates NULL for one
schedule interval after a deploy rather than alarming on day one. A fifth state, `read:
"stale"` or `"unavailable"` from the refresher, renders as "can't check" (Eng review 1.2).
Design review 2B: superseded for `"stale"` — Settings shows the last reading with a note for up to
2 minutes, using `jobs.read_at`; `"unavailable"` still renders "can't check". See 15a.
**Thresholds are per task** (Eng review 2.5): each row's staleness is three times *its own*
`beat_schedule` interval — 30 min for the 10-minute syncs, 3 h for the hourly sweeps — derived on
the server from `celery_app.conf.beat_schedule`, and "worker dead" means every row is stale, so
the frontend and the cron consume `stale` flags rather than re-deriving them.

**Reuse `parseServerTime`, do not rewrite it** (CEO review 4B-A). The API serializes
`timestamp without time zone` with no `Z`, and `new Date()` reads that as local time — the bug
logged 2026-09-11, where a five-hour-old sync rendered "just now". The fix exists at
`ICloudSettings.jsx:545` but is **module-private**. Extract `parseServerTime` *and* the
freshness-dot presentation into a shared module, and have both `ICloudSettings` and the new jobs
indicator consume it: the two surfaces show the same concept, and the bug then has exactly one
place it can ever be fixed. Tests pin `process.env.TZ` to `America/Los_Angeles` and use the API's
real no-`Z` shape — the old fixtures used `toISOString()`, whose `Z` hid the bug entirely.
Visual-regression coverage is **not** added (CEO review 6A-A); unit tests cover the four states
and extending the VRT suite to Settings stays with its existing TODO.

**Settings must not use the authenticated API client for `/healthz`.** Adversarial review:
`frontend/src/lib/api.js` attaches the bearer and on 401 runs silent refresh then redirects to
`/auth`. `/healthz` is public and gate-exempt, but a 421 (mis-deployed origin lock), a CORS
failure, or a missing `jobs` key handled as a 401-shaped error would log the household out of
Settings while they are looking at the "are jobs alive?" line. Fetch with `apiUrl('/healthz')`
and `cache: 'no-store'`, no `Authorization`, no interceptor. Missing `jobs` renders "can't
check" and never throws (Design review 2: Settings reads only `jobs`, so a missing
`gate_break_glass` or `version` changes nothing it renders) — that is the backend-first window (new
frontend, old `/healthz`) and the image-rollback window (PR1b frontend, PR1a backend). Poll
while Settings is mounted (`refetchInterval: 30_000`, stops on unmount); a one-shot on mount
is the 103-day outage for anyone who does not reload.

**15a. What the household sees on Settings** <!-- Design review (plan-design-review, 2026-09-14) -->

Settings is opened by anyone on the shared household login, usually to change something else
(add a family member, the timezone, a meal slot). The indicator is therefore designed for two
readers at once: a household member who should understand it without knowing what Celery is,
and the operator, who needs to tell "one job is behind" from "the worker is dead" at a glance.

*Information architecture* (Design review 1A: decided — own card plus a conditional top alert).
Two surfaces, one data source: both read the same `/healthz` query, so they can never disagree.

- **Top alert, first and only:** what is wrong, in plain words, then a "See background jobs" link. No
  dismiss control — the alert disappears when the jobs recover, because a dismissible outage
  warning is how an outage gets ignored. It is not shown for "can't check" (a deploy or edge
  problem, not a job failure, and not something to put at the top of the household's Settings).
- **Card, first:** one headline stating the overall state, with the dot. **Second:** one row per
  beat job, plain-English name plus how long ago it last succeeded. **Third:** nothing.
- **The per-job rows are always visible** in every state that has a reading (Design review 8C:
  decided — mockup option A, over "exceptions only" and a "Show all 4 jobs" toggle). Green is
  backed by four visible ages that tick on each poll, which is what the operator checks after a
  deploy, and the card keeps one height as its state changes, so the Account card below never
  jumps during a 30-second poll. See the Design Source of Truth.

*Interaction states* (Design review 2). **The headline follows the worst job, never the most
recent success.** Summarizing four jobs as "ran N min ago" from the newest timestamp would let a
dead upload sweep hide behind a healthy iCloud sync — the reassuring lie CEO review 2B-A forbids.

- **Stale reading, not a flap** (Design review 2B: decided — last reading plus a note). This
  supersedes Eng review 1.2's "`read: "stale"` renders as can't check": that rule would flip the
  card to "Can't check" for about a minute every time the Postgres primary wakes (open question
  4) and on every dropped poll, which trains the reader to ignore it. Showing the last reading
  stays honest only because each job's staleness keeps advancing from its real timestamp, so
  two backend requirements follow: `stale` is computed **when the request is served**, from the
  in-memory rows and the current time — never frozen at the refresher's last successful read —
  and `jobs` carries `read_at`, the time of that last successful read (memory only). "Newest
  reading" above means `jobs.read_at` from the most recent response in hand.
- **Recovery is quiet.** When jobs recover, the headline and dot change on the next poll and
  the top alert unmounts. No toast, no animation.
- **Rows keep a fixed order** (the two 10-minute syncs, then the two hourly sweeps), so they do
  not reshuffle every 30 seconds; red text and the word "overdue" mark the stale ones. The
  headline carries the card's only dot (Design review 5: one dot per card, not five).
- **A job is never dropped.** A beat task name the frontend has no label for renders with its
  task name humanized (`sweep_abandoned_uploads` → "Sweep abandoned uploads"), because a missing
  row hides a stale job. Names outside `beat_schedule` never reach the card (the server filters
  them).
- **Settings depends only on `jobs`.** A missing `version` or `gate_break_glass` key does not
  change anything Settings renders, and Settings never renders either (Design review 7A, 7B).

- **Never color alone.** The dot is `aria-hidden`; the headline words carry the state, and a
  stale row says "overdue" as well as turning red (WCAG 1.4.1).
- **Announcements.** Neither the headline nor the rows is a live region — ages change on every

  announces; the top alert never does, so a change is not read twice.

Three of the original six were closed on 2026-09-12 by executing The Assignment; they are kept
below as answers rather than deleted, because the evidence is what item 7 and item 8 now rest on.

**Closed — Why does production run two web machines?** Neither deliberate nor drift: both were
created 15 seconds apart by the original M2 deploy on 2026-04-30, which is `fly deploy`'s default
for an app with an HTTP service. Production has never run `web=1`. See item 7, which now presents
this as a cost-versus-redundancy decision rather than a correctness fix.

**Closed — Can this Vercel project build a production-branch commit without promoting it?** Yes.
Settings → Environments → Production → Branch Tracking → disable "Auto-assign Custom Production
Domains"; builds then sit in state Staged until promoted. No plan-tier restriction documented.
See item 8.

**Closed — Which Fly Postgres product is this, and what is its restore command?** Unmanaged Fly
Postgres Flex (`mealy-app-prod-db`, `flyio/postgres-flex:17.2`), so the restore path is
`fly pg create --snapshot-id <id>` from a volume snapshot. See item 3.

Still open:

1. **Cloudflare API token scope and storage.** The drift script needs a read-only token. Kept as
   a local operator credential in v1 rather than a CI secret; revisit if the script is ever
   scheduled. Confirm the minimum scopes during PR1.
2. **Drill cadence.** The field's floor for a small team is monthly. For a one-household app
   with a single operator that may be more ceremony than it earns; the drill document states a
   cadence and the re-run triggers, and the number is the operator's call at execution time.
   One input is now known: a host migration can reset the snapshot timeline without warning, so
   cadence alone is not sufficient — the re-run triggers matter more than the interval.
3. **What is the real break-glass when Cloudflare is down?** Still the most consequential open
   item. This plan briefly closed it on `cloudflare-state.md`'s "redeploy the previous image"
   answer, which expired the moment the origin-lock code shipped in every image: rolling back to a
   previous image no longer removes the gate, blanking `ORIGIN_VERIFY_SECRET` refuses to boot,
   blanking `PUBLIC_API_HOST` 421s everything, and the only remaining lever is
   `APP_ENV != production`, which also loosens auth config and CORS. **The deployment currently
   has a documented break-glass procedure that does not work.** PR1 lands a real one. It cannot
   be rehearsed in production.

   The Assignment's paper exercise (2026-09-12) established that this is **two** questions, not
   one, and the plan previously conflated them:

   - **Mode A — Cloudflare proxy or WAF degraded, DNS still resolving.** Grey-cloud both records
     and traffic reaches Fly and Vercel directly, but with no Transform Rule there is no
     `X-Origin-Verify` and the gate 421s everything. This one is solvable: a `GATE_BREAK_GLASS`
     flag read by `production_host_gate`, and it belongs in `fly.toml [env]` rather than as a Fly
     secret — for exactly the reason recorded in LESSONS for `STORAGE_BACKEND`, that a secret
     survives a code rollback and would leave the gate silently open forever, whereas a versioned
     flag is cleared by the same rollback that reverts the code.
   - **Mode B — Cloudflare DNS itself is down.** Neither hostname resolves, and grey-clouding
     does not help because that is still Cloudflare's DNS. The only reachable name is
     `mealy-app-prod.fly.dev`, which the Host check rejects; and the SPA would have to run from
     `*.vercel.app`, which is not same-site with the API, so the `SameSite=Strict`
     `__Host-refresh` cookie will not ride and login breaks regardless (the same mechanism as the
     Vercel-preview TODO). Mode B is probably **accepted risk** for v1 rather than solved — but
     it gets written down as accepted, in the diagnostics doc, rather than discovered during an
     outage.

   **Blast radius to enumerate before shipping Mode A's flag:** with the gate bypassed there is
   no WAF rate limit on `/auth/*`, so argon2 on a 1 GB web VM is DoS-able by anyone who finds
   the origin; and `resolve_client_ip` starts trusting attacker-supplied `CF-Connecting-IP`, so
   auth logs become forgeable for the duration. That is the concrete argument for pairing this
   with the P2 app-layer rate-limit TODO, or for documenting the exposure window explicitly and
   keeping the flag's lifetime measured in minutes.

   **Design settled (Eng review 7, folded):** `GATE_BREAK_GLASS = "0"` in `fly.toml [env]`, strict
   parse (only the string `"1"` enables it; `true`, `yes`, and padded values stay off, with a unit
   test per case); when on, `gate_reason` skips only the origin-verify check — the Host check
   stays — and every admitted request logs one `app.gate` WARNING with `outcome="bypassed"`;
   `/healthz` reports `gate_break_glass`. Enable during an incident with
   `fly deploy -a mealy-app-prod --image <current ref> -e GATE_BREAK_GLASS=1` (no build, about a
   minute; `-e` overrides the toml value for that release only), clear with a plain `fly deploy`
   from `master`. Detection of a flag left on: the daily cron asserts `/healthz.gate_break_glass`
   is false *and* that the direct-to-origin probe still 421s, and `fly secrets list` must never
   show the name (a secret would survive a rollback and override the toml default). Rehearsed in
   the integration suite and a local `APP_ENV=production` compose run; never in production.
   Adversarial review: the flag code ships in **PR1b**. Between PR1a and PR1b, Mode A is still
   unsolved — do not attempt `-e GATE_BREAK_GLASS=1` against a PR1a image; it is a no-op.
   After the clearing deploy, if `/healthz.gate_break_glass` is still true, `-e` stuck as a
   machine-level env. Do not `fly secrets set` to "fix" it. Diagnostics entry: remove the
   override (`fly machine update` / equivalent) until the flag is false, then record that
   `-e` was sticky so the next incident does not repeat it.

5. **What is the narrowest Fly token that can read machines and volume snapshots?** Item 13
   needs one in GitHub Actions. **Largely answered** (Eng review 8, verified against flyctl
   v0.4.102 on the operator host): `fly tokens create readonly -o <org> -x 8760h` creates "an API
   token limited to reading a single org and its resources" — read-only, org-scoped, one-year
   expiry instead of the 20-year default. What remains for PR1b is confirming it can run
   `fly volumes snapshots list`, `fly pg backup list`, and `fly ips list`; if any is refused,
   item 13 drops to its credential-free subset (origin lock, `/healthz`, cache headers) rather
   than accepting a deploy-capable token on a schedule. Raised in CEO review, candidate 1.
6. **Where does item 15's background-job timestamp live: a Redis key or a one-row table?**
   **Decided: a table, one row per task name** (Eng review 1A, 2026-09-12). `job_heartbeats`
   (`task_name` PK, `last_success_at` **timestamptz** — the new column follows REVIEW_CHECKLIST →
   PostgreSQL rather than the legacy naive columns, and the API serializes it with a `Z` —
   `last_error`, `error_count`), one additive Alembic revision with a real `downgrade()`, upserted
   with `INSERT ... ON CONFLICT` so redelivery is idempotent. Per-task rows are what let the
   diagnostics doc tell "the upload sweep is stale but the iCloud sync is fresh" (a task-specific
   failure) from "every row is stale" (a dead worker). A Redis key would go blank in exactly the
   outage it is meant to report, because Redis is part of the async stack. The migration also
   gives PR1b a real revision for the runbook's migration-listing step. BACKEND_STRUCTURE's ER
   diagram gains the table.

4. **Why is the Postgres primary stopping and starting hourly, and should it?** Opened
   2026-09-12. The DB machine's event log shows `exit stopped flyd` at `04:00:27Z` followed by
   `start starting proxy` at `04:10:24Z`, and the same pattern an hour earlier — the Fly proxy
   is waking a machine that idles out. On an app whose Celery beat fires every 10 minutes this
   is at best pointless and at worst a source of connection errors that look like something
   else; `pool_pre_ping` (added in #30) is presumably what has been absorbing it. Establish
   whether this is deliberate cost-saving or a default that arrived with the recent host
   migration, and either document it in the diagnostics doc as expected or turn it off.

Resolved earlier in planning and therefore *not* open: whether smoke check 4 needs a
purpose-built no-op task (it does not — `app.tasks.health_check` already exists, is off the beat
schedule, and has a result backend), and which shape the gate's IP-logging fix takes (a separate
emitter, not a wrapper and not a `trust_edge_headers` parameter).

The assignment was: before any implementation starts, open the Fly dashboard and answer when the
second `web` machine was created and what else happened that day — then four supporting facts,
none of them knowable from the repo.

| Question | Answer |
|---|---|
| When was the second `web` machine created? | `2026-04-30T23:35:13Z`, **15 seconds after** the first. The original M2 deploy created both; `fly deploy` provisions two by default for an app with an HTTP service. Never deliberate, never drift — production has never run `web=1`. |
| Can Vercel build without promoting? | Yes. Settings → Environments → Production → Branch Tracking → disable "Auto-assign Custom Production Domains". Builds sit in state **Staged**; promote from the Deployments list with no rebuild. |
| Which Postgres product, and what is its restore command? | Unmanaged **Fly Postgres Flex** (`mealy-app-prod-db`, `flyio/postgres-flex:17.2`). Restore is `fly pg create --snapshot-id <id>` from a volume snapshot. An image update to 17.7 is available. |
| Are snapshots enabled, and how old is the newest? | Configured (`Scheduled snapshots: true`, retention 5) but **there were none**. The volume was created `2026-09-11T23:30Z` by a host migration and the snapshot timeline restarted. `fly pg backup` was also disabled. |
| What is the smallest change that gets traffic to the origin with Cloudflare down? | Still open — and it turned out to be two questions, not one. See open question 3 (Mode A / Mode B). |

**What the assignment found that it was not looking for**, and the reason it was worth doing as
a discrete step rather than folding into implementation: production was running with **no restore
point at all**, and no check anywhere would have said so. Data was intact — the public
`/auth/status` endpoint returned `{"account_exists":true}` — but recoverability had silently
gone to zero when the database changed hosts. The plan's thesis is the silent failure nobody is
looking for; the assignment found a live one before PR1 wrote a line. Item 12 and smoke check 9
exist because of it, and the one action that should not wait for PR1 is
`fly pg backup enable -a mealy-app-prod-db`.

**Still outstanding for the operator:** flip the Vercel setting (after `vercel login` — the local
token is expired), enable continuous backups, decide the `web` count now that item 7 presents it
as a cost-versus-redundancy call, work out Mode A's break-glass on paper, and establish whether
the Postgres primary's hourly stop/start cycle is deliberate (open question 4).

### Job heartbeat data flow (item 15 — Eng review 1A, 1.2, 3)
```
  worker (Celery)                        web (uvicorn)                          readers
  ┌────────────────────────┐             ┌───────────────────────────────┐
  │ any task ends          │             │ lifespan: refresher task      │
  │   task_postrun signal  │             │   every 30 s:                 │
  │   state == SUCCESS? ───┼─no─▶ drop   │   wait_for(read rows, 1.0 s)  │
  │   name in beat_schedule?─┼─no─▶ drop │     ok ────▶ cache = rows     │
  │        │ yes           │             │     timeout / error ─▶ keep   │──▶ /healthz.jobs ──▶ Settings dot
  │   run_async(upsert)    │             │       last-known, read=stale  │        │           (5 states)
  │   ON CONFLICT (name)   │             │                               │        └──▶ ops-check.yml
  │   ok → error_count=0   │             │ GET /healthz: memory only —   │             (liveness group)
  │   raises? swallow,     │             │   never awaits the store      │
  │   WARNING, errors++    │             └───────────────────────────────┘
  └───────────┬────────────┘
              ▼
       job_heartbeats  (four beat tasks only; keyed by Celery task name)
       task_name PK · last_success_at timestamptz · last_error · error_count
       stale(row)   = now − last_success_at > 3 × beat_schedule[task].interval
                      (interval from entry["task"], not beat key)
       worker dead  = every *beat* row stale · NULL = "no data yet" (not stale)
       reader ignores any row whose name is not in beat_schedule
```
